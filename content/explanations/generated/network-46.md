## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银对账沙盘:客户端统计某接口 P99=3 秒,服务端日志同一请求处理耗时 80ms——3 秒去哪了?客户端计时含网络+排队+重试,服务端日志只算处理段;把两端日志按请求 ID 拼起来,差值即"消失的时间"。

1. 耗时构成:客户端视角=连接(建连/复用)+排队(客户端池/服务端 accept 队列)+网络传输(去程+回程)+服务端处理+重试叠加;服务端日志的"处理耗时"通常从 handler 入口到响应写出——排队与网络不在内,两者口径天然不同。
2. 定位法:traceId 串联两端日志(distributed D14 的 traceparent 传播)→对齐同一请求的客户端发起点/服务端入口/响应回程时间→差值分解:入口前差=排队或网络,出口后差=回程或客户端处理;MTU 类问题(包没到,见 Q44)在"服务端无该请求记录"上现形。
3. 常见元凶排序:客户端连接池排队(池小,请求等连接)、服务端 accept/全连接队列排队(见 Q5)、重试叠加(1 次失败+2 次重试,客户端计时×3)、TLS 会话重建(复用失效时握手,Q9)、响应体大(回程传输慢,见 Q48)。

## 参考分析

### 第二步扩展① 机制:两端口径的边界

- 客户端计时:URL 连接发起→响应读完(含一切等待)。
- 服务端计时:handler 进入→响应写出(框架口径各异,有的含反序列化有的不含)。
- 边界差=连接建立(首请求)+排队+网络往返——复用连接可消除前者,但排队与网络始终在两端之间。
- 口径差异不是 bug,是"分层的计时"——拼起来才是全链路。

### 第二步扩展② 反例:定位错向的三种事故

- 事故一:客户端慢→压服务端加机器——实际是客户端连接池 5 连接打 500 并发,排队 2.5 秒。
- 先查池指标(借出等待时间)。
- 事故二:只看服务端 P99 优化 SQL——SQL 已 80ms,瓶颈在回程传输(响应 10MB,弱网 3 秒)。
- 优化方向是响应瘦身或压缩。
- 事故三:重试无标记——客户端重试 2 次,服务端看到 3 条 80ms 记录,客户端体验 3 秒。
- 重试要打标(traceId 相同+attempt 字段)。

### 第二步扩展③ 取舍:埋点的精细度

- 全链路埋点(连接/排队/网络/处理四段):定位最快,日志量大。
- 关键接口精细+长尾粗粒度:成本平衡。
- SDK 统一封装:一次投入全域生效(客户端框架统一打点)。
- 按接口重要性分层,资金链路全埋点——"消失的时间"必须有段级数据才能归因。

## 案例

### 第三步发散·验证与推演 验证:口径差异的实测证据

- 本机实测(Q23 同源):
~~~
java N3Timeouts
连接阶段失败:SocketTimeoutException,耗时 2019ms
读取阶段失败:SocketTimeoutException,耗时 1505ms(连接已建立)
端口拒绝:ConnectException,耗时 17ms
~~~
- 验证:连接/读取/拒绝三段计时独立(2019/1505/17ms)——客户端视角天然分段的直接证据。
- 服务端"处理 80ms"与客户端 3 秒的差值按"排队+网络+重试"分解推演并明示。
- traceId 串联按 distributed D14 实测引用(W3C traceparent 三层传播)。

### 第三步发散·发散要点 追问链:口径三刀

- **追问①**：clock skew——跨机器时间戳比对要先校时(NTP 偏移),差值分析用"同一端计时的差"而非跨端绝对时间比对
- **追问②**：日志采样——全量 trace 日志成本高,慢请求(>P99)全采+正常请求采样,保留"消失时间"的样本代表性
- **追问③**：与 Q24 的衔接——读超时三成因(下游慢/丢包/中间设备)的区分依赖两端时间差,本题的串联方法是 Q24 的工程落地

## 总结点

1. 两端口径天然不同
2. traceId 拼接差值归因
3. 先查池排队再优化 SQL
