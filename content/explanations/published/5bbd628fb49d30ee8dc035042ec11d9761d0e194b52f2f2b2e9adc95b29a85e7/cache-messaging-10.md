## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 7 教学场景：一段包含循环的 Lua 脚本执行超时，整个 Redis 阻塞直到 script kill。从单线程模型解释"脚本是原子命令"的两面性，给出脚本的复杂度红线与拆分原则。

1. Lua 脚本在 Redis 中作为单个原子命令执行：执行期间不插入其他客户端命令——原子性的另一面是"脚本执行多久，全实例阻塞多久"。死循环脚本必须 script kill 或 SHUTDOWN NOSAVE 才能解除。
2. 复杂度红线：避免无界循环与大集合遍历（脚本内处理的数据量决定阻塞时长）；读写操作数控制在可预估的小范围；耗时计算（加密、大 JSON）不进脚本。
3. 拆分原则：需要遍历大数据集的逻辑拆成"SCAN 客户端游标 + 小批量脚本"，脚本只做原子判断与更新；脚本的输入参数限定 key 数量（Cluster 下同 slot 约束），超范围逻辑回应用层编排。

## 参考分析

### 机制：原子性与阻塞是同一枚硬币

Lua 原子执行 = 执行期间 Redis 是你的——这正是它在并发修改（如限流扣减、分布式锁释放校验）中不可替代的原因；同一枚硬币的反面：你占有多久，全世界等多久。类比包场：包场保证不受打扰，包场一小时全场停摆——脚本的复杂度红线就是"包场时长"。

### 反例：脚本内遍历大集合的三重伤害

脚本循环 SCAN 全库删除模式匹配键：一，执行期间所有请求阻塞（秒到分钟级）；二，脚本无法被部分中断（只能 kill 丢弃全部已执行效果）；三，Cluster 下遍历跨 slot 违反同 slot 约束直接报错。三重伤害都源自"把批量运维逻辑塞进了原子命令"。

### 取舍：什么逻辑值得进脚本

值得：需要"读-判-写"原子性的小操作（限流扣减、锁释放校验、计数器组合）——离开脚本的原子性就有竞态。不值得：批量运维（SCAN 删除）、大数据处理、纯计算。判据一句话：这段逻辑如果没有原子性会出错吗？不会就不要进脚本——脚本池的复杂度也是一种技术债。

## 案例

### 对照操作：阻塞时长的量化与 script kill

教学验证：执行一个 5 秒循环脚本，另一客户端测 ping 延迟并尝试 script kill。预期：ping 阻塞 5 秒；若脚本未执行过写操作 script kill 成功、已执行过则只能 SHUTDOWN NOSAVE。实验可复跑，"script kill 的限制"从文档变成亲历。

### 追问：为什么 Cluster 下脚本要求同 slot

脚本原子执行的保证依赖"单实例处理"——跨 slot 的 key 分布在不同实例，无法在同一原子上下文中操作。规避：hash tag 强制同 slot（{user1000}.profile 与 {user1000}.orders），或拆分逻辑回应用层。hash tag 是便利也是约束——同 tag 的 key 会集中在同一分片，可能制造热点。

## 总结点

1. 脚本执行多久，全世界等多久
2. 无界循环是生产禁区
3. 小原子进脚本，大批量回应用
