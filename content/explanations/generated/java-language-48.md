> 场景与约束：网银接口沙盘:方法名 createOrder(暗示幂等?不——每次创建新单)与 processPayment(暗示不幂等?)——幂等语义靠文档/Javadoc 不够(调用方不看文档)——幂等的工程表达:接口注解+唯一约束+调用方契约(分布式 8 题的 API 面)。

1. 方法名的局限:命名无法强制调用方行为(幂等键的传递)——"幂等"是调用方与服务端的协议(键的传递+服务端去重)——命名只是文档的一部分。
2. 工程表达三层:服务端实现(幂等键唯一约束,第 3 题 banking——强制幂等)、接口契约(OpenAPI 注解/文档:幂等键的 header 声明——X-Idempotency-Key)、调用方 SDK(SDK 自动生成/传递幂等键——调用方无感)。
3. 与 HTTP 的对齐:HTTP 语义的幂等(GET/PUT/DELETE 幂等,POST 不幂等——REST 的动词语义)——REST 动词的幂等语义与业务幂等的映射(POST 的业务幂等靠幂等键,不靠动词)。

## 参考分析

### 机制:幂等的三层表达

层一,服务端:幂等键的唯一约束(插入冲突=重复,返回首次结果——banking 3 题)。层二,契约:OpenAPI 的幂等键声明(header 参数+幂等语义标注)+文档(哪些接口幂等/幂等键的生成规则——第 14 题)。层三,SDK:客户端自动生成键(单号派生)+自动重试带键(调用方无感——SDK 的幂等是"透明的正确")。三层缺一:只有服务端=调用方不知道传键;只有契约=没有实现;只有 SDK=服务端没去重。

### 反例:幂等表达缺失的事故

事故一,方法名误导:createOrderIfNotExists(名字暗示幂等)——但服务端无幂等键校验(并发双创建)——名字的"暗示"不是实现。事故二,文档与实现背离:文档说幂等,实现无去重(调用方重试双花,第 49 题)。事故三,SDK 不带键:SDK 重试不带幂等键(重试=新请求)——重试双花(分布式 8 题)。三条的正解:三层齐备(实现+契约+SDK)——幂等的工程化(不是文档化)。

### 取舍:幂等键的强制程度

强制:关键接口(资金)强制幂等键(缺失 400——网关拦截,第 33 题 distributed)。建议:非关键接口幂等键可选(缺失自动生成[服务端生成——调用方无键时])——自动生成的键=请求级(不防重试——重试换新键)——强制的等级按资金后果(第 44 题)。演进:从"建议"到"强制"的过渡(监控无键请求的比例——归零后强制)。

## 案例

### 验证:幂等表达的断言组

验证:服务端断言(同键重放零副作用——幂等实现的行为断言);契约断言(OpenAPI 的幂等键声明与实现一致——契约测试);SDK 断言(SDK 重试自动带键——重放的副作用=1)——三组固化幂等的三层表达;无键请求的监控(比例)进指标(第 48 题)。

### 追问链:幂等表达三刀

一刀:"幂等键的 API 设计?"——header(X-Idempotency-Key)vs body 字段(业务字段)——header 的通用性(与业务解耦)vs body 的可见性——HTTP 语义的 header 幂等键是标准形态。二刀:"幂等与 REST?"——REST 的 PUT 天然幂等(完整替换)/POST 不幂等——POST 的业务幂等靠键(不靠动词);PUT 的幂等也要防并发(第 29 题 distributed 编辑冲突)——REST 动词的幂等是 HTTP 语义,业务幂等是另一层。三刀:"幂等键的文档?"——幂等键的生成规则/作用域/TTL(第 3 题 banking)——幂等键自身的契约(文档,第 14 题)。

## 总结点

1. 名字不表达,三层才表达
2. 服务端去重+契约声明+SDK 自动
3. 资金接口强制键,缺失 400
