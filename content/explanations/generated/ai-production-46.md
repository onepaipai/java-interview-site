> 场景与约束：网银事故复盘沙盘:AI 给出错误答案造成客诉,复盘时"当时的检索内容/模型版本/提示词都拿不到了"——事故证据的留存=请求 ID 贯穿+指纹快照+版本对账,复现是设计出来的能力,不是复盘时的运气。

1. 证据包的构成:请求 ID(贯穿网关/检索/模型/日志,第 21 题统一 ID)+上下文快照(检索指纹+提示词版本+模型版本,第 20/47 题)+输入输出(元数据层+采样内容层)+时间线(各组件的时间戳)——证据包让事故可在测试环境一比一重放。
2. 重放的能力:按证据包重建当时上下文(指纹解析到文档版本,第 27 题引用定位)、同版本模型/提示词重新生成——复现=验证根因假设的手段(第 47 题定位流程的核心环节)。
3. 留存的分级:事故相关请求的证据包完整保留(内容层+指纹层),普通请求按第 21 题分层——事故触发时"锁定"相关请求的证据(采样策略外的强制留存),防止 TTL 清理丢证据。

## 参考分析

### 第二步扩展① 机制:复现能力的三个前提

- 可复现=可重建输入+可固定模型+可追溯版本:输入(检索内容)靠指纹与版本化语料(第 10/18 题),模型靠版本固定(供应商模型 API 也会变,要记录版本号或用本地固定版本复现),提示词靠版本化(第 47 题)。
- 三前提齐备,事故重放才是工程能力。
- 缺一项,复盘只能靠"记忆与推测"。

### 第二步扩展② 反例:证据缺失的三种事故

- 事故一:检索内容未留存——"当时的证据是什么"无解,根因假设无法验证(检索缺陷还是生成缺陷成了罗生门)。
- 修复=指纹层常开+事故强制留存。
- 事故二:模型版本不明——供应商模型悄悄升级,复现用的版本与事故版本不同(结论失真)。
- 修复=响应元数据带模型版本(第 9 题计量口径同源)。
- 事故三:复盘时才建留存——事故后开启日志,但事故已经过去了(证据已随 TTL 清理)。
- 修复=留存策略平时就位,事故只做"锁定"。

### 第二步扩展③ 取舍:留存量与复现能力的平衡

- 全量内容留存:复现完美但隐私与存储爆炸(第 44 题不兼容)。
- 全指纹+事故锁定:复现覆盖事故类,普通请求不可重放(够用)——复现能力的设计目标是"事故可复现",不是"所有请求可重放"。

## 案例

### 第三步发散·验证与推演 验证:证据包的推演核对

- 推演核对(教学示例):注入一次"错误答案"事故——证据包走查:请求 ID 贯穿断言(四组件日志同 ID 可查)、上下文重建断言(指纹解析出的文档版本与事故时刻一致)、重放断言(同版本重新生成的输出与事故输出同形态——根因可验证)。
- TTL 锁定断言(事故相关证据不被清理)。
- 验证:证据包四要素断言可程序化。
- 复盘演练(用证据包 30 分钟内完成根因定位)——复现能力的成熟度以演练计时。

### 第三步发散·追问扩展 追问链:证据三刀

- **Q1：证据包的隐私?**
  - 答：证据包含内容(必然敏感,第 44 题):事故证据的访问=审批+审计+短 TTL(复盘后按合规策略处置)——证据的权限与留存单独设计。
- **Q2：重放的模型版本已下线?**
  - 答：供应商旧版本不可用时,用本地近似版本复现+标注差异(复现的诚实性:能完全复现/近似复现/不可复现三级标注)。
- **Q3：证据包的自动化?**
  - 答：事故触发时自动打包(监控告警联动:错误率突增→相关请求证据自动锁定)——证据收集不依赖人工记起。

## 总结点

1. 请求 ID 贯穿+指纹快照+版本对账
2. 复现是设计出来的,不是复盘靠运气
3. 事故证据强制留存,防 TTL 清丢
