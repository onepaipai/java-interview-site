## 参考回答

> 场景与约束：网银多机房沙盘:域名解析返回三个机房 IP 轮转(DNS 负载均衡)——某机房半死不活,DNS 照样分发;应用内服务发现(注册中心+客户端负载均衡)能按健康度实时摘除——两层机制的时效与健康感知能力不同,层级也不同。

1. DNS 负载均衡:域名级、解析时决策(客户端每 TTL 拿一次列表)、粗粒度(机房/集群)、无健康检查(或仅探活级)——适合机房间容灾与流量地理调度;缺陷:缓存 TTL 尾部(Q2)、健康感知弱、多 A 记录轮转的客户端行为不统一。
2. 应用服务发现:实例级、调用时决策(客户端每次从注册中心取健康实例列表)、细粒度(单实例摘除/权重/灰度)、健康检查实时——适合机房内服务间调用;代价:注册中心运维+SDK 侵入或 sidecar。
3. 分层组合:DNS(机房级入口,如 api.bank.com→两机房 LB)+LB(集群级)+服务发现(实例级)——每层解决不同粒度的"去哪"问题;跨机房容灾靠 DNS+健康探活,机房内弹性靠服务发现+自动扩缩容。

## 参考分析

### 机制:决策时点与信息粒度

DNS 在"域名→IP"时决策,信息=IP 列表+权威侧配置,粒度=机房;服务发现在"实例→地址"时决策,信息=实例健康/权重/版本,粒度=实例;决策时点决定时效:DNS 受 TTL 缓存制约(分钟级收敛),服务发现秒级推送——时效需求决定选层。

### 反例:层级错配的三种事故

事故一:机房内实例扩缩容依赖 DNS——实例变化频繁,TTL 尾部导致调用打到已销毁实例(超时重试放大,见 Q22);机房内必须服务发现。事故二:跨机房容灾只靠服务发现——注册中心本身跨机房同步分区时信息失真(见 Q43),机房级调度反而要回到 DNS+独立健康探活的简单可靠层。事故三:多 A 记录轮转当主备——客户端解析实现各异(有的固定取第一个),故障切换行为不可控;主备切换要靠 DNS 故障转移+健康检查或全局 LB。

### 取舍:服务发现的两种形态

客户端发现(注册中心+SDK 负载均衡):少一跳、延迟低,但 SDK 侵入+多语言成本;服务端发现(sidecar/内部 LB):应用零侵入,多一跳转发;按技术栈统一度选——单一 JVM 生态客户端发现省跳,多语言/混合栈 sidecar(服务网格)统一(与 Q20 mTLS 的 sidecar 形态衔接)。

## 案例

### 验证:时效差异的实测证据

本机实测(Q2 同源):
~~~
java N5DnsCache
首次解析 www.baidu.com=110.242.69.21 耗时 48ms
二次解析 耗时 0ms(JVM 进程内缓存命中)
两次结果相同=true
~~~
验证:进程内缓存冻结解析结果(0ms 且同记录)——DNS 决策的时效边界实测;实例级秒级摘除按注册中心推送语义推演并明示;两层粒度与时机的分工矩阵成立。

### 追问链:发现三刀

一刀:健康检查的责任分层——DNS 探活(机房级,L4 拨测)、LB 健康检查(集群级,Q41)、注册中心心跳+实探(实例级)——三层各自定义"活着",口径不一致会出现"LB 认活但注册中心摘了"的摇摆。二刀:一致性哈希与服务发现的组合——实例变化时一致性哈希减少数据迁移(distributed D13 实测:200 虚拟节点迁移 19% vs 取模 80%)。三刀:与 Q2 的衔接——负缓存与新实例上线(新实例注册后客户端 DNS 无该记录?——服务发现绕开 DNS 正是为此)。

## 总结点

1. DNS 管机房发现管实例
2. 时效差在 TTL 与推送
3. 三层各管一级粒度
