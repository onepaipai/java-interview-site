## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银缓存沙盘:穿透(查不存在的数据→缓存永远 miss→DB 被打)、击穿(热点 key 过期→瞬间大量请求打到 DB)、雪崩(大量 key 同时过期或 Redis 宕机→DB 崩溃)——cache-messaging 批次的专项详解(第 15/33 题)。

1. 穿透(查不存在):请求的数据在缓存和 DB 都不存在→每次都打到 DB(缓存永远 miss);解决:布隆过滤器(快速判断"肯定不存在",第 30 题 collections)+缓存空值(不存在的数据也缓存短 TTL)+参数校验(入口拦截非法 ID)。
2. 击穿(热点 key 过期):热点 key 过期瞬间→大量并发同时 miss→同时打 DB(singleflight 场景);解决:互斥锁(单线程重建缓存,其他等待——分布式 D6:200 并发合并后 1 次)+逻辑过期(物理不过期,值内含过期时间——过期后异步更新)+永不过期(热点数据)。
3. 雪崩(大量 key 同时过期/Redis 宕机):多个 key 同时过期(同批设置相同 TTL)→DB 瞬间被打;Redis 宕机→全量请求打到 DB;解决:过期时间加随机(TTL±随机偏移)+Redis 高可用(哨兵/集群)+多级缓存(L1 本地+L2 Redis)+限流兜底(第 45 题)。

## 参考分析

### 第二步扩展① 机制:三种场景的"缓存失效"模式

- 穿透=缓存"永远 miss"(数据不存在)。
- 击穿=热点 key "瞬间 miss"(过期)。
- 雪崩=大量 key "同时 miss"(批量过期/宕机)——三者的根因不同(不存在/过期/宕机),解法也不同(布隆过滤器/互斥锁/高可用+随机 TTL)——统一的目标=保护 DB(缓存是 DB 的挡箭牌,箭牌碎了 DB 就暴露)。

### 第二步扩展② 反例:缓存防护的两种事故

- 事故一:布隆过滤器不更新——删除数据后布隆过滤器仍判"可能存在"→缓存空值占内存。
- 修复=定期重建或计数布隆(第 30 题 collections)。
- 事故二:互斥锁无超时——锁等待超过 DB 恢复时间→请求堆积。
- 修复=锁超时+降级(等待超时→返回默认值或旧缓存)。

### 第二步扩展③ 取舍:防护的投入与收益

- 穿透防护(布隆过滤器):内存成本(布隆过滤器)+误判率(1%)。
- 击穿防护(互斥锁/逻辑过期):复杂度增加。
- 雪崩防护(高可用+随机 TTL):运维成本——按"DB 的承受力"决定防护等级(DB 能扛 1000 QPS→穿透 500 QPS 需要防护)。

## 案例

### 第三步发散·验证与推演 验证:三场景的走查核对

- 验证:穿透断言(查不存在 ID 100 次→DB 查询 100 次→加布隆过滤器后 0 次)。
- 击穿断言(热点 key 过期→200 并发同时 miss→加互斥锁后 DB 只查 1 次)。
- 雪崩断言(1000 key 同 TTL 同过期→DB 突增→加随机 TTL 后平滑)。
- cache-messaging D6 实验(200 并发同键合并后 1 次)。
- 验证:三种场景的 DB 压力断言可程序化(计数器)。

### 第三步发散·追问扩展 追问链:缓存三刀

- **Q1：缓存预热?**
  - 答：上线前主动加载热点数据到缓存(避免上线瞬间穿透);预热的数据源=历史热点+业务预测——预热也是"主动填缓存"(不是等用户触发)。
- **Q2：多级缓存的一致性?**
  - 答：L1 本地(应用内存)+L2 Redis:更新时先失效 L2 再失效 L1(广播/版本号)——多级缓存的一致性窗口更大(第 24 题)。
- **Q3：缓存的监控?**
  - 答：命中率(hit rate)/ miss 率/DB 回源 QPS/缓存大小——命中率下降=缓存失效问题(穿透/击穿/雪崩的前兆);命中率是缓存的核心指标。

## 总结点

1. 穿透=布隆,击穿=互斥,雪崩=高可用+随机 TTL
2. 统一目标=保护 DB
3. 命中率是缓存的核心指标
