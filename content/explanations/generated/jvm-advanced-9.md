## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银额度服务沙盘:监控显示 GC 占比 3%,但接口 P99 与 GC 事件强相关。解释除 STW 暂停外的四条传导路径,并给出各自的可观察证据与缓解手段。

1. 暂停只是显性成本:并发周期抢 CPU、写屏障开销、缓存冷启动与 TLB/页相关效应都不计入"GC 时间",却直接影响接口延迟。
2. 分配速率本身就是延迟源:新对象分配虽快,但 TLAB 补货、大对象直入老年代、随之而来的并发标记都被分配曲线牵引。
3. 判定靠对齐而非占比:把 GC 事件时间戳、并发周期起止、CPU 使用率与 P99 窗口对齐,一条条排除传导路径。

## 参考分析

### 第二步扩展① 机制:四条不进占比的传导路径

- 路径一:并发标记与搬迁线程和应用抢 CPU,实测 G1 的 Concurrent Mark Cycle 在小堆上毫秒级,但生产大堆可达秒级,期间业务吞吐下降。
- 路径二:G1/ZGC 的写屏障与读屏障插在业务代码里,ZGC 的读屏障尤其重,热点路径指令预算被吃掉。
- 路径三:GC 后 survivor/缓存冷启动——疏散把热对象搬走,代码缓存的 TLB 与页局部性变差,后续若干请求变慢。
- 路径四:大对象分配直入老年代,触发更早的并发标记(连锁到 mixed/IHOP),占用不体现在当次暂停里。

### 第二步扩展② 反例:3% 占比与强相关的矛盾怎么成立

- 实测锚点:G1 young 暂停中位 2.948ms、最大 32.202ms,单线程负载下 GC 时间占比不足 5%。
- 但 ZGC 组的 Allocation Stall (main) 59.822ms 完全不在 GC 时间内,却把请求拖了近 60ms。
- 再来一条:并发标记周期 195.485ms(实测 Concurrent Mark Cycle 行)与业务并发运行,不产生 STW 却压低了吞吐。
- 两条都说明"占比"是垃圾指标——它只统计 GC 线程花的 CPU 时间,不统计 GC 事件对应用的时间转嫁。

### 第二步扩展③ 取舍:先对齐证据,再决定动哪里

- 把 P99 抖动窗口与 GC 日志逐条对齐:窗口内有 STW,查暂停分布。
- 窗口内只有并发周期,查 CPU 与并发线程数(-XX:ConcGCThreads)。
- 窗口内两者皆无,查 Allocation Stall/安全点/虚存缺页等应用侧事件。
- 对症下药:并发抢 CPU 调 ConcGCThreads 或错峰,屏障开销在热点代码上减分配,冷启动靠预热(见第 40 题)。
- 占比指标只适合做长期趋势,不适合做归因。

## 案例

### 第三步发散·验证与推演 实证:三条传导路径的可观察量

- 本机实测(Java 17.0.17):
```
Concurrent Mark Cycle 195.485ms        (与业务并发,不在 GC 占比内)
Allocation Stall (main) 59.822ms       (ZGC 堆满时的应用停顿)
Pause Full (G1 Compaction Pause) 80.755ms
```
- 验证:用 -Xlog:gc* 的完整时间戳与链路追踪 P99 窗口对齐,三条证据分别落在不同窗口,说明接口抖动的来源不止一行 Pause 日志。

### 第三步发散·追问扩展 追问链:占比陷阱三刀

- **Q1：那什么指标能替代占比?**
  - 答：暂停分布加并发周期时长加应用侧停顿事件的三联表,再对齐业务 P99;占比只在长期趋势里当辅助。
- **Q2：并发周期多长算长?**
  - 答：没有绝对值,与堆和存活集相关,小堆实测 195ms,生产数十 GB 堆会到秒级;看它占总周期比例与出现频率。
- **Q3：写屏障开销怎么量化?**
  - 答：JMH 级微基准或 JITWatch 对比屏障开关的汇编差异,生产上用吞吐差近似;别用生产日志量化它,信号太小。

## 总结点

1. 占比是假象,对齐才见真
2. 并发抢 CPU,屏障吃指令
3. Stall 冷启动,都在窗口里
