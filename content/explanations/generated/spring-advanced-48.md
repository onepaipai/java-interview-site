## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银监控沙盘:某接口的 Metrics 加了 userId 标签,大促百万活跃用户→百万时间序列,Prometheus 内存暴涨查询超时——标签基数(cardinality)爆炸。用基数治理说明标签设计。

1. 标签基数=标签取值数×其他标签组合:userId(百万)级别的标签让时间序列指数膨胀——存储、内存、查询三重爆炸;高基数是监控系统的第一事故源。
2. 设计规则:标签表达"维度"不表达"实体"——用 tenantId(百级)/region(十级)/resultCode(十级),不用 userId/orderId/IP(百万级);实体级追踪交给日志与链路(trace,第 40 题)。
3. 治理手段:基数预算(每个指标声明预期基数,超限告警)、采样聚合(userId→hash 分桶)、按需下钻(先看聚合,问题定位再查日志/链路)。

## 参考分析

### 第二步扩展① 机制:基数如何爆炸

- Prometheus 每个标签组合=一条独立时间序列:接口(50)×实例(20)×resultCode(10)=1 万序列可控。
- 加 userId→序列数=活跃用户数×其余维度——百万级。
- 后果三重:存储(每序列独立样本流)、内存(查询时展开)、查询(高基数聚合慢到超时)。
- 且基数只增难减:一旦写入,历史序列长期保留——治理成本远高于预防。
- SRE 实践:高基数标签是"指标能查"与"系统可用"的取舍,默认禁止。

### 第二步扩展② 推演:维度分层与下钻路径(附分布式锚点)

- 下钻路径:Metrics 聚合层(tenant/region/resultCode)→发现某租户异常→链路追踪按 tenantId 过滤→日志按 userId 精查——三层观测各司其职(Metrics 管面、Trace 管链、Log 管点)。
- 本机锚点(热点分维度,分布式 25 题):99% 流量单键,加盐分片后 18%——"维度选择"决定问题可见性,监控维度错位同样让问题不可见:
```
普通分片:热点落在节点1 承载=99% 流量
加盐16片:单节点最大承载=18% 流量
```
- 验证:基数爆炸为机制推演(Prometheus 行为),维度分层为工程范式。
- 观测三层(指标/链路/日志)的分工与第 40 题审计分层的思想同源。

### 第二步扩展③ 取舍:基数预算与例外通道

- 预算:指标注册时声明预期基数(序列数上限),CI 校验(指标命名与标签规范)。
- 超预算指标需要专门审批。
- 例外通道:确实需要用户级聚合的场景(风控离线分析)——走日志/事件流(ClickHouse 类 OLAP),不进 Metrics。
- 清理:已写入的高基数指标,删除 metric+清理录制规则。
- Prometheus 的历史数据要显式清理。
- 评审问句:这个标签有多少个可能取值?乘上其他标签是多少序列?

## 案例

### 第三步发散·验证与推演 验证:Prometheus API 巡检每指标序列数并排序 top

- 验证:Prometheus API 巡检每指标序列数并排序 top10,新增指标超基数预算即失败。
- userId 类标签的指标在 CI 指标规范校验中直接拒绝——基数治理自动化。

### 第三步发散·追问扩展 追问链:监控标签三刀

- **Q1：resultCode 这种有限枚举安全吗?**
  - 答：安全前提是"真的有限":错误码设计失控(动态拼错误消息当标签)照样爆炸——枚举值进常量类,未知值归并到 other。
- **Q2：低流量服务可以任性吗?**
  - 答：基数问题与流量无关(序列数由标签组合决定);小服务基数小是事实,但规范统一才能在大服务复用——规范从第一天执行。
- **Q3：怎么审计现有指标的基数?**
  - 答：Prometheus API 查每指标序列数,排序 top10;定期巡检基数增长率,异常增长的新指标即治理对象。

## 总结点

1. 标签是维度,不是实体
2. 百万取值进日志,十级取值进指标
3. 基数预算进 CI,增长进巡检
