## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB，单 SKU 可售库存是事实源；多个请求可能同时扣减，客户端可能在服务端提交后超时重试。目标是库存不为负、同一业务请求只生效一次；不讨论多仓预占的完整状态机。

1. 不要把“先 SELECT 再在应用里判断”当作并发保护。对单行扣减可在事务内执行带 stock >= quantity 条件的 UPDATE，并以影响行数判断成功或库存不足。
2. 订单记录、库存变更与幂等请求身份应在同一数据库事务协调；重试复用稳定业务键，并由唯一约束处理并发首次请求。超时后结果未知，应查询或用同一键重放。
3. 多 SKU、多仓或预占/释放需要额外定义锁顺序、状态迁移和补偿；缓存只能加速读取，不能替代最终库存约束。

## 参考分析

### 原子条件更新把判断与扣减放到同一写操作

典型语句为 UPDATE inventory SET quantity = quantity - :q WHERE sku_id = :id AND quantity >= :q。对正数 q，数据库在并发更新冲突时串行化目标行的写入，并根据当前可更新版本重新判断条件；成功必须检查恰好一行受影响。零行可能表示 SKU 不存在或库存不足，接口应按业务需要区分。
这比先读出 1 再写回 0 更安全，因为“读到可售”与“执行扣减”之间没有留给另一个请求超卖的窗口。数量必须先校验为正数、范围合法；否则负数扣减会变成加库存。事务还要协调订单状态，避免扣减成功但订单创建失败。类比演唱会闸机的原子扣票：判定“还有票”和“撕下这张票”必须发生在同一个闸机上，分两步就给了超卖空隙。

### 唯一约束处理并发重试，不能靠先查后插

客户端超时无法知道服务端是否已提交。以调用方和业务操作构造幂等键，在事务中插入唯一请求记录、执行扣减并保存结果；并发请求由唯一索引仲裁。重复键且参数相同应返回原结果或处理中状态；重复键却携带不同 SKU/数量应明确冲突。
如果先单独提交幂等标记，再扣库存，进程崩溃可能留下“已处理但未扣减”；反过来先扣减再独立记键，则可能重复扣减。两者必须处在同一原子边界。事务失败时整体回滚，外部消息则通过事务性发件箱等机制另行协调。

### 锁定读适用在需要读取并维护更大不变式时

若业务必须根据库存、预占量、仓库状态等多列共同决策，可以在事务中 SELECT ... FOR UPDATE 锁定明确的记录，再验证并更新。锁定读会等待竞争事务，并可能因访问范围和索引产生更广锁冲突；应检查执行计划、锁等待和死锁图，缩短事务并保持多行稳定加锁顺序。
对于纯粹的单行扣减，条件 UPDATE 通常更简单。不能仅凭使用了 FOR UPDATE 就承诺没有死锁，也不能把 READ COMMITTED/REPEATABLE READ 名称当作完整业务不变式证明。死锁受害事务只在副作用边界可重放、且有次数和退避限制时才整体重试。

## 案例

### 并发验收：库存为 1 时两个请求竞争

在隔离的 MySQL 8.4 测试库把某 SKU 库存设为 1，让两个事务同时执行条件扣减 quantity=1。预期只有一个 UPDATE 影响一行，另一个影响零行；最终库存为 0，成功订单数为 1。随后在同一事务中故意让订单写入失败，验证库存更新一起回滚。
本项目 H2 演示只能验证条件更新的教学逻辑；InnoDB 锁行为、实际执行计划及死锁情况需在目标 MySQL 版本实测，不能把上述预期描述为已运行结果。

### 故障推演：提交成功但响应丢失

固定业务幂等键，让服务完成订单与库存事务后丢弃响应，再以相同键并发重试。预期库存只扣一次，调用方最终获得同一订单结果；以不同数量复用原键时应返回参数冲突，不得继续扣减。
记录数据库事务结果、幂等状态、成功订单数和库存变化，并在提交前、提交后响应前分别终止服务。验收不以 HTTP 日志或 UPDATE 调用次数为准，而以库存守恒、唯一业务结果和可恢复的未知状态为准。

## 总结点

1. 判定与扣减同一条 UPDATE，分步必超卖
2. 把库存条件放进原子 UPDATE
3. 业务结果与幂等记录同事务
4. 超时重试复用原业务键
