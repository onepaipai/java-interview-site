## 参考回答

> 场景与约束：Java 17 / Redis 7 教学场景：把三步库存操作包进 MULTI/EXEC，期望出错自动回滚，结果部分执行后错误仍在。对照 Redis 事务与关系库事务的三点语义差异：入队错误、运行时错误不回滚、无隔离级别选择。

1. Redis MULTI/EXEC 的保证是"命令按顺序原子执行、不被其他客户端插队"——它保证的是隔离与原子提交，不保证回滚：EXEC 前的语法错误整个事务丢弃，EXEC 后的运行时错误（如对 String 执行 LPUSH）不回滚已执行的命令。
2. 三点差异：一，关系库回滚的是"已执行的变更"，Redis 运行时错误后继续执行剩余命令；二，Redis 无隔离级别选择（天然串行无并发读问题，也无回滚段）；三，Redis 事务不支持依赖前置命令结果的逻辑分支——需要 WATCH 乐观锁或 Lua。
3. 正确姿势：把"必须全部成功或全部失败"的多步操作改用 Lua 脚本（脚本内错误处理显式化），或用 WATCH + 重试的乐观事务；MULTI/EXEC 适合"批量命令打包"而非"需要回滚保护的业务事务"。

## 参考分析

### 机制：Redis 事务是"命令打包"，不是"原子性承诺"

MULTI 相当于把命令放进信封一次寄出（保证顺序与不插队），但寄出后每封信独立投递——投递失败不召回前面的信。关系库事务像有担保的交易：任何一步失败全部撤销。类比解释了为什么"Redis 事务里一半成功一半失败"是设计内的行为，不是缺陷。

### 反例：三步库存操作的半执行现场

MULTI 内依次 DECR stock（成功）、LPUSH log（对错误类型，运行时错误）、DECR reserve（成功）——stock 被扣、reserve 被扣、log 失败，无回滚。业务上库存与预留不一致。修复：改用 Lua 脚本内先类型检查再执行，或用 WATCH 保证前置读取到执行之间无变化。

### 取舍：WATCH 乐观锁与 Lua 的分工

WATCH + MULTI/EXEC：监视 key，EXEC 时若 key 被改则整个事务不执行（返回 nil，应用重试）——适合"读-算-写"且冲突率低的场景；Lua：脚本原子执行且可在脚本内做条件分支——适合"多步强耦合、需要中间判断"的操作。两者都不提供关系库的回滚段；需要"复杂业务事务"就该留在关系库。

## 案例

### 对照操作：运行时错误不回滚的复现

教学验证：MULTI 内依次 SET a、LPUSH a（类型错误）、SET b，EXEC 后检查。预期：a 被设置、LPUSH 报错、b 也被设置——半执行状态保留。对照 WATCH 版本在 a 被并发修改后 EXEC 返回 nil（全部不执行）。实验可复跑，语义差异当场对比。

### 追问：为什么 Redis 不实现回滚

回滚需要 undo 日志，与 Redis 的内存模型和性能目标冲突；且 Redis 命令的错误多是编程错误（类型误用），入队检查已拦截大部分——设计者认为回滚在 Redis 场景收益不抵成本。理解这个取舍后，"把关系库的事务习惯带到 Redis"的反模式就能主动识别。

## 总结点

1. MULTI 打包不保证回滚
2. 入队错全丢，运行时错不回头
3. 要回滚的业务留在关系库
