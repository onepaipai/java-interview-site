## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银大促沙盘:秒杀 1000 件,10 万人涌入——库存扣减必须防超卖(CAS 原子),请求必须防无限排队(前置限流+快速失败+异步结果);实测证据:两步扣减超卖 95 笔,CAS 恰好 0 超卖。

1. 防超卖:库存扣减单条原子 SQL(UPDATE stock SET n=n-1 WHERE id=? AND n>0,受影响行数=0 即售罄)或 Redis DECR+落库异步——禁止"先查后改"两步(实测:竞态窗口下 100 人抢 5 件超卖 95 笔;CAS 0 超卖,distributed D7)。
2. 防无限排队:入口限流(令牌桶按库存量级发放,卖出完即快速失败,不进业务链路)、请求分层过滤(静态页+CDN 扛浏览,真正到达扣减的流量≈库存量级)、异步结果(提交后排队号+轮询/推送结果,等待期不占服务线程)。
3. 组合形态:前置校验(黑名单/限购)→令牌桶→库存预扣(Redis)→异步落库(队列削峰)→结果查询,漏斗逐层压流量;预扣与落库的分叉补偿:预扣成功落库失败=掉单(对账检测→回补库存,回补幂等),预扣失败但 DB 已扣=超卖风险(DB CAS 兜底拒绝)——两条补偿链写进预案,不是"队列兜一切"。总原则=万人抢 1000 变成 1000 万人快速被告知没抢到。

## 参考分析

### 第二步扩展① 机制:漏斗与原子扣减

- 漏斗模型:每层只放行"下层能消化"的量——CDN(浏览)→限流(配额≈库存×安全系数)→原子预扣(Redis 单线程天然串行)→异步落库(削峰+最终一致)。
- 原子扣减的语义:WHERE n>0 的条件更新=检查与扣减合一,无竞态窗口。
- Redis DECR 返回负数即拒绝,配合 Lua 保证"检查+扣"原子。

### 第二步扩展② 反例:抢购的四种事故

- 事故一:两步扣减超卖——查库存 5、扣减时并发,负库存。
- 资损+公关事故(D7 实测 95 笔)。
- 事故二:无限排队——失败请求也进队列慢慢处理,线程池堆积雪崩(见 Q22 重试放大)。
- 失败要快速返回。
- 事故三:热点行锁——全部扣减打到同一行,DB 行锁串行瓶颈。
- Redis 预扣把热 Spot 从 DB 挪走。
- 事故四:排队号无幂等——用户重复提交占多个名额。
- 幂等键按用户+活动唯一。

### 第二步扩展③ 取舍:Redis 预扣 vs DB 原子扣

- Redis 预扣:吞吐高(10 万级),一致性=预扣与落库可能分叉(掉单靠对账兜底)。
- DB 原子扣:一致最强,吞吐受行锁限制(千级)。
- 组合:抢购期 Redis 扛流量+队列落库,落库失败回补库存(补偿,幂等)。
- 按峰值量级选,量级小(几百 TPS 内)直接 DB 更简单。

## 案例

### 第三步发散·验证与推演 验证:超卖形态的实测证据(交叉引用+本批实证)

- distributed 批次 D7 实测(100 人抢 5 件):
~~~
两步非原子(检查+yield+扣减):成功扣 100 次、超卖 95 笔
CAS 条件累计:恰好 5 笔、0 超卖
~~~
- 本批 SD7PreDeduct 预扣补偿链(10000 请求抢 1000,0.5% 落库失败):
~~~
java SD7PreDeduct
预扣成功 1000/拒绝 9000
落库成功 995/落库失败(掉单) 5 位次[200, 400, 600, 800, 1000]
对账检出分叉 5 笔→回补后 DB 可售余量 10 (回补幂等)
最终售出 995 (无超卖;掉单回补后库存虚占被消除)
~~~
- 推演核对:漏斗与快速失败形态与 network Q22/47 的退避与快速失败证据衔接。
- 验证:原子扣减防超卖(CAS 0 超卖)+分叉补偿链(掉单检出→回补)都有实测数字支撑。

### 第三步发散·发散要点 追问链:抢购三刀

- **追问①**：库存预热与回补——活动开始前把库存加载到 Redis,取消/超时订单回补(幂等,防重复回补);回补与扣减同键
- **追问②**：防黄牛——设备指纹+限购(幂等键含用户维度)+行为风控,入口过滤比事后追溯便宜
- **追问③**：与 Q46 恢复洪峰的衔接——活动结束后队列积压的落库任务恢复时用指数退避,防恢复期二次打满

## 总结点

1. 条件更新防超卖
2. 失败快速返回不排队
3. Redis 扛热 DB 兜底
