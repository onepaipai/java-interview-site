## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银高并发沙盘:长上下文问答并发一上来就 OOM——自回归生成的每一步都要带着所有历史 token 的 KV Cache,内存占用随"并发数×上下文长度"乘积增长,是推理容量的一等约束。

1. KV Cache 的账:每个 token 在每层留 K 与 V 两份向量(头数×头维度×2),总内存≈并发数×上下文长度×层数×每 token 字节——长上下文(32K)×高并发(64)时以数十 GB 计,乘积关系意味着一个因子翻倍内存翻倍。
2. 对并发的影响:显存被 KV Cache 占满后,新请求无法进入(排队)——长请求占住缓存,短请求被拖累(队头效应);吞吐与 P99 都受它支配。
3. 工程对策:PagedAttention 类分页管理(显存碎片消除,同显存承载更多并发,第 paged 论文)、上下文压缩(第 32 题直接减 token)、前缀缓存(相同系统提示的 KV 复用,跨请求摊销)、限流按"上下文长度加权"(长请求占配额多,第 45 题公平配额的加权因子)。

## 参考分析

### 机制:为什么自回归生成离不开 KV Cache

生成第 N 个 token 时要对前 N-1 个 token 做注意力——重算历史是 O(N²) 灾难,所以历史 token 的 Key/Value 在首次计算后缓存复用。代价=缓存随生成持续增长(直到序列结束才释放):一个 32K 上下文的请求,从首 token 到尾 token 全程占着最大缓存。类比食堂餐位:从打饭到吃完一直占座,坐多久×多少人=座位需求——长会话是"久坐者"。

### 反例:KV 容量的三种事故

事故一:按"并发数"限流不按长度——10 个 32K 长请求同时到,显存爆;修复=限流按 token 预算加权(第 45 题)。事故二:显存碎片——请求长度参差,连续分配失败(明明总量够);修复=分页管理(paged 论文形态)。事故三:前缀缓存失效频繁——系统提示词/检索上下文每请求变,缓存无复用;修复=稳定前缀前置(系统提示不动)+动态部分后置,提高前缀命中率。

### 取舍:上下文长度、并发与成本的三角

业务要长上下文→并发与成本线性代价——按场景分级:精读长文档的低并发通道 vs 短上下文高并发通道,分开部署(舱壁,分布式 D3 同构);窗口不是越大越好(第 26 题),窗口决策同时是容量决策。

## 案例

### 验证:KV 占用的推演核对

推演核对(教学示例):按公式估算(7B 模型,32 层,头 32×维 128,fp16 KV)——32K 上下文单请求 KV≈(32K token×32 层×2×32×128×2B)≈16GB 量级;对照"按并发限流"的 OOM 复现与"按 token 预算限流"的稳定形态。验证:估算与实际显存监控对齐(NVIDIA SMI),分页管理的碎片消除以"同显存并发数提升"实测——推理容量账要按乘积公式算,不按请求数拍脑袋。

### 追问链:KV 三刀

一刀:"KV Cache 能跨请求共享吗?"——相同前缀(系统提示+固定上下文)的 KV 可复用(前缀缓存),前缀分界要 token 级对齐;检索上下文每请求不同,复用面=系统提示部分。二刀:"量化 KV 呢?"——KV 精度(fp16→int8)省显存损质量,与第 15 题向量量化同理——回归评估门槛。三刀:"流式输出的 KV 峰值?"——流式不省 KV(照样增长到序列尾),省的是首 token 延迟与用户感知;容量账不变。

## 总结点

1. KV 内存=并发×上下文的乘积
2. 长请求占座,限流按 token 加权
3. 前缀缓存摊销,分页消碎片
