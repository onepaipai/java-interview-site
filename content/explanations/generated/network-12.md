## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银接口沙盘:前端拿到 HTTP 200 但 body 里 code=500——传输层成功、业务层失败被混为一谈;监控按 HTTP 状态统计成功率虚高,告警漏报,错误处理逻辑在两层间漂移。

1. 分工原则:HTTP 状态码表达传输与协议层结果(200 成功到达、4xx 客户端请求问题、5xx 服务端问题、429 限流、503 过载),业务错误码表达业务语义(余额不足、卡状态异常)——body 的 code 只在 200/4xx 内细化业务原因。
2. 配合模式:2xx=业务成功或带业务码的"成功但有注意事项";4xx+业务码=请求被理解但业务拒绝(401/403/404/422 承载协议语义);5xx=系统级失败不携带业务码——监控按层统计:可用性看 5xx 比例,业务成功率看业务码分布。
3. 一致性纪律:同一类失败全链路同一映射(网关、服务、重试逻辑对 4xx/5xx 的处理一致),错误码字典版本化管理(见 spring-basics Q19 统一骨架),升级只增不改。

## 参考分析

### 机制:两层的语义边界

HTTP 层回答"这次通信发生了什么":连接、路由、鉴权、限流、协议错误;业务层回答"这笔业务的结果":成功/拒绝/待处理。混用的代价:重试逻辑按 5xx 退避会把业务拒绝也重试(余额不足重试百次)、按 4xx 中止会把系统故障当用户错误。

### 反例:状态码滥用的三种事故

事故一:全 200+body code——监控可用性 100%,故障夜无人发现。事故二:业务拒绝用 500——下游重试组件按 5xx 退避,余额不足被重试到熔断。事故三:限流返回 200+错误码——客户端不识别 429 的 Retry-After,无退避地立即重试放大故障(见 Q47)。

### 取舍:RESTful 严格性 vs 兼容性

严格 REST:每个错误精确映射 4xx/5xx——语义清晰但客户端版本兼容成本高;务实模式:粗分层(2xx/4xx/5xx)+body 细化——兼顾监控与兼容。选务实分层时,429/503 等关键协议语义必须保留在状态码层(重试组件依赖它们)。

## 案例

### 验证:两层语义的对照推演

推演核对:本机 N8 实验证实协议层错误在状态码层表达(Range 越界返回 416 而非 200+错误码),N7 实验证实 304 在传输层表达"无变化"——HTTP 自身语义就在状态码层;业务码只在 2xx/4xx body 细化;验证:分层映射与协议自身行为一致,监控按层统计的依据成立。

### 追问链:错误码三刀

一刀:Retry-After 与 429/503 的配合——服务端告知重试时机,客户端遵守(见 Q47),状态码层的协议语义不可下放 body。二刀:错误码与幂等键的关系——重复请求返回首次结果用 200+原业务码,幂等冲突(键占用中)返回 409——重试组件据此决策(见 Q11)。三刀:与 spring-basics Q19 的衔接——统一骨架(code/message/traceId)承载业务码,状态码承载传输层,两层骨架在本仓库内容中已对齐。

## 总结点

1. 传输层状态业务层码
2. 监控按层统计不混算
3. 429 等协议语义留在状态码
