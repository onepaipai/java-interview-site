## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银多端沙盘:手机银行+网银+柜面三端登录同一账户——认证=证明"你是你"的技术选型;多端的会话管理(互踢/共存/限时)是认证体系的运维面。

1. Token vs Session:Token(JWT/Opaque——客户端持有,无状态,适合 API/移动端)+Session(服务端持有,可撤销,适合 Web);金融系统常用组合:Web 用 Session(可即时踢出)+移动端用 Token(离线可用)+Token 撤销走黑名单(第 22 题撤销模型)。
2. 单点登录(SSO):一次登录→多系统可达——OIDC/SAML 协议,认证中心(ISP)签发 Token,各子系统验证——SSO 的登出(单点登出)是难点(各子系统的会话独立,要统一通知)。
3. 多因素(MFA):密码(知识)+短信验证码(持有)+U盾/动态令牌(生物/硬件)——金融场景按交易风险分级:低风险密码,中风险+短信,高风险+U盾/人脸——多因素是增强验证(第 126 题 challenge)的实现手段。
4. 多端互踢:同一账户的多设备登录策略——互踢(新登录踢旧)或共存(最多 N 设备)或限制(网银+手机各一个);互踢的实现=Session/Token 的版本号(新登录 version+1,旧 version 校验失败),金融场景通常"手机+网银共存但同端互踢"。

## 参考分析

### 机制:认证体系的"信任链"

认证=建立信任链:首次认证(密码+MFA)→签发凭证(Token/Session)→后续请求凭凭证(不再重复认证)→凭证有效期/撤销(过期/主动登出/安全事件强制踢出)——链的每一环都是攻击面:凭证被偷=身份被盗,撤销不及时=攻击窗口。

### 反例:认证体系的两种事故

事故一:Token 永不过期——泄露的 Token 永久有效;修复=短效 Access Token+长效 Refresh Token(第 22 题)。事故二:多端互踢实现有竞态——A/B 设备同时登录,后登录踢前登录,但前者的在途请求用旧 Token 已通过鉴权(竞态窗口);修复=请求粒度的版本校验(不是登录时校验)。

### 取舍:安全强度与用户体验

每次交易都 MFA:安全但用户崩溃;只登录时 MFA:体验好但交易期间凭证被盗=风险。折中:登录 MFA+高风险交易 step-up MFA(第 126 题增强验证)——按交易风险触发,不全局加压。

## 案例

### 验证:认证体系的走查核对

验证:多端登录断言(手机+网银共存/同端互踢)、MFA 分级断言(低风险免 MFA/高风险触发)、SSO 断言(一次登录多系统可达+登出通知)、Token 撤销断言(修改密码后全端失效)——四组固化认证体系(本仓库 SecurityConfig 的 Session+CSRF 为 Web 简化实现)。

### 追问链:认证三刀

一刀:"JWT 的撤销?"——JWT 自包含不可撤销(签了就有效到过期)——撤销走黑名单(Redis 缓存 jti,第 22 题)或短效+Refresh。二刀:"生物识别的定位?"——生物特征=最高安全但不可撤销(指纹泄露无法换)——生物识别作为 MFA 因子(不替代密码),生物模板本地存储(不上传)。三刀:"认证日志?"——登录/登出/失败/MFA 触发全记(第 130 题审计),异常登录(新 IP/新设备)告警(第 126 题风控)。

## 总结点

1. Token 管移动,Session 管 Web
2. MFA 按交易风险分级
3. 多端互踢=版本号校验
