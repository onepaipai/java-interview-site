> 场景与约束：网银 SDK 沙盘:SDK 升级后宿主 NoClassDefFoundError/NoSuchMethodError(二进制不兼容)——二进制兼容=旧编译产物(字节码引用)在新版本下可链接——源兼容(源码可编译)与二进制兼容(字节码可链接)是两个维度。

1. 兼容矩阵:加方法(二进制兼容+源兼容)、删方法(两者都不兼容)、改方法签名(不兼容——签名即方法标识)、改返回类型协变(兼容[桥方法,第 4 题])、加字段/改字段类型(字段按类型+名解析——改类型不兼容)。
2. 反直觉的不兼容:改 checked 异常列表(二进制兼容——异常表不在调用方字节码;源不兼容[调用方 catch 需改])、final 化方法/类(源兼容+二进制兼容——但语义变化[override 被拒])、static 化实例方法(不兼容——invokevirtual 改 invokestatic)。
3. 工具与流程:二进制兼容检查(japi-compat/JDK 的 jdeps)、语义化版本(破坏性变更=大版本,第 41 题)、消费者测试(第 14 题契约测试的编译产物形态)。

## 参考分析

### 机制:链接的解析规则

字节码引用:方法引用=类+方法名+描述符(参数与返回类型)——任一变化=新符号(旧引用 NoSuchMethodError)。字段引用=类+字段名+描述符。链接的时机:首次使用时解析(懒)——不兼容的爆炸点=首次调用(运行期,构建期不暴露——jdeps/japi 前移)。协变返回:桥方法让协变返回二进制兼容(编译器生成桥,第 4 题)。

### 反例:不兼容变更的三种事故

事故一,删方法:SDK 删 deprecated 方法(以为没人用)——宿主 NoClassDefFoundError(使用量未归零,第 41 题)。事故二,改签名:重命名参数不影响二进制(参数名不在描述符)但改类型炸——签名变更的敏感性。事故三,接口加抽象方法:实现类全炸(未实现)——接口的破坏性变更=默认方法替代(第 7 题)。三条的正解:兼容矩阵进变更评审(第 50 题)+工具检测(japi)+废弃流程(两段式,第 41 题)。

### 取舍:兼容检测的工具链

工具:japi-compat(clirr 思想:两个 jar 的 API diff)、jdeps(依赖分析)、Revapi(规则化检测)。流程:CI 的兼容门禁(破坏性 PR 拦截)+版本策略(语义化)+消费者测试(第 14 题)。成本:检测工具的配置(规则库)与维护——按 SDK 的用户面(第 43 题)决定检测深度。

## 案例

### 验证:兼容矩阵的断言组

验证:兼容断言(加方法的二进制兼容[旧字节码在新 SDK 上链接成功]——编译产物跨版本测试);不兼容断言(删方法的 NoSuchMethodError 复现);桥方法断言(协变返回的桥方法[注:本机 javap 可验,标注])——三组固化兼容矩阵;兼容检测进 SDK 的 CI(第 33 题供应链)。

### 追问链:兼容三刀

一刀:"默认方法的兼容?"——接口加默认方法=二进制兼容+源兼容(实现类无需改,第 7 题)——默认方法的兼容红利。二刀:"sealed 的兼容?"——sealed 化(限制继承)=源兼容(实现类加 extends/permits)二进制兼容(链接不变)但语义收紧——兼容≠无影响(语义的兼容矩阵,第 14 题契约)。三刀:"反射的兼容?"——反射 API(方法名/字段名)的兼容=符号兼容(同上)+注解保留策略(第 28 题)——反射用户的兼容面更广(名字即契约)。

## 总结点

1. 链接符号=类加名加描述符
2. 协变返回桥方法兼容
3. 兼容矩阵进 CI,破坏性拦截
