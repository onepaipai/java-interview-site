## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银定时任务沙盘:多实例部署,同一时刻只允许一个实例跑任务——分布式锁保证互斥。Redis 锁(SET NX+过期+续约)与 ZK 锁(临时顺序节点+watch)是两种实现,各自的失效模式不同。

1. Redis 锁:SET key value NX PX ttl(原子设锁+过期)——value 存持有者标识(防误删);解锁=Lua 脚本(比对 value+删除,原子);续约=看门狗(定时延长 TTL,防业务未完成锁过期);缺陷=主从切换时锁丢失(异步复制,主挂未同步到从→新主无锁→另一实例获锁→双持锁)。
2. ZK 锁:临时顺序节点(会话断开节点自动删——连接断=锁释放)+watch 前一个节点(前一个删了我就获锁)——优点=无锁过期问题(会话活着锁就在)+公平(顺序节点排队);缺点=性能低于 Redis(ZK 写要过半数确认)+运维复杂(ZK 集群)。
3. Redlock(Redis 官方多节点锁):向 N 个独立 Redis 实例同时加锁,过半成功才算获锁——解决单点 Redis 的主从切换丢锁;争议=时钟假设与假死(第 14 题展开);Simple Redis 锁够用则不升 Redlock。

## 参考分析

### 机制:锁的"失效语义"决定适用场景

Redis 锁=TTL 过期自动释放(防死锁)——但业务未完成锁先过期=互斥失效(另一实例获得锁);续约解决但增加复杂度。ZK 锁=会话断开自动释放(连接活着锁就活着)——网络闪断=锁释放(可能双持);两者的"失效语义"不同:Redis 锁靠 TTL 保鲜,ZK 锁靠连接保鲜——选型看"任务时长与网络稳定性"哪个可控。

### 反例:分布式锁的两种事故

事故一:Redis 锁无续约——任务 5 分钟,TTL 设 60s→60s 后锁过期,另一实例获锁→双跑;修复=看门狗续约或 TTL>最大任务时长。事故二:Redis 锁误删——实例 A 的锁过期后实例 B 获锁,A 完成后直接 DEL(删了 B 的锁);修复=解锁用 Lua 比对 value(只删自己的锁,第 14 题)。

### 取舍:Redis 锁 vs ZK 锁的决策矩阵

吞吐:Redis 高(内存操作)>>ZK;公平:ZK(顺序排队)>Redis(非公平);可靠性:ZK(CP)>Redis(AP,主从切换可能丢锁);运维:Redis 更普及> ZK 需集群——定时任务互斥(吞吐低+防重跑)→Redis 锁够用;选主/严格互斥→ZK 或 etcd;大部分场景:Redis 锁+看门狗+幂等兜底(锁失效了也不重复——锁只是优化,幂等才是防线,第 38 题纪律)。

## 案例

### 验证:分布式锁的走查核对

验证:Redis 锁断言(SET NX 成功获锁/重复获锁失败/TTL 过期后可重获/Lua 解锁只删自己的);双持锁场景推演(主从切换窗口,标注推演——未做 Redis 集群实验);对照幂等兜底(锁失效+双跑→幂等键拦截→零副作用)——锁+幂等的纵深防线。

### 追问链:锁三刀

一刀:"看门狗的实现?"——获锁后启动定时器(TTL/3 时续约),任务完成后取消——看门狗的失败处理(续约失败=锁可能已丢→任务应中止而非继续)。二刀:"锁与队列的选择?"——互斥用锁(同一时刻一个);削峰用队列(排队处理)——定时任务互斥用锁,任务堆积用队列(两者不是竞争关系)。三刀:" fencing token?"——锁的代际令牌(每次获锁 token+1,写入时校验 token 新旧,第 15 题租约/栅栏)——锁失效后旧持有者的写入被存储层拒绝——fencing 是锁失效的兜底(不依赖锁的完美)。

## 总结点

1. Redis 锁靠 TTL 保鲜,ZK 靠连接
2. 解锁 Lua 比对 value,不误删
3. 锁是优化,幂等是防线
