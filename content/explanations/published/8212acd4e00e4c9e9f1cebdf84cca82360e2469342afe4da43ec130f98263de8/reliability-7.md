> 场景与约束：网银值班沙盘:告警 CPU 95%——第一反应"重启"?错误;第一步是回答"谁在消耗 CPU":定位消耗线程(线程栈/火焰图)、区分业务流量与异常循环(死循环/正则回溯/GC 风暴),再决定止损动作——先诊断后处置,处置要可回滚。

1. 五分钟诊断序:确认范围(单实例或全集群)、看流量(QPS 同步涨=业务量问题,不涨=异常消耗)、抓线程栈(火焰图找 TOP 线程)、查 GC(GC 风暴常伪装 CPU 高)、看近期变更(发布/配置/定时任务)——先诊断后处置,动作要可回滚。
2. 常见消耗源:死循环(代码 bug:循环条件错)、正则回溯(灾难性回溯,CPU 100% 单线程)、GC 风暴(内存不足,CPU 被 GC 吃掉——与 Q8 内存排查衔接)、序列化风暴(大对象反复转换)、缓存失效风暴(回源计算,Q22 击穿)——每种的处置不同(重启只对内存泄漏类有效,死循环重启后复发)。
3. 止损动作分级:单实例异常→摘流量后重启(保集群);全集群异常→按根因定(配置回滚秒级/扩容缓解 CPU 密集型流量/限流保命)——动作前先说"这个动作对哪类根因有效",无效动作浪费故障窗口(与 Q21 止损优先级衔接)。

## 参考分析

### 第二步扩展① 机制:诊断与处置的匹配

- CPU 消耗=业务线程+GC 线程+内核(网络/IO)。
- 火焰图把"谁在烧"直接可见(自顶向下:入口→热点函数)。
- 处置匹配表:业务量涨→扩容/限流。
- 死循环→摘实例+修复。
- 正则回溯→熔断该接口+修复正则。
- GC 风暴→内存排查(Q8)不是重启。
- 缓存回源→击穿治理(Q22)。
- 匹配错了=浪费故障窗口。

### 第二步扩展② 反例:CPU 处置的三种事故

- 事故一:无脑重启——死循环 5 分钟后复发,重启循环把故障拖长。
- 先抓栈。
- 事故二:全集群扩容掩盖 GC 风暴——实例翻倍 CPU 依旧 90%(GC 占 80%),钱花了问题没解决。
- 先看 GC 占比。
- 事故三:摘错实例——把正常高负载实例摘了,异常实例还在。
- 按消耗源摘(线程栈定位)。

### 第二步扩展③ 取舍:诊断深度 vs 止损速度

- 影响面大(全集群错误率涨):先止损(限流/回滚,30 秒内动作)再诊断。
- 影响面小(单实例):先诊断(2 分钟内火焰图)再精准处置——速度与深度的权衡由影响面决定,不是性格决定。

## 案例

### 第三步发散·验证与推演 验证:处置匹配的推演核对

- 推演核对:诊断序(范围→流量→栈→GC→变更)与 network Q46 的分段计时、jvm 批次的火焰图/NMT 证据链同源(内联与 GC 证据:jvm 批次 PrintInlining/GC 日志实测)。
- GC 风暴形态引用 jvm 批次 pause.log(511M->407M Full GC 80ms)与 direct OOM 证据。
- 验证:五分钟诊断序可执行,处置匹配表每项有既有证据锚(明示:CPU 场景未复现,按方法论推演)。

### 第三步发散·发散要点 追问链:CPU 三刀

- **追问①**：CPU 与 Load 的区别——Load 高可能是 IO 等待(CPU 空闲),CPU 高才是计算瓶颈;两个指标分开看
- **追问②**：容器环境——CPU limit 与 throttling(被限流≠CPU 忙),throttling 指标单独看(限流造成延迟,加 CPU 反而有效)
- **追问③**：与 Q9 线程池的衔接——CPU 密集型线程池大小=核数,IO 密集型更大;线程池参数与 CPU 特性匹配

## 总结点

1. 先抓栈再处置
2. GC 风暴伪装 CPU 高
3. 动作匹配根因才有效
