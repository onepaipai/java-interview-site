## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17、G1 收集器的在线 API，目标是 p99 延迟而非平均停顿。需要区分 GC 暂停、safepoint、应用排队和下游等待，不能把 MaxGCPauseMillis 当成服务 SLA。

1. 先固定请求负载、堆大小、JDK、收集器和延迟目标，建立 GC、safepoint、应用排队、CPU 与分配速率的基线。
2. 按证据拆分尾延迟来源：Young/Mixed/Full GC、对象复制、到达安全点、线程调度、锁和下游等待，不要只看一次 GC pause。
3. 每次只改变一个关键变量，并同时比较 p50/p95/p99、吞吐、CPU、堆占用和错误率；目标是满足业务预算，不是让某个 GC 数字单独变好。

## 参考分析

### 先定义测量边界

请求 p99 是从入口接收至响应返回的时间，GC pause 只是其中一个组成部分。排队、线程调度、锁竞争、网络和数据库等待都可能制造长尾；若只对 GC 日志调参，可能把等待转移到线程池或下游。
固定 JDK 小版本、硬件/容器配额、数据集、请求分布和预热阶段，记录分配速率、存活集、GC 类型、暂停、safepoint 时间与用户延迟，才有可比基线。类比田径计时：先说清从发令到撞线量的是哪段、精确到毫秒还是微秒——尾延迟目标先要一份测量契约。

### 目标参数是启发式而非硬上限

G1 的 MaxGCPauseMillis 是回收器的期望目标，回收器据此调整回收集合，不保证每次暂停都不超过目标。存活对象复制、堆压力、线程竞争和操作系统调度都可能使实际停顿超出目标。
把目标设置得过低可能导致更频繁的小回收、吞吐下降或老年代增长；把堆无限增大又可能放大 Full GC 和容器压力。

### 用实验闭环而不是单参数优化

先确认是分配速率过高、存活集过大、Humongous 对象、回收跟不上还是非 GC 原因。再针对性调整堆边界、分配模式、对象生命周期或收集器参数，并用相同负载比较多个窗口的长尾。
发布门禁应同时观察用户成功率、p99、GC CPU 和错误预算；GC pause 变短但业务拒绝增多不能算调优成功。

## 案例

### 基线与对照实验

固定压测曲线和数据集，分别记录 G1 Young/Mixed/Full GC、safepoint、分配速率、p99、吞吐和 CPU。先建立基线，再只改变一个参数或对象分配模式；预期能定位尾延迟中 GC 的实际占比，而不是预设 GC 必然是根因。

### 发布验收

在阶跃流量、长尾请求和恢复阶段重复测试，检查 p99/p999、错误预算、堆回收后存活量和容器 RSS。验证新配置不会靠拒绝请求或缩小工作集制造虚假的延迟改善；本文数字为实验设计，不是已测线上结果。

## 总结点

1. 先签测量契约，再谈尾延迟
2. 先拆分尾延迟来源
3. 暂停目标不是硬上限
4. 调参必须同时看用户结果
