## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银数据沙盘:Agent 直接执行生成的 SQL 查客户数据——SQL 注入式的"模型注入"(第 25 题)可让任意查询执行。模型查询数据库的能力边界=只读视图+参数化+行级权限+限额,四道闸缺一不可。

1. 能力四闸:只读(SELECT-only,DDL/DML 语法层拒绝)、参数化(模型只提供参数值,SQL 模板预定义——不让模型写完整 SQL,注入面归零)、行级权限(查询自动携带用户权限过滤,第 16/44 题——模型不能查"越权行")、限额(查询超时/行数上限/频率限制——防全表扫与资源拖垮,第 36 题)。
2. 接口形态:模型可用的不是"数据库连接"而是"受控查询 API"(预定义查询集+参数)或"只读视图+受限 SQL 方言"——暴露面越小越好;自由 SQL 是最后的选项(且必须配只读账号+权限视图+审计)。
3. 错误回喂:查询失败(语法/超时/权限)的错误信息回喂模型时,错误详情要过滤(不泄露 schema 细节与数据值——错误信息也是信息泄露通道)。

## 参考分析

### 第二步扩展① 机制:模型=不可信查询发起者

- 模型生成的 SQL 由"提示注入或幻觉"驱动——任何来自模型的 SQL 都要按"不可信输入"对待(第 25 题检索内容同级别)。
- 四道闸的设计假设=模型可能被诱导发起任意查询,防线必须在模型之外(数据库/中间层),不能靠"提示词让它别查敏感表"。

### 第二步扩展② 反例:能力失控的两种事故

- 事故一:自由 SQL+只读账号——只读不等于无害:全表扫拖垮库(第 36 题)、越权数据全返回(只读账号无行级权限)。
- 修复=行级权限+限额。
- 事故二:错误信息直喂——"table customers column salary not found"回喂模型,模型据此推断 schema 继续试探。
- 修复=错误信息过滤(通用错误码回喂)。

### 第二步扩展③ 取舍:预定义查询集 vs 受限自由查询

- 预定义查询集(参数化模板):最安全,覆盖固定场景(余额/流水/账单),新场景要开发。
- 受限自由查询(只读视图+方言限制):灵活,风险与治理成本高。
- 落地节奏:高频场景预定义起步,确需灵活性再开受限自由+全套闸+审计加严。

## 案例

### 第三步发散·验证与推演 验证:四道闸的推演核对

- 推演核对(教学示例):四类攻击样本(DDL 尝试/注入式全查/越权行查询/全表扫拖库)×四道闸——断言:DDL 语法层拒、非模板 SQL 拒(预定义形态)、越权行被行级过滤(返回空)、全表扫被限额截断+告警。
- 错误回喂断言(过滤后的错误码)。
- 验证:四闸断言可程序化(每闸独立测试)。
- 对照无闸形态的四类穿透复现。

### 第三步发散·追问扩展 追问链:数据闸三刀

- **Q1：聚合/统计查询呢?**
  - 答：聚合也有信息泄露(计数推断),行级权限同样作用于聚合(分母被权限过滤);限额对聚合按扫描成本计。
- **Q2：查询结果进上下文的量?**
  - 答：结果集进上下文受窗口预算(第 26 题),大结果集摘要化或分页——结果也是成本。
- **Q3：写操作呢?**
  - 答：见第 30 题(修改数据的边界),本题只管读;读写混谈是边界模糊的开始。

## 总结点

1. 只读+参数化+行级权限+限额,四闸
2. 错误信息回喂也要过滤
3. 预定义查询集起步,灵活后开
