## 参考回答

> 场景与约束：网银智能客服沙盘:接入流式(SSE)后"等待感"消失——首 token 秒出,文字逐步出现;但总时长没变、错误答案照样流出来(错了也是流畅地错)、中途取消的清理是新问题——流式改善的是"感知延迟",不改变"正确性、总时延与取消语义"。

1. 流式改善的:首 token 时延的感知(TTFB 从"等完整回答"变为"秒级出字"——用户感知响应快了数倍)、长回答的阅读并行(边生成边读,总等待=生成时间但不空等)、中断能力(用户看到跑偏可提前停止——省 token 与时间);实现=SSE/WebSocket 分块传输(network Q32 的 SSE 细节)。
2. 流式没解决的:总生成时长(token 逐个生成,总量不变——流式只是"提前看到")、正确性(错误内容照样流畅输出,Q5 防线不因流式豁免)、中途取消的语义(用户停止后:已生成部分算不算数?任务后台是否继续?——取消传播,Q46)、结构化输出的可用性(流式 JSON 不完整直到结束——程序消费要等结束或增量解析)。
3. 工程配套:流式的错误处理(生成中途出错:已流出的内容+错误事件——客户端要能处理"半截回答")、取消传播(客户端断开→服务端停止生成——Q46 的取消语义)、监控分指标(TTFB 与总时长分开,Q32)。

## 参考分析

### 第二步扩展① 机制:感知延迟与真实延迟

- 感知延迟=TTFB(首 token 时间)=排队+提示处理+首 token 生成。
- 总延迟=TTFB+全部 token 生成时间。
- 流式只优化感知(用户从 TTFB 就开始消费),总延迟由 token 数×生成速率决定——降总延迟要靠模型/缓存/更短回答,流式是体验优化不是性能优化。
- TTFB 与总时长分开监控(Q32)——混为一个指标会掩盖问题。

### 第二步扩展② 反例:流式误用的三种事故

- 事故一:流式当性能优化——"上了流式就不用优化生成速度了"(总时长没变,用户读完还是要等全)。
- 定位清楚。
- 事故二:流式的错误不处理——中途异常,客户端挂着半截回答无提示。
- 错误事件+终止语义。
- 事故三:结构化输出流式直解析——JSON 没结束就 JSON.parse,报错。
- 增量解析或等结束。

### 第二步扩展③ 取舍:流式 vs 一次性的场景

- 长回答+对话界面:流式(体验质变)。
- 程序消费(结构化输出):一次性(完整校验后用)。
- 短回答:流式收益小(复杂度>收益)——按消费方式(人读 vs 程序读)选传输形态。

## 案例

### 第三步发散·验证与推演 验证:感知与真实的推演核对

- 推演核对:TTFB 与总时长分监控与 Q32(首 token 与完整回答分别监控)直接一致。
- 取消传播与 Q46(超时后台堆积)、network Q32(SSE 自动重连)衔接。
- 正确性不受流式影响与 Q5(防线分层)一致。
- 验证:改善边界(感知 vs 真实)可执行(明示:按流式实践推演)。

### 第三步发散·发散要点 追问链:流式三刀

- **追问①**：与 Q32 的衔接——TTFB 的监控与优化(排队/预计算/缓存)是流式体验的根基
- **追问②**：与 Q42 的衔接——流式的计费按 token(流式不改变计费模型)
- **追问③**：与 network Q31 的衔接——SSE 的心跳与重连在流式链路的适用

## 总结点

1. 流式改善感知不改总时长
2. 错误照样流畅地流出来
3. 取消传播是新问题
