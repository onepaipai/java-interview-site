## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银报文沙盘:解析多种消息类型时，旧代码用 instanceof 链逐级判断并强转；团队升级到 JDK 21 后讨论改用 switch 模式匹配，需要说明空值、穷尽性与版本边界。

1. 模式匹配把"类型判断 + 强转 + 取值"合成一条表达式或语句，减少样板代码；变量只在匹配成功的作用域内可用。
2. switch 模式匹配在 JDK 21 转正（JEP 441），可配合 record 解构与 guard 条件；null 必须用 case null 显式处理，否则会抛 NullPointerException。
3. 穷尽性只在密封类型等已知类型集合下可被编译器静态保证；面对开放继承体系仍需 default 分支，不能说"switch 模式一定穷尽"。

## 参考分析

### 第二步扩展① 机制:从判断强转到绑定变量

- 传统写法先 if (obj instanceof Order o) 再使用 o，重复判断与强转。
- 模式匹配在匹配成功时直接绑定变量。
- switch 进一步把多个类型分支集中到一个表达式，record 模式还能拆出组件。
- 类比海关查验:旧写法是"看护照—确认国籍—再翻译"三步重复。
- 模式匹配是一次查验后直接给对应通道的通行证——但无护照（null）的人仍要单独处理。

### 第二步扩展② 边界:null 与穷尽性是两个问题

- switch 对 null 不自动放行:传统写法里没有分支命中时可能落到 else，而 switch 需要显式 case null（或先判空），否则运行时抛 NPE。
- 穷尽性方面，sealed 类/接口限定了许可子类，编译器可检查所有分支。
- 普通接口或父类可被任意新类实现，必须有 default 兜底。

### 第二步扩展③ 取舍:可读性与版本约束

- 模式匹配减少强转和临时变量，适合多类型分派。
- 复杂 guard 条件和过多分支仍会损可读性，必要时保留策略表或 Visitor。
- 版本上，项目基线 Java 17 不能编译 JDK 21 的 switch 模式。
- 回答要给出版本前提和 null 处理策略。

## 案例

### 第三步发散·验证与推演 验证:分支覆盖的推演

- 教学验证（JDK 21+）:构造 Order、Refund、未知类型与 null 四类输入，断言前三类进入对应分支、null 按 case null 处理。
- 再新增一个未覆盖的 sealed 子类，观察编译是否报错。
- 该验证为设计口径，本项目 Java 17 基线未运行该实验。

### 第三步发散·追问① 追问:instanceof 模式还常用吗

- 常用。
- 单个类型判断用 instanceof 模式更简单，只需要提取一个组件时也不会引入多余的分支语法。
- 多类型分派或需要一次性解构 record 的多个组件时，switch 模式更集中。
- 两者不是替代关系，按分支数量和是否需要解构选择，混合使用也很正常。

## 总结点

1. 匹配即绑定，少写强转
2. null 显式处理，穷尽靠 sealed
3. JDK 21 转正，17 不能用
