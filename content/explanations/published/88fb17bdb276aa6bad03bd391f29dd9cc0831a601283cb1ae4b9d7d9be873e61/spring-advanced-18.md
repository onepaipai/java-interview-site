## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银转账沙盘:URL 层只挡了"登录",转账接口的方法级 @PreAuthorize 校验账户归属——两层缺一:只靠 URL,横向越权(IDOR)直达;只靠方法,入口暴露面失控。说明两层各自的职责边界。

1. URL 授权管"入口面":哪些路径需要什么角色、防未认证扫描;方法授权管"业务不变式":当前用户能否操作这个具体资源(归属、状态、金额权限)。
2. 横向越权(IDOR)只能由方法级(或服务层显式校验)拦截:URL /accounts/{id} 对所有登录用户开放,归属校验必须在方法内——URL 层根本不知道 id 属于谁。
3. 配合模型:URL 层粗(角色+路径),方法层细(资源+动作);方法层校验放在服务层边界而不是 controller,保证非 HTTP 入口(消息、任务)同样受保护。

## 参考分析

### 第二步扩展① 机制:两层的过滤点与盲区

- URL 层在过滤链(第 17 题)执行:匹配路径与角色,未命中即 401/403——它不解析业务参数。
- 方法层(@PreAuthorize/@PostAuthorize 或显式判断)在方法调用时执行:SpEL 可引用参数与返回值做资源级判定。
- 盲区互补:URL 层挡不住参数级越权。
- 方法层若只在 controller 上注解,MQ/定时任务入口就绕过了——把业务校验沉到服务边界,两种入口共享同一防线。

### 第二步扩展② 推演:IDOR 的拦截路径(附真实安全上下文证据)

- 场景:GET /accounts/98765,当前用户只拥有 12345。
- URL 层:登录即可达。
- 方法层 @PreAuthorize("@acctAuth.owned(#id)") 判定归属→403。
- 本机锚点(Q19 真值示例):方法内拿到的 Authentication 就是 SecurityContextHolder 当前值(实测 alice 与 anonymous 的可见性差异):
```
alice:anonymous
```
- 校验逻辑用同一上下文:anonymous(未认证)直接拒绝。
- 验证:授权语义为规范行为,完整 IDOR 场景未在本机搭 HTTP 层,标注推演。
- 服务层单测可覆盖校验逻辑。

### 第二步扩展③ 取舍:权限判断的落点与复用

- 落点:服务层显式判断优先于注解 SpEL(可读、可测、可复用)。
- 注解适合"角色门"这类简单判定。
- 复用:归属校验封装成 AccessGuard 组件(owned(userId, resourceId)),URL 层、方法层、服务层引用同一实现——三处规则漂移是越权事故的温床。
- 测试:归属判定逐角色逐状态的单测矩阵。
- 越权用例(拿别人的 id)进回归集。

## 案例

### 第三步发散·验证与推演 验证:横向越权用例(用户 A 拿资源 B 的 id 调接口)断言

- 验证:横向越权用例(用户 A 拿资源 B 的 id 调接口)断言 403,URL 层与方法层分别移除防护各复测一次,确认两层各自有效。
- 归属校验的单测矩阵按角色×状态全覆盖。

### 第三步发散·追问扩展 追问链:授权三刀

- **Q1：@PostAuthorize 什么时候用?**
  - 答：返回值含敏感字段需按结果过滤时(读后过滤);它防泄露不防执行,重操作应在 @PreAuthorize 拦。
- **Q2：方法授权的性能?**
  - 答：每次调用都过 SpEL/守卫:归属校验通常一次索引查询,可接受;复杂权限计算走缓存(权限缓存,第 21 题,注意失效)。
- **Q3：怎么审计授权完备性?**
  - 答：枚举写接口,逐个标注"URL 层拦什么、方法层拦什么",空缺项即清单;横向越权用例自动化进 CI。

## 总结点

1. URL 管入口,方法管资源
2. IDOR 只能方法层或服务层拦
3. 校验沉服务层,两个入口共享
