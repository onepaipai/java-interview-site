> 场景与约束：Java 17 / Redis 7 教学场景：一个 500 万元素的 Hash 大键导致 DEL 卡顿 2 秒、迁移卡住、内存倾斜。说明大键的生成场景、阻塞机制与"渐进式治理"（SCAN 拆分、UNLINK 异步删除、业务侧限界）。

1. 阻塞机制：Redis 单线程执行命令，DEL/HGETALL 一个百万字段的大键要一次性处理全部数据——期间所有请求排队；主从同步、迁移（slot 迁移序列化）也被大键放大。
2. 生成场景：无界结构（把 Hash 当 HashMap 无限 put）、批量导入设计不当、序列化大对象存 String（如整个列表 JSON 化）——共同点是"没有为键的大小设上限"。
3. 治理三步：业务侧设上限（字段数/值大小写入编码规范）；发现用 `redis-cli --bigkeys`（采样）或 MEMORY USAGE 定点；删除用 UNLINK（异步回收替代同步 DEL），拆分用 HSCAN 渐进迁移而非一次性拷贝。

## 参考分析

### 第二步扩展① 机制：单线程模型让"慢命令"成为全局事件

- Redis 的快来自单线程无锁——代价是任何一个慢命令都会阻塞所有请求。
- 大键操作本质是"单次处理海量数据"，处理时间线性于元素数。
- 类比收银台只有一个：一个顾客推来整购物车的零钱要数十分钟，全队都得等——大键就是那个数零钱的顾客。

### 第二步扩展② 反例：UNLINK 与 DEL 的差别要讲机制

- DEL 同步释放内存：大键释放期间主线程阻塞（释放本身可能涉及成千上万次 free）。
- UNLINK 把释放移到后台线程异步执行，命令本身只做摘除。
- 但 UNLINK 不是万能：引用计数结构的嵌套释放仍可能部分阻塞。
- 理解"命令本身轻"与"内存回收重"的分离，才能正确选择。

### 第二步扩展③ 取舍：拆分的粒度与查询代价

- 500 万元素 Hash 拆成 100 个 5 万子键（后缀分片）：写按 key 哈希路由，读需要遍历时多次 HSCAN——原子操作（如某字段的自增）在拆分后可能跨键，需要 Lua 或重构。
- 拆分解决延迟与迁移问题，代价是跨键操作的复杂度——按"是否有跨字段原子需求"决定拆分粒度。

## 案例

### 第三步发散·验证与推演 对照操作：大键阻塞的量化复现

- 教学验证：500 万元素 Hash 上分别执行 DEL、UNLINK、HSCAN 分批迁移，用另一客户端测 ping 延迟。
- 预期：DEL 期间 ping 阻塞约 2 秒，UNLINK 毫秒级返回、后台回收，HSCAN 每批延迟可控。
- 三组延迟曲线并排可复跑。

### 第三步发散·追问① 追问：为什么大键在 Cluster 迁移时问题加倍

- slot 迁移按 key 序列化传输：大键的序列化与网络传输在同一 slot 迁移事务内完成——大键让迁移卡顿、超时重试。
- 运维侧规避：迁移前用 --bigkeys 预检目标分片、必要时先拆分再迁移。
- 大键治理是集群运维的前置条件，不是事后补救。

## 总结点

1. 单线程模型，慢命令即全局阻塞
2. UNLINK 异步回收，DEL 同步等待
3. 业务设上限，SCAN 渐进拆
