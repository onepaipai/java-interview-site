## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：手写循环测"两段代码谁快"，同一段代码两次结果差 5 倍。用 JIT 的分层编译、死代码消除与常量折叠解释手写基准的失真来源，说明 JMH 的对策。

1. 预热：前若干次执行发生在解释器/C1，C2 未介入；计时起点不同结论完全相反。基准必须先跑到编译稳定（JMH 用多轮 iteration 处理）。
2. 死代码消除：未被使用的计算结果会被 C2 整体删除——"测了个寂寞"，看似在算实际什么都不做；结果必须被消费（Blackhole.consume）。
3. 常量折叠与.profile 污染：编译期可知的输入被折叠成常量；同一 JVM 里先跑的基准污染类型 profile 影响后跑的（需要 fork 隔离）。

## 参考分析

### 机制：JIT 优化的是"它认为的语义"

C2 按语义等价自由变换：没被消费的计算等于没发生（DCE）、编译期可算的直接换成常量（折叠）、单态调用直接内联。类比评卷只看交卷的答案：演算纸（未消费结果）直接作废。手写基准的"被测代码"经常整段作废，量到的只是循环壳。

### 反例：三次测量的三种假象

一，不预热：先测 A 后测 B，A 花了大部分时间在解释执行，结论 B 快——其实是"先冷后热"；二，结果不消费：整个计算被 DCE，耗时近零；三，同 JVM 顺序跑：A 的类型 profile 让 B 的多态点内联失败。三种假象在手写基准里常态出现。

### 取舍：JMH 的四件套与适用边界

预热迭代（触发编译）、Blackhole/返回值消费（防 DCE）、fork 隔离（防 profile 污染）、随机输入（防折叠）。JMH 也只对"微基准"可信：线程交互、IO、真实负载仍要压测环境。原则：微基准做组件选型，端到端做容量结论，两者不互相替代。

## 案例

### 对照操作：手写基准的三连翻车

教学验证：同一个方法三种写法各测一次——不预热直接计时、结果存局部变量不消费、固定常量输入。预期：三次结果互相矛盾（慢、近零、快得离谱）；换成 JMH 加预热与 Blackhole 后结果稳定且解释合理。实验可复跑，一次展示三类失真。

### 追问：基准里 volatile 读为什么能防 DCE

volatile 读有可观测副作用且不能被折叠，是廉价的"消费"手段；JMH 的 Blackhole 内部也是类似思路（配合更严格的语义）。同理，基准中故意做的非确定分支（基于随机数选择结果）也是防折叠手段。理解手段背后的"可观测性"要求，比背 API 更重要。

## 总结点

1. 先热再测，消费结果
2. 同 JVM 顺序跑会互相污染
3. 微基准选型，压测定容量
