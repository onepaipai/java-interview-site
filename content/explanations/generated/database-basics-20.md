## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银日终事故沙盘:一个忘提交的报表事务挂了 3 小时——undo 表空间涨 20GB、磁盘告警、全库查询变慢;MVCC 的旧版本必须为「最早的事务快照」保留,purge 线程被它卡住。

1. 机制:每个事务的 Read View(快照)要求「创建时未提交的事务的旧版本」不可清理——purge 线程清理「不再被任何活跃 Read View 引用」的 undo 记录;长事务(即使只读)持有老快照=它创建之后的所有历史版本都不能清——写入越忙、长事务越久,undo 堆积越多(磁盘涨+遍历变慢)。
2. 影响链:①磁盘——undo 表空间持续涨(活跃期不回收);②性能——版本链越长读越慢+purge 落后拖写;③复制——历史列表长度大时延迟;监控=INNODB_TRX 时长+History list length。
3. 治理:应用侧——事务短小(外部调用移出事务)+autocommit 纪律(连接池漂移是隐性长事务来源)+只读事务标注;DBA 侧——trx 时长告警(60s)/超时 kill 工单化。

## 参考分析

### 机制:快照引用如何构成清理障碍

undo 版本链的回收判据=「没有任何活跃 Read View 还需要这个版本」——判定依赖最老的 Read View:min(活跃事务的 read view)决定可清理边界;长事务=边界冻结在其创建时刻,期间所有写入的旧版本全保留;这就是「全库 undo 涨幅≈写入速率×长事务时长」的公式——3 小时长事务+1000 TPS 写入=千万级旧版本;purge 是后台线程有吞吐上限,堆积后追赶也要时间——故障恢复不是 kill 事务就立即结束。

### 反例:长事务的三种来源

事故一:业务代码里事务包 HTTP 调用——外部慢(3 秒超时)=事务 3 秒×每秒百次调用=常数级长事务在跑;修复=事务内只做库操作,外部调用移出+补偿(第 42 题)。事故二:连接池 autocommit=false 未显式提交——连接归还后事务仍开(池化连接的隐性长事务);框架层确认提交纪律。事故三:交互式事务(人工操作中间挂起)——设计上禁止跨人工操作的事务。

### 取舍:可见性与清理的权衡

隔离级别与快照时机(第 17 题)决定「需要保留多久」;业务侧的终极方案=缩短快照需求(报表拆分小事务/预聚合表替代长查询);「读不提交」的只读长事务同样冻结边界(很多人以为只读无害)——快照引用不看读写;告警先行:trx 运行时长>60s 告警、>300s 强制 kill 工单化。

## 案例

### 验证:长事务断言组(本机可复跑)

验证:堆积断言(开一个长事务,持续写入另一会话——History list length 线性涨、undo 表空间增长);清理断言(kill 长事务后 purge 追赶,历史列表回落——有滞后);遍历变慢断言(同一行被反复更新后,长事务存在时普通 SELECT 耗时增长——链长效应);监控断言(INNODB_TRX 的 trx_started/trx_rows_locked 可查询);事务内 HTTP 断言(应用层:事务内慢调用→事务时长=调用时长)。预期:堆积-清理-监控闭环。

### 追问链:undo 三刀

一刀:undo 与 redo 的对称——undo 保回滚+快照(逻辑逆),redo 保持久(物理重放),两套日志两个生命周期(第 28 题职责);二刀:8.0 的 undo 表空间独立与自动截断(innodb_undo_log_truncate)——磁盘回收有了自动化,但活跃引用仍冻结;三刀:与 MVCC 的整体观——「无锁读」的隐蔽成本全部显形于此(第 18 题),MVCC 不是免费的并发。

## 总结点

1. 最老快照冻结清理边界
2. undo 涨幅≈写入速率×长事务时长
3. 事务里禁外部调用+autocommit 纪律
