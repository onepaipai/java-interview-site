> 场景与约束：Kafka 4.1，消费者读取扣减事件后写 MySQL，最后提交消费位点；进程可能在任意两步之间崩溃。目标是重复投递不会重复扣减，而不是仅让 Topic 中少出现重复记录。

1. 不能。幂等生产者主要约束生产者重试造成的日志重复，不会替外部 MySQL 更新、HTTP 调用或消费者业务建立原子提交边界。
2. Kafka 事务可以协调 Kafka 内部的记录写入与消费位点，配合正确的消费隔离语义；外部数据库副作用仍需自己的事务、唯一业务键或与目标系统协作的协议。
3. 对 MySQL 消费者，我把事件去重记录与业务更新放在同一事务，提交后才确认位点。允许重放，但重复业务效果被数据库约束挡住；再用故障注入验证每一个提交窗口。

## 参考分析

### 第二步扩展① 把“只一次”拆成日志、处理与业务结果三层

- 同一生产请求重试不写出重复日志，与一个事件不会被消费者执行两次是不同承诺。
- 再平衡、崩溃和位点提交失败都可能导致已处理记录被重新交付。
- 消费者函数可能运行多次，而业务账本只产生一次有效变更，两者并不矛盾。
- 如果生产方把同一个业务动作重新作为一条新的合法消息发送，传输层幂等也不自动识别业务重复。
- 因此 event_id 或业务操作键要在重试与重发时保持正确语义，而不能每次失败都重新生成一个随机 ID。
- 类比快递保送一次是物流层的承诺，文件签收后归档一次是你的业务动作——物流重派不等于你会重复归档，两本账分开记。

### 第二步扩展② MySQL 原子边界：去重标记不能先单独提交

- 数据库事务先插入唯一键 (consumer_name,event_id)，再更新业务记录，两者一起提交。
- 若唯一键冲突，校验事件身份与结果后按已处理返回。
- 若业务更新失败，整个事务回滚，使去重记录也消失。
- 数据库成功、位点提交前崩溃时，记录会重放，但唯一约束阻止第二次业务效果。
- 反过来，先提交位点再提交数据库会丢业务效果。
- 存在并行消费时，位点只能越过已经连续完成的记录，不能因为较大 offset 先完成就跳过尚未成功的较小 offset。

### 第二步扩展③ 边界外副作用、保留窗口与顺序

- 如果事务中还调用第三方扣款接口，数据库回滚无法撤回已经发生的远端扣款。
- 需要第三方接受稳定幂等键与结果查询，或者把调用意图持久化为状态机，由可恢复执行器推进。
- 无法协作的目标不能轻易承诺端到端只一次。
- 去重记录保留时间要覆盖可发生的历史重放和人工补发窗口。
- 删除去重记录后再回放旧消息，会重新产生效果。
- 按账户顺序处理时还要维持键到分区的路由以及消费者执行顺序。
- 幂等不能替代顺序约束。

## 案例

### 第三步发散·验证与推演 故障矩阵：在两个提交之间杀进程

- 用固定 event_id 投递一次库存扣减，分别在数据库提交前、提交后但位点确认前、位点确认响应丢失时终止消费者，再启动并重复投递。
- 预期数据库只有一次有效扣减，去重记录与业务效果总是同时存在或同时不存在。
- 把去重插入故意移到独立事务作为反例：先落去重再崩溃会导致业务永远不执行。
- 把位点先提交作为另一个反例：重启后消息不再交付而数据库没有变更。
- 验证应统计业务变更与位点，不以消费者日志里的“收到一次”作为证据。

### 第三步发散·追问① 面试追问：能否用 Redis SETNX 去重？

- 如果 Redis 标记与 MySQL 更新分别提交，就重新产生双写窗口：标记成功而数据库失败会漏处理，数据库成功而标记丢失会重复处理。
- 锁或去重缓存可以减轻并发争用，但最终正确性仍需落到可证明的持久原子边界。
- 再测试同一业务动作使用两个不同 event_id、批量处理中间一条失败、旧消息超出保留窗口后人工回放。
- 预期系统按明确的业务幂等键与重放策略处理，而不是只通过“同一个 Kafka offset 重试”这一种情况。

## 总结点

1. 物流保一次，归档靠对账
2. 传输去重不等于业务只一次
3. 业务更新与去重同事务
4. 提交顺序必须经得住崩溃重放
