# 题目回答审查与排版标准

本轮以用户要求为准：结论干练、分析分点、案例具体、总结好记。与现有 [写作方案](README.md) 和 [通用骨架](TEMPLATE.md) 配合使用，本文件补充审查与排版的验收要求。

## 固定结构

每题按以下四个二级标题排列，最后一节必须是“总结点”：

1. **参考回答**：直接回答题目，每点一个知识点，先给结论，再补必要前提。
2. **参考分析**：逐点说明为什么、如何发生、关键边界；至少一处给出生活化类比或熟悉场景对照，随后立即回到机制；不要换句话重复上一节。
3. **案例**：代码或实战场景任选适合该题的一种，必须有操作过程和结果。
4. **总结点**：提炼便于回忆的短句，其中一条可以是口诀（押韵或对仗）后接机制短语；不增加新知识，也不使用缺少前提的绝对结论。

使用 Markdown 有序列表，一点一行。不要把 `1、……2、……3、……` 连成一个段落。内容通常各列 2–5 点即可，数量服从题目，不能为凑点数拆句。

## 内容验收

| 部分 | 通过要求 | 退回情形 |
| --- | --- | --- |
| 参考回答 | 开头即结论；每点通常 1–2 句；说清必要前提 | 绕背景、堆概念、同义复述、遗漏题干中的子问题 |
| 参考分析 | 机制、原因、边界对应明确；每点只解释一个问题；含至少一个类比或对照，且类比后回到机制 | 只列术语；把回答扩成长篇介绍；用“视情况而定”代替条件；拿类比当结论 |
| 案例 | 能看出输入/场景、关键步骤、结果；代码或 SQL 标明适用环境 | 无关示例、伪造生产经历、只有代码无结果、结论与代码不一致 |
| 总结点 | 通常 2–4 点；含一条口诀接机制短语；能唤起前面的关键结论 | 再写一遍全文、口号化、引入新概念、为押韵牺牲正确性 |

字数用于提醒压缩，不作为凑字数目标。必要条件不能为了短而删掉。比如“自调用不触发内部方法的事务配置”不能写成“自调用一定没有事务”。

## 通俗好记要求

深度不等于难懂。每题在满足四段结构的同时，还要做到：

1. **一个类比**：参考分析里至少有一处生活化类比或熟悉场景对照（如把 volatile 发布不可变快照比作“公告栏一次换一整页”）。类比只负责建立直觉，紧跟一句回到机制，不拿类比当结论。
2. **一条口诀**：总结点里保留一条短口诀（对仗或押韵，如“可见不原子，快照整体换”），同一处用逗号或破折号接机制短语，保证回忆时既有钩子又有事实。
3. **反直觉单独成点**：本题最容易被答错的一点（如“volatile 不保证原子性”）必须在回答或分析里单独成点，不埋进长句。
4. **术语先展开**：首次出现的机制名词先用一句大白话说明，再使用术语；不堆缩写。

口诀与类比服从准确性：为押韵牺牲前提、把类比绝对化都按退回处理。深入格式总结点每点上限 60 字，标准格式仍为 22 字。

技术事实按目标版本核对官方文档或原始资料。区分规范、实现细节和教学假设；没有实际执行的代码不得写“已验证通过”。引用放在对应分析点末尾，或案例之后、总结点之前，用一行简短资料链接即可。

## 案例写法

代码优先保留能解释结论的最小片段，注明语言及必要版本。代码较长时按“准备、执行、结果”拆成对应步骤，每段代码紧跟所属步骤，不把所有代码统一堆到最后。

场景案例按“场景 → 操作/定位 → 结果”列 3 点；故障题须给定位证据。教学案例标明“教学场景”，不得编造事故经历或提升比例。

多线程、事务、分布式等题目必须保留决定结果的并发顺序、提交边界或失败路径。复杂问题可以增加必要细节，仍然一条只讲一件事。

## 图表与阅读排版

1. 图用于解释流程、时序、状态转换或结构关系；简单定义、两三步直线关系用文字即可。
2. 一张图只表达一个主题，放在对应分析点或案例步骤后；前有一句说明，后有一句结论。
3. 节点用短语，边注明必要条件；复杂分支拆成主流程和失败流程，分别放到对应文字处。
4. 多张图纵向排列并留白，不并排挤压，不连续堆放；先删掉信息重复的图。
5. 电脑和 390px、320px 手机宽度都要看清。文字不可辨认时调整布局或拆图，不能只缩小整图。
6. 代码使用标明语言的围栏；表格只用于比较，最多保留少量关键列。长代码、宽表格在各自区域滚动，不能撑宽整页。
7. 四段标题统一为二级，案例内步骤使用有序列表；最多增加一层子项。加粗只标关键词，不把整段全部加粗。
8. “总结点”单独成段，与上文留白；不使用大量图标、彩色块或装饰分隔线。
9. 页面实际能渲染图表才算交付图表。当前渲染器会把 Mermaid 围栏当代码显示，不能把源码截图当作流程图验收通过。已导出的清晰图片可使用现有 Markdown 图片展示。

## 可直接交给生成 AI 的要求

> 每道题只用“参考回答、参考分析、案例、总结点”四个二级标题，按此顺序输出。“参考回答”和“参考分析”都用编号分点，一点一个知识点，结论先行，保留关键条件，删除铺垫和重复；参考分析里至少给一个生活化类比建立直觉，随后立即回到机制，并把最容易被答错的点单独列出来。“案例”按题型选择最小代码或具体实战场景，交代关键步骤及预期结果；教学场景要标明。最后“总结点”用几条短句帮助记忆，其中一条是口诀加机制短语，不重复全文、不添加新知识。需要流程或结构图时才画，一图一主题，图跟着对应文字放，避免连续堆图和手机上缩成一团。代码标明语言，技术细节按版本核对官方资料。术语第一次出现先用大白话解释。不得写占位句、泛泛而谈或虚构验证结果。

## 审查记录格式

每题记录：题目标识、结论（通过/待修改/待验证）、具体问题、修改建议、技术核对及桌面/手机排版情况。

- **通过**：四段完整、事实与案例核对完成、页面检查通过。
- **待修改**：指出具体句子或段落及改法，不能只写“太长”“优化一下”。
- **待验证**：结构可以通过，但代码、版本或图表显示尚无验证证据。

自动扫描只能检查结构与部分排版风险，不能替代事实核对和逐题审查。另一 AI 仍在生成时，以读取快照记录结果，保留题目标识与版本；不直接覆盖其正在修改的回答。
