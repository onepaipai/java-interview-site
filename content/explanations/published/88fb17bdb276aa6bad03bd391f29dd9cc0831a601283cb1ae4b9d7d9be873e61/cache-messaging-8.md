## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 7 教学场景：用户对象 40 个字段整存 String，每次改昵称要重写整个对象；拆 Hash 字段后读取要 HGETALL 多次往返。对比整存与拆存的读写模式、序列化成本与更新粒度，给出按访问模式选择的框架。

1. 整存 String（JSON 序列化）：读一次 GET 拿全量、写一次 SET 整体覆盖——适合"读写都以对象为单位、字段同时变化"的场景；代价是局部更新放大（改 1 字段重写全量）与无法部分读取。
2. 拆存 Hash：HSET 按字段更新、HMGET 按需读取——适合"字段独立变化、读写只涉及部分字段"；代价是整对象读取需要 HGETALL（大对象多次往返）、序列化按字段处理、TTL 与事务按键整体。
3. 决策三问：读写是"整对象"还是"字段级"？字段数与单字段大小？是否存在跨字段原子更新需求（Hash 天然支持同键多字段原子 Lua，String 需要整体 CAS）？

## 参考分析

### 第二步扩展① 机制：序列化边界决定更新放大系数

- 整存的更新放大 = 对象大小 / 变更字段大小：40 字段改 1 个，放大 40 倍的序列化与网络。
- 拆存的读取成本 = 需要的字段数 × 往返（或一次 HGETALL）。
- 类比存书：整本借还（整存）vs 按章节取阅（拆存）——按"每次实际用多少"选装订方式。

### 第二步扩展② 反例：整存大对象的部分更新风暴

- 用户资料 40 字段每次改昵称重写 8KB JSON：写放大 40 倍、序列化 CPU 浪费、且并发更新两个不同字段会互相覆盖（最后写赢）——整存模式下的字段级并发冲突被放大成对象级丢失。
- 改 Hash 后 HSET 昵称独立生效，并发冲突收敛到字段级。

### 第二步扩展③ 取舍：混合模式与迁移成本

- 热字段（高频更新）拆 Hash、冷字段（几乎不变的大块如头像 URL）整存 String 引用——混合按字段访问模式分治。
- 迁移成本：两种模式的客户端 API 不同，混用增加心智负担。
- 判据一句话：字段级并发更新是否存在——存在则必须拆（或整体 CAS），不存在整存更简单。

## 案例

### 第三步发散·验证与推演 对照操作：更新放大与并发覆盖的对照

- 教学验证：40 字段对象两线程并发改不同字段各 1 万次，分别用整存 String 与 Hash 字段。
- 预期：整存版最终只有一方的修改存活（互相覆盖）。
- Hash 版两个修改都保留。
- 再用带宽统计对比单字段更新的网络量。
- 实验可复跑。

### 第三步发散·追问① 追问：Hash 的 HGETALL 在大对象上会不会变成新的"大键"

- 会。
- 字段数几百的 Hash 本身就是大键候选（HGETALL 阻塞、DEL 缓慢）。
- 拆存不是无界拆：Hash 字段数设上限（如 ≤100），超限说明对象本身该拆表或该用整存+版本化更新。
- 键大小纪律（第 7 题）与拆存决策联动。

## 总结点

1. 整存整取，拆存拆取
2. 局部更新放大系数决定形态
3. 字段级并发更新存在，必须拆
