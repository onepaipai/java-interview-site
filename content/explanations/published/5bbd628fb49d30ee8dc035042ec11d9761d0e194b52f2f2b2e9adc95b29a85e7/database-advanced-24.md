## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB，两个会话，默认非锁定 SELECT。业务先读取余额再更新同一账户，误以为 REPEATABLE READ 会让事务中所有操作永远看到同一份状态。

1. 我先区分一致性非锁定读、锁定读和本事务自己的修改。RR 下普通 SELECT 通常复用首次一致性读建立的快照，但 SELECT FOR UPDATE 和 UPDATE 不是按同一旧快照完成并发控制。
2. 事务能看到自己的写入，因此结果集可能混合自己的新版本和其他行的旧快照版本。这不意味着隔离级别失效，而是把不同读写语义混在一起理解了。
3. 涉及余额或库存不变式，我使用条件更新、唯一约束或必要的锁定读来保护写入，并用双会话按确定顺序复现；不能用“先查存在再修改”替代数据库原子约束。

## 参考分析

### 先把快照的创建时点说清楚

RR 的普通一致性读一般在首次这类读取时建立事务快照，并不是执行 BEGIN 就必然固定所有后续读取；WITH CONSISTENT SNAPSHOT 另有显式语义。RC 的普通一致性读则会为每次读取建立新快照。只报隔离级别名称，不能解释某次读取为什么看到某个值。

MVCC 通过行版本与可见性规则支持历史读取。快照保护的是这一类读取的可见范围，不是给整个事务复制一份可任意写回的数据库。对并发决策来说，读到的历史值与最终允许修改的当前记录是两个问题。类比入场时领到的纸质目录：整个场次你翻的都是同一版，而当前读是直接去货架看最新标价——两份信息并存，各答各的问题。

### 为什么更新后又能读到一个新值

A 的首次普通 SELECT 看到余额 100；B 把余额更新为 200 并提交。A 再普通读取仍看到 100。A 接着执行 UPDATE account SET balance=balance+10 WHERE id=1，这次更新针对可修改的当前记录，若没有其他冲突，余额变为 210；A 随后普通读取能看到自己的 210。

如果 A 一开始在应用内计算 100+10，再 SET balance=110，就可能覆盖已经发生的业务变化。版本列条件更新能发现冲突，数据库内增量表达式适合原子累加；选择哪种方法取决于业务动作，而非一律使用乐观锁。

### 保护不变式：锁、约束与失败重试各有位置

单行库存可用带 stock>=数量 条件的 UPDATE，并检查影响行数。多行转账需要一个事务和稳定锁顺序。跨行“至少有一人值班”这类约束可能发生写偏斜，需要把决策收敛到可锁住的共同记录、采用合适隔离策略，或重新设计约束。

锁定读也有代价：锁范围与实际访问索引、查询条件、隔离级别相关。不能承诺“加 FOR UPDATE 就不死锁”。对死锁或锁超时要区分是否适合重试整个事务，重试有次数与退避，而且外部副作用需要幂等。

## 案例

### 双会话实验：100、100、210 分别来自哪里

先在独立初始化事务里写入 id=1、balance=100。会话 A 设置 RR 并 BEGIN，普通 SELECT 得到 100；会话 B 更新为 200 并 COMMIT；A 普通 SELECT 仍得 100，然后执行增量 UPDATE，再读取预期得到 210，最后提交。

验证记录每一步的 SQL、事务开始与提交时点，特别注明第一次读取必须是普通一致性读。将 A 第二次读取改成 FOR UPDATE 后会看到当前可锁定版本，这一对照能解释差异。H2 的兼容模式不能充当这个 InnoDB 实验已经通过的证据。

### 面试追问：可重复读是否就解决了超卖？

没有。两个请求都从快照看到 stock=1，随后各自按旧值创建订单，单靠读取稳定并不保证只接受一单。设计应让扣减与订单、请求去重在本地事务中协调，利用条件更新或锁定库存记录守住不变式。

预期验收不是“两个查询结果相同”，而是并发提交后有效订单数不超过初始库存、库存不为负、相同业务请求只扣一次。再加入事务回滚和客户端超时重试，检查库存与订单能否一起恢复。

## 总结点

1. 快照读走旧版本，当前读见最新
2. 普通快照读不等于所有读写
3. 本事务可见自己的修改
4. 用约束与原子更新保护不变式
