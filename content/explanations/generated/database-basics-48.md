## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银列表接口沙盘:前端传 sortBy=amount&order=desc——ORDER BY 无法参数化(#{} 不能用于标识符),${} 拼接=注入面;解法=白名单映射,把「任意字符串」折叠成「枚举到列名」。

1. 注入面的成因:ORDER BY/DIRECTION/表名/列名是「标识符」,预编译占位符(#{})只对「值」有效——标识符必须文本替换(${})→用户输入直达 SQL 结构;攻击面=sortBy=(CASE WHEN ... THEN sleep(5) END)(盲注)/多语句/报错注入——legacy/2 与第 41 题的 ${} 风险在标识符场景的专答。
2. 白名单映射(标准解):前端传「语义 key」(amount/desc),后端维护 Map{key→物理列名}+方向枚举(ASC/DESC)——SQL 里出现的是白名单内的固定字符串,用户输入永不进 SQL;非法 key 直接 400;映射表=服务端拥有的「语义→标识符」字典,注入面被折叠为零。
3. 配套防线:①默认排序(未传/非法用默认,避免报错信息泄露)②列名对外脱敏(物理列名不暴露,前端只见语义 key——顺带解决重构改名风险)③ORDER BY 里的表达式禁用(只允许映射出的纯列名)④审计(异常 key 的请求记录告警——探测行为可见)。

## 参考分析

### 第二步扩展① 机制:为什么白名单能根治而转义不能

- 标识符注入的防御困境:值注入可预编译(数据与结构分离),标识符本身就是结构——没有「参数化」可用。
- 黑名单(过滤关键字)注定漏(编码变体/嵌套表达式)。
- 白名单换思路:不校验输入是否「安全」,而是「不使用输入」——输入只是选择器,SQL 里的全部标识符来自服务端字典。
- 「校验输入」与「不信任输入」的差别=白名单的根治性(第 25 题 owasp 上传同思想:类型白名单而非黑名单)。

### 第二步扩展② 反例:动态排序的两种事故

- 事故一:黑名单过滤(SELECT/UNION/sleep)——(CASE WHEN...)/编码变体绕过。
- 白名单替换。
- 事故二:映射表遗漏新列——前端新排序项 500(默认排序兜底+映射表随列演进)。
- 事故三:方向参数拼接(ASC/DESC 之外的任意串)——方向也要枚举(仅 ASC/DESC 两个值)。

### 第二步扩展③ 取舍:白名单映射/枚举传输/查询对象

- 语义 key+映射(通用,前后端解耦)。
- 直接传物理列名+白名单校验(耦合列名,重构脆)。
- 查询对象(前端传结构化查询 DSL,服务端构造——复杂筛选场景)。
- 多层排序(多列)的映射表按「列表集合」设计。
- 映射逻辑集中一处(工具类)+评审强制(新接口的排序参数必须过白名单)。

## 案例

### 第三步发散·验证与推演 验证:注入断言组(本机可复跑)

- 验证:注入穿帮断言(${sort} 传 (CASE WHEN 1=1 THEN sleep(3) END)——延迟响应复现。
- 白名单版同输入→400)。
- 白名单断言(合法 key 正常排序(结果序对照)。
- 非法 key 400+默认排序兜底)。
- 方向断言(order 传任意串→仅 ASC/DESC 生效)。
- 重构断言(物理列改名→前端无感(语义 key 不变))。
- 审计断言(非法 key 请求被记录)。
- 预期:注入面被白名单折叠为零可证。

### 第三步发散·发散要点 追问链:注入三刀

- **追问①**：值注入与标识符注入的分界——#{}/${} 的本质(第 41 题):值可参数化,结构必须白名单;
- **追问②**：MyBatis 的动态 SQL 与 bind——<bind> 与 OGNL 的注入面(表达式层),动态 SQL 的复杂逻辑上移 Java(规约 23 条);
- **追问③**：输出侧的同类问题——动态 ORDER BY 在导出/报表的复制(每个出口都要过白名单),注入面清单化审计(第 151 题质量闸)

## 总结点

1. 标识符无参数化,白名单映射根治
2. 语义 key 解耦物理列名
3. 方向也枚举,非法默认
