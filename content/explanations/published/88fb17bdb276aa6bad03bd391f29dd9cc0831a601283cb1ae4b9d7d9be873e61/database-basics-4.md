## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银账户查询沙盘:SELECT id,name WHERE name=? ——name 有二级索引:非覆盖=二级树找到主键再回主键树取整行(两次树查找×每行);覆盖=单树完成(Extra: Using index)。

1. 覆盖索引定义:查询所需的全部列(含 WHERE/ORDER BY/SELECT)都在同一索引中——存储引擎不回表,整棵查询在一棵 B+ 树内完成;EXPLAIN 标志=Extra: Using index;本质=用「索引更宽」换「回表消失」。
2. 回表的代价结构:每行=二级树查找(得主键)+主键树查找(取整行)——两次树遍历×行数;主键树查找按主键随机分布(非自增时更是随机 IO,第 1 题);覆盖后=单树顺序/定位扫描,批量查询差距放大(百万行查询秒级 vs 毫秒级);排序也能被覆盖消除(ORDER BY 列在索引→免 filesort)。
3. 设计方法:把高频查询的 SELECT 列表并入联合索引尾(等值列在前)——索引宽度权衡:每加一列所有写入都要维护它(写放大),只覆盖 80% 流量的 Top 查询;SELECT * 与覆盖索引天然对立(要覆盖就得按需选列)。

## 参考分析

### 第二步扩展① 机制:回表的两级查找结构

- 二级索引叶子=(索引列值,主键)——完整行只在主键树。
- 「回表」=按主键再走一次主键树。
- 覆盖查询的全部数据在一棵树上=一级完成。
- 代价差=(1+1)×log n vs 1×log n 每行,且回表的主键顺序随机(缓存不友好),覆盖扫描是顺序的——「两次随机 vs 一次顺序」在大结果集上是数量级差距。
- 这也是为什么「索引列顺序=等值在前覆盖在后」的联合索引设计模式有效。

### 第二步扩展② 反例:覆盖索引的三种事故

- 事故一:SELECT * 期待覆盖——* 永远覆盖不了(行都回了)。
- 按需选列才可能覆盖。
- 事故二:为覆盖把大字段(TEXT/JSON)塞索引——索引页膨胀,单页行数骤减,树变高,定位变慢(第 37 题VARCHAR/TEXT 取舍)。
- 覆盖列要小。
- 事故三:覆盖索引建太多——写放大指数级(第 34 题),覆盖是给 Top 查询的,不是给所有查询的。

### 第二步扩展③ 取舍:覆盖 vs 索引宽度 vs 写放大

- 覆盖收益与查询频率成正比、与索引列宽度成反比——Top5 查询各建覆盖索引是常见落点。
- 评估闭环=优化前基线 explain+耗时 → 建索引 → 对照(第 50 题专答「优化不伤写入」——写入侧回归必须做)。
- 大结果集分页+覆盖组合(延迟关联,第 14 题)是深分页的标准解。

## 案例

### 第三步发散·验证与推演 验证:覆盖断言组(本机可复跑)

- 验证:EXPLAIN 断言(覆盖=Using index,非覆盖无此标志——同查询改 SELECT 列表对照)。
- 耗时对照(百万行 SELECT id,name vs SELECT *:覆盖与非覆盖毫秒级 vs 秒级)。
- filesort 消除断言(ORDER BY 列进索引后 Extra 消失)。
- 写放大对照(覆盖索引增删后 insert 吞吐变化——第 50 题回归同源)。
- 预期:Using index 与耗时差同时成立。

### 第三步发散·发散要点 追问链:覆盖三刀

- **追问①**：延迟关联——深分页先覆盖索引取主键再回表 join(第 14 题),覆盖的中间形态;
- **追问②**：前缀索引与覆盖互斥——前缀索引(截断)无法覆盖完整值(第 45 题失效场景),取舍要明;
- **追问③**：MySQL 8.0 降序索引——ORDER BY 混合方向(第 8 题database-advanced)让覆盖+排序同时成立,老版本只能 filesort

## 总结点

1. 覆盖=一棵树完成,Using index
2. 回表=两次树查找+随机 IO
3. 覆盖给 Top 查询,宽度换回表
