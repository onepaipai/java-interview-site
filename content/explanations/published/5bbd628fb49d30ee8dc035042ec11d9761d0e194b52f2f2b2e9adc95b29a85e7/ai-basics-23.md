> 场景与约束：网银集成沙盘:Function Calling 返回 JSON,直接反序列化——某次输出字段名变了(模型"发挥"),反序列化异常,接口全挂;结构化输出的"结构"是概率性的(JSON 可能截断/字段漂移/类型错)——后端校验(schema 校验+类型检查+枚举约束)是集成的可靠性闸门,模型承诺不算数。

1. 失效形态:JSON 截断(半对象)、字段漂移(改字段名)、类型错误(金额成字符串)——即使 JSON mode,语义层字段值仍可能错(Q5);后端校验三层=schema 强约束+语义(值域/枚举/必填)+业务(跨字段一致)。
2. 校验失败的处理:重试(带错误反馈的再生成:"你的输出缺少 X 字段"——引导式修复,一次重试成功率 80%+)、降级(校验连续失败→走兜底路径:默认值/人工/旧逻辑)、告警(校验失败率是模型/提示漂移的信号——突然升高=上游变了,Q48)。
3. 与 Function Calling 的配合:工具调用的参数 schema 由平台校验后才执行(参数错误不进执行层,Q24);校验器随 schema 版本走(schema 变更=校验器变更,同步发布);校验错误的结构化反馈进评测(哪类字段常错→提示/示例修正,Q7)。

## 参考分析

### 机制:引导式重试的效率

重试不是"原样再来"——把校验错误结构化反馈给模型("输出缺少 amount 字段,类型应为 number")→模型针对性修复;实测经验:一轮引导修复解决 80%+ 的格式错误,两轮后仍失败=系统性问题(提示缺陷/模型能力不足)→降级路径;重试的 token 成本(错误输出+反馈+再生成)与降级的业务成本权衡。

### 反例:免校验的三种事故

事故一:直接反序列化——字段漂移抛异常,接口 500;schema 校验。事故二:格式校验无语义——JSON 合法但金额单位错(分当元),资金事故;语义校验层。事故三:重试无上限——校验失败无限重试,死循环烧 token;重试上限+降级。

### 取舍:校验严格度 vs 可用性

严格(全字段强校验,失败即拦):可靠性最高,误拦(模型输出其实可用但缺可选字段)损失体验;宽松(只校关键):可用性高,脏数据漏;分层:必填与类型强校验,可选字段宽容+默认值——校验的松紧按字段的风险分级。

## 案例

### 验证:校验分层的推演核对

推演核对:三层校验与 Q5(幻觉防线的校验层)同构;引导式重试与 Q33(超时重试的风险)互补(重试要有反馈与上限);降级路径与 Q13(一键降级预案化)衔接;校验失败率告警与 Q48(监控自身失效)的思路同源;schema 版本与 Q48(提示版本)联动;验证:三层+处理路径可执行(明示:按集成实践推演)。

### 追问链:校验三刀

一刀:与 Q24 的衔接——Function Calling 的参数校验在平台层,工具实现再校验一次(纵深)。二刀:与 Q45 的衔接——SQL 生成的校验=语法解析+表列存在性+权限白名单,是结构化校验的重度形态。三刀:与 Q7 的衔接——示例与契约一致是校验通过率的第一因(示例教错=校验天天挂)。

## 总结点

1. 结构是概率的校验是闸门
2. 引导式重试一次八成
3. 校验失败率是漂移信号
