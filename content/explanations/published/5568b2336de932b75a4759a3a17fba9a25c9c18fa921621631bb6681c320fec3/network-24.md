> 场景与约束：网银故障定位沙盘:调用下游报读超时,但连接每次都成功——是下游慢、网络丢包、还是中间设备挂起?三种原因三种处置,读超时本身不告诉你是哪种,要按证据分层定位。

1. 读超时的三种成因:下游应用慢(收到请求处理慢)、传输丢包(数据在路上重传)、中间设备静默(连接表项丢失后不回也不清)——客户端视角都是"soTimeout 到点",必须靠分段计时区分。
2. 分段计时法:记录 connect 耗时(建连质量)、请求首字节时间 TTFB(下游处理+回程)、完整耗时——TTFB 大=下游慢;connect 正常但 TTFB 随机超时=丢包/重传;固定卡在特定时长(如 NAT 老化点)=中间设备。本机实验:连接 2019ms/读取 1505ms/拒绝 17ms 三段形态即分段计时的基线。
3. 定位工具链:抓包(TCP 重传/零窗口标志)、下游日志(收到请求的时间)、连接池统计(借出时长)、按请求 ID 串联上下游日志(耗时对不上=传输段问题)。

## 参考分析

### 第二步扩展① 机制:读超时发生的位置

- 读超时=内核接收缓冲在 soTimeout 内没有可读数据——可能是请求没到(丢包重传中)、响应没回(下游慢/挂)、连接被中间设备冻结(表项丢失)。
- 三者的区分证据在"两端日志的时间差":两端都记录收到/发出时间,差值即网络段贡献。

### 第二步扩展② 反例:定位错向的两种事故

- 事故一:读超时一律加重试——下游慢查询场景重试=放大负载(见 Q22),越重试越慢。
- 先看下游是否收到请求再决定。
- 事故二:把 NAT 老化判为下游故障——凌晨低峰期固定超时,加"keepalive 保活"才修复,浪费一轮下游排查。
- 固定时长+低峰集中是中间设备特征。

### 第二步扩展③ 取舍:分段计时的埋点成本

- 全链路分段(连接/发送/等待首字节/接收):日志量与复杂度上升,定位能力最强。
- 粗粒度(TTFB+总耗时):覆盖 80% 场景。
- 按接口分级——核心资金链路全埋点,长尾接口粗粒度。
- 与 traceId 串联(distributed D14)组合,单条请求的耗时地图自动生成。

## 案例

### 第三步发散·验证与推演 验证:三段形态的实测证据

- 本机实测(JDK 17.0.17,与 Q23 同源):
~~~
java N3Timeouts
连接阶段失败:SocketTimeoutException,耗时 2019ms
读取阶段失败:SocketTimeoutException,耗时 1505ms(连接已建立,对端收下不回)
端口拒绝:ConnectException,耗时 17ms
~~~
- 验证:读取阶段失败时连接早已成功(实验里服务端 accept 后 read 到字节)——读超时与连接健康无关的直证。
- 三段计时基线(2019/1505/17ms)为分段定位提供参照形态。

### 第三步发散·发散要点 追问链:读超时三刀

- **追问①**：soTimeout 与整体 deadline 的关系——soTimeout 是单次 read 的等待上限,整体 deadline 是请求生命周期封顶;多段 read/多段调用的场景两者都要配(见 Q23)
- **追问②**：零窗口与慢的区分——TCP 零窗口(接收方缓冲满)也会表现为"无数据可读",抓包看 Window 字段即区分
- **追问③**：与 Q7 的联动——对端崩溃可能表现为 RST(快失败)或静默(超时),keepalive 与应用心跳把"静默"提前变成"可探测"(见 Q8)

## 总结点

1. 读超时三成因靠分段计时
2. 两端日志时间差即网络段
3. 先看下游收没收到再重试
