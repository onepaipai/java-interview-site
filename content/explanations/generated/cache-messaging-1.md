## 参考回答

<!-- explanation:deep -->

> 场景与约束：商品详情采用 MySQL 为事实源、Redis 为可丢弃缓存，允许短暂展示旧值，但价格结算必须读取权威状态。并发读写、删除失败与进程崩溃都在讨论范围内。

1. 先删缓存再提交数据库，会给并发读留下把旧数据库值回填到空缓存的窗口。先提交数据库再失效缓存，能让多数后续回源读到新值，因此是常见顺序。
2. 这个顺序仍不等于强一致：提交后删除可能失败，早先开始的慢读也可能在删除后回填旧值。TTL、可靠失效重试和版本协议分别解决不同窗口，延迟双删不能给出完整证明。
3. 我先按业务定义最大可接受陈旧时间。展示数据可用最终收敛方案；库存扣减、资金判断等关键写入回到权威事务，不用缓存命中率替代正确性指标。

## 参考分析

### 用并发时序解释选择，而不是背顺序

错误窗口一：W 删除缓存，R 回源读到尚未提交的旧值 v1 并回填，W 再提交 v2。此后缓存持续提供 v1，直到再次失效。改成提交后删除，普通后到读回源会拿到 v2。

仍有窗口二：R 在 W 提交前已经读到 v1，但回填迟到；W 提交 v2 并成功删除后，R 才 SET v1。即使每次写都执行了“先更新再删”，缓存也可能倒退。这个反例决定了该方案的承诺应是可解释的最终收敛，而非没有陈旧读。类比公告栏：先改底账再撕旧告示，最坏只是少一张告示；若先撕旧告示，路人可能按还没改的底账把旧告示原样贴回。

### 删除失败与旧值回填，需要分别治理

数据库提交后进程崩溃，内存中的删除动作和重试意图都会消失。可在同一数据库事务记录 outbox 失效事件，提交后异步投递，或使用可靠 CDC 传播变化；消费者允许重复删除，监控最老未处理事件年龄。TTL 提供兜底，但窗口由其实际生效、重填和故障行为共同决定。

版本回填只有在所有写入者遵守同一原子比较协议、版本单调且必要的版本屏障不会随删 key 一起丢失时，才能拒绝旧读。仅把 version 字段放进 JSON，或者先 GET 再 SET，都不足以证明不会覆盖新状态。

### 方案取舍：新鲜度、可用性和回源容量

写后读如果必须看到自己的结果，可以在限定窗口绕过缓存，或携带期望版本并在达不到时回源；同时规定主从复制延迟下应读哪个节点。全局强一致读取要求更强的协调，成本不能藏在一句“加分布式锁”里。

当 Redis 故障或批量失效，直接全部回源可能压垮数据库。应给回源独立并发上限、同键请求合并和过载响应。是否允许返回旧值按字段和场景区分：商品描述可以降级，结算价格应按权威规则重新确认。

## 案例

### 可重复实验：制造“删除成功却又变旧”

给回源读增加可控屏障：R 读取 v1 后暂停；W 提交 v2 并删除缓存；放行 R，让它回填 v1。验证下一次普通缓存读取确实返回 v1，这能否定“只要顺序正确就绝无陈旧值”的说法。

再引入版本屏障或明确的短 TTL 与可靠失效补偿，检查旧回填被拒绝或在约定窗口内收敛。分别模拟数据库提交后杀进程、Redis 删除失败、事件重复和乱序；记录错误版本返回次数、收敛耗时、回源并发与失效积压，不能只检查一次 DEL 返回成功。

### 面试追问：延迟双删的延迟取多少？

固定延迟无法覆盖所有慢查询、调度暂停与网络尾延迟，第二次删除自身也会失败。可以根据测得的请求分布把它作为降低概率的辅助措施，但不能把某个毫秒数当成一致性定理。

更完整的回答应明确：哪些字段允许陈旧、最长窗口如何衡量、关键请求如何绕过、删除意图怎样持久化、故障超过窗口后怎样告警或降级。验收同时验证正确性与数据库容量，避免缓存方案在故障恢复时形成新的回源洪峰。

## 总结点

1. 先改底账再撕告示，回填单独治
2. 顺序选择要能画出并发反例
3. 可靠失效仍需处理迟到回填
4. 关键决策依赖权威状态
