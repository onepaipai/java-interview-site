## 参考回答

<!-- explanation:deep -->

> 场景与约束：数据库变更通过 CDC 日志投递到搜索索引和下游服务。消费者可能在写入目标后、提交位点前崩溃，也可能重连回放或遇到乱序；目标是最终可重建而不是假设消息只来一次。

1. CDC 消费通常至少一次：目标写入成功但位点提交失败时，重启会再次投递；因此事件要有稳定 ID、业务版本或唯一约束来幂等处理。
2. 断点必须持久化并与目标进度建立可恢复关系。位点先提交可能丢数据，目标先提交可能重复，外部目标需要自己的去重或可重建协议。
3. 乱序、删除、快照与增量切换都要有版本语义；不能只按到达时间覆盖新状态，恢复后还要能校验积压和重建结果。

## 参考分析

### 第二步扩展① 提交顺序决定丢失还是重复

- 消费者读取事件 e，先写搜索索引，再保存位点，进程若在两步之间崩溃，重启会再次处理 e。
- 这要求目标写入幂等。
- 若先保存位点再写目标，崩溃后 e 可能不再投递，形成永久缺口。
- 把目标写入与位点放进同一个事务只在目标存储支持该原子边界时成立。
- Kafka/日志系统的事务不能自动覆盖任意数据库或搜索引擎写入，通常需要目标侧唯一键、版本条件、可重放索引或协调服务。
- 类比记账本与收据的先后：先记了账丢了收据是重复入账，先拿收据丢了账本是漏记——取决于哪一步先落笔。

### 第二步扩展② 事件身份与业务版本不能混为一谈

- event_id 用于识别同一事件的重复投递。
- aggregate_id + version 用于判断同一实体的顺序与新旧。
- 两个不同事件可能有不同 ID，但由于乱序，旧版本不能覆盖新版本。
- 删除事件需要墓碑或明确的版本，不能把“没有文档”当成永远不存在。
- 快照阶段与增量阶段要有一致的边界，避免同一变化被漏掉或重复处理。
- 消费者应保存来源位点、事件版本和处理状态，便于从断点继续或重建。

### 第二步扩展③ 可观测性要围绕可恢复进度

- 监控最老未处理事件年龄、位点推进速度、重试次数、死信量、版本冲突和目标与源的抽样差异。
- 只看消费者线程存活不能证明进度，位点不动且无异常日志可能是锁等待或持续重试。
- 对于不可幂等的外部副作用，应先持久化执行意图并要求下游接受稳定幂等键。
- 无法协作时只能降低承诺，不能用 CDC 重放保证撤销已经发生的副作用。

## 案例

### 第三步发散·验证与推演 崩溃窗口实验

- 固定一个 event_id，让消费者在目标写入前、目标写入后位点确认前分别终止，再恢复消费。
- 预期目标最多出现一次有效业务效果，重复到达被唯一键或版本条件识别。
- 位点不会越过未成功的事件。
- 把事件改成旧版本乱序到达，预期目标拒绝覆盖更高版本，并保留冲突指标。

### 第三步发散·追问① 断点与重建验收

- 从中间位点重新消费一段事件，比较目标快照和完整重建结果。
- 模拟删除、快照切换、死信修复和消费者扩容。
- 验收看业务状态、版本单调性和缺口对账，不只看消息数量。
- 这些是可执行验证步骤，具体 CDC 产品的位点字段和顺序能力需要按目标实现核对。

## 总结点

1. 事件 ID 治重，版本治乱，位点管断点
2. 目标先写会重复，位点先写会丢失
3. 事件 ID 管重复，版本管乱序
4. CDC 必须支持断点重放和对账
