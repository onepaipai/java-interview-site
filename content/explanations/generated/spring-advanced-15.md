## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银首页沙盘:热点 key 过期瞬间 200 个请求同时回源,团队开 sync=true 后单机内击穿消失,但 8 个实例仍各自回源 1 次(共 8 次),误以为"已解决"。用本机击穿实验说明 sync 的边界。

1. sync=true 是 JVM 内 singleflight:同实例的并发同键请求合并为一次加载;跨实例无任何协调——8 实例=最多 8 次回源。
2. 本机实测(distributed 10 题,同构机制):200 并发同键,无合并回源 200,singleflight 合并后 1——sync 管的是"进程内"那一段。
3. 分布式击穿的完整解:singleflight(进程内)+分布式互斥(单飞,Redis 锁或一致性哈希单点加载)+逻辑过期(热点永不过期,异步刷新)。

## 参考分析

### 第二步扩展① 机制:sync 的作用层与盲区

- sync=true 让缓存拦截器对该 key 加进程内锁,并发线程只有一个执行加载,其余等结果——本机 D10 实验证实同键 200 并发回源从 200 降为 1(同构机制)。
- 盲区:锁是 JVM 级的,N 个实例各自持锁各自加载——回源次数=实例数。
- 热点 key 高峰恰好每实例各来一次"穿透"。
- 与 Redis 限流的"本地 vs 全局"同构(分布式 18 题):进程内协调便宜,跨进程协调才解决总量。

### 第二步扩展② 实证:进程内合并的效果与跨实例边界

- 本机实验(Java 17.0.17,200 并发同键,CompletableFuture 合并):
```
无合并: 200 并发同键 -> 后端调用=200
singleflight: 回源调用=1
```
- 解读:sync=true 等价于右侧形态——进程内收益真实。
- 跨实例部分需要分布式方案:同一 key 的加载路由到固定实例(一致性哈希,分布式 4 题)或 Redis setnx 抢加载权,其余实例短等。
- 验证:进程内可复跑。
- 跨实例形态未在本机多实例环境复现,标注推演。

### 第二步扩展③ 取舍:击穿防护的分层选择

- 层一,sync=true:零成本,进程内合并——默认开启,无副作用。
- 层二,分布式单飞:热点 key 加载权抢锁,回源次数=1——加 Redis 依赖与失败语义(锁超时降级为本地加载)。
- 层三,逻辑过期:热点数据常驻,后台异步刷新——读路径零击穿,代价是短暂陈旧与刷新任务管理。
- 选择:普通 key 用层一。
- 可识别热点(TOP-K 监控,分布式 25 题)用层二。
- 极热且可容忍秒级陈旧用层三。

## 案例

### 第三步发散·验证与推演 验证:删热 key 并发 200 请求,统计回源数:进程内 syn

- 验证:删热 key 并发 200 请求,统计回源数:进程内 sync 后应等于实例数(跨实例盲区),加分布式单飞后回源数=1——回源数即击穿防护的度量,分层开启时逐层对比。

### 第三步发散·追问扩展 追问链:击穿三刀

- **Q1：sync=true 有什么代价?**
  - 答：加载期间同键线程阻塞等锁:加载慢(2 秒)时同键请求排队 2 秒——热点 key 加载慢时反而是 P99 杀手;配合加载超时与降级默认值。
- **Q2：缓存空值怎么防穿透?**
  - 答：不存在的数据缓存短 TTL 空标记(sync 也支持),配合布隆过滤器挡"确定不存在"的查询——穿透与击穿是两个问题,分开治。
- **Q3：击穿演练怎么做?**
  - 答：故障注入:删热 key+瞬时并发,观测回源数(应=实例数上限);对比开启分布式单飞后的回源数=1。

## 总结点

1. sync 管进程内,不管跨实例
2. 热点要分布式单飞或逻辑过期
3. 回源数是击穿的度量
