## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银升级沙盘:服务计划从 JDK 17 迁到 JDK 25，请求链路用 ThreadLocal 传递用户上下文；需要说明 ScopedValue 的绑定方式、适用边界与版本状态。

1. ScopedValue 把值与作用域绑定:在 where 指定的动态作用域内可读，退出自动消失——不需要 remove，也没有线程池复用导致的串号。
2. 它要求值不可变、生命周期结构化，适合请求身份、租户、追踪上下文这类"一次绑定、向下传递"的数据；可变缓存和跨异步边界的资源句柄仍用显式参数或并发容器。
3. 版本边界要讲清:JDK 21–24 为预览，JDK 25 由 JEP 506 转正；项目仍是 Java 17 时只能作为升级预研，不能写出可编译的生产代码。

## 参考分析

### 第二步扩展① 机制:作用域绑定替代线程绑定

- ThreadLocal 把值挂在线程上，值随线程复用到下一个任务。
- ScopedValue 把值挂在一次 where 调用的动态作用域上，只有在该作用域及其被调用的代码里可读，退出即不可见。
- 类比工牌:ThreadLocal 像把工牌留在座位上，下一位客人会看到。
- ScopedValue 像入场时佩戴、离场时自然失效的临时通行证——人还在，权限随场次结束而消失。
- 结构化并发让子任务继承同一作用域，因此不必手动复制上下文。

### 第二步扩展② 边界:不可变与可重入

- ScopedValue 的值应是不可变对象。
- 需要"换值"时用嵌套 where 覆盖，内层退出后自动恢复外层值。
- 它不是全局可变容器，不支持像 ThreadLocal.set 那样在任意深层方法里改写。
- 重复绑定和where 的嵌套顺序要显式设计，避免把"当前值来自哪一层"变成隐式约定。
- JDK 25 的 orElse 不再接受 null，空值语义要显式表达。

### 第二步扩展③ 取舍:迁移成本与收益

- 迁移收益是消除清理责任、降低线程池串号风险、与虚拟线程和结构化并发配合更自然。
- 成本是调用链要接受结构化作用域，已有的拦截器式 set/remove 框架需要改造。
- 对仍然运行 Java 17 的服务，优先做上下文审计和显式传参。
- 把 ScopedValue 列入升级后的迁移项，而不是为了新 API 提前引入多套上下文机制。

## 案例

### 第三步发散·验证与推演 验证:作用域边界的推演

- 教学验证（升级到 JDK 25 后执行）:在 where 作用域内读取用户 ID 断言正确。
- 作用域外读取断言不存在或走 orElse 默认。
- 嵌套 where 验证内层退出后恢复外层值。
- 再放入结构化并发子任务，断言子任务能看到父作用域的值。
- 以上为验证设计，本项目基线 Java 17 未运行该 JDK 25 实验。

### 第三步发散·追问① 追问:结构化并发还是预览吗

- JDK 25 的结构化并发（JEP 505）仍是第五次预览，与已转正的 ScopedValue 不同。
- 回答时要把"API 转正"和"仍预览"分开说。
- 若要求稳定 API，就不要把预览接口当成不可变的长期契约。
- 升级评估要记录使用的 JDK 版本与预览开关。

## 总结点

1. 线程绑定易串号，作用域绑定自动收
2. 不可变向下传，可变仍显式
3. JDK 25 转正，JDK 21 到 24 预览
