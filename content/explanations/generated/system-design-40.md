## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银排障沙盘:用户反馈"支付失败",值班要在 5 分钟内回答"哪个环节、为什么"——可观测平台的三支柱(trace/日志/指标)由 traceId 关联:指标定位"何时何服务异常",trace 定位"哪一跳失败",日志给出"具体原因"——关联设计决定排查速度。

1. 三支柱分工:指标(聚合视图,告警入口)、trace(请求级路径,定位跳)、日志(细粒度证据,定位因);关联键:traceId 全链路贯穿(W3C traceparent,见 distributed D14),日志嵌入 traceId 与 trace 关联,指标异常按时间点下钻到该时段 trace 样本。
2. 关联工程:统一 ID 语义(traceId 跨服务同值)、采样与日志的关联(trace 采样的请求,其日志全保留——排查完整性;未采样请求靠日志+指标兜底,network Q46 两端拼接)、失败请求优先(错误 trace 强制保留,Q19 尾部采样)、展示层串联(指标异常→一键跳到该时段慢/错 trace→展开看日志)。
3. 落地纪律:所有服务接统一 SDK(trace+日志格式+标记透传,与 Q38 压测标记同一套上下文机制)、跨线程/异步显式传递(spring-basics Q19 教训:线程池不继承,装饰器传递)、用户视角入口(按用户/订单号反查 traceId——排障从"用户说的"开始)。

## 参考分析

### 机制:ID 关联与下钻路径

下钻链:告警(指标:支付错误率 5%)→时段(14:02-14:05)→trace 样本(该时段错误 trace)→失败 span(渠道调用超时)→日志(该 span 的详细错误:渠道返回"余额不足")——每步点击可达,人工不拼接;反向:用户投诉(订单号)→traceId 索引(订单号嵌入 trace 属性)→完整链路——双向查询(正向:指标→trace;反向:业务 ID→trace)都要建索引。

### 反例:可观测关联的四种事故

事故一:traceId 不贯穿——MQ/异步断链,链路只见前半段(与 Q19 采样断链同源);传播纪律+断链检测。事故二:日志无 traceId——trace 定位到跳,日志搜不到细节(时间窗内几千条靠猜);日志格式强制含 traceId。事故三:三支柱三套工具——切平台查,上下文丢失;统一平台或统一入口。事故四:业务 ID 不进 trace——用户给了订单号,平台查不到(只有内部服务名);业务键作为 trace 属性索引。

### 取舍:自建 vs 商用可观测平台

自建(开源栈 Prometheus/Jaeger/ELK):可控成本低,运维重;商用(SaaS 可观测):开箱即用,数据出境与成本;折中:指标自建(Prometheus 成熟轻量)+trace 商用或自建(按团队运维能力)——可观测平台的成本与收益按团队规模分级,别为了"全自建"耗尽排障之外的人力。

## 案例

### 验证:ID 贯穿的实测证据(交叉引用)

distributed D14 实测+network Q46 实测:
~~~
D14:W3C traceparent 三层传播,trace-id 贯穿
Q46:客户端与服务端两端日志按请求 ID 拼接,差值即"消失的时间"
~~~
Q19 补充:线程池上下文需显式装饰传播(DelegatingSecurityContextCallable);验证:traceId 贯穿+日志关联+失败保留的组合在既有实测上闭环——三支柱的关联工程是排障速度的决定因素(明示:可观测平台行为未实测)。

### 追问链:可观测三刀

一刀:与 Q19 采样的衔接——尾部采样保错慢,未采样请求的排障靠日志+指标,关联键一致才能补位。二刀:与 Q21 告警的衔接——告警事件带下钻链接(指标→trace 的一键跳),告警与可观测是同一平台的两个视图。三刀:与 Q18 审计的边界——可观测数据(采样/过期)不能当审计用(审计全量不可变),两类数据管道分开(Q19 已述)。

## 总结点

1. 指标定位 trace 定跳日志定因
2. 双向索引正反都通
3. 失败请求强制保留
