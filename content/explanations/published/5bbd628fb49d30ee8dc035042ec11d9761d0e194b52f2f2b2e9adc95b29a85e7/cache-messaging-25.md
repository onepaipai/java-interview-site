## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Kafka 教学场景：同一业务实体的事件需要严格有序，团队把消息发到不同分区后乱序。理解"分区内有序"的边界（同 key 同分区）、全局有序的真实成本，以及"按 key 路由 + 消费端按版本收敛"的组合方案。

1. 有序的粒度是分区：同一分区内严格按写入顺序消费；不同分区之间没有顺序承诺——按 key 路由（同 key 同分区）只能保证"单实体有序"，全局有序需要单分区（牺牲并行度）。
2. 全局有序的真实成本：单分区=单消费者组内单线程消费，吞吐上限=单分片写入上限——用全局有序换掉横向扩展，多数业务不可承受。
3. 组合方案：按业务实体 key 路由保证实体内有序 + 消费端按业务版本号/事件序号收敛乱序（后到的旧版本被忽略）——顺序保证从"依赖分区"迁移到"依赖业务版本"，乱序不再是缺陷而是常态输入。

## 参考分析

### 机制：有序性的范围与并行度成反比

分区内有序 = 排队窗口按分区分割；全局有序 = 所有事件进同一窗口。类比银行：每个柜员按叫号顺序服务自己的客户（分区内有序），全行只有一个总叫号器（全局有序）则柜员只有一个——有序的范围画多大，并行度就缩多少。

### 反例：重试与多生产者的乱序注入

同一实体的两条事件：v2 先发成功、v1 首次发送失败重试后到达——分区内顺序变成 v2, v1。重试、多生产者实例、幂等发送的乱序修复都会注入乱序。只靠"同 key 同分区"挡不住，消费端必须按版本收敛。

### 取舍：需要全局有序时的设计替代

真需要全局有序的场景（账务流水）考虑：单分区专用 topic（吞吐够用即可）、或数据库序列化写入（回到数据库方案）。多数"看起来要全局有序"的场景，本质是"每实体有序 + 跨实体可乱"——按 key 路由+版本收敛就够了。把全局有序的要求证伪，是最省成本的一步。

## 案例

### 对照操作：乱序注入与版本收敛

教学验证：同 key 事件 v1（延迟注入）与 v2 正常发送，消费端按版本号处理。预期：到达顺序 v2,v1；无版本收敛时 v1 覆盖 v2（状态回退），版本收敛后 v1 被忽略。实验可复跑，收敛逻辑十行代码防住乱序事故。

### 追问：为什么"消费端串行化处理"不是替代方案

消费端把同 key 事件排队串行处理（本地队列/锁），乱序仍在队列里——串行化执行不改变到达顺序。版本收敛改变的是"接受什么"，串行化改变的是"怎么执行"——两者正交，都需要时可以叠加（按版本收敛 + 同 key 串行执行）。

## 总结点

1. 分区内有序，范围是分区
2. 全局有序牺牲并行度
3. 按 key 路由加版本收敛
