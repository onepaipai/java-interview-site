## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银升级沙盘:一次 ALTER TABLE 大表锁表 40 分钟,升级回滚后数据字典不一致——可恢复升级的结构:向前兼容的两步迁移+单执行者+回滚预演(banking 36 题的架构方法面)。

1. 两步迁移(向后兼容):第一步加性变更(加列/新表——旧代码无感);第二步发布新代码(使用新结构);第三步(下版)清理旧结构——任一时点旧代码与新 schema 兼容,升级与回滚都安全。
2. 可恢复三件套:迁移的幂等与断点(IF NOT EXISTS/已应用检查——中断重跑安全)、单执行者(Flyway 锁或流水线单点,第 36 题 banking)、回滚预演(备份+回滚脚本在预发演练过——回滚不是文档是演练过的动作)。
3. 大表的在线变更:gh-ost/pt-osc(在线工具)替代直接 ALTER——变更执行与业务解耦,失败可中止可续跑。

## 参考分析

### 机制:两步迁移与兼容窗口

窗口设计:扩展列(V1)→代码双写读写新列→切换读→清理旧列(V2,下版)——窗口内回滚应用=旧代码读旧列(仍在写,数据不丢)。在线变更:gh-ost 影子表+触发同步+原子换名——锁时间从"全程"缩到"换名瞬间";失败中止=删影子表原表无损。断点:迁移工具的 applied 版本表——中断重跑从断点继续(分布式 42 题断点同构)。

### 反例:不可恢复升级的三种形态

形态一,破坏性一步到位:改列类型+删旧列一个脚本——失败回滚到"旧代码+新 schema"=全站报错。形态二,迁移脚本不可重跑:无 IF EXISTS 检查——中断后重跑报"已存在"卡死。形态三,回滚靠信仰:无备份/回滚脚本没演练——出事后 8 小时手写恢复。三条的修复=两步迁移+幂等脚本+回滚预演,全在升级前完成。

### 取舍:兼容窗口的长度

窗口=两版代码并存期(一个发布周期):窗口内双写/双读的代码复杂度是代价;窗口过短=回滚空间不足。节奏:清理步(第三步)必须等"确认不再回滚到旧版"(观察期)——清理不可逆,最后执行。审批:破坏性变更(删列)单独审批+备份验证(备份可恢复才许删,第 45 题归档完整性)。

## 案例

### 验证:可恢复性的断言组

验证:断点续跑断言(迁移中断后重跑成功且无副作用重复);回滚预演断言(预发执行回滚脚本成功+数据完整);兼容窗口断言(窗口内旧代码跑全量回归通过)——三组让"可恢复"从文档变成已验证事实;每次升级的演练记录归档(第 32 题审计)。

### 追问链:升级三刀

一刀:"schema 版本与代码版本的对应?"——schema 版本支持的代码范围显式(N 版 schema 支持 N-1 到 N 版代码)——兼容窗口的机械化表达;部署编排按范围校验。二刀:"多实例的升级顺序?"——滚动升级前 schema 先行(两步迁移使 schema 领先代码)——实例混跑期(N 与 N+1 并存)被兼容窗口覆盖(第 41 题分布式 41 题冷启动门禁)。三刀:"升级的数据校验?"——迁移后数据校验(行数/抽样比对/约束校验)进迁移脚本——迁移不只是"结构对了",数据也要对(第 46 题资金不变式)。

## 总结点

1. 两步迁移留兼容窗口,回滚不是信仰
2. 单执行者加断点,中断重跑安全
3. 大表走在线工具,清理放最后
