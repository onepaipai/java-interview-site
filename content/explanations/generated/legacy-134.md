## 参考回答

> 场景与约束：网银限流沙盘:限流四算法+分布式限流(多实例共享配额)——算法的选择取决于"你要防什么"(突发/匀速/精确),分布式则要解决"配额共享"的问题。

1. 四算法一行对比:固定窗口(简单,有边界突刺——D1 实测 200/200 全放行)/滑动窗口(精确,无边界突刺,内存高)/令牌桶(允许突发,预存令牌,常用于 API 限流)/漏桶(严格匀速,削峰填谷,常用于保护下游)。
2. 选择判据:防接口被打爆→令牌桶(允许正常突发);保护慢下游→漏桶(匀速出口);精确计数→滑动窗口;简单计数→固定窗口(可接受突刺)——sd 第 7 题有三算法实测(固定 200/200/令牌桶 139/滑动 100)。
3. 分布式限流:多实例共享配额——一,集中式(Redis+Lua 原子扣减——每次请求查 Redis,精度高但 Redis QPS 成为瓶颈);二,本地预取+中心仲裁(每实例从中心批量取配额,本地消耗,用完再取——吞吐高但精度=预取粒度,sd 第 7 题的形态);三,一致性哈希按 key 分片(同 key 路由同实例——单 key 精确,跨 key 不共享)。

## 参考分析

### 第二步扩展① 机制:分布式限流的"精度-吞吐"权衡

- 集中式(Redis 每请求):精确(全局配额准确)但吞吐受限(Redis QPS 上限≈10 万,每请求查一次)。
- 本地预取:吞吐高(本地判定,无网络)但配额按预取粒度粗略(±100 请求)。
- 混合:高频接口本地预取+低频接口集中——按"配额价值"选择(计费类精确,防护类宽松,第 45 题取舍)。

### 第二步扩展② 反例:分布式限流的两种事故

- 事故一:每请求查 Redis——Redis QPS 被限流打满(10 万 QPS 全是限流查询),限流平台先被打死(第 20 题自保设计)。
- 修复=本地预取。
- 事故二:预取粒度太大(一次取 1 万)——配额误差=±1 万(突发时全放行或全拒绝)。
- 修复=按流量速率动态调预取粒度。

### 第二步扩展③ 取舍:限流层与熔断的分工

- 限流=入口保护(按配额拒绝,正常行为的管控)。
- 熔断=出口保护(按健康状态切换,故障行为的响应)——限流管"正常流量太多",熔断管"下游出问题了"——两层不可互替(第 22 题降级/第 135 题熔断)。
- 限流的响应=429,熔断的响应=503——客户端据此决定重试策略。

## 案例

### 第三步发散·验证与推演 验证:分布式限流的走查核对

- 验证:本机 D1 实验(固定窗口 200/200 vs 令牌桶 120/200)+sd 第 7 题 SD4(三算法同帧)+sd 第 7 题本地预取架构——分布式限流的"精度-吞吐"曲线在 sd 第 7 题有实测支撑。
- Redis Lua 的原子性(限流脚本)在 cache-messaging 批次有 Redis 原子操作的证据衔接。

### 第三步发散·追问扩展 追问链:限流三刀

- **Q1：限流的 key 怎么选?**
  - 答：按用户(防个人滥用)/按接口(防接口过载)/按全局(总容量)——三维叠加(第 15 题),key 的选择决定"限的是谁";key 错=误伤或漏放。
- **Q2：被限流的客户端体验?**
  - 答：429+Retry-After(明确告知何时重试)+排队入口(第 38 题体验设计)——被限流不是错误,是"请稍后"。
- **Q3：限流参数的调优?**
  - 答：阈值按容量压测校准(第 34 题)而非拍脑袋;突刺容忍度按业务(抢购窗口可短时超限,稳态服务不可)。

## 总结点

1. 四算法各防一种突刺
2. 分布式=精度与吞吐的权衡
3. 限流管入口,熔断管出口
