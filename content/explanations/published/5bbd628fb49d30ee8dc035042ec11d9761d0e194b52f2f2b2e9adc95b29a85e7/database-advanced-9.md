## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB 教学场景：筛选接口有 6 个可选条件（状态、类目、地区、金额段、时间、关键词），任意组合导致索引无法覆盖所有排列。给出"锚点索引 + 组合收敛"的设计方法与边界。

1. 承认现实：N 个可选条件的排列组合是 2^N，索引不可能覆盖全部排列。设计目标是"每个高频组合有一条最优索引，其余组合落在可接受成本内"。
2. 锚点法：选一个几乎必填、选择性最好的条件作为锚点列建复合索引（如 tenant_id 或类目），其余高频条件按组合频次各建一两条短索引；低频组合接受锚点索引过滤后的回表过滤。
3. 组合收敛手段：接口层限制"未带锚点条件的查询"走预聚合或搜索引擎；MAX_EXECUTION_TIME 兜底防长查询；对确实任意的全文/多维筛选，引入专用引擎（ES）而不是让 MySQL 硬扛。

## 参考分析

### 机制：把 2^N 的组合空间折叠成"锚点 × 少数变体"

可选条件像自助调料台：全排列无穷，但真实订单 90% 都带"店铺+日期"。锚点索引服务这个主轴，调料（可选条件）在锚点过滤后的小结果集上回表过滤——行数少了，没索引的过滤也不贵。类比把无穷组合收敛到"主路 + 支路"。

### 反例：为每个条件各建单列索引的失效

6 个单列索引：优化器最多做 index merge（often更差）或选其中一个，其余条件逐行回表过滤——组合越偏（只带冷门条件）回表越多。现场证据：EXPLAIN 的 type=index 或 ref 但 rows 巨大、Extra 出现 Using where 无 Using index。正解是把"高频组合"固化为复合索引，而不是给每列发索引。

### 取舍：哪些查询该交给搜索引擎

信号：关键词模糊匹配（LIKE %x%）、多条件任意组合且无锚点、排序维度动态、需要分面统计——这些是搜索引擎的设计域。MySQL 侧保留"锚点明确、结构化条件"的查询。边界划清后，两侧各自用最合适的索引结构，不再互相迁就。

## 案例

### 对照操作：组合频次驱动的索引验收

教学验证：从接口日志统计 6 条件的真实组合频率，为 TOP2 组合建复合索引；对 TOP5 组合逐个 EXPLAIN ANALYZE。预期：TOP2 毫秒级、TOP3–5 在锚点过滤后可接受、未被覆盖的冷组合被 MAX_EXECUTION_TIME 截断并计入搜索引擎迁移清单。验收表可离线复用。

### 追问：为什么不给冷组合也加索引

每个索引都是写放大与 Buffer Pool 的占用（进阶相关题的治理结论）；冷组合的查询频次撑不起固定成本，且冷组合往往意味着需求在漂移。用"锚点过滤后的可接受成本 + 限时长"承接漂移期，需求稳定后再固化索引——索引跟着需求成熟度走。

## 总结点

1. 2 的 N 次方不可能全覆盖
2. 锚点索引走主路，支路接受回表
3. 任意组合交给搜索引擎
