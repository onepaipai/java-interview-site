## 参考回答

1. 先写不能违反的业务约束，再画数据所有权与提交边界；不要按表或技术层直接拆服务。
2. 约束需要两个服务同时提交才能成立，就切断了原事务；应重划边界或明确选择一致性协议。
3. 允许中间态就建模在途、待确认和补偿；不允许则保留原子边界，并用部分提交与分区验证取舍。

## 参考分析

1. 事务不变式描述某个原子边界内不能被观察到的非法状态，例如同币种已记账分录借贷不平或余额透支。
2. 把借记和贷记拆到两个独立库后，两个 RPC 顺序成功不是原子提交证明；第二步失败时第一步不会自动回滚。
3. Saga 的补偿是新的业务动作，可能失败或无法完全撤销；已发货、已通知用户等外部效果尤其不能视作数据库回滚。
4. 若业务允许跨渠道在途资金，可用明确的中间账户与状态保持账务平衡，但这改变了业务模型，不能直接删掉约束。
5. 同库不同模块可以先限制写入口和依赖，再按实测瓶颈拆分；服务数量不是领域边界合理性的度量。

## 案例

1. 场景（教学示例）：站内同币种转账原本同事务写借记、贷记；拆为“扣款服务”和“入账服务”，第二个服务宕机。

2. 推演：A 扣款已提交，B 入账未提交；若模型没有在途账户，这笔已入账交易就出现单边分录，重试也可能重复扣款。

```text
错误边界：扣款库提交 → RPC 失败 → 入账库没有记录
本例取舍：账务服务统一拥有借贷分录和余额变更
同一事务：校验余额 → 写两边分录 → 更新余额 → 写 Outbox
任一步失败：整个本地事务回滚
事务提交后：异步通知与展示更新，可重试但不得再次记账
```

3. 结果：本例把两边账务留在同一提交边界，通知失败只影响展示；不会出现已提交交易只有一边分录。

4. 验证：在每一步注入异常和重复消息；核对同币种每笔分录合计为零、余额不越界、业务键不重复；跨渠道业务另建在途状态。

## 总结点

1. 先写不变式，再划边界。
2. 补偿是新动作，不是回滚。
3. 局部原子，边界外可恢复。
