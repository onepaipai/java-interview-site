## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银合并账期沙盘:若干 [start,end] 区间,重叠的合并——排序依据(按 start)决定扫描方向;边界判定(end>=next.start 即重叠,含相接)是约定不是数学,要与业务对齐。

1. 标准两步:①按 start 升序排序(O(n log n)——排序是合并的前提,乱序扫描无法局部判定);②线性扫描:当前区间与下一个——next.start<=cur.end 则重叠,合并为 [cur.start,max(cur.end,next.end)](end 要取 max!next 可能完全被包含);否则当前定案,推入结果。
2. 边界语义三选:相接算重叠([1,2] 与 [2,3] 合并为 [1,3]——时间轴连续段,用 <=);相接不算([1,2) 与 [2,3) 是两个半开区间——用 <);浮点/时间戳要先定精度与开闭——「重叠」的判定式一行,但语义错误全盘错;合并的输出约定同样要定(输出是否排序/是否去重)。
3. 复杂度:排序 O(n log n) 主导+线性扫描 O(n);空间 O(n)(结果);变体:插入区间(有序直接扫,不用再排)/区间列表相交(双指针同步推进,取 max(start) 与 min(end) 判交)——合并、插入、相交三题一套排序+扫描骨架。

## 参考分析

### 机制:为什么按 start 排序后只需一次线性扫描

排序后,下一个区间的 start≥当前所有已处理区间的 start——它只可能与「最近一个未定案区间」重叠(再早的已定案,且它们的 end 不会够到新 start——若够到就不会定案);「最远前进的 end」是唯一需要维护的状态:合并时 end 取 max 防止「大区间吞小区间后又被小区间的 end 收缩」——max(cur.end,next.end) 一行是本题最常见 bug 的修复。

### 反例:区间合并的三种事故

事故一:合并忘取 max(end)——[1,10] 与 [2,3] 合并成 [1,3],大区间被吞;事故二:排序按 end——扫描判定失效(start 乱序无法保证「只看下一个」),结果漏合;事故三:相接语义混用——账期合并(该相接)与会议室占用(相接不算冲突)判定相反,一处 <= 一处 <;语义要先与业务对齐再写代码。

### 取舍:排序合并 vs 并查集 vs 线段树

静态一次合并:排序+扫描 O(n log n) 标准解;区间动态增删+随时问合并结果:线段树/TreeMap(按 start 有序插入,合并邻居 O(log n) 摊还,日历系统实现);区间分组(谁和谁连着):并查集(第 31 题)——按「查询模式」选结构,本题模板只适合一次性批处理。

## 案例

### 验证:合并断言组(本机可复跑)

验证:基本断言([1,3][2,6][8,10]→[1,6][8,10]);包含断言([1,10][2,3]→[1,10]——max(end) 证据);相接断言([1,2][2,3] 按 <= 合并为 [1,3],按 < 保持两段——语义开关双测);乱序输入断言(打乱顺序结果一致——排序必要性);金标断言(随机区间与暴力两两合并对照一致)。预期:max(end) 与相接语义是两组分辨器。

### 追问链:区间三刀

一刀:区间相交(不合并,求交)——双指针取 [max(start),min(end)],start>end 无交;会议室(最少房间)=按 start 排序+最小堆放 end(第 21 题堆复用);二刀:TreeMap 日历——floorEntry 查前驱定冲突+合并前后邻居,动态版 O(log n);三刀:工程迁移——账期合并/停机窗口合并/促销时段合并,核心都是「先排序后一次扫+max 端点」;时间区间统一用半开+毫秒精度(java-language 时间陷阱同源)。

## 总结点

1. 按 start 排序,一次扫描
2. 合并端点取 max(end)
3. 相接是否重叠,先定语义
