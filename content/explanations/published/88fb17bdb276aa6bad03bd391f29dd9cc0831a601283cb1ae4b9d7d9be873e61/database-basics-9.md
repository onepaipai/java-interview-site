## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银接口沙盘:SELECT * 在宽表(50 列含 TEXT)上把 200MB 查询拉成 2GB——传输/内存/覆盖全毁;列增删时 * 的消费方(ORM 映射/INSERT INTO t SELECT *)静默错位。

1. 性能三伤:①网络与序列化——不需要的列照传(大字段 TEXT/BLOB 是重灾区);②覆盖索引失效——* 必回表(第 4 题);③内存与排序——排序/临时表要装载全部列,sort buffer 翻倍;大字段还触发行溢出页(第 50 题VARCHAR/TEXT)读放大。
2. 兼容性两伤:①INSERT INTO t2 SELECT * FROM t1——t1 加列后列数不匹配直接报错,删列后静默错位(类型兼容时数据污染,最难查);②ORM/结果集映射——按列名取值尚可,按位置取值(JDBC getXxx(3))错位;视图与存储过程里 * 在定义时展开,基表变更后视图需重建(行为漂移)。
3. 合理例外:探索性查询(人工诊断)/真正的整行消费(按主键取单行完整对象)——SELECT * 不是禁令,是「默认应写列名」的工程纪律;评审要点=生产代码路径上的 * 逐个追问「这些列真的都被消费吗」。

## 参考分析

### 第二步扩展① 机制:为什么 * 的成本随表演进放大

- 表是活的——列会加宽(TEXT 进来)/列会增多(业务演进)。
- * 把「表的当前宽度」耦合进每条查询——耦合点越多,演进越贵:任何列变更都影响全部 * 查询的传输量与映射。
- 显式列名=把「依赖面」缩到真实消费的列——这是最小依赖原则在 SQL 的体现(第 33 题IoC 依赖显式化同思想)。
- SELECT 列表也是「查询契约」的一部分,契约越窄越稳。

### 第二步扩展② 反例:星号的两种事故

- 事故一:报表 SELECT * 含 3 个 TEXT——排序临时表落盘(filesort on disk),接口超时。
- 按需 5 列后毫秒级。
- 事故二:INSERT SELECT * 跨环境同步——源表加列后列数不符报错(运气好)或类型兼容错位(运气差,静默污染)。
- 显式列名+列校验。
- 事故三:ORM 按位置映射——全表列变更后 getXxx(3) 取到别的列。
- 按名映射+显式列。

### 第二步扩展③ 取舍:显式列 vs 代码简洁

- 显式列名的「啰嗦」是契约成本,换来演进安全。
- 折中=视图/查询对象封装列清单(一处定义多处用)。
- 大宽表的按需列+延迟加载(ORM fetch specific)。
- 审计场景(必须全列留痕)用显式列+变更时同步——* 的便利不该出现在生产查询里,出现在工单排查里无妨。

## 案例

### 第三步发散·验证与推演 验证:星号断言组(本机可复跑)

- 验证:传输量对照(宽表 SELECT * vs 5 列:字节量/耗时对照)。
- 覆盖断言(* 无 Using index,显式列覆盖=Using index——第 4 题呼应)。
- 临时表断言(ORDER BY 大表 * 的 Extra=Using temporary/filesort vs 窄列)。
- 兼容断言(INSERT SELECT * 在源加列后的报错/错位复现)。
- 视图断言(视图 * 在基表加列后 SHOW CREATE VIEW 的展开行为)。
- 预期:性能与兼容双维度可见。

### 第三步发散·发散要点 追问链:星号三刀

- **追问①**：列裁剪与列存——分析型查询的列式存储(只读需要的列)是 * 反模式的架构级解(第 152 题 OLAP 选型);
- **追问②**：大字段分离——TEXT/BLOB 单独表或对象存储(第 50 题),主表窄化让 * 伤害可控;
- **追问③**：ORM 的投影 API——SELECT 特定列+DTO 投影(第 24 条规约:入参返回 DTO 隔离),框架层消灭 *

## 总结点

1. *=表的当前宽度耦合进查询
2. 覆盖失效+大字段传输
3. 显式列=最小依赖契约
