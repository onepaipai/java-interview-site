## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银余额沙盘:千万用户查余额,转账后立即查询必须看到新值吗?强一致(读主库)贵且慢,最终一致(读副本+缓存)快但可能读到旧值——按"查询场景的风险等级"分档,而不是全局一刀切。

1. 分档设计:交易确认页=强一致(读主库或转账事务同库读,容忍慢);展示类(首页/历史)=最终一致(副本+缓存,容忍秒级旧值);风控类=快照一致(按时间点读,可重放)——档位写进接口契约,调用方按需选。
2. 容量推演(本机实测):千万 DAU×8 次/日→峰值约 3333 QPS;缓存命中 90% 后 DB 仅 333 QPS(单实例充裕,1 主 2 从冗余);写入峰值约 67 TPS(单主可承,热点账户行锁才是真瓶颈)——一致性档位决定的读路径差异直接改变容量结论。
3. 缓存一致性:余额缓存用"转账时失效"而非"定时过期"——写路径主动失效(evict)+短 TTL 兜底,读路径 miss 回源;顺序纪律:先更新 DB 再删缓存(cache-aside 主流形态,"先删后更"在并发读写下回填旧值的窗口更大),并发尖锐场景补延迟双删或版本号比对兜底(与 cache-messaging 批次的失效策略同构)。

## 参考分析

### 第二步扩展① 机制:一致性与读路径的映射

- 读主库:一致最强,容量=主库上限(写多时读挤占)。
- 读副本:容量线性扩展,代价=复制延迟窗口(余额转账后立查副本可能旧值)。
- 缓存:容量最高,一致性=失效策略决定。
- 分档的本质是把"谁需要绝对新"从"全部请求"缩小到"交易确认"一个点——容量收益从整体读路径释放。

### 第二步扩展② 反例:一致性选错的三种事故

- 事故一:全部读主库——大促查询挤占写事务,主库 CPU 打满。
- 交易确认才需要主库。
- 事故二:交易确认页读缓存——转账 5000 后页面显示旧余额,客诉与重复转账风险。
- 确认页必须绕缓存。
- 事故三:副本延迟无监控——复制延迟 30 秒没告警,展示类也失真。
- 延迟指标与分档 SLA 对齐。

### 第二步扩展③ 取舍:热点账户的特殊处理

- 热点账户(工资发放户):行锁串行化拖垮整库——按账户维度拆分(影子账户/缓冲记账,入账先记账本后合并)。
- 一致性档位之上再加"热点分档"。
- 判断标准:单账户 TPS 超过行锁吞吐(约数百 TPS)即热点化——容量估算要含热点分析(SD3 的写入推演已示警)。

## 案例

### 第三步发散·验证与推演 验证:容量链条的实测证据

- 本机实测(SD3Capacity,确定性推演):
~~~
java SD3Capacity
日请求=80000000,峰值小时=12000000 ≈ 3333 QPS
余额表: 10000000 行 × 128B ≈ 1.2 GB(单表可承受,按分区键预留拆分)
缓存命中率 90% → DB QPS ≈ 333(单实例 MySQL 可承 ~5000 读 QPS,1 主 2 从充裕)
写入(转账峰值)≈ 67 TPS(单主可承,瓶颈在热点账户行锁——按账户维再拆)
~~~
- 本批 SD5CacheOrder 缓存一致性顺序对照(确定性事件序列):
~~~
java SD5CacheOrder
A 先删缓存后更新 DB: 回源读到 balance=100,回填后缓存=balance=100 (旧值驻留到 TTL)
B 先更新 DB 后删缓存: 回源读到 balance=200 (新值——正常序列一致)
C 残余窗口: 慢回源回填后缓存=balance=100 (旧值——B 也有窗口)
C 延迟双删: 二次删除后读回源 balance=200 (脏窗口被二次删除收敛)
~~~
- 验证:每步算式可审计。
- 一致性顺序(先更后删的必然残余窗口与延迟双删的收敛)有实测形态支撑——推演链闭环。

### 第三步发散·发散要点 追问链:一致性三刀

- **追问①**：与 CAP 的衔接——余额服务分区时选 C(拒绝查询保账实一致)还是 A(返回可能旧值),按档位分(交易档选 C,展示档选 A);distributed Q2 有系统证据
- **追问②**：余额与流水的分离——余额是派生值,流水是事实源(banking B3:直改余额被重放校验拦截);一致性档位作用在"流水→余额"的投影延迟上
- **追问③**：与 Q49 数据增长的衔接——十倍增长时缓存命中率与分片键是先改的两处,估算模型要预留敏感性分析

## 总结点

1. 交易确认才读主库
2. 展示类最终一致够用
3. 热点账户行锁先分档
