## 参考回答

<!-- explanation:deep -->

> 场景与约束：Spring Security 6.5 Servlet 教学设计：/api/admin/** 需要管理员，/api/** 需要登录，其他页面有公开入口。比较链的选择匹配与链内部授权匹配。

1. FilterChainProxy 按顺序选取首先匹配请求的 SecurityFilterChain，而非把所有匹配链的规则叠加；宽泛链排在前面会遮住后面的专用链。
2. securityMatcher 等决定一条链是否被选择，链内 requestMatchers 决定该链中的授权规则，两层匹配职责不同。
3. 还需为预期的其他请求提供兜底链；没有链匹配的请求不能假设自动受到另一条链保护。分别测试匿名、普通用户和管理员的所有入口。

## 参考分析

### 第一层匹配：选链只选当前请求适用的一组设施

专用管理链通常应比宽泛 API 链更早匹配。每条链可能包含不同的认证、CSRF、会话与异常处理设置，选错链不仅影响一个角色判断，还可能改变登录入口和响应协议。@Order 只是排序工具，必须与链的匹配范围一起解释；不要把同一请求当成先通过普通链再补上管理员链。类比分诊台按症状分科室：第一个匹配的科室（链）接管全部流程——分诊顺序排错，病人就会被送进错误的科室。

### 第二层匹配：授权规则不能代替选链范围

某条链内部写了管理员路径规则，但如果该链根本没有被选中，这条规则不会执行。反过来，选中链后仍需有正确的授权规则，匹配到管理链不等于已经拒绝普通用户。应同时画出“路径选哪条链”和“该链用什么身份允许哪些动作”的表格，便于逐项验收。

### 兜底与协议：遗漏请求也要能解释

限定 securityMatcher 后，未匹配请求可能绕过整条安全链，因此公开静态资源和其他业务入口都应有明确策略。登录处理端点也需要位于适用链范围内。API 期望 JSON 的认证拒绝若走了页面登录链，可能意外返回重定向或 HTML，不能只验证管理员登录后的成功路径。

## 案例

### 权限矩阵：三种身份乘三类路径

教学测试分别以匿名、普通用户和管理员访问管理 API、普通 API 和公开页面，并记录选中的链和最终状态。再故意把宽泛 API 链排在管理链前做对照，预期能识别专用保护被遮住的风险。检查数据库副作用是否发生，不能只靠状态码判断拒绝确实先于业务执行。

### 遗漏追问：新端点未落入任意匹配范围

增加一个不属于 /api/** 的敏感端点，检查兜底链是否按预期拒绝；同时验证登录与错误端点能到达正确处理器。预期每个路径都有可解释的选链和授权结果，页面与 API 保持各自协议。此处描述教学配置矩阵，没有声称完成用户现有全部安全链的渗透测试。

## 总结点

1. 分诊排第一，科室规则排第二
2. 首先匹配的链负责当前请求
3. 选链与链内授权分两层
4. 兜底和失败协议都要验证
