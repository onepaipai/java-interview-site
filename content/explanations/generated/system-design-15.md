## 参考回答

> 场景与约束：网银 App 沙盘:用户手机+电脑+平板同时在线,改密码后所有设备必须重新登录;多设备=会话按设备独立(设备指纹+会话清单),改密退出=会话版本号机制全量失效——spring-basics Q26/27 的系统化展开。

1. 多设备模型:每设备独立会话(设备 ID+登录态+有效期),会话清单按用户维度管理(列表/命名/单设备登出);并发策略可配(互踢/共存/上限数);设备指纹(机型+系统+绑定推送 Token)用于展示与风控(异地新设备登录提醒)。
2. 改密退出机制:会话版本号——用户凭证版本(每次改密+1)高于会话签发版本才有效;改密=版本+1→所有旧会话校验失败→全设备重新登录;分级策略:改密全失效,密码泄露嫌疑全失效+风控,单纯登出单设备(清单操作)。
3. 安全加固:会话固定防护(登录后换新 ID,spring-basics Q26)、HttpOnly+Secure+SameSite(network Q36/37)、活跃会话展示(用户可见"这些设备在线",可主动踢)、异常登录通知(新设备/新地域)。

## 参考分析

### 机制:版本号与会话清单

存储:会话表(用户 ID、设备 ID、签发版本、过期时间、最近活跃);校验:token 有效+签发版本==当前用户凭证版本+未过期;改密:UPDATE 用户 SET cred_version=cred_version+1→下一次各设备请求校验版本不符→拒绝并引导登录;会话清单 API 支持单设备登出(删对应行);与 Q14 权限版本的差异:凭证版本管"身份有效性",权限版本管"授权内容"。

### 反例:会话系统的四种事故

事故一:全局单会话互踢——用户手机登录把电脑踢下线,办公场景不可用;按设备独立。事故二:改密只失效当前设备——其他设备继续操作(资损风险);版本号全量失效。事故三:会话清单无 UI——用户不知道有多少设备在线,泄露无感知;可见可踢。事故四:退出登录只删 token 副本——服务端会话仍在,token 泄露后仍可用;服务端状态删除为准。

### 取舍:有状态会话 vs 无状态 JWT

有状态(服务端会话表):可踢可清单化,存储与查询成本;无状态 JWT:零查询,但撤销难(黑名单=变相有状态)。金融系统选"有状态为主+短期 token":撤销与多设备语义必须服务端状态支撑——撤销及时性(Q14)是硬需求,无状态省的成本换不来。

## 案例

### 验证:版本失效的推演核对

推演核对:spring-basics Q26 实测证据(改密失效全部会话,旧会话访问受保护接口 401 跳登录)直接支撑本设计;会话固定防护(登录换 ID)同仓库内容;多设备清单按产品语义推演并明示;验证:"凭证版本号全量失效+设备清单可管"的机制在仓库已有实测内容上成立。

### 追问链:会话三刀

一刀:与 Q14 权限版本的组合——用户有"凭证版本"与"权限版本"两个号,任一不符都重校验;两版本独立演进(改密不动权限)。二刀:风控联动——异地/新设备登录触发提醒或二次验证,风控信号(设备指纹变更)与会话安全闭环。三刀:推送 Token 的生命周期——设备登出要解绑推送(否则继续收消息,泄露存在感),与 Q9 通知中心的绑定表衔接。

## 总结点

1. 会话按设备独立
2. 凭证版本全量失效
3. 服务端状态是撤销的前提
