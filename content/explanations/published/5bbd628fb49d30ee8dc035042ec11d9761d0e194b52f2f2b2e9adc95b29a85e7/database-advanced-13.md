> 场景与约束：Java 17 教学场景：订单号要求全局唯一，分片后各片的本地唯一约束管不到其他分片。梳理全局唯一的三条实现路径——发号器、业务键设计、全局校验服务——与各自的失效模式。

1. 发号器路径：中心化或号段式发号（每分片预取一段号区间，用完再取），或雪花类算法（时间戳+机器位+序列）——唯一性由生成端保证，分片只存结果，无需跨片校验。
2. 业务键路径：把"全局唯一"的需求从数据库层上移到业务层——用天然唯一的业务事实（手机号+商品+活动）作为幂等键，配合应用侧去重表（落在一个固定分片或独立服务）。
3. 全局校验路径（尽量避免）：写后查全局索引服务确认唯一——引入分布式事务味道与可用性耦合，仅在无法改变键设计时使用；失败模式是"校验服务挂了写全停"。

## 参考分析

### 机制：唯一性校验的执行位置决定架构成本

本地唯一约束便宜（B+ 树原子裁决，见 database-basics 相关题）；全局唯一要么"在生成端就唯一"（发号器，把校验消灭在源头），要么"集中到一个点校验"（全局服务，形成瓶颈）。类比身份证：全国唯一靠发证机关统一编码，不是靠各地派出所互相查重。号段分配自身的原子性：取号用数据库行级条件更新（UPDATE segment SET max_id=max_id+step WHERE biz=?，取回新 max_id）或 Redis INCR——两个节点取到重叠号段即唯一性破防，发号器自身必须并发安全。

### 展开：B+ 树结构为什么对主键形态敏感

InnoDB 以 16KB 页为 B+ 树的基本单位：非叶子节点只存键与子页指针，聚簇索引叶子存整行，二级索引叶子存主键值再回表，叶子间双向链表支撑范围扫描。三层树（每页约上千键、叶子每页数十行的量级）即可承载千万行——树高决定一次查找要读几个页。随机主键（UUID v4）让插入落点随机：目标页满即分裂、中间键上移，产生碎片与写放大；自增主键总是追加到最右页，分裂最少。主键设计因此同时影响唯一性、空间与写路径——这也是下一块 UUID 追问的机制底座。

### 反例：号段发号器的三个事故位

一，号段分配后实例宕机，号段作废产生空洞——无害，但监控要把空洞当正常；二，多机房时钟漂移让雪花算法时间位错乱——时钟回拨防护必须内置；三，号段步长太小导致高峰期频繁取号、太大导致重启浪费与 ID 漂移。参数与监控都要跟上，发号器不是"实现完就完"。

### 取舍：唯一性需求的分级

物理唯一（订单号、流水号）：发号器，永无冲突且有序利于分片；业务唯一（同用户同商品同活动只买一次）：业务键 + 去重表（幂等），比全局唯一索引更贴近语义；展示唯一（用户名）：允许改名类方案回避全局约束。先分级，再选实现——所有唯一都上全局约束是过度设计。

## 案例

### 对照操作：三种路径的并发与故障对照

教学验证：并发 1 万次取号对比三条路径——发号器零冲突零网络（号段内本地）、全局校验服务每请求一次网络且服务故障即写失败、业务键去重表按 key 原子裁决。预期：吞吐与故障半径的差异支持"生成端唯一"的推荐，实验可复跑。

### 追问：为什么 UUID 不是免费的唯一方案

UUID v4 无序导致 InnoDB 页分裂（随机主键插入），索引体积大且缓存差；UUID v7 有序改善了插入，但 128 位仍比 bigint 宽。发号器的趋势递增 ID 对 B+ 树最友好——"唯一"之外还要考虑"有序与宽度"，这是主键设计的第二层考量。

## 总结点

1. 唯一性在生成端最便宜
2. 发号器有序利于分片，UUID 随机伤树
3. 业务唯一用去重表，别全上全局校验
