## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 主从异步复制教学场景：实例 A 在主库获锁，锁尚未复制到从库时主库宕机，从库提升为新主——锁"消失"，实例 B 又获锁，A、B 并发。解释异步复制的结构性原因与 Redlock 的取舍。

1. 结构性原因：Redis 主从复制是异步的——主库执行 SET NX 后立即返回成功，同步到从库存在延迟；故障切换（哨兵/Cluster）以"新主拥有最新数据"为准，但"最新"不含尚未复制的写。锁在故障切换中丢失是异步复制的结构性结果，不是配置缺陷。
2. 影响面：单主 Redis 锁在主从切换时的互斥假设被打破——Redlock 算法尝试修复：向 N 个独立主库同时加锁，过半成功才算获锁，切换后多数派仍成立。
3. Redlock 的代价与争议：需要 N 个独立实例、时钟假设、获取失败的 fencing 成本——Redlock 改善了互斥强度，但"客户端假死 + fencing 缺失"场景下仍不完美。结论：正确性要求极高的场景，互斥放资源端（fencing/数据库约束），Redis 锁只做效率层。

## 参考分析

### 机制：异步复制把"提交成功"与"全局可见"分开

主库返回 SET NX OK 时，锁只存在于主库内存；复制是从容的异步投递。类比总店登记与分店传真：总店登记了你的预约，传真到分店前总店失火，分店不知道有预约——换到分店办公（切换）后预约消失。Redlock 是"向多家总店同时登记"，多数店有记录才算数。

### 反例：切换窗口的并发复现

教学验证（哨兵环境）：A 获锁后立即 `DEBUG SLEEP` 阻塞主库触发切换（或手工 failover），B 在新主获锁。预期：A 的锁未复制到新主，B 获锁成功，A、B 同时认为自己持锁——互斥假设在切换瞬间失效。实验需隔离环境，可复跑。

### 取舍：Redlock、单主锁与资源端栅栏的选择

单主 Redis 锁：效率层首选（简单、快），接受切换瞬间的互斥缺口；Redlock：互斥强度升级但复杂度与争议并存——需要 N 独立实例与故障场景论证；资源端栅栏（fence token）：唯一提供正确性保证的层。组合：Redis 锁挡住 99% 的并发（效率），栅栏挡住最后 1%（正确）——分层各管各的。

## 案例

### 对照操作：切换窗口的量化观察

教学验证：A 获锁 → 触发 failover → B 尝试获锁 → 记录 A、B 的持锁时间线。预期：两实例的重叠持锁窗口可观测（秒级）。再把资源端加栅栏复测，旧令牌写入被拒。实验需专用环境、可复跑。

### 追问：为什么"等复制完成再加锁"不是好方案

WAIT 命令可等待从库确认复制——把锁写入的可见性从异步变同步，代价是每次加锁多一次跨库等待（可用性绑定复制链路）；且 WAIT 只保证"已发送到从库"，不保证切换时新主恰好是那个从库。等待复制是缓解不是根治——根治仍是资源端裁决。

## 总结点

1. 异步复制，锁可切换蒸发
2. Redlock 加多数派，不解决假死
3. 效率锁在 Redis，正确性在资源端
