## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银故障沙盘:连接池 100 连接全忙,接口全线超时——止损顺序:先看连接在等谁(活跃连接的 SQL/耗时),慢 SQL 则 kill 慢查询+收紧超时,下游慢则收紧应用侧超时与池,流量型则限流——池打满是症状,止血要针对"连接被谁占着"。

1. 诊断三问:活跃连接在执行什么(慢 SQL/长事务/等待锁——show processlist/pg_stat_activity)、等待方是谁(应用线程排队年龄,Q9)、总量是否被业务增长超过(流量型)——三问定位"占着连接的元凶";长事务(事务内远程调用,network Q14:2 秒远程=连接被占 2 秒)是常见元凶。
2. 止损动作按元凶:慢 SQL→kill 慢查询(立即释放连接)+应用侧 statement timeout 收紧;长事务→拆事务(远程调用移出,该改动紧急发布)或 kill 挂起会话;锁等待→kill 阻塞源头;流量型→应用限流(池按容量配额)+扩容连接(慎重,数据库总连接数上限)。每步释放的连接数可观测(止血效果实时可见)。
3. 预防配对:池参数与 DB 容量匹配(应用实例数×池大小<数据库 max_connections——Q14 扩容加重的教训)、超时三件套(获取连接超时/语句超时/事务超时,全部显式配置)、慢 SQL 监控与治理常态化(network Q14 连接占用时长分布)。

## 参考分析

### 机制:连接占用与池动力学

连接占用时长=事务/语句执行时长;池耗尽的动力学:占用时长膨胀(慢 SQL/长事务)→周转率降→吞吐降→排队——与 Q9 线程池的"时长型"同构,元凶在 SQL 层;止损的本质=缩短占用(kill/超时)或减少并发(限流),扩容(加连接)只在"占用时长正常+流量增长"时有效——诊断决定动作,again。

### 反例:连接池打满的三种事故

事故一:加连接缓解慢 SQL——连接 100→300,数据库 CPU 与锁竞争更重,全库恶化(Q14 场景);kill 慢 SQL 才对。事故二:事务内远程调用常态化——每次调用占用连接 2 秒,峰值期池必然打满(network Q14 的架构债);拆事务。事故三:获取连接超时未配置——应用线程无限等待连接,线程池也跟着打满(两个池连环);borrowTimeout 必配。

### 取舍:池大小的权衡

大池(高并发):DB 上下文切换与锁竞争加剧(每个连接是 DB 进程/线程);小池:排队多(年龄涨);经验起点=核数×2+磁盘数(PostgreSQL 社区)或按 DB 容量反推——池大小是"DB 视角的并发预算",与 Q48 容量估算联动。

## 案例

### 验证:连接占用的实测证据(交叉引用)

network Q14 架构推演+Q3 拒绝形态:
~~~
network Q14:事务内 HTTP 2 秒→连接占用 2 秒→并发 500=1000 秒总占用——池耗尽(推演)
network Q3:拒绝 ConnectException 17ms(显式快速失败的形态)
D3:慢任务塞满共享池,快任务排队 967ms(时长型同构)
~~~
验证:"先看连接在等谁"的诊断序与时长型元凶(长事务/慢 SQL)的处置(kill/收紧超时)在既有实测形态上成立;数据库侧细节(processlist)按 DB 语义推演并明示。

### 追问链:连接池三刀

一刀:与 Q9 的衔接——池打满+线程池打满是连环(线程等连接),两层的排队年龄都要看。二刀:只读分流——查询走只读副本(独立池),写池不被读挤占(与 Q3 一致性分档衔接)。三刀:连接池监控——活跃/等待/获取耗时分布三指标常态化,打满前的趋势(获取耗时 P99 抬头)比打满更早暴露。

## 总结点

1. 先问连接在等谁
2. 长事务是头号元凶
3. 池大小是数据库预算
