> 场景与约束：网银商户信息沙盘:商户缓存按需加载从不淘汰,运行两周后 Full GC 频率逐日上升。给出从怀疑到确认到分级的完整定位手法,并说明为什么"没上限"比"没有淘汰"更隐蔽。

1. 确认信号三件套:老年代基线随时间单调抬升、Full GC 后高位横盘、jmap -histo 里业务缓存键值类型名列前茅。
2. 定位到持有者:支配树找到 static 集合入口,或直接在代码里检索 static Map/List 与 @Component 里的容器字段。
3. 分级治理:加 TTL/容量上限是止血,接 Guava Cache/Caffeine 的过期加权重是标准解,批注易混淆点——弱引用不能替代淘汰策略。

## 参考分析

### 第二步扩展① 机制:无上限缓存的泄漏画像

- static Map 的键被 GC Roots 持有,值连带可达,永久晋升老年代。
- 画像特征:每次 Full GC 后基线都比上一次略高(回收不掉的底座在长大),间隔越来越短。
- 与"有上限但淘汰策略错"的差别在于:后者曲线锯齿状(到上限触发清理),前者单调上升无锯齿。
- 实证口径:代理实验显示不保活的代理类会被卸载——反证 static 集合保活是一切的前提条件,持有者不断,GC 永远不回收。

### 第二步扩展② 边界:三类容易误判的相邻现象

- 其一,类加载器泄漏也会让"类与字符串"堆积,直方图上 Class 与 String 打头,别急着怪缓存(见第 14 题)。
- 其二,JIT 与元空间增长是正常开销,有上限(Metaspace 64MB 保留/实际提交按需),增长会停滞,泄漏是永不停滞。
- 其三,堆外与直接内存不进堆直方图,若 BufferPool 指标同步增长,是另一类问题(见第 17 题)。
- 三者的共同点是都会表现为"内存涨",差异在涨的位置与口径。

### 第二步扩展③ 取舍:止血、标准解与反模式

- 止血:给 Map 加容量检查,超限告警或拒绝写入,一行代码当周可上。
- 标准解:Caffeine maximumSize/expireAfterWrite,淘汰策略与业务时效对齐,网银商户信息适合写后 10 分钟过期加重载。
- 反模式:用 WeakHashMap 当缓存——键的弱引用让回收时机不可控,值若引用键还会整体失效。
- 也别依赖 System.gc 定时清理,那是把不确定行为当设计。

## 案例

### 第三步发散·验证与推演 实证:保活与卸载的对照(定位逻辑的锚点)

- 本机实验(Java 17.0.17):200 个动态代理对象存入 List 保活,GC.class_histogram 显示 200 个 $Proxy 类在册(总 Class 实例 2958)。
- 同程序不保活时这些类从直方图消失。
- 推演到缓存泄漏:static List 相当于这里的 keep 列表——持有者不断,直方图与支配树就能看到整棵保留树。
- 验证:把保活列表置 null 后触发 GC,直方图行数回落,对应到业务就是"删除引用即释放"。

### 第三步发散·追问扩展 追问链:缓存泄漏三刀

- **Q1：为什么 Full GC 不回收?**
  - 答：可达性分析判定 static Map 仍可达,回收器无权回收,这是设计而非缺陷。
- **Q2：怎么在线上无 MAT 时快速确认?**
  - 答：jcmd GC.class_histogram 看业务类型排名加 jcmd VM.uptime 对比多时点直方图差量,类型实例数只增不减即高嫌疑,再回代码查 static 容器。
- **Q3：上限设多大?**
  - 答：按业务有效集规模(如活跃商户数)乘安全系数,并用预发同型流量压测验证淘汰行为;上限不是拍一个 10 万,而是让过期曲线与业务失效曲线对齐。

## 总结点

1. 基线抬升无锯齿,就是没上限
2. 直方图找类型,支配树找主人
3. 弱引用不淘汰,上限才是解
