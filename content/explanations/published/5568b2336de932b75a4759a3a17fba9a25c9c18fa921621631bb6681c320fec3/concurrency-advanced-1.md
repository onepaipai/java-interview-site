## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17。以一个基于 AbstractQueuedSynchronizer 的独占锁为例，讨论同步状态的含义、竞争失败后的排队与释放后的唤醒；不把某个 JDK 版本的私有节点字段当作 API 契约。

1. AQS 提供状态读写与排队协作框架，具体同步器必须定义状态代表什么，以及线程何时可以获取、何时可以释放；AQS 不替锁或信号量决定业务语义。
2. 获取失败的线程进入等待队列，释放方改变同步状态并促使等待者重新竞争。被唤醒不等于一定获得资源，线程必须重新检查获取条件。
3. 实现时要证明状态转换与可见性正确，并覆盖中断、超时、重入或共享传播等适用语义；验证应检查互斥/许可不变式和进展，而不是依赖内部队列字段。

## 参考分析

### 第二步扩展① 状态是协议，不是“锁定标志”的通用含义

- AQS 的同步状态由子类约定。
- 例如独占锁可以把 0 表示未持有、正数表示重入次数，并另行记录持有者。
- 信号量可把状态解释为剩余许可数。
- 框架通过 tryAcquire/tryRelease 一类钩子询问子类是否成功，状态的合法范围、溢出处理和所有权校验都属于同步器自己的协议。
- 状态读写通常需要原子操作与适当的内存可见性。
- 若状态显示已释放却没有发布临界区写入，等待线程即使成功获取也可能看不到前一持有者的数据。
- 因此正确性不止是 CAS 是否成功，还包括释放与获取之间的 happens-before 关系。
- 类比停车场的车位协议：地锁状态只表示有无车，进出规则与叫号顺序是另一套约定——AQS 的 state 与队列正是这两层的分工。

### 第二步扩展② 队列负责等待协调，不能把唤醒当作交接所有权

- 竞争失败时线程可入队并停车，释放时框架推进等待者重新尝试。
- 唤醒可能与新到线程竞争，条件也可能被其他线程改变，所以等待者必须循环检查获取条件。
- 这也是锁实现不能只“signal 一次就认为资源归我”的原因。
- 取消、中断、超时以及队列头推进都需要与再次竞争协调。
- AQS 支持独占与共享两类获取方式，并支持条件队列与同步队列之间的转换。
- 具体公平性由子类的获取判定决定：即使采用公平策略，也要区分排队顺序承诺和操作系统调度，不应声称每个线程都能在固定时间内完成。

### 第二步扩展③ 工程取舍：复用框架前先写清进展与取消语义

- 自定义同步器适合状态机明确且需要与 Java 锁工具协作的场景。
- 若普通 Lock、Semaphore 或 CountDownLatch 已表达需求，复用标准实现通常更容易审查。
- 新增同步器需要明确重入、所有权、共享许可、条件等待、取消和序列化等行为，否则“能跑通一次”不足以构成正确实现。
- 实现细节会随 JDK 演进。
- 源码可帮助理解某版本如何避免丢失唤醒或处理取消，但节点字段、排队算法和内部方法不是应用应依赖的稳定契约。
- 接口语义以目标 JDK API 与规范为准。

## 案例

### 第三步发散·验证与推演 验证互斥协议：不能只用吞吐测试

- 教学测试实现一个独占同步器，让多个线程在临界区递增共享计数并记录同时进入人数。
- 预期同时进入人数最大为 1，所有线程正常结束后计数等于成功进入次数。
- 再注入获取线程中断、等待超时及持有者错误释放，验证等待者能退出、状态不会被错误清零。
- 可用 jcstress 风格测试检查可见性与竞争交错，并用线程转储/队列指标观察阻塞。
- 这只是测试设计，不代表本项目已运行 jcstress 或证明所有调度下无饥饿。

### 第三步发散·追问① 故障推演：释放与入队交错时检查丢失唤醒

- 安排线程 A 持有资源，线程 B 获取失败后准备入队，线程 A 在 B 停车附近释放。
- 反复施加屏障或压力，检查 B 不会在资源已空闲时永久停留。
- 正确实现必须使“检查失败—登记等待—停车”与释放方的状态变化协同，最终让等待者再次检查条件。
- 验收证据应包括受控交错、超时上界与线程状态。
- 单次成功日志无法证明不存在丢失唤醒。
- 性能评测还需在同一 JDK、硬件和竞争分布下比较标准锁，避免把教学计数器结果当成线上延迟结论。

## 总结点

1. 先定协议再排队，唤醒不等于得锁
2. 子类定义状态协议与获取条件
3. 排队唤醒后仍要重新竞争
4. 验证安全性也验证进展边界
