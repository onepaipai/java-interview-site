## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银发版事故沙盘:同一版本里既删列又上新代码——旧实例还在读那列,滚动发布期间 502 风暴;兼容式演进(expand-migrate-contract)让每个时刻的「代码×表结构」组合都合法。

1. 核心约束:滚动发布期间,新旧代码同时运行,共用同一个表结构——任何一步必须同时兼容新旧代码;「删列+新代码」一步到位=旧代码 SELECT 该列报错(不兼容);正确顺序=扩(加列,新旧都无感)→迁移(数据回填)→切换(新代码用新列)→收缩(确认全部实例新版后删旧列)——四步各自兼容。
2. expand-migrate-contract 三段:Expand=加列/加表/加索引(对旧代码透明——新列可 NULL 有默认);Migrate=双写(新列与旧列同步写)+回填(历史数据刷新列,分批,第 41 题批量纪律);Contract=停用旧列(代码不再读写)→观察期→删除(最后的破坏性动作,唯一需要「全部实例已升级」保证的步骤)。
3. 反向操作(删列/改类型/收窄)的危险清单:删列(旧代码读报错)/NOT NULL 收紧(旧代码插 NULL 失败)/改列类型(隐式转换变化)/收窄长度(旧数据截断失败)——破坏性变更必须排在「全部实例已确认新版」之后;发布顺序的纪律=「表结构领先代码半步,落后代码一步」。

## 参考分析

### 第二步扩展① 机制:双写窗口的兼容性保证

- 迁移段的本质=新旧两套 schema 表示并存(旧列+新列同真值)——双写让任意一侧升级都不丢数据(新代码写两列,旧代码读旧列)。
- 回填把存量拉齐后,「真相源」从旧列切到新列(读切换)。
- Contract 阶段的「观察期」=读已切但列还在(回滚空间)。
- 每一步都可独立回滚(除了最后的 DROP——它是唯一不可逆的,所以放最后且要全量确认)——兼容性设计的本质=把不可逆动作挤到序列末端。

### 第二步扩展② 反例:发布顺序的两种事故

- 事故一:删列与新代码同版发布——滚动中旧实例 500。
- Expand-Contract 拆四步。
- 事故二:NOT NULL 收紧先于代码适配——旧代码插 NULL 失败。
- 收紧=Contract 末段(代码先适配)。
- 事故三:双写期不同步(只在新代码路径双写,定时任务/老路径单写)——回填后又分叉。
- 双写要覆盖全部写路径(审计写入口)。

### 第二步扩展③ 取舍:四步纪律的成本与简化

- 小表/低风险:两步(加列+代码切换+下版删列)可压缩。
- 大表加列:8.0 INSTANT(秒级)让 Expand 免费。
- 回填大表:分批(第 41 题)。
- 观察期时长=一个完整发布周期+监控无异常。
- 纪律的成本换来「任意时刻可回滚」——发布顺序是 schema 演进的护栏。

## 案例

### 第三步发散·验证与推演 验证:兼容断言组(本机可复跑)

- 验证:不兼容复现(删列+旧代码 SELECT 报错——事故演示)。
- 四步走断言(Expand(旧代码无感)→双写数据一致→切换读新列→删旧列,每步新旧代码均正常——兼容性矩阵)。
- 回填断言(分批回填的双列一致校验)。
- 回滚断言(每一步的回滚路径(切回旧列)可用)。
- 观察期断言(读已切、列未删期间旧数据不写入新列的漂移检测)。
- 预期:四步各步兼容可验。

### 第三步发散·发散要点 追问链:演进三刀

- **追问①**：与迁移工具的配合——Liquibase/Flyway 的 precondition/标签按环境分步执行(第 44 题追加版本);
- **追问②**：API 的同型纪律——接口字段废弃的 deprecation 流程(第 150 题版本兼容)——「先兼容后收缩」是 schema 与 API 共用的演进模式;
- **追问③**：数据回填的批量纪律(第 41 题)+监控(双写一致率指标)——Expand-Migrate 段的可观测性决定切换信心

## 总结点

1. Expand→Migrate→Contract,不可逆放最后
2. 双写覆盖全部写路径
3. 表结构领先代码半步
