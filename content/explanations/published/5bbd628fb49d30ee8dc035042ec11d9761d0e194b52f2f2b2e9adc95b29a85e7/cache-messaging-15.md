## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 7 教学场景：内存未达 maxmemory 但 key 查不到（过期删除），或内存打满后 key "莫名消失"（内存淘汰）。区分两种删除机制的触发时机、执行方式与对业务的不同含义。

1. 过期删除：针对设置了 TTL 的 key，到期后由三种策略组合清除——惰性删除（访问时检查）、定期删除（周期抽样清理）、主从由主库删除后同步 DEL 到从库。它回答"到期的 key 何时真正消失"。
2. 内存淘汰：内存达到 maxmemory 后触发的腾空间行为，按 maxmemory-policy 策略选 victim（noeviction/所有 K 系/LRU/LFU/random/按 TTL）——淘汰的对象不限于有 TTL 的 key，常驻 key 也会被逐。
3. 业务含义不同：过期删除是"预期内的数据生命周期"（TTL 到了本来就该消失）；内存淘汰是"资源压力下的意外损失"（没设 TTL 的关键数据也可能被逐）——监控与告警的口径因此不同。

## 参考分析

### 机制：一个是"闹钟到点"，一个是"房间腾地"

过期删除像食品保质期：到点下架（惰性检查+定期巡检）；内存淘汰像货架满了必须下架一些商品腾位子——下架谁由策略（LRU 最久未动/LFU 最少访问）决定，与保质期无关。两者可以叠加：一个有 TTL 的 key 也可能在到期前被内存淘汰提前逐出。

### 反例：noeviction 下写入失败的连锁反应

策略为 noeviction（默认）且内存打满：所有写命令返回 OOM 错误——缓存层的写失败如果没有降级（应用把缓存写失败当致命错误），业务跟着失败。而 allkeys-lru 下写成功但可能逐掉热点 key。两种策略对应两种故障形态——策略选择就是选择"失败的方式"。

### 取舍：淘汰策略的选择框架

纯缓存（可重建）：allkeys-lru/lfu——逐谁都行，命中率优先；缓存+部分常驻数据（不允许逐）：volatile-lru + 常驻数据不设 TTL——但风险是 volatile 集合满后仍可能逐常驻键；持久化数据（Redis 当主存）：noeviction + 容量监控告警——宁可写失败也不静默丢数据。策略跟"数据能否丢失"走。

## 案例

### 对照操作：两种删除的现场区分

教学验证：设置 TTL 的 key 到期后 EXISTS 为 0（过期删除）；打满内存后未设 TTL 的 key 消失（内存淘汰，allkeys-lru）。用 `INFO memory` 的 evicted_keys 计数区分两者——计数增长说明在内存淘汰，业务要警觉。实验可复跑。

### 追问：为什么过期删除要用"惰性+定期"组合而不是纯定时

纯定时需要为每个 key 维护精确定时器（百万级 key 的定时器开销巨大）；惰性（访问时检查）漏掉"再也没被访问的 key"，定期抽样补漏——组合以极低成本逼近全量及时清除。这个"成本与及时性折中"的设计思想，在第 5 题 TTL 抖动、第 3 题逻辑过期中反复出现。

## 总结点

1. 保质期到点下架，货架满逼下架
2. evicted_keys 增长即警觉
3. 策略选择=选择失败方式
