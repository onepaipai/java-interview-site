## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Caffeine + Redis 教学场景：L1 本地缓存 + L2 Redis 组合后，节点间看到不同版本的数据。分析两层缓存的一致性代价（失效广播的到达延迟、节点时钟差），给出按"可容忍陈旧度"的分层设计。

1. 代价的结构：L2（Redis）删除/更新后，各节点的 L1（本地缓存）不知道——每个节点的 L1 独立过期，节点间数据版本不同。失效广播（pub/sub 或消息）能通知，但到达有延迟且不保证送达（离线节点错过消息）。
2. 一致性的现实上限：L1 + 失效广播的最坏不一致 = 广播延迟 + 未送达节点的 TTL 时长——这个上界无法归零（除非 L1 不缓存会变的数据）。
3. 分层设计：L1 只放"变化极少或可短暂陈旧"的数据（配置、字典、商品详情的展示字段）；变化敏感数据（库存、余额）直达 L2 或不走缓存；L1 TTL 压短（秒级）+ 广播失效 + 发布时主动 evict 本地。

## 参考分析

### 第二步扩展① 机制：L1 让"一致性的控制面"从 1 层变成 N+1 层

- 只有 L2 时，删除 Redis 即全网一致。
- 加了 L1，每个实例多了一份需要失效的副本——失效要到达 N 个节点。
- 类比总部改价（L2）与各分店价签（L1）：改价传单要送到每家店，送达前各家价签不一。
- 节点数越多，"全网同价"的窗口越长。

### 第二步扩展② 反例：广播失效的两个漏网场景

- 一，节点 GC 停顿或网络抖动错过 pub/sub 消息（订阅不是持久订阅）——该节点的 L1 旧值存活到 TTL。
- 二，广播顺序与写入顺序不一致（消息分区并行）——旧失效覆盖新失效。
- 修复：L1 条目带版本（与 L2 对齐，见 cache-messaging/2 的版本协议），TTL 兜底不可省略。

### 第二步扩展③ 取舍：L1 的容量与 TTL 的乘法

- L1 的价值 = 命中率 ×（省下的 Redis 往返）。
- 成本 = 不一致窗口 × 影响面。
- TTL 秒级的 L1：命中率略降（过期频繁）但不一致窗口受控。
- TTL 分钟级的 L1：命中率高但不一致窗口拉长。
- 按数据的"陈旧容忍秒数"反推 TTL——容忍度是业务属性，不是缓存参数。

## 案例

### 第三步发散·验证与推演 对照操作：节点间不一致的观测

- 教学验证：两节点 L1 各缓存同 key，节点 1 更新 L2 并广播失效。
- 观察节点 2 的 L1 旧值存活到 TTL。
- 预期：节点 2 在 TTL 内读到旧值、节点 1 立即新值——节点间不一致被直接观测。
- 实验可复跑。

### 第三步发散·追问① 追问：为什么"L1 不缓存会变的数据"是终极解法

- 失效广播、版本比较、TTL 都在缩短不一致窗口，但无法归零（网络与调度有下界）。
- 把"会变的数据"移出 L1，L1 只留真正静态的内容（配置、白名单）——不一致问题从根上消失，代价是这些数据每次读走 Redis（Redis 单次往返微秒级，多数场景可接受）。

## 总结点

1. L1 让失效从一层变 N+1 层
2. 广播有漏网，TTL 是下界
3. 会变的数据不进 L1
