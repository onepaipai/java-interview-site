## 参考回答

<!-- explanation:deep -->

> 场景与约束：知识助手沙盘:团队在 Spring Boot 3 + Spring AI 1.x 项目里评估用 ChatClient 封装模型调用；需要说明框架带来的抽象、版本边界与什么时候该绕过抽象。

1. ChatClient 把提示、模型选项、工具调用与响应映射封装成流式 API，减少重复的 HTTP/SSE 解析与 JSON 绑定代码。
2. 抽象便于切换模型供应商，但"可切换"不等于零成本:不同厂商的流式事件、工具调用格式与错误码仍有差异，要做兼容测试。
3. 当需要对超时、分帧、取消、计费细节做精确控制，或框架版本暂不支持某能力时，保留直接调用路径，不要把"全量套框架"当目标。

## 参考分析

### 第二步扩展① 机制:框架封装了哪些重复劳动

- 直接调用模型 REST API 要自己处理鉴权、SSE 分帧、增量拼接、工具调用的参数解析与错误重试。
- ChatClient 把这些做成一致的调用链，并配合 Advisor 机制做检索增强与记忆。
- 类比网购:直接调 API 像自己联系工厂发货，框架像平台下单——省事，但退换货规则仍要看平台条款。

### 第二步扩展② 边界:抽象层不会消灭模型差异

- Streaming 的结束标志、工具调用的增量片段、token 计量与限流响应，不同供应商有差异。
- 框架版本升级也可能改变默认行为。
- 切换模型或升级 Spring AI 时，用固定评测集核对输出结构、流式事件和错误映射，不能只因为接口编译通过就认为等价。

### 第二步扩展③ 取舍:核心链路与边缘链路

- 流式输出、提示模板和工具编排适合用框架提高开发效率。
- 涉及合规、精确计费、极端延迟优化的链路可以保留直接调用。
- 关键是统一超时、取消、审计与密钥管理口径，避免两套实现两套安全标准。

## 案例

### 第三步发散·验证与推演 验证:兼容性的推演

- 教学验证:同一组提示在两个模型供应商上分别用 ChatClient 调用，断言流式片段拼接后的最终文本、工具调用参数结构、错误响应分类一致。
- 记录差异清单。
- 这是验证设计，不代表本项目已完成双供应商实测。

### 第三步发散·追问① 追问:Spring AI 版本怎么讲

- Spring AI 1.x 适配 Spring Boot 3。
- 后续 2.x 随 Spring Boot 4 演进。
- 回答要按项目实际使用的 Boot 与 Spring AI 版本核对官方文档，不要混用不同大版本的 API。

## 总结点

1. 框架省样板，差异仍需测
2. 流式与工具按版本核对
3. 核心链路可绕开抽象
