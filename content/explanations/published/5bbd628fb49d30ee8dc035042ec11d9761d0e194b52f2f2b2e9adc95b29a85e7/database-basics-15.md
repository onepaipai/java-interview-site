## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 教学设计：租户订单按 created_at DESC、id DESC 排序，多个订单创建时间相同。游标保存上一页最后一行的时间和 ID，并固定查询过滤条件。

1. 排序组合要构成稳定且唯一的全序，时间可能重复时增加 ID 等稳定决胜字段；游标携带完整位置，下一页谓词与排序方向一致。
2. 游标还需绑定租户、过滤和必要版本，服务端继续验证授权；位置不是快照，跨请求并发插入、删除或排序字段变化仍可能影响可见结果。
3. 选择匹配访问模式的索引，并定义正反向翻页、空值和边界规则。游标擅长连续翻页，不天然提供任意页码跳转或固定时点快照。

## 参考分析

### 唯一顺序：只保存时间会漏掉并列记录

当多行 created_at 相同，下一页只写 created_at 小于上一页时间，会跳过同一时间剩余行；写小于等于又可能重复。用时间与 ID 的字典序形成唯一位置，下一页同时比较两个字段。排序列为可变值或可空值时，还要额外定义移动与空值次序，不能把增加一个 ID 当成全部分页问题解决。类比按出生时间加姓名排座位：只按时间排，同一秒出生的人无法定序——唯一化补列让每个位置都唯一可达。

### 查询契约：位置属于一组固定条件

同一个位置在不同租户、状态和排序模式下没有相同含义，游标应携带或绑定这些条件并防止任意修改，服务端仍执行资源授权。不要让客户端提供游标就跳过租户过滤。签名游标只能限制篡改，不能让已失效权限继续有效，也不能替代数据库里的访问条件。

### 并发可见性：连续翻页不等于历史快照

每次 HTTP 请求一般有不同事务，新增更靠前的行可能不进入后续页，删除会改变剩余集合，更新排序键还可能造成跨页移动。应按产品说明允许的语义；需要一致导出时考虑明确快照或物化结果，并评估长事务成本。索引是否高效也应通过实际计划验证，不能从结果正确推断性能已证明。

## 案例

### 完整 SQL：同时间记录按 ID 继续翻页

以下会话临时表只用于教学，当前游标为时间 10:00:00、ID 4，下一页预期返回 ID 3、2，排除另一租户。项目将原样执行这段 SQL 核对结果；H2 的结果仅证明此样本的排序和过滤，不证明 MySQL 的索引计划。

~~~sql
CREATE TEMPORARY TABLE cursor_example (
  tenant_id INT NOT NULL, id BIGINT PRIMARY KEY,
  created_at TIMESTAMP NOT NULL, title VARCHAR(30) NOT NULL
);
INSERT INTO cursor_example VALUES
  (7, 4, '2026-10-01 10:00:00', 'four'),
  (7, 3, '2026-10-01 10:00:00', 'three'),
  (7, 2, '2026-10-01 09:00:00', 'two'),
  (7, 1, '2026-10-01 08:00:00', 'one'),
  (8, 8, '2026-10-01 09:30:00', 'other tenant');
SELECT id FROM cursor_example
WHERE tenant_id = 7 AND
  (created_at < '2026-10-01 10:00:00' OR
   (created_at = '2026-10-01 10:00:00' AND id < 4))
ORDER BY created_at DESC, id DESC LIMIT 2;
~~~

### 追问：翻页之间新增和修改记录

在第一页后插入更早和更晚的记录，并修改一行排序字段，检查产品约定下哪些应出现、哪些可能移出后续范围；再测试游标被用于另一租户或筛选。预期边界和授权清晰，不能宣称这个样本已经保证并发期间绝无遗漏或重复。索引、反向翻页及空值策略要另有目标数据库测试。

## 总结点

1. 时间加姓名，位置才唯一可达
2. 唯一排序和完整位置配套
3. 游标绑定查询但不代替授权
4. 跨请求位置不等于一致快照
