## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB 教学场景：订单表要加 `refund_status NOT NULL DEFAULT 0`，直接执行风险不明。设计分步方案：瞬时加列、默认值语义、存量回填与最终收紧的完整流程。

1. 首选单步：8.0+ 的 ALGORITHM=INSTANT 加列只改元数据（秒级），新行用默认值，旧行读取时按默认值补齐——逻辑上等价于"已有 NOT NULL DEFAULT"。执行前核对 instant 支持矩阵与表状态（无全文索引冲突等）。
2. 需要回填的变体：默认值 0 不能表达业务语义（如要按已有订单推导状态）时，分三步——INSTANT 加列为可空或带中性默认 → 低峰分批回填（UPDATE ... LIMIT 循环，观察主从延迟）→ 校验全量完成后收紧为 NOT NULL（收紧是又一次 DDL，走第 17 题的守护流程）。
3. 禁止事项：禁止在业务高峰对大表直接 UPDATE 全量回填（一条语句一个巨型事务，undo 膨胀、复制串行化，见第 40 题）；禁止"先 NOT NULL 后补默认值"的顺序（存量行无值可填）。

## 参考分析

### 机制：默认值是"读取时补齐"的元数据语义

8.0 的 instant 加列把默认值记在元数据里，旧行物理上没有这个字段，读取时按元数据补齐——这就是它能秒级完成的原因。类比新表格加一栏：旧档案不必每页重印，查阅时按规则补看这一栏。理解"补齐语义"才能解释为什么加列便宜、回填另算。

### 反例：一次性回填的三重伤害

一条 UPDATE 3000 万行：一，巨型事务持有行锁数小时，业务写入排队；二，undo 膨胀挤占回滚段；三，binlog 单个大事务阻塞复制回放，主从延迟小时级。分批回填（每批 5000 行 + 间隙观察延迟）把三个问题都摊薄——批大小是杠杆，配合监控调节。

### 取舍：NOT NULL 收紧的时机

回填完成且校验通过（无 NULL 残留、业务双写验证新值写入正确）才收紧；过早收紧会因回填未完成而失败甚至阻塞。收紧的 DDL 走第 17 题守护流程；收紧后应用代码同步改为"不再容忍 NULL"——数据库约束与应用版本要一起发布。

## 案例

### 对照操作：分步回填的延迟曲线

教学验证：300 万行测试表回填，对比单条全量 UPDATE 与分批（5000 行/批 + 从延迟阈值控制）两条路径。预期：前者复制延迟小时级且业务写阻塞；后者延迟受控、总时长接近。曲线并排，实验可复跑。

### 追问：为什么新行不用回填

新行由业务代码显式写入默认值 0（应用已发版），或依赖列默认值兜底——回填只服务于"存量行"。把"新行"与"存量"分开治理，回填的范围从"全部"缩到"历史"，工作量与风险同步缩小。范围缩小后，回填脚本也简化为按主键区间推进的单遍任务，不再需要复杂的状态管理。

## 总结点

1. 加列 instant 秒级，回填另算
2. 分批加限速，盯主从延迟
3. 回填校验后才收紧 NOT NULL
