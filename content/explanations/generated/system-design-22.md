## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银缓存平台沙盘:营销活动把共享 Redis 的内存与连接打满,交易缓存的读写全被拖慢——全局缓存平台必须"配额+隔离+治理":按业务分集群/分池、内存与 QPS 配额、键规范与淘汰策略(cache-messaging 批次的击穿/雪崩/穿透治理在此平台化)。

1. 隔离模型:物理隔离(核心交易缓存独立集群——大促营销不碰交易)、逻辑隔离(同集群分 DB/前缀+内存配额)、代理层隔离(统一入口做配额与审计,直连禁止);隔离级别按业务风险定——交易类物理隔离是底线。
2. 配额治理:内存配额(超限拒绝写入+告警,防止一个业务挤占全局)、QPS 配额(代理层限流,与 Q7 多配额模型同构)、键 TTL 规范(禁止永久键,默认 TTL 上限)、大键扫描(超大 value/热 key 自动发现)——治理让"平台"可持续而不是"共享 Redis 大杂烩"。
3. 故障与恢复:单业务击穿(热 key 失效打穿)限制在该业务配额内(singleflight 合并回源,distributed D6/D10 实测:200 并发回源 200 vs 合并后 1)、雪崩防护(过期时间加随机)、集群故障降级(缓存不可用时业务降级读库的预案与限流,防 DB 被打垮)。

## 参考分析

### 机制:配额与热 key 治理

代理层(如 Codis/自研 proxy)按"业务 ID+键前缀"统计内存与 QPS,配额超限的写入返回错误(业务降级到本地缓存/DB);热 key 发现:按 key 维度的 QPS 排名,超阈值的热 key 自动本地副本(应用内缓存兜一层);击穿治理=代理层 singleflight(同 key 并发回源合并)——分布式批次的实测数字直接复用。

### 反例:缓存平台的四种事故

事故一:无配额共享——营销活动写入 20GB,交易缓存的键被驱逐(内存挤占),交易变慢;配额硬限制。事故二:热 key 无感知——明星商品 key QPS 5 万打满单分片;热 key 自动副本。事故三:永久键堆积——写入无 TTL,内存慢性增长到 OOM;默认 TTL+审计。事故四:直连绕过代理——业务为省事直连 Redis,配额与审计全失效;网络策略强制走代理。

### 取舍:统一平台 vs 业务自建

统一平台:治理与隔离好,建设成本高;业务自建 Redis:灵活但失控(配额/规范/运维分散)。折中:核心平台(交易/会话)+白名单自建(特殊场景申请,仍接入监控)——平台的边界按"多少业务需要强制治理"画。

## 案例

### 验证:击穿治理的实测证据(交叉引用)

distributed 批次 D6/D10 实测:
~~~
200 并发同键回源:无合并 200 次后端调用,singleflight 1 次
过期写(v1 覆盖 v2):带版本检查拒绝
~~~
cache-messaging 批次补充穿透/雪崩治理(布隆/随机 TTL);推演核对:配额隔离与 Q7 限流平台的配额模型同构;验证:隔离(配额)+治理(热 key/击穿)的平台化结论在既有实测上成立(明示:缓存平台行为未实测)。

### 追问链:缓存三刀

一刀:与 Q3 一致性分档的衔接——缓存一致性(失效策略)在平台层提供选项(写失效/短 TTL/版本仲裁),业务按档选。二刀:多级缓存的一致性——本地缓存(L1)+全局缓存(L2)的失效广播(版本号/ Pub-Sub 失效),本地缓存 TTL 短兜底。三刀:与 Q49 数据增长的衔接——键规模十倍时的分片扩容(一致性哈希,distributed D13 实测迁移 19%)是缓存平台的容量预案。

## 总结点

1. 交易缓存物理隔离
2. 配额硬限制热 key 副本
3. singleflight 合并回源
