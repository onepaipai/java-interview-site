## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银闸机沙盘:服务 A 拿锁处理任务时发生 8 秒 GC 停顿,锁过期被 B 接管;A 恢复后继续写共享存储,把 B 已完成的工作覆盖。用栅栏令牌实验说明"锁不等于资格",资格需要单调凭证。

1. 锁的授权会过期,持有者不知道:GC 停顿、网络分区、时钟漂移都会造成"自以为还持有锁"的幽灵持有者。
2. 栅栏令牌=每次发锁时单调递增的编号:写入时携带,存储层校验"凭证不小于已见最大编号",旧凭证被结构性拒绝。
3. 实现位在存储层:存储必须校验令牌才有效;锁服务发令牌,存储层执行校验,两者配合才闭环。

## 参考分析

### 数据库条件更新:栅栏写入的唯一入口

时间线:锁 TTL 5 秒,A 持锁处理;A 第 4 秒进入 8 秒 GC;第 5 秒锁过期,B 获锁(编号+1)并完成写入;第 12 秒 A 醒来,自认仍持锁,继续写——覆盖 B 的结果。锁服务无法通知 A(它失联了),A 也无法自检(它不知道自己停了多久)。解法:锁服务每发一次锁发一个单调递增令牌(fencing token);存储层记录已见最大令牌,写入令牌小于等于已见值即拒绝。B 的令牌大于 A,A 的迟到写入必然被拒。

### 反例:没有栅栏的覆盖与有栅栏的拒绝

本机实验(Java 17.0.17,D15)两种形态对照:
```
A 获租约, 栅栏=1
租约过期后 B 二次领取, 栅栏=2
A 恢复后写入(旧栅栏1): 拒绝(栅栏1 < 当前2)
B 写入(栅栏2): 接受:B的新数据
```
若删掉栅栏检查,A 的旧数据会覆盖 B 的新数据(实验中已验证此对照)。生产对应物:ZK 的 zxid/version、数据库行版本、Kafka 事务生产者 epoch——都是"单调凭证+存储校验"的同构实现。

### 取舍:令牌校验的落地位置与成本

落地位置:数据库层(条件更新 WHERE fence >= seen)、存储服务层(元数据表记录 max_fence)、或业务状态机(阶段号)。成本:存储层要多一次版本读取与比较,写入路径多一列;换来的保证是"幽灵写入结构性不可能"。不支持校验的存储(纯 Redis SETNX 场景)需要在业务侧补版本列。评审要点:有锁无栅栏=半套方案,问问"过期持有者的写入谁拦"。

## 案例

### 实证:租约过期与栅栏拒绝(同程序重跑一致)

本机实验(Java 17.0.17,D15):2 秒租约、模拟时钟推进 3 秒、B 二次领取:
```
租约过期后 B 二次领取, 栅栏=2
A 恢复后写入(旧栅栏1): 拒绝(栅栏1 < 当前2)
B 写入(栅栏2): 接受:B的新数据
```
验证:删除栅栏检查的对照组中旧数据覆盖新数据——栅栏从"可选优化"升格为"正确性组件"的证据。存储层的栅栏写入是一条条件更新,新令牌放行、旧令牌与重复令牌一律拒绝:
```sql
UPDATE protected_resource
SET payload = :payload, fence_token = :token
WHERE id = :id AND fence_token < :token
```
对照验证:fence_token=0 时令牌 42 首次写入命中(1 行,payload 变 new);旧令牌 41 与重复令牌 42 均不满足 fence_token < :token 被拒(0 行)——栅栏语义可在任意数据库上执行复验。

### 追问链:栅栏三刀

一刀:"令牌由谁保证单调?"——锁服务自身需要单调保证(单实例自增/共识服务 epoch);若锁服务分片且各自发号,令牌可比较性被破坏——发令牌的服务本身要强一致。二刀:"只读操作需要栅栏吗?"——需要类似物:读到的数据要校验"租约是否仍有效"(lease read 的租约检查),否则读到幽灵期数据;强度要求不同,机制同源。三刀:"与第 8 题幂等键什么关系?"——幂等防"同一动作重放",栅栏防"过期资格的合法写入";一个是去重,一个是淘汰,互补不可互替。

## 总结点

1. 锁会过期,资格要凭证
2. 令牌单调,存储校验
3. 有锁无栅栏,等于半套方案
