> 场景与约束：一个订单 API 需要同时关注成功、延迟和业务正确性。设计用户级 SLI、目标窗口、分母与排除规则，并说明指标如何驱动发布和容量决策。

1. 先从用户可观察的结果定义 SLI，例如有效请求中的成功率、符合截止时间的延迟和正确完成率，而不是先选 CPU 或进程存活。
2. SLO 必须写清分母、时间窗口、请求分类、超时是否算失败及多区域聚合方式；否则百分比无法指导决策。
3. 指标要能触发行动：错误预算消耗应影响发布风险、容量和修复优先级，同时保留业务对账指标，避免把“快速返回错误”优化成好看数据。

## 参考分析

### SLI 是测量定义，不是监控名称

“可用率 99.9%”只有在分母明确时才有意义。应定义哪些请求属于用户有效请求、健康检查是否排除、客户端取消和限流如何分类、每次请求按一次还是按业务对象计数。延迟也要明确从入口接收还是用户收到响应开始，以及按哪个分位数统计。
对于订单，HTTP 200 可能只是受理，不代表扣款完成；可另设业务完成率、未知状态年龄和对账差异指标。类比体检指标：先定义血压怎么量、量几次，数值才有意义——SLI 是测量定义，监控图表只是读数。

### SLO 连接错误预算与决策

窗口内允许的失败比例形成错误预算。预算不是可以主动消耗的故障额度，而是衡量变更和稳定性投入的风险空间。快速燃烧应暂停高风险发布并先修复根因，持续低速燃烧则提示容量、依赖或设计问题。
多个用户群、区域和关键路径可能需要分层目标；整体平均值不能掩盖一个重要租户或关键支付流程已经失败。

### 可执行性来自动作和证据

每个 SLI 告警应对应负责人、排查入口、止损手段和恢复条件。指标最好能关联 trace、日志和部署版本，从症状追到具体变更；不要用单一 CPU 作为服务质量代理。
SLO 需要定期根据真实用户影响校准。目标过高会把正常尾部波动变成噪音，目标过低则无法保护体验；应结合成本、业务价值和可恢复能力。

## 案例

### 定义订单 API 的指标

按请求结果区分成功完成、确定业务拒绝、超时未知和系统错误；延迟用符合业务截止时间的请求比例并同时记录 p50/p95/p99。分母排除内部探针但保留真实限流用户，避免把拒绝从体验中抹掉。
这是指标设计示例，阈值要由业务历史和用户期待确定，不预设一个通用百分比。

### 验证发布影响

在一次隔离发布中比较版本、区域和关键接口的错误预算燃烧率、尾延迟、未知状态和业务对账。若响应率提高但未知结果或重复业务增加，发布不能判定为改善。
验收要求指标能定位到版本和请求链，并能触发回滚、限流或人工介入。

## 总结点

1. 先定怎么量，再看图表数值
2. SLI 从用户结果而非机器状态出发
3. 分母和分类决定指标含义
4. SLO 必须能触发具体行动
