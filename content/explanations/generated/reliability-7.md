## 参考回答

<!-- explanation:deep -->

> 场景与约束：线上服务 CPU 突然升高，用户错误率和延迟未知。要求先保护用户并保留现场，再区分流量、代码、锁竞争、GC、日志或下游重试造成的 CPU 上升。

1. 先确认用户影响、实例范围、流量变化和资源限制，采取可回退的止损；不要一上来重启，把线程、剖析和请求证据全部抹掉。
2. 同时关联部署版本、请求量、错误/重试率、GC、锁争用和依赖延迟，区分 CPU 是原因还是过载后的症状。
3. 止损后保留时间线和证据，再决定扩容、限流、回滚、降级或修代码；恢复验证必须看用户结果而不只是 CPU 回落。

## 参考分析

### 先判断影响范围与安全动作

确认 CPU 是单实例、单可用区还是全局上升，查看成功率、p95/p99、队列和连接池。若用户受影响，优先用已验证的摘流、限流、扩容或回滚；每个动作都记录时间和回退路径。重启会清除线程栈和 GC 状态，除非资源失控，否则应先采集最小证据。类比厨房起火先关火再查原因：先确认有没有客人被烫到（用户影响）并做安全动作，火源排查是第二步。

### CPU 高的候选根因

流量突增、热循环、序列化、日志、锁自旋、GC 频繁和下游重试都可能提高 CPU。应关联每请求 CPU、QPS、延迟、GC pause、线程状态和版本；QPS 不变而 CPU 升高更像代码或竞争，重试随错误升高则可能是故障放大。

### 证据与恢复验收

使用低开销线程采样、JFR 或 profiler 保留热点证据，注意工具开销和敏感数据。恢复要同时看 CPU、延迟、错误率、队列年龄和业务成功；CPU 降低但请求被拒绝或转移到未观测路径，不算真正恢复。

## 案例

### 现场保留演练

在隔离环境制造热循环或重试风暴，先记录线程采样、GC、请求量、版本和依赖状态，再执行摘流/限流/回滚。预期用户指标改善且证据仍可定位；这是诊断演练，不代表生产已执行。
对照重启前后证据完整度、资源释放、用户错误和恢复速度，确认止损没有把问题转移到其他实例或下游。

### 恢复追问：扩容还是回滚

对照流量突增、单版本回归和下游错误三种情况。预期流量突增可临时扩容但要确认依赖容量，版本回归优先回滚，重试风暴先切断放大源；每种动作都检查尾延迟和下游压力。
验收还要确认新实例预热不会把流量一次性推满，回滚版本的错误率和业务成功率确实改善，并保留完整的证据时间线供事后复盘。

## 总结点

1. 先关火再查源，用户影响优先
2. 先确认用户影响再止损
3. 保留现场证据后定位根因
4. CPU 回落不等于业务恢复
