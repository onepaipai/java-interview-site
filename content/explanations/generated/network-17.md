## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银行情沙盘:升级 HTTP/2 后行情推送变流畅,但单个丢包仍让所有流卡顿——HTTP/2 消除了 HTTP 层的队头阻塞(响应互相独立),却把阻塞下沉到 TCP 层(单流丢包全连接等待重传)。

1. HTTP/2 解决的层:HTTP/1.1 的队头阻塞在"响应必须按序完整交付"(pipeline 受限),HTTP/2 用流+帧把响应拆成交错帧,响应间不再互相等待——应用层队头阻塞消除。
2. 未解决的层:所有流共享一条 TCP 连接,TCP 保证字节流有序——任何一段丢失,后续已到达的数据都要等重传补齐才能交付(HOL at TCP);丢包率高时(HTTP/2 单连接)性能可能劣于多条 HTTP/1.1 连接。
3. HTTP/3/QUIC 的方案:流独立于传输层连接,QUIC 的流级有序——一个流丢包只阻塞该流,其他流继续;代价是 UDP 普及度、中间设备对 UDP 的干预与加密不可关(见 Q18)。

## 参考分析

### 第二步扩展① 机制:HTTP 层与 TCP 层的阻塞转移

- HTTP/1.1 的响应按序交付把队头阻塞留在 HTTP 层。
- HTTP/2 用流交错把应用层队头阻塞转移到 TCP 有序交付层。
- 所有流共享一条 TCP 连接和同一个拥塞窗口，一段丢失会让后续已到达的数据等重传补齐，弱网和高丢包下 H2 单连接可能劣于多条 HTTP/1.1 连接。
- HTTP/3 用 QUIC 把流级有序放到传输层，每个流只阻塞自己，但代价是 UDP 中间设备兼容性与生态成熟度。

### 第二步扩展② 反例:升级 H2 的三种事故

- 事故一:高丢包链路上单连接 H2 反而更慢——TCP 队头阻塞叠加,大文件传输吞吐劣化。
- 弱网行情推送考虑 H3 或多连接。
- 事故二:服务端推送(Server Push)滥用——推的资源客户端已有,带宽浪费,Chrome 已移除支持。
- 事故三:TCP 连接数骤降后拥塞窗口变小——单连接初始窗口慢启动,首包延迟敏感场景要调优或预热。

### 第二步扩展③ 取舍:HTTP/1.1 长连接池 vs HTTP/2 单连接

- 连接池(1.1):并行连接绕过队头阻塞,但握手/内存/端口成本随连接数线性。
- H2 单连接:复用极致,阻塞集中在 TCP 层。
- H3:流级独立,但生态与中间设备成熟度待考量。
- 按丢包率与流并发度选:低丢包高并发 H2,高丢包考虑 H3,客户端兼容优先 H2。

## 案例

### 第三步发散·验证与推演 验证:两层阻塞的推演核对

- 推演核对:本机 N1 实验证实 TCP 字节流"有序完整交付"语义(8KB 分 2 次 read,后续数据等前序)——这正是 H2 下单流丢包阻塞其他流的传输层机制。
- HTTP 层流交错按 RFC 9113 帧语义推演并明示。
- 验证:阻塞转移链条(TCP 有序是根因,H3 改流级序)成立。

### 第三步发散·发散要点 追问链:H2 三刀

- **追问①**：头部压缩 HPACK 与队头的关系——HPACK 三件套:静态表(61 个常见头预置)+动态表(连接级缓存,后续按索引引用)+Huffman 编码(字符串压缩);压缩上下文跨流共享,所以头部丢包同样阻塞解码(比数据丢包影响更大),QPACK(H3)改进为独立流,把头部解码与流级阻塞解耦
- **追问②**：流优先级——H2 可声明依赖与权重,行情场景给"价格流"高优先级,阻塞时先保关键流(RFC 9113 对优先级模型有重新设计,跨版本实现有差异)
- **追问③·与 Q9 借出失败的联动——单连接被关**：所有流一起失败,失败影响面从"一条请求"扩大到"一批请求",重试逻辑要按连接级处理

## 总结点

1. H2 消除 HTTP 层阻塞
2. TCP 有序仍是瓶颈
3. H3 流级有序收尾
