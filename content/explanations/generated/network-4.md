## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银报文沙盘:客户端连发三条消息"MSG-A|""MSG-B|""MSG-C|",服务端一次 read 读到 18 字节三条粘连;发一条 8KB 大消息却被 2 次 read 分片——TCP 只保证字节流有序不丢,从不保证"一次写对应一次读"。

1. 根因:TCP 的读写单位是字节不是消息——发送端 Nagle 合并小写、接收端缓冲区按到达顺序堆字节、MSS 分段、内核缓冲腾挪,都会让"写的边界"在读侧不可见;粘与半是同一件事的两个表象。
2. 本机实证:8KB 消息被 2 次 read 读完(半包形态);客户端延迟读取时 3 次小写被 1 次 read 读走 18 字节(粘包形态)——两种形态都在 loopback 上稳定复现,与网络状况无关。
3. 正解=应用层分帧:定长(浪费)、分隔符(如 | 或 \n,需转义)、长度前缀(推荐,变长高效)、HTTP 的 Content-Length/Transfer-Encoding 分块——边界由协议定,不由 TCP 定。

## 参考分析

### 第二步扩展① 机制:读写边界为什么错位

- 发送侧:write 只是交给内核发送缓冲,实际分段由 MSS 决定。
- 接收侧:read 从接收缓冲取字节,取多少取决于缓冲区现存量与应用缓冲大小——两侧的边界没有任何同步机制。
- 流式语义是特性不是缺陷:它让吞吐优化(Nagle/合并)成为可能,代价是消息边界上移到应用层。

### 第二步扩展② 反例:粘包的三种事故

- 事故一:按 read 次数当消息个数解析——合并时把三条当一条,报文解析错乱。
- 事故二:缓冲区小于消息——半包解析直接截断,余额字段缺尾。
- 事故三:分隔符出现在业务数据里——用 | 分隔但金额文本含 |,分帧错位。
- 三条的正解:长度前缀分帧+解析缓冲区累积(不足一帧先攒着)。

### 第二步扩展③ 取舍:三种分帧方式的选择

- 定长:解析最简单但 padding 浪费,适合固定宽度协议。
- 分隔符:可读性好但要转义与扫描,适合文本协议(日志/Redis 协议)。
- 长度前缀:解析 O(1) 支持二进制,是自定义协议的默认选择。
- HTTP 两者都用:Content-Length 定长、chunked 分块分隔。

## 案例

### 第三步发散·验证与推演 验证:粘与半的双向实证

- 本机实测(JDK 17.0.17,loopback):
~~~
java N1StreamFraming
第一次 read 返回 6 字节,内容=MSG-A|
8KB 消息被 2 次 read 分片读完(半包)

java N1bMerge
3 次写、延迟后 1 次 read 返回 18 字节,内容=MSG-A|MSG-B|MSG-C|(三条消息被一次读走=粘)
~~~
- 验证:8KB 被 2 次 read 分片(半)、3 次写被 1 次 read 读走(粘)——两种形态实测复现,读写边界错位成立,分帧必须上移到应用层。

### 第三步发散·发散要点 追问链:粘包三刀

- **追问①**：UDP 有粘包吗——没有,数据报天然有边界,代价是应用要自己处理丢包乱序(见 Q27 BIO/NIO 与 UDP 语义)
- **追问②**：HTTP 为什么感觉不到粘包——Content-Length 或 chunked 就是它的分帧协议,解析器按帧边界读,粘半在框架里已被处理
- **追问③**：长连接上分帧和短连接谁更难——短连接可以"关连接即一帧"偷懒,长连接必须显式分帧——连接复用让分帧从可省变成必需(见 Q9)

## 总结点

1. TCP 只保证字节流有序
2. 粘半是边界的两个表象
3. 长度前缀是最稳分帧
