## 参考回答

> 场景与约束：网银审计争端沙盘:created_at 是应用时间还是 DB 时间(NOW())?两台应用服务器时钟差 2 秒→流水顺序错乱——时间来源单一化(应用统一时钟或 DB 时钟)是审计可信的前提。

1. 两种来源的优劣:DB 时间(NOW()/DEFAULT CURRENT_TIMESTAMP)——单一时钟源(同库内一致)+防应用时钟漂移;但分库/多库时各库时钟仍不同源,且应用拿不到精确值(要回读);应用时间——业务语义清晰(请求到达时间/业务发生时间)+与应用日志可关联;但依赖 NTP 与服务器时钟质量。
2. 审计的真实需求=可追溯与可排序:时间戳字段分层——created_at(记录创建,应用注入+DB 兜底 DEFAULT)/业务发生时间(event_time,上游传入——支付回调里的支付时间)/DB 落库时间(DB NOW)——三时间各有用途,混用一个字段是事故之源;分布式下用「单调序列号」排序(时间戳+序号,雪花,legacy/49)避免时钟回拨乱序。
3. 时钟回拨与精度:应用时钟回拨(NTP 校准)→时间倒流→审计顺序错乱——关键流水用「单调时钟+NTP 溯源」或 DB 序列兜底;精度:DATETIME(3)/TIMESTAMP(6) 毫秒微秒——同秒多笔靠毫秒分辨;TIMESTAMP 的时区陷阱(存 UTC 显示随会话时区——第 19 题banking 夏令时回拨)。

## 参考分析

### 第二步扩展① 机制:时间作为排序键的可靠性

- 审计的第一用途=「按发生顺序重建」——时间戳是排序键,排序键的正确性=来源单一+单调。
- 应用多实例时钟漂移(毫秒级常态,秒级异常)破坏单调。
- DB NOW() 在单库内单调(同一时钟)但跨库分叉。
- 真正可靠的顺序=「全局有序号」(时间戳+节点+序列的雪花,或 DB 自增)——时间用于人读,序号用于机器排序,两层分开。
- 这也是事件溯源(event sourcing)的通用设计。

### 第二步扩展② 反例:时间生成的两种事故

- 事故一:两应用实例时钟差 2s——回调流水 created_at 乱序,对账顺序错(第 16 题banking 对账同域)。
- 修复=序号排序或单时钟源。
- 事故二:DEFAULT CURRENT_TIMESTAMP 与应用注入混用——同一表两个来源,语义漂移。
- 字段职责单一。
- 事故三:TIMESTAMP 时区——服务器时区变更后历史时间偏移 8 小时。
- 统一 UTC 存储+显示层转换。

### 第二步扩展③ 取舍:应用注入 vs DB 兜底 vs 混合

- 标准组合=应用注入业务时间+DB DEFAULT CURRENT_TIMESTAMP 兜底(应用漏传时仍有值)+NOT NULL 纪律。
- DB 触发器自动填充(强一致但调试黑盒)。
- 框架审计字段(MyBatis Plus/Spring Data Auditing)统一注入——「单一注入点」防止散落。
- 审计字段的值来源必须在团队规范里写死(一句话规范避免十次争端)。

## 案例

### 第三步发散·验证与推演 验证:时间断言组(本机可复跑)

- 验证:一致性断言(应用注入 vs DB NOW 的差值测量(时钟漂移可见))。
- 回拨断言(构造应用时间回退,流水乱序复现。
- 雪花序号排序不受影响)。
- 精度断言(DATETIME(3) 同毫秒多笔分辨)。
- 时区断言(TIMESTAMP 存 UTC 的会话时区显示差异)。
- 兜底断言(应用漏传→DEFAULT 生效非 NULL)。
- 预期:来源单一与单调性双验证。

### 第三步发散·发散要点 追问链:审计三刀

- **追问①**：审计字段族——created_by/updated_by(谁)与 created_at(何时)配套,Spring Data Auditing 统一注入(第 91 题 spring 事件同域);
- **追问②**：事件时间的分布式语义——上游业务时间 vs 接收时间的区分(事件溯源/流处理 watermark,第 150 题契约);
- **追问③**：与金额审计的配对——动账流水表的时间+序号+金额三要素(第 158 题资金审计),审计可信=全要素单一来源

## 总结点

1. 时间分层:业务时间/创建时间/落库时间
2. 机器排序用序号,时间给人读
3. 单一注入点+NOT NULL 兜底
