## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Schema Registry 教学场景：消息协议 v2 增加字段并改了字段语义，旧消费者解析失败、新消费者读到旧消息缺字段。设计前后向兼容的演进规则：加字段必带默认、不删只废、语义不变更名，及 Schema Registry 的强制保障。

1. 兼容的四个方向：前向兼容（新 schema 读旧数据）、后向兼容（旧 schema 读新数据）、全兼容（双向）——先确定"新消息与旧消费者、旧消息与新消费者"谁的存活期更长，再定兼容方向。
2. 演进规则三条：加字段必带默认值（旧消费者忽略未知字段，新消费者给旧消息补默认）；字段只标记废弃不删除（旧生产者仍在发，直接删导致旧消费者解析失败）；语义不可复用（改名的字段用新名字，旧名字永久保留语义）。
3. Schema Registry 的强制保障：Confluent Schema Registry 在注册时校验新 schema 与配置的兼容级别，不兼容直接拒绝注册——把"靠团队自觉的兼容"变成"基础设施强制的兼容"。

## 参考分析

### 第二步扩展① 机制：消费者与生产者永远不同步

- 滚动发布意味着新旧消费者/生产者在一段时间内并存——任何协议变更都必须在"混合存活期"内可运转。
- 类比国际会议的同声传译：新旧译员并存期间，发言（消息）必须新旧译员都能理解——要么发言兼容两种理解，要么给译员时间换班。

### 第二步扩展② 反例：字段语义复用的静默错误

- status 字段从"数字状态码"改为"字符串枚举"，字段名不变——新生产者发字符串、旧消费者按数字解析，解析"成功"但语义全错（静默错误比解析失败更危险，见 cache-messaging/19 同源原则）。
- 修复：语义变更用新字段（statusV2），旧字段标记 deprecated 并在观察期后废弃。

### 第二步扩展③ 取舍：强制 Registry 与文档约定的成本

- Schema Registry：强制兼容（不兼容拒绝注册）、支持多格式（Avro/Protobuf/JSON Schema），代价是基础设施与注册流程。
- 文档约定（兼容规则写在团队规范）：零基础设施，靠 code review 把关。
- 消息量与消费方数量大的系统值得 Registry。
- 内部小系统文档约定+测试断言（新 schema 对旧样例消息的解析测试）也可运行。

## 案例

### 第三步发散·验证与推演 对照操作：兼容方向的验证矩阵

- 教学验证：v1 消息样例集与 v2 消息样例集，分别用 v1/v2 消费者解析。
- 预期矩阵四格：新读旧（默认值补齐）、旧读新（未知字段忽略）、新读新、旧读旧——四格全绿即全兼容。
- 矩阵测试进 CI，schema 变更自动跑。
- 可复跑。

### 第三步发散·追问① 追问：为什么"只加不删"也有终点

- deprecated 字段无限保留会让 schema 膨胀、新成员困惑。
- 终点判定：旧生产者全部下线（观察生产日志的 schema 版本分布）后，废弃字段才可进入删除流程——删除本身作为一次"后向兼容变更"再走一轮演进。
- 废弃是状态，删除是事件，两者间隔以"生产者分布"为准。

## 总结点

1. 新读旧补默认，旧读新忽略
2. 语义变更换新名，旧名不删只废
3. Registry 把自觉变强制
