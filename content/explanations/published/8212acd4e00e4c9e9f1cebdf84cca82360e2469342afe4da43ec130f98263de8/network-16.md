## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银门户沙盘:反向代理缓存了门户首页,不同用户登录后看到同一份缓存——缓存的响应里带着第一个用户的姓名;Vary 头缺失或身份维度未隔离,缓存把"一个人的页面"变成"所有人的页面"。

1. Vary 的语义:响应头 Vary: User-Agent 告诉代理"缓存键要加上 UA 维度"——不同 UA 各存一份;缺 Vary 时代理按 URL 缓存,不同请求上下文(压缩能力/语言/身份)共享同一份响应。
2. 身份维度:带 Cookie/Authorization 的响应绝不能进共享缓存(Cache-Control: private/no-store)——代理是共享组件,个人化响应进共享缓存即数据串户;网银页面必须明确声明 private。
3. 缓存键的工程定义:URL+Vary 头的组合;隐式维度还有 Accept-Encoding(gzip 版本)、Cookie(private 化规避)——键设计漏一个维度,缓存就从加速器变成串户器。

## 参考分析

### 第二步扩展① 机制:缓存键与维度隔离

- 代理缓存键=规范化 URL+每个 Vary 头的值(规范化后)。
- Vary: * 表示"响应不可缓存"(键无法穷举)。
- 身份隔离两条路:响应声明 private(仅客户端可存)或请求侧把身份移出缓存路径(缓存仅覆盖公开资源,个人化走 API)。

### 第二步扩展② 反例:缓存串户的三种事故

- 事故一:登录态页面被代理缓存——用户 A 登录后代理记下响应,用户 B 命中同一 URL 看到 A 的数据(真实事故形态,金融系统致命)。
- 事故二:Vary: User-Agent 滥用——UA 无限变体(爬虫/设备碎片化)把缓存打成筛子,命中率归零。
- 事故三:Accept-Encoding 未声明——压缩代理把 gzip 内容发给不支持压缩的客户端,解析失败。

### 第二步扩展③ 取舍:缓存的收益与隔离成本

- 公开资源(静态/公告):代理缓存收益最大,键=URL。
- 个人化资源:private+no-store,代理旁路。
- 折中方案:页面骨架缓存+数据 API 个人化(ESR 模式)——缓存命中骨架,个人数据异步拉取。
- 隔离成本(键维度多、命中率降)用"减少个人化内容占比"来换。

## 案例

### 第三步发散·验证与推演 验证:键维度的推演核对

- 推演核对:本机 N7 实验证明"请求头进入服务端决策"(If-None-Match)与"响应头声明缓存语义"(Cache-Control)的机制。
- Vary 与 private 的串户路径按 RFC 9110 共享缓存语义推演并明示(未复现串户事故,避免在真实环境制造数据混淆)。
- 验证:缓存键=URL+Vary、个人响应必须 private 的结论与协议语义一致。

### 第三步发散·发散要点 追问链:Vary 三刀

- **追问①**：Vary 规范化陷阱——代理对头值规范化(大小写/空格)不一致会造成重复缓存条目,命中率虚降;CDN 对 Vary 支持差异大,多 CDN 部署要实测
- **追问②**：private 与代理鉴权的关系——代理对 Authorization 请求默认不缓存(除非 s-maxage/public 显式声明),这不是 bug 是保护
- **追问③**：与网关限流的衔接——缓存命中不进限流计数(省资源),但个人化 API 每请求必达后端,限流与缓存维度要一致设计

## 总结点

1. 缓存键等于 URL 加 Vary
2. 个人响应必须 private
3. 骨架缓存数据个人化
