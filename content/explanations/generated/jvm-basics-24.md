## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：服务冷启动的前几秒响应慢、CPU 飙高，随后恢复正常。用分层编译的五层模型解释解释器与 C1/C2 的接力过程，说明预热期间发生了什么。

1. 分层编译五层：0 解释 → 3 C1 带 profiling → 1 C1 全优化 → 2 C1 有限 profiling → 4 C2 深度优化；默认从 0 直接跳 3，再升 4。
2. 热点探测按调用计数与回边计数，达到阈值触发编译（OSR 支持编译循环中段）；C1 快速出活让应用先跑顺，profiling 数据喂给 C2 做激进优化。
3. 预热期慢与 CPU 高是常态：大量方法在排队编译、编译线程与业务抢核；预热完成后解释与 C1 版本被替换，性能进入稳态。

## 参考分析

### 机制：先求可用，再求最优

解释器像临时工立刻上岗（慢但对），C1 是熟练工快速上线并顺便记录用户习惯（profiling：哪个分支热、哪个类型单态），C2 是老师傅按真实习惯重排整条产线（内联、逃逸分析、向量化）。类比解释了"为什么 Java 跑久了更快"：越跑越了解你的负载。

### 边界：profiling 数据是 C2 的赌注

C2 按单态假设做虚调用内联、按分支概率重排——赌的是 profile 延续。形态变化触发去优化回解释器（见第 27 题），重新 profiling 再编译。所以"分层"不只是速度分层，也是"假设验证"的迭代循环；JFR 的 Compilation/Deoptimization 事件能看到整个循环。

### 取舍：编译资源与业务线程抢核

预热期编译队列积压，容器 CPU 限额低时更明显；可用 `-XX:CICompilerCount` 调编译线程、启动期避免巨方法（编译耗时长）、或用 AppCDS 减少加载验证成本。灰度预热（先小流量）与启动预热脚本（提前 touch 热点路径）是常见配套。

## 案例

### 对照操作：观察五层升级过程

教学验证：`-Xlog:jit+compilation=info` 下运行热点循环。预期：同一方法先出现层次 3 再出现层次 4 记录，编译耗时从 C1 的毫秒级到 C2 的几十毫秒；配合 JFR ExecutionSample 对比预热前后同方法耗时。实验可复跑，把抽象分层变成日志时间线。

### 追问：为什么不让 C2 直接编译所有方法

C2 编译成本高（profiling 数据收集 + 优化耗时），全量编译会让启动更慢且浪费在冷方法上；分层让 99% 的方法停在 C1/解释层，只把真热点送 C2。这是"按收益分配编译资源"的资源调度问题，与 GC 分代假设同构：把贵的手艺花在少数热点上。

## 总结点

1. 解释应急，C1 抢跑，C2 精修
2. 计数到阈值就编译，OSR 编循环
3. 预热抢核，先小流量
