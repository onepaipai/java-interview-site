## 参考回答

<!-- explanation:deep -->

> 场景与约束：Redis 6.2 / MySQL 8.4 教学场景：读写分离 + 旁路缓存架构，写路径"更新库→删缓存→延迟 N 毫秒再删一次"，偶发不一致仍被业务方发现。用并发交错推演双删仍遗留的窗口，给出可收敛的替代协议。

1. 延迟双删消除的是"写事务期间旧读回填"的常见窗口：第二次删除清掉事务期间被旧值污染的缓存。但它没有消除"第二次删除之后、下一次回源之前"的读路径交错。
2. 遗留窗口推演：第二次删除后，一个更早启动的旧读事务仍在读库（RR 快照）并回填旧值——该回填晚于双删，缓存再次变旧。窗口由"读事务时长"决定，N 毫秒的固定延迟无法覆盖。
3. 可收敛替代：删除动作携带数据版本，缓存回填时校验版本只接受更新数据；或缓存条目带 TTL 兜底，把"最坏不一致时长"从无限收敛到 TTL 上限。

## 参考分析

### 第二步扩展① 机制：固定延迟覆盖不了可变时长的读事务

- 延迟 N 毫秒的假设是"所有旧读都在 N 毫秒内结束"——读事务的时长由查询复杂度、锁等待、调度决定，没有上界。
- 类比追公交车：固定等 30 秒再走一次，只能赶上多数乘客，赶不上腿慢的——腿慢的乘客（长事务）会在你走后再上车。
- 双删是工程启发式，不是一致性协议。

### 第二步扩展② 反例：读快照长事务的回填复现

- 读事务 T1 以 RR 快照启动（读到旧值），被大查询拖延 3 秒后才写缓存。
- 写事务 T2 在这 3 秒内完成了更新库 + 双删。
- T1 的回填晚于双删——缓存旧值驻留直到 TTL。
- 实验可注入大查询制造拖延并观察，可复跑。

### 第二步扩展③ 取舍：版本协议与双删的分工

- 版本协议（缓存条目带数据版本，回填校验）在因果上正确但要求缓存结构带版本、回填路径全改。
- 双删零改动、覆盖多数场景。
- 务实组合：保留双删 + 缓存条目加短 TTL 兜底 + 监控不一致时长。
- 改造优先级取决于业务对不一致窗口的容忍度。

## 案例

### 第三步发散·验证与推演 对照操作：长读事务的窗口复现

- 教学验证：T1 开 RR 事务读旧值后暂停。
- T2 完成更新库+双删。
- T1 恢复并 SET 旧值到缓存。
- 读缓存验证为旧值。
- 预期：双删后缓存仍旧、直到 TTL 过期或下一次写。
- 把 N 从 100 调到 5000 毫秒验证窗口仍在（只要长事务超过 N）。
- 实验可复跑。

### 第三步发散·追问① 追问：为什么不能把 N 设得足够长

- N 越长，第二次删除离用户越远——期间所有读都可能回填旧值再被删掉，等于把"删除后到二次删除前"的窗口反向放大。
- 且 N 上限永远可能被极端长事务突破。
- 正确方向不是调 N，而是让回填自带版本校验，使旧回填天然失效。

## 总结点

1. 双删是启发，不是协议
2. 长事务窗口没有上界
3. 版本校验或 TTL 兜底，收敛窗口
