## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银单号沙盘:所有交易单号来自 ID 服务——ID 服务宕机=全站停发;时钟回拨=号段重复;段用尽=取号阻塞——设计前必须先列故障假设:可宕(多段缓存)、可回拨(检测拒绝)、可耗尽(提前预取),每种假设对应一个机制。

1. 号段模式(Leaf-segment):本地缓存号段(如 1 万个),DB 取段失败可继续发号至段尾;故障假设=DB 可短时不可用(段内自持);双 buffer 预取下一段,取段耗尽前异步加载——发号不阻塞在 DB。
2. 雪花模式(Snowflake):机器位+时间位+序列位;故障假设=时钟可能回拨(实测:回拨 1ms 检测→拒绝发号返回 -1,恢复后继续,distributed D17)——回拨期间停发而非降级乱发;机器 ID 分配唯一(zookeeper/配置中心仲裁)。
3. 共同故障假设:发号服务本身无状态多实例(任一实例可服务)、ID 不可回退(单调性保证排序与对账)、趋势递增但容忍缝隙(宕机丢段不丢已发号)——假设清单写进设计文档,每条对应机制与演练。

## 参考分析

### 机制:两种模式的故障面

号段:DB 不可用时段内自持(时长=段大小/发号速率),双 buffer 掩盖取段延迟;风险=实例宕机丢未发完的段(缝隙,业务需容忍)。雪花:时钟回拨停发(等待或告警换机),机器 ID 冲突=号段重叠(灾难,分配必须仲裁);风险=依赖时钟的单调性。两者共同的兜底:ID 全局唯一性由"段/机器"维度隔离保证,不依赖跨实例协调。

### 反例:ID 服务的四种事故

事故一:单实例发号——宕机即全站停发;多实例+段隔离。事故二:NTP 大步回拨未检测——雪花重复号(同一毫秒序列重发);回拨检测+拒绝。事故三:机器 ID 手工分配冲突——两实例同 ID,号段重叠,单号重复入账;仲裁分配+启动校验。事故四:段大小拍脑袋——段太小取段频繁(DB 压力),段太大宕机浪费过大(缝隙大);按发号速率动态调。

### 取舍:趋势递增 vs 严格递增

趋势递增(号段/雪花):发号无协调、吞吐高,缝隙容忍;严格递增(单点/共识):无缝隙但吞吐与可用性受限——业务需要"严格"的极少(对账按时间排序即可),绝大多数场景趋势递增够用。选型先问:业务是否真需要严格单调,还是只需唯一+可排序。

## 案例

### 验证:回拨与缝隙的实测证据(交叉引用)

distributed 批次 D17 实测(雪花,回拨注入):
~~~
时钟回拨 1ms → 检测 → 拒绝发号(返回 -1)
恢复后继续发号,同毫秒序列递增
~~~
推演核对:号段缝隙与宕机假设按实现语义推演(段内已发号不受影响);机器 ID 冲突的后果推演与"仲裁分配"机制对应(raft/仲裁服务,distributed 批次);验证:每条故障假设(可宕/可回拨/可耗尽)都有对应机制,假设-机制矩阵闭环。

### 追问链:ID 三刀

一刀:ID 泄漏业务信息——时间位暴露单量速率(竞对可估日单量);对外展示 ID 与内部 ID 分离或混淆。二刀:ID 与分片键——按 ID 范围分库分表时趋势递增造成写热点(新号都在最后一片),按哈希或按业务键分片(与 Q49 十倍增长的分片决策衔接)。三刀:与 Q31 定时调度的衔接——任务 ID 也走 ID 服务,重复触发的判定靠任务幂等键而非 ID 唯一性。

## 总结点

1. 故障假设先行机制随后
2. 回拨检测拒绝发号
3. 趋势递增缝隙容忍
