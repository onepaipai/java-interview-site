## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银并发读沙盘:普通 SELECT 走快照读(版本链,无锁)——但 SELECT ... FOR UPDATE/UPDATE/DELETE 是当前读(加锁);「MVCC 让读无锁」只对快照读成立;混合使用还有「快照与当前不一致」的漂移。

1. 快照读 vs 当前读:普通 SELECT=快照读(沿版本链找 Read View 可见版本,无锁);FOR UPDATE/UPDATE/DELETE=当前读(最新版本+加锁);「查询无锁」只对快照读成立。
2. 混合漂移问题:同一事务先快照读(看到旧快照)再当前读(最新)——两次结果可能不同:RR 下快照固定,当前读总是最新——「先 select 确认再 update」的检查-执行模式有竞态(检查时的快照与执行时的最新之间,别人可能已改);正确姿势=检查与执行合并成当前读(SELECT FOR UPDATE)或条件 UPDATE(原子判定)。
3. MVCC 的边界:①不解决写写冲突(仍靠锁)②长事务拖 undo 清理(第 20 题)③间隙锁只在 RR 当前读出现(第 17 题);「无锁读」的代价=旧版本存储+purge 线程——MVCC 是读路径优化,不是并发控制的替代。

## 参考分析

### 第二步扩展① 机制:快照读无锁的代价转移到哪里

- 无锁读不是免费:①版本链存储(undo 膨胀,长事务放大)②purge 清理(CPU+IO)③可见性判定(沿链遍历,旧版本越多越慢)——读路径的锁成本换成了空间+后台成本。
- 这正是「长事务是 MVCC 天敌」的机制(第 20 题)。
- 对比锁读:无 undo 代价但阻塞并发——两种读的两套成本账,按读写比例选(读多=MVCC 赢,写多=锁更直接)。

### 第二步扩展② 反例:无锁读误解的两种事故

- 事故一:select 确认再 update——竞态窗口内他人扣减,超扣(检查-执行非原子)。
- 修复=FOR UPDATE 或条件 UPDATE(第 25 题)。
- 事故二:以为 FOR UPDATE 也走快照——当前读加锁,与快照语义混合的事务里「看到的行」不一致(漂移)。
- 同一事务内明确两种读的用途,别混。

### 第二步扩展③ 取舍:快照/锁定/乐观三种读策略

- 一致性要求低(展示/报表):快照读(无锁高并发)。
- 检查即执行:条件 UPDATE(原子,首选)。
- 需要读后判断复杂逻辑再改:FOR UPDATE(悲观)或版本号乐观重试(第 25 题/103 题)——按冲突概率与逻辑复杂度三选。
- MVCC 让「读」不再挡「写」,但「改」永远要当前读语义。

## 案例

### 第三步发散·验证与推演 验证:锁语义断言组(本机可复跑)

- 验证:快照无锁断言(普通 SELECT 期间另一事务可 UPDATE 提交——不阻塞)。
- 锁定读断言(FOR UPDATE 期间他人 UPDATE 阻塞/超时)。
- 漂移断言(RR 事务快照读 vs 当前读结果差——混合使用演示)。
- 条件更新断言(check-then-act 竞态复现 vs 条件 UPDATE 原子成功——第 25 题同源)。
- undo 膨胀断言(长事务期间历史链长增长,第 20 题呼应)。
- 预期:两种读的锁行为与漂移可见。

### 第三步发散·发散要点 追问链:读策略三刀

- **追问①**：一致性读的三时点——语句开始/事务开始/显式 START TRANSACTION WITH CONSISTENT SNAPSHOT(第 19 题database-advanced 一致性快照);
- **追问②**：无锁读与可串行化——SERIALIZABLE 下普通 SELECT 也转锁定读(级别改变读语义),第 17 题呼应;
- **追问③**：应用层缓存的一致性——快照读读到旧值与缓存旧值叠加(第 152 题缓存失效同域)——读路径的一致性是端到端问题

## 总结点

1. 普通 SELECT 无锁,锁定读/DML 当前读
2. 检查-执行必须原子,防漂移
3. MVCC 是读优化,不替代锁
