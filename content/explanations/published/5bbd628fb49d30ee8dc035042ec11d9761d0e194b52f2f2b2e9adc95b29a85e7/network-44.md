## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银专线沙盘:小接口(几百字节)全正常,大报文接口(2KB+)必失败——中间链路 MTU 与双方 MSS 协商不一致,大包被分片或被丢(PMTU 黑洞);问题只在"报文超过某阈值"时出现,小请求毫发无损。

1. 机制:以太网 MTU=1500 字节,超 MTU 的包 IPv4 按 DF 位处理(带 DF 丢弃并回 ICMP 需分片报文,不带则中间路由器分片、性能差),IPv6 禁中间分片一律靠源端缩小;TCP 靠 MSS 协商避免分片——隧道(GRE/VPN/PPPoE)额外封装吃头部,实际可用 MTU=1500-封装开销,而 MSS 协商不知道隧道存在。
2. PMTU 黑洞:路径中最小 MTU 比协商 MSS 小时,大包在隧道口被丢(IPv6)或被分片(依赖 DF 位,黑洞丢弃带 DF 的大包)——ICMP"需要分片"报文被防火墙拦截时,发送端永远不知道该缩包,重传无限循环;现代解法是 PLPMTUD(RFC 8899,用大包探测、不依赖 ICMP)。
3. 表现与定位:小请求(<阈值)正常、大请求(timeout/reset)、握手正常(SYN/ACK 小)——三特征组合即 MTU 问题;定位:ping -f -l(带 DF 分段试探阈值)、抓包看 ICMP type 3 code 4、tcpdump 看重传模式。

## 参考分析

### 机制:阈值与协商的错位

MSS=MTU-40(IP+TCP 头);双端协商 MSS 各报自己的接口 MTU——都报 1460,但中间隧道实际只放行 1400;小于 1400 的包畅通,大于的丢——"阈值上下泾渭分明"正是小包正常大包失败的机制;TLS 握手证书报文(2-4KB)恰好是大包,所以握手失败也是常见表现(与 Q21 的"握手成功≠业务健康"互补:这里是握手失败)。

### 反例:MTU 的三种事故

事故一:VPN 专线开 SSL 双向——证书报文超隧道 MTU,握手卡死,运维怀疑证书错误折腾半天;先 ping -f 试探阈值。事故二:防火墙拦 ICMP——PMTU 发现失效,发送端不知缩包,表现为"偶发卡死";中间设备必须放行 ICMP type 3 code 4。事故三:容器 overlay(VXLAN)——封装吃 50 字节,宿主机 MTU 1500 而容器内仍按 1500 配,跨节点大包必失败;容器 MTU 要按 overlay 类型下调。

### 取舍:MSS clamp vs 全局调小

MSS clamp(边缘设备改写 TCP MSS 为实际可用值):精准,只影响该链路;全局调小接口 MTU:一劳永逸但牺牲所有流量的效率。专线/隧道入口做 clamp 是标准解;云环境(VPC/对等连接)按官方 MTU 文档配置(多数云支持 9000 巨帧内网,出公网仍 1500)——按"封装开销"精确计算而非拍脑袋。

## 案例

### 验证:阈值特征的推演核对

推演核对:本机 N1 实验证实"TCP 分段与缓冲边界"(8KB 分 2 次 read)——分段大小受 MSS 约束的传输层事实有实测支撑;PMTU 黑洞与 ICMP 依赖按 RFC 1191/8201 语义推演并明示(未复现隧道环境);验证:"阈值上失败阈值下正常+握手受影响"的特征组合可从 MSS/MTU 机制严格推导,定位顺序(ping -f→抓 ICMP→clamp)成立。

### 追问链:MTU 三刀

一刀:QUIC 对 MTU 更敏感——UDP 包超 MTU 直接丢且无 IP 分片兜底,H3 强依赖 PMTUD,中间网络 ICMP 拦截对 H3 伤害大于 TCP(见 Q18 代价面)。二刀:TLS 与 MTU 的交叉——大证书链(ECDSA 比 RSA 短)降低握手报文超限概率;证书选择也影响 MTU 敏感度。三刀:与 Q46 的衔接——MTU 问题在"客户端快服务端慢"的矛盾画像中表现为客户端超时服务端无记录(包根本没到),跨端日志比对是定位抓手。

## 总结点

1. 大包失败小包正常即 MTU
2. ICMP 黑洞让缩包失灵
3. 隧道口 MSS clamp 是解
