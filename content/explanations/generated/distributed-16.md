## 参考回答

<!-- explanation:deep -->

> 场景与约束：两个任务更新同一资源。任务 A 获得租约后长时间暂停，租约过期；任务 B 获得新授权并完成写入，此后 A 恢复。讨论重点是旧写是否会被真正保存资源的一方拒绝。

1. 锁过期只改变协调服务中的所有权，不会终止旧进程。栅栏令牌让每次授权取得单调递增的序号，由资源端原子检查并拒绝较旧令牌，阻止恢复后的旧持有者覆盖新结果。
2. 关键条件有三个：授权序号可靠递增、请求携带令牌、所有写入路径都经过资源端比较。只在客户端检查锁、只比较随机持有者 ID，或者先查令牌再另行写入，都不构成完整保护。
3. Fencing 解决的是旧授权写入问题，不自动提供请求幂等、多资源事务或立即撤销。不能支持令牌比较的外部系统，需要业务版本、条件写入或另一套目标端能执行的保护协议。

## 参考分析

### 用暂停反例区分续租、解锁与旧写保护

A 取得 token=41 后暂停；租约失效；B 取得 token=42 并写入。即使 A 恢复时已经无法续租，它早先准备好的网络请求仍可能发出。比较持有者 ID 的安全解锁能避免 A 删除 B 的锁，却不能防止 A 写共享数据库。

资源保存当前已接受的最高 token。B 的 42 使该值推进到 42，随后到达的 41 被拒绝。必须强调“资源已经观察到新令牌”这一前提：如果旧请求先到、新授权尚未在资源端建立屏障，单纯记最大值并不会立即感知协调服务发生了换主。

### 数据库条件更新：比较与写入必须原子

例如资源行保存 fence_token 和业务版本，SQL 用 WHERE fence_token < :token 再更新 payload 与 fence_token。较新授权首次写入后，旧令牌的影响行数为零。这里每次授权只演示一个最终写入；影响行数为零必须返回失去授权或冲突，不能悄悄按成功处理。

```sql
UPDATE protected_resource
SET payload = :payload, fence_token = :token
WHERE id = :id AND fence_token < :token;
```

若同一授权要执行多次写入，需定义允许相同 token 的条件并增加操作序号或请求去重，避免同令牌内乱序覆盖。令牌值不能由任意客户端自增或伪造，否则一个异常大值会阻塞后续合法写入。类比过期门禁卡：停卡不代表持卡人离场，读卡器必须当场比对编号，旧卡刷不开新门——拒绝要发生在资源端。

### 工程边界：令牌生成、资源覆盖与可用性

递增性需要在授权系统的故障与恢复模型下成立，简单用会丢状态的计数器并不能保证重启后不倒退。资源端每个有副作用的入口、批处理和运维脚本也必须执行保护，否则旁路写入会破坏承诺。

对于外部邮件或不支持条件更新的渠道，发送请求后无法靠本地令牌撤销，应该改为持久任务状态机、目标端幂等键或受控单写入口。安全保护可能拒绝请求并降低某段时间的可用性，这是合理取舍；不能为了自动恢复而跳过令牌校验。

## 案例

### 故障注入：让旧持有者在新写之后恢复

在 A 获得 41 后用测试屏障暂停，等待租约失效；B 获得 42，成功写入 new；再恢复 A 发送 old。预期 A 被资源端拒绝，最终 payload 仍为 new，拒绝原因可关联资源 ID 与令牌，而不是依赖 A 自觉退出。

反例一，去掉 SQL 条件，旧值会覆盖；反例二，在应用里先 SELECT token 再无条件 UPDATE，并在两步之间插入 B 的写，说明非原子检查同样不安全。再验证协调服务重启后令牌仍单调，以及写入权限不能绕过受保护入口。

### 面试追问：相同令牌重试为何失败？

上面的严格小于条件会让同令牌第二次写影响零行，这是有意限制的单次最终写协议；它既可能是重复成功，也可能是冲突，不能仅凭零行就猜结果。可以保存 operation_id 与结果，再按同一操作重放确定响应。

验收需覆盖旧 token、新 token、相同 token 重试、同 token 不同参数、请求乱序及资源端重启。必须分别解释授权新鲜度、业务幂等和业务版本冲突，才能说明一个实现到底保证了什么。

## 总结点

1. 旧进程还活着，资源端必须拒旧
2. 租约过期不会终止旧进程
3. 资源端原子拒绝旧授权写入
4. 栅栏、幂等与顺序分别设计
