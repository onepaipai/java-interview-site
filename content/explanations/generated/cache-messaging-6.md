## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 7 Cluster 教学场景：某分片 CPU 100% 其他分片空闲，怀疑热键但不敢全量 KEYS 扫描。梳理低开销识别手段（采 LRU 样本、monitor 采样、客户端统计）与治理优先级。

1. 识别手段按开销排序：redis-cli --hotkeys（走 LFU 淘汰策略时零额外成本）；`redis-cli monitor` 短时采样（生产慎用，阻塞风险）；客户端侧按 key 统计 QPS（应用已知的调用分布）；Cluster 的 slot 维度 CPU/流量偏差先定位热分片再缩小范围。
2. 识别的开销纪律：任何全量扫描（KEYS *、全量 monitor）在高生产环境都会制造新故障——识别工具本身必须比被查问题更轻。
3. 治理优先级：本地缓存（L1 挡读）→ key 拆分（热点 key 加随机后缀分散到多分片，读侧聚合）→ 读写分离副本 → 架构性下沉（见并发进阶第 47 题的三级治理，原理同构）。

## 参考分析

### 机制：热键把"分片并行度"归零

Cluster 按 key 哈希分散负载，但单 key 只落一个分片——该分片成为单点。类比景区 10 条通道，某明星粉丝全挤 3 号：通道总数无关紧要，3 号通道的容量才是瓶颈。热键的识别先看分片级不均衡，再下钻到键级。

### 反例：MONITOR 全量监控的二次故障

值班在生产主从上开启 MONITOR 试图找热键：MONITOR 流式输出所有命令，主从带宽与 Redis CPU 雪上加霜，故障放大。修正：先走 --hotkeys 或客户端统计（零额外压力），MONITOR 只在从库、只开几秒、只做采样。排查工具的开销纪律与第 42 题（jvm-basics）诊断工具选择同构。

### 取舍：key 拆分的读侧代价

热 key 拆成 N 个后缀副本后写要写 N 份（或写主副本读随机读——接受副本间短暂不一致），读侧如果要"完整值"还需聚合。N 的选择：写到能分散 CPU、读到聚合成本可接受。秒杀库存类把"库存数"拆成多桶分别扣减（见并发进阶第 47 题），是拆分+聚合的典型应用。

## 案例

### 对照操作：三级识别的开销对照

教学验证：同一热键环境分别用 --hotkeys、短时 monitor 采样、客户端 QPS 统计定位。预期：三者都能找到目标 key，开销（Redis CPU 增量）差异显著——hotkeys 零增量、monitor 数十个百分点。开销表写进运维手册，实验可复跑。

### 追问：为什么客户端统计有时比 Redis 端更准

Redis 端看到的是"到达的命令"，客户端统计能关联到"哪个业务场景发起"——归因到业务代码才能治本（加缓存、改逻辑）。端上工具定位"哪个 key 热"，客户端定位"为什么热、从哪来"——两级配合，先端上后客户端。

## 总结点

1. 分片先定位，键级再下钻
2. 扫描工具的 开销要小于问题
3. 拆分散负载，聚合管读侧
