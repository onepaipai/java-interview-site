## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银沙盘:重载(编译期按静态类型选方法)与重写(运行期按实际类型分派)——同样的调用代码,重载看变量声明类型、重写看对象实际类型——两者混用的调用点行为易误判(方法参数的静态分派)。

1. 重写(Override):运行期动态分派(对象实际类型的方法——虚方法表);重载(Overload):编译期静态绑定(变量声明类型+参数静态类型选签名)——一个在运行,一个在编译。
2. 经典陷阱:重载参数的静态分派——service.handle(Object o) 与 handle(String s):传入 String 类型的 Object 变量→调 handle(Object)(编译期看声明类型)——"我以为调 String 版"。另一个:字段不参与多态(字段按静态类型——方法多态字段不多态)。
3. 与第 6 题spring(代理)的关系:自调用绕过重写的动态分派(spring-advanced 1 题)与重载的静态分派是两个维度——代理影响重写(this 的实际类型),不影响重载(编译期已定)。

## 参考分析

### 机制:两个分派时机

重写的分派:invokevirtual/invokeinterface——按接收者的实际类型查虚方法表(运行期)——多态的核心。重载的绑定:编译期按(静态类型,参数静态类型,自动装箱/变长参数的优先级)选方法——精确匹配>装箱>变长(重载解析的三段优先级,装箱陷阱:Integer 参数与 int 参数的重载在传 int 时的选择)。字段与静态方法:静态绑定(按引用类型)——"字段不多态"。

### 反例:静态分派的两种误判

误判一,重载的装箱陷阱:handle(int) 与 handle(Integer) 重载,传 Integer 变量→handle(Integer)(精确优先);传 int→handle(int)——重载解析的优先级(精确>装箱>变长)决定行为(第 19 题装箱的连带)。误判二,父类引用调子类重载:子类新增重载 handle(String),父类引用调用→父类签名(子类重载不在父类接口中——编译期绑定)——重载不放多态。两条的正解:重载的调用方用子类引用,或重写替代重载(多态语义)。

### 取舍:重载的使用纪律

纪律一,同族方法的重载保持"行为一致"(同一语义的不同参数形态——语义不同不重载,改名);纪律二,避免装箱/变长的重载歧义(int 与 Integer 不重载——二选一);纪律三,重载的文档与测试(每个重载的用例——静态分派的行为固化,第 24 题评审)。重写的纪律:spring-advanced 1 题的代理纪律(经代理才分派)。

## 案例

### 验证:分派时机的断言组

验证:重写动态分派断言(父类引用调子类重写方法——运行期分派实证);重载静态分派断言(Object 变量传 String 值调 Object 版——编译期绑定实证);装箱优先级断言(int 与 Integer 重载的解析行为)——三组用编译运行对照固化两个分派时机。

### 追问链:分派三刀

一刀:"invokevirtual 的内部?"——虚方法表(vtable)按实际类型查——单分派(按接收者);多分派(按参数类型)不支持(重载在编译期处理)——单双分派的语言差异是重载/重写差异的理论根源。二刀:"invokestatic 与私有?"——静态方法与私有方法非虚分派(invokestatic/invokespecial——编译期绑定)——不可重写(私有/static/final)——"重写失败"的隐形原因。三刀:"invokedynamic?"——Lambda 与字符串拼接的 invokedynamic(运行期引导——Lambda 的实现策略与拼接的策略由引导方法定,第 21 题)——Java 7+ 的第五条调用指令。

## 总结点

1. 重写运行分派,重载编译绑定
2. 字段不多态,装箱有优先级
3. 代理只影响重写不影响重载
