## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：服务 P99 偶发尖刺几毫秒到几十毫秒，GC 与网络都排除了。用去优化（deoptimization）机制解释尖刺来源：类型 profile 变化、守卫失败、类重定义触发全量重编译。

1. C2 的激进优化是带守卫的赌注：按 profile 假设"这里只有一种类型/分支不常走"，守卫失败时立即去优化——丢弃编译代码、回解释执行并重新 profiling。
2. 常见触发：新子类出现使单态变多态、分支概率翻转、方法被替换（Instrumentation/热部署）、类卸载。每次去优化后要重新走分层编译路径，期间性能明显低于稳态。
3. 波动特征：尖刺与新形态首次出现的时间点重合（新数据类型、新租户路径、功能开关切换），且同点可复现——这是与 GC 尖刺区分的关键线索。

## 参考分析

### 第二步扩展① 机制：赌注押错，全部重来

- C2 按 profile 把多态点缩成单态直调，守卫就是"类型还是它吗"。
- 类比定制流水线只装一种零件，来料换了型号必须停线重装夹具：停线（去优化到解释器）、重新观察（profiling）、重开线（C2 再编译）。
- 一次尖刺 = 停线 + 重学 + 重编译的总和。

### 第二步扩展② 反例：一个新租户打翻全服 profile

- 支付网关按"只会走卡支付"优化了分派点。
- 新租户接入银行直连（第二个实现），全实例分派点陆续去优化——不是只有新租户慢，而是所有请求在重编译期都慢。
- 定位线索：尖刺时间与新代码/新数据上线时间对齐。
- JFR Deoptimization 事件给出确切方法与原因（unstable if / unloaded class 等）。

### 第二步扩展③ 取舍：为形态稳定而设计 vs 接受重学习

- 把"会新增实现"的热点收敛到显式策略表（switch/查表）可以牺牲一点稳态吞吐换取形态稳定。
- 也可以灰度预热（新代码上线先小流量触发重编译）。
- 接受去优化也是合理选择——关键是有事件数据，让尖刺可归因而不是玄学。

## 案例

### 第三步发散·验证与推演 对照操作：JFR 抓一次去优化

- 教学验证：单态接口热点稳定运行后，动态注册第二实现（或用 Instrumentation redefine）。
- 预期：JFR 记录 Deoptimization（reason=unstable if 或 action=making not entrant），同期请求延迟出现尖刺。
- 数十秒后回到新稳态。
- 实验可复跑，尖刺归因一目了然。

### 第三步发散·追问① 追问：去优化与逃逸分析失败是同一回事吗

- 都是"守卫失败回解释器"，但守卫对象不同：逃逸分析的守卫多在"对象没逃出去"的假设上，去优化还包括类型、分支、方法替换等。
- 面试里区分这两者，展示的是对"JIT 全部优化都带退出条款"这一统一视角的理解。

## 总结点

1. 优化带守卫，赌错就重来
2. 尖刺对齐上线点，JFR 给归因
3. 形态稳不稳，决定尖刺有没有
