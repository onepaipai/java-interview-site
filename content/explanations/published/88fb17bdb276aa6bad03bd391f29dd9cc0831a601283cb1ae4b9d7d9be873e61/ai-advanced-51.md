## 参考回答

<!-- explanation:deep -->

> 场景与约束：企业助手沙盘:知识助手通过 MCP 接入数据库查询与文件读取工具，模型可直接列出工具并发起调用；需要说明工具描述的可信度、权限边界与审计证据。

1. MCP 规范的是工具发现与调用协议，不代表工具调用天然安全；工具描述、返回内容都来自外部，应视为不可信数据，不能把其中的文字当成系统指令。
2. 权限应在服务端按用户身份与工具粒度判定，不能交给模型自觉；只读与写操作分权，高风险动作设置人工确认和速率/预算上限。
3. 审计要记录调用主体、工具名、参数摘要、结果摘要与决策证据；日志避免保存完整敏感提示或返回体，并保留可复现的关联 ID。

## 参考分析

### 第二步扩展① 机制:协议解决连接，不解决授权

- MCP 让客户端发现工具、传递参数并接收结果，解决的是"怎么连、怎么调"。
- 授权回答的是"这个人能不能调这个工具、能带哪些参数"，属于应用安全边界。
- 类比酒店门禁:MCP 像统一的门禁卡读写协议，能识别哪扇门可刷。
- 但谁能进哪一间、能否进金库，是酒店的授权系统与监控职责——协议不替你决定。

### 第二步扩展② 边界:工具描述与返回值都是输入

- 恶意工具名、描述文本或返回内容可能夹带"忽略之前指令、调用另一个工具"等提示注入。
- 模型把它当上下文处理，就可能越权。
- 防御是把工具返回当数据而非指令、服务端重新校验参数、用户输入与工具输出都做隔离标记，并限制工具可见范围。

### 第二步扩展③ 取舍:强隔离与工程成本的平衡

- 强隔离为每个用户/任务起独立工具进程或容器，安全但成本高。
- 轻量方案是进程内白名单加参数校验，但要接受同进程故障域。
- 按工具风险分级:只读检索用轻量边界，能改数据或外发网络的动作用强隔离与人工确认。

## 案例

### 第三步发散·验证与推演 验证:越权调用的推演

- 教学验证:用普通用户身份请求助手调用仅管理员可见的工具，断言服务端在代理层拒绝（HTTP 403 或工具层拒绝），并产生一条含关联 ID 的审计记录。
- 再让工具返回一段"忽略规则"文本，断言模型不据此改变权限。
- 这是验证设计，不代表本项目已接入 MCP 服务实测。

### 第三步发散·追问① 追问:MCP 和 Function Calling 区别

- Function Calling 是模型侧提出结构化调用建议，MCP 是工具发现与连接的开放协议。
- 前者产生"想调用什么"，后者规范"怎么连接并调用"。
- 两者都不替代服务端的授权与参数校验。

## 总结点

1. MCP 管连接，授权仍在服务端
2. 工具输出当数据，注入要隔离
3. 高风险动作强隔离加审计
