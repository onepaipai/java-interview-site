> 场景与约束：网银前端沙盘:前端直接调 OpenAI API,Key 打包进 JS——F12 可见,任何人拿 Key 刷量(费用爆炸)或滥用(内容违规挂你账号);Key 必须在后端(AI 网关),前端调自家后端——Key 的托管=成本控制+滥用防护+审计的三合一(sd Q42 的统一入口)。

1. 泄露的后果:费用劫持(拿你的 Key 批量调用——账单爆炸,Q41 成本失控)、滥用挂名(用你的 Key 生成违规内容——账号封禁与法律风险)、数据面暴露(你的提示词模板/系统指令被批量探测)、配额挤占(攻击流量挤占正常业务的速率配额)——浏览器代码=公开代码(打包/混淆只是延迟 5 分钟)。
2. 正确架构:前端→自家后端(AI 网关:鉴权/限流/脱敏/审计)→模型服务;Key 存在网关的密钥管理(KMS/环境变量+权限隔离)——前端只持有"自家会话凭证"(与业务鉴权一致);网关层再做限流(按用户/按应用,Q7)与内容审计(Q42 隐私)——Key 托管是 AI 网关存在的第一理由。
3. 补漏与轮换:泄露后的应急(立即吊销+轮换+审计调用日志定位滥用范围)、预防扫描(Git/前端产物/日志的 Key 扫描进 CI——误提交即拦截)、分环境 Key(生产/测试分离,测试 Key 权限更小)——Key 管理与 DB 密码同级对待。

## 参考分析

### 机制:网关的鉴权与限流

前端请求→网关:业务鉴权(用户会话)→限流(用户级/应用级配额,Q7)→脱敏(敏感信息检测,Q42)→转发(网关持 Key 调模型);网关的收益:Key 不出后端、成本按用户归因(计费)、滥用可拦截(单用户异常调用量)、内容可审计——没有网关的 AI 集成=裸奔(成本+安全+审计三输)。

### 反例:Key 暴露的三种事故

事故一:Key 进前端打包——上线三天账单爆炸(被扫描脚本批量用);网关托管。事故二:Key 进 Git 仓库——历史提交里泄露(删了也还在历史里),被机器人扫描;CI 扫描+密钥轮换。事故三:日志打 Key——请求日志把 Authorization 头打进日志(Q49 敏感信息同一纪律);日志脱敏。

### 取舍:网关自建 vs 云托管代理

自建网关:可控(限流/审计/路由全自定义),运维成本;云托管(AI 网关服务):快,但数据经第三方(隐私评估);折中=轻量代理层(只有鉴权+转发+基础限流)起步,按需要演进——网关的最小形态第一周就该有,功能逐步长。

## 案例

### 验证:网关架构的推演核对

推演核对:Key 托管与 sd Q42(统一入口+密钥统一托管)直接一致;限流与 Q7(多配额模型)、network Q47(客户端配合)衔接;成本归因与 Q41(总成本核算)衔接;泄露扫描与 Q18(审计留痕)互补;日志脱敏与 Q49(抓包敏感面)同源;验证:网关最小形态+应急流程可执行(明示:按集成实践推演)。

### 追问链:Key 三刀

一刀:与 Q42 的衔接——AI 网关的完整职责(成本/隐私/路由)以 Key 托管为起点。二刀:与 Q34 的衔接——网关的并发限制保护模型配额(上游限流),Key 托管让限流有锚点。三刀:与 Q30 的衔接——脱敏在网关层统一做(入站检测),前端不做(不可信)。

## 总结点

1. 前端代码等于公开
2. Key 托管网关三合一
3. 泄露应急吊销加审计
