## 参考回答

> 场景与约束：网银订单沙盘:订单金额用 double 存储(9.99+0.01≠10.0 的精度损失)——累加/比较/舍入三层的误差积累,与 BigDecimal/long 分的对照(banking B1 实验:double 累加 0.1×1000=99.9999999999986)。

1. double 的二进制本质:IEEE 754 双精度(二进制小数)——0.1 无法精确表示(0.1=循环二进制)——十进制的金额语义在二进制浮点上必然失真:实测累加 1000 个 0.1 偏差 1.4E-12(单笔无感,累加可见)。
2. 三层的误差积累:存储(9.99 的近似表示)、运算(累加/乘除的误差传播)、比较(==判等的假阴性)——每层都放大上一层;金额的"分"级误差在万笔聚合后变成"分"级资损(第 20 题舍入积累)。
3. 正解:long 分(整数运算,零浮点误差)+BigDecimal(十进制语义,展示与低频计算)——double 只允许出现在"非资金的展示估算"(利息预估的 UI)——红线:资金路径零 double(banking 20 题纪律)。

## 参考分析

### 机制:二进制浮点与十进制语义的错位

错位的来源:0.1 十进制=二进制循环小数(0.000110011...)——double 存 64 位近似(相对误差 1E-16 量级);单次运算的误差微小(不可见),累加/乘除的传播使误差到可见量级(1000 次 0.1 累加的 1.4E-12,万笔交易的分级差异)。比较的陷阱:0.1+0.2==0.3 为 false(0.30000000000000004)——金额相等判断必须用 compareTo 或长整型 ==。

### 反例:double 金额的三层事故

事故一,聚合差异:日报表合计与逐笔之和差几分(舍入方向漂移,第 20 题积累)——对账差异单。事故二,比较失效:优惠判断(amount==0)失败(0.0000001 的残留)——业务逻辑错误。事故三,传输放大:double 序列化到前端(JS Number 精度)——显示金额与后端不一致。三条的正解:存储与运算 long 分/BigDecimal、展示格式化、传输字符串或分。

### 取舍:迁移 double 存量的路径

存量 double 字段的迁移:数据库列类型(decimal)通常已对——代码层的 double 使用逐路径替换(读→BigDecimal.valueOf[不走 new BigDecimal(double)]→运算→存 long/BigDecimal);渐进按资金路径优先(第 25 题 distributed 类型边界的风险优先)。红线检查:静态扫描 double 类型的金额字段(命名含 amount/fee/balance)——扫描器进 CI。

## 案例

### 验证:精度误差的断言组

验证:累加断言(B1 实测:1000 次 0.1 的偏差 1.4E-12——BigDecimal 零偏差对照);比较断言(0.1+0.2==0.3 false 的展示);红线扫描断言(金额字段 double 的扫描器拦截)——三组固化 double 红线;long 分与 BigDecimal 的换算用例(往返无损)。

### 追问链:double 红线三刀

一刀:"float 呢?"——更差(32 位)——float 金额同红线;科学计算(非资金)可用。二刀:"Math.round 的陷阱?"——Math.round(2.5)=3(四舍五入)但负数 Math.round(-2.5)=-2(向上取整)——舍入的负数语义与 BigDecimal 的 HALF_UP 不同——统一用 BigDecimal 或显式定义。三刀:"double 的合法用途?"——展示估算(利息预估的 UI 提示)、科学参数(利率模型内部)——进入"资金落地路径"(分录/余额)前必须转换(边界转换函数收口)。

## 总结点

1. 二进制浮点错位十进制语义
2. 累加比较舍入,三层误差积累
3. 资金路径零 double,红线进扫描器
