## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：排查一个"字段读取到默认值"的疑难前，先按 JVMS 第 5 章把类生命周期切成三段，说明每段的输入输出与可观察时点。

1. 加载：读字节码流、按格式解析，在方法区（元空间）建类结构并生成 Class 对象；加载器负责定位与委派。
2. 链接 = 验证（字节码合法性与安全约束）+ 准备（静态字段分配并置零值，不是用户初值）+ 解析（符号引用转直接引用，可延迟到首次使用）。
3. 初始化：执行 <clinit>（静态字段赋值 + 静态块），JVM 保证加锁且只执行一次——这是"类初始化锁"与静态状态竞态问题的根源（见第 21 题）。

## 参考分析

### 第二步扩展① 机制：三段把"有类"与"类可用"分开

- 加载是"把图纸搬进图纸室"，链接是"验真、划线、对号入座"（验证合法性、给静态字段划位并清零、把符号引用钉成直接地址），初始化是"按图纸通一次电"（跑 <clinit>）。
- 类比解释了最常见的误答：`static int x = 42` 的 42 是初始化阶段写的，准备阶段只有 0。

### 第二步扩展② 边界：解析可以延迟，常量是编译期埋好的

- 符号引用解析按需进行（lazy resolution），未用到的引用可能始终不解析。
- `static final int` 字面量是编译期常量，直接内联进调用方常量池，访问它根本不触发目标类初始化（见第 22 题）——这是"引用了类却没加载它的初始化"的经典解释。

### 第二步扩展③ 取舍：验证阶段的安全收益与启动成本

- 验证挡住伪造字节码、类型混淆与栈溢出攻击，是 JVM 安全模型的地基。
- 代价是类加载耗时，AppCDS（Application Class Data Sharing）把已验证的元数据存档复用正是为了省这段。
- 讨论类加载优化时，验证不是可以关掉的开关，而是可缓存的成本。

## 案例

### 第三步发散·验证与推演 对照操作：观察准备与初始化的分工

- 教学验证：`static int a = 42; static final int B = 7;`，在另一个类的静态块里打印 a 与 B，并打印两个类的初始化顺序。预期：a 经过"先 0 后 42"的过程（可用子类引用触发父类初始化的时序观察），B 在调用方直接内联为 7、不触发定义类初始化（用 -verbose:class 验证）。实验可复跑。

### 第三步发散·追问① 追问：为什么构造器不能代替 <clinit>

- 静态状态属于类而非实例，<clinit> 由 JVM 保证线程安全与单次执行。
- 构造器管实例状态。
- 把"全局唯一初始化"写进构造器会导致重复执行与竞态，写成 <clinit> 或持有 holder 类才正确——这也是 holder 单例模式（并发模块第 3 题）的类加载原理。

## 总结点

1. 加载搬图纸，链接验真划线
2. 准备清零，初始化才赋值
3. 编译期常量不点火
