## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银接口沙盘:调用下游偶发第一次请求 Connection reset,重试即成功,日志里毫无规律——典型原因:借出的连接已被对端(或中间设备)关闭,客户端不知道,首包发出才撞上 RST。

1. 根因链条:连接空闲超时(服务端 keep-alive timeout 或中间 NAT 表项老化)→对端/中间设备静默关闭→客户端连接池仍持有→借出→写首包→收到 RST 报错;重试新建连接即成功——偶发、无规律、集中在空闲较久之后的请求。
2. 本机对照:复用基线 0.29ms/req 稳定;而"服务端空闲超时短于客户端池持有时长"的组合正是事故配置——复用收益与借出死连接风险是同一枚硬币的两面。
3. 正解分层:池化策略(客户端空闲超时取服务端的一半,借出时校验 validityTimeout/提前探测)、失败分类(RST 在首包=可安全重试一次,幂等前提下,见 Q10)、监控(reset 计数按池归因)——三层叠加把偶发变成可观测的常规事件。

## 参考分析

### 第二步扩展① 机制:借出时序与 RST 时机

- 时序:请求 N 用完连接归还→空闲 T 秒→服务端 keep-alive 超时发 FIN/RST→客户端池未感知→请求 N+1 借出→TCP 状态未同步→首包出→reset。
- RST 到达时机决定表现:借出前到达(池校验发现,静默剔除)、首包后到达(报错)、响应中到达(整体失败)——第一类无害,后两类要靠重试与校验兜。

### 第二步扩展② 反例:三种失败配置

- 配置一:客户端池 idle 检测 60 秒>服务端 keep-alive 30 秒——必然偶发 reset,频率随空闲分布。
- 配置二:重试无幂等保障——非幂等 POST 重试造成双写(见 Q10/11)。
- 配置三:把 reset 计数当网络故障告警——阈值治标,根因是池与服务端超时错配。

### 第二步扩展③ 取舍:借出校验的成本

- 借出时逐次探测(发 ping/轻量请求):每次多一 RTT,收益换稳定性。
- 带时间戳免校验(池记录归还时间,超过阈值即弃):零额外请求,阈值要准。
- 完全靠重试兜底:代码最简,但非幂等操作不安全。
- 生产常见组合:时间戳剔除+幂等重试一次+reset 计数监控。

## 案例

### 第三步发散·验证与推演 验证:复用基线与失败组合的对照

- 本机实测(JDK 17.0.17,loopback):
~~~
java N4KeepAlive
第2轮 100 请求:复用=29ms(0.29ms/req),close=90ms(0.9ms/req)
~~~
- 推演:复用稳定的基线上,把服务端空闲超时配短于池持有时长即复现首包 reset(依赖对端行为,未在 loopback 强制制造,按 RFC 9112 keep-alive 超时语义推演并明示)。
- 验证:复用收益与借出风险同源(空闲期),池策略取服务端超时一半的经验值成立。

### 第三步发散·发散要点 追问链:借出失败三刀

- **追问①**：为什么重试即成功——新建连接绕过死连接,失败只发生在"借出存量连接"的路径上,重试走新建自然成功
- **追问②·HTTP/2 的对应形态——单连接多流,连接被关**：所有流一起失败,表现为突发批量报错(见 Q17)
- **追问③**：TLS 会话恢复与这个问题的关系——新建连接用 session resumption 省握手,失败重试的代价被压低,重试一次的成本可控

## 总结点

1. 借出死连接首包撞 RST
2. 池超时取对端一半
3. 首包 reset 幂等可重试一次
