## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银索引结构沙盘:千万行数据的等值+范围查询——B+ 树 3 层搞定(每次 IO 16KB 页装千级指针);B 树数据占节点太高、红黑树层数爆炸、哈希无范围。

1. 磁盘 IO 是核心约束:索引查询每层一次页 IO(16KB)——B+ 树矮胖:非叶子只存键+指针(16KB 装约千级指针)→千万行 3 层(千×千×每叶几百行);叶子存数据且双向链表串联——范围查询/排序沿链表顺序扫(一次定位+顺序读);非叶子不存数据=每页容纳更多键(更矮)。
2. vs B 树:B 树数据存在所有节点(非叶子也存)→每页键数少→树更高(4-5 层)→IO 更多;范围查询要中序回溯(跨层跳转);B+ 树数据全在叶子+链表=范围天然高效——数据库几乎都选 B+ 变体(InnoDB/PG)。
3. vs 红黑树/哈希:红黑树=二叉(每节点 2 分支)→千万行 23 层→23 次 IO(磁盘场景不可接受——内存结构才适合);哈希=等值 O(1) 但无序(范围/order by/最左前缀全废)+冲突处理+不支持部分匹配——MySQL Memory 引擎才用,InnoDB 自适应哈希只是热点页加速(不是索引本体)。

## 参考分析

### 第二步扩展① 机制:16KB 页与树高的定量推导

- 主键 bigint 8B+指针 6B=14B/键——16KB 页≈1170 个键(非叶子)。
- 叶子页按每行 1KB 存≈16 行/页→3 层容量=1170×1170×16≈2190 万行——3 次 IO 查任意一行(根节点常驻内存+中层大概率在 buffer pool→实际 1 次 IO 常见)。
- 这是“千万行=3 层”的完整推导(第 44 题引用的估算)。

### 第二步扩展② 反例:结构误用的两种事故

- 事故一:红黑树做磁盘索引(面试自造)——层数=IO 次数爆炸。
- 修复=理解树高×IO 的关系,B+ 树的矮胖是为页结构服务。
- 事故二:哈希索引做报表——范围查询全表扫。
- 修复=等值场景用哈希(内存/缓存键),范围场景 B+ 树——结构选型跟着查询模式走(第 48 题优化同源)。

### 第二步扩展③ 取舍:页大小与树的调参

- 页越大=键越多=树越矮=IO 越少,但单次 IO 读的内容更多(随机访问浪费)+写放大。
- 16KB=InnoDB 折中。
- LSM 树(RocksDB/ bolts)走另一条路:内存写+批量刷盘(写优化,读放大)——TP 场景 B+ 树(读均衡),写吞吐极致场景 LSM(第 152 题 architecture 存储选型同源)。

## 案例

### 第三步发散·验证与推演 验证:树高的实测走查

- 验证:页结构断言(innodb_space/诊断工具看页类型:非叶子 NODE 页只存键+指针,叶子 LEAF 页存行+双向链表指针)。
- 树高断言(千万行表 index tree height=3——information_schema INNODB_SYS_INDEXES 或诊断页)。
- 范围扫描断言(叶子链表顺序读——explain range+页读取模式)。
- 哈希对照(Memory 引擎等值快/范围扫全表)——数据库模块 B+ 树实验可复用。
- 预期:树高与容量推导吻合。

### 第三步发散·发散要点 追问链:索引结构三刀

- **追问①·LSM 树**：写优化(先写 memtable+WAL→批量刷 SSTable→后台 compaction)——读需多层查找(布隆过滤器缓解);B+ vs LSM=读优化 vs 写优化
- **追问②·页分裂与合并**：插入中间→分裂(50/50);删除过半→合并——随机主键的分裂代价(第 49 题主键同源)
- **追问③·索引下推 ICP**：where 条件部分在索引层先过滤(减少回表——EXTRA: Using index condition)

## 总结点

1. 非叶子只存键,叶子存数据带链表
2. 千万行 3 层,IO 决定树形
3. 红黑树内存用,哈希无范围
