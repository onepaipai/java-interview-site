## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：账户余额更新必须同账户串行、不同账户并行。设计按键串行执行器：从全局锁到分片执行器的演进，明确每种的串行保证边界与坑。

1. 最简结构：按 key 哈希到 N 个单线程执行器（或分段队列）——同 key 永远落同一队列自然串行，不同 key 分布到不同队列并行。
2. 必须保证哈希稳定与任务不可变：哈希函数只依赖 key 本身（不能混入时间或随机数）；任务对象在入队后不被外部修改，否则串行执行读到的状态不一致。
3. 已知坑与对策：哈希倾斜使某队列成为热点（对热点 key 二次拆分或本地合并，见第 47 题）；同 key 长任务造成队头阻塞（该 key 的后续任务全部延后，需要超时与降级）；队列无界则整体过载被掩盖（沿用并发基础第 17 题的有界原则）。

## 参考分析

### 机制：把互斥问题转化为"队列归属"问题

对同一 key 的并发更新，加锁是一方"等另一方"，按键分队是"同一方的活永远排在同一条队伍"。类比医院按科室排队：同科室天然串行（一个诊室），不同科室互不影响——把"按什么分组"设计对了，锁就不需要了。哈希就是分诊规则。

### 反例：三个常见的实现事故

一，key 哈希前被 toLowerCase/trim 影响不一致，同 key 落不同队，串行保证悄悄失效；二，N 个执行器用 round-robin 而非按 key 哈希，串行语义完全丢失；三，队列积压后"扩容执行器"导致同 key 换队——正在排队的旧任务与新任务并行执行。每个事故都指向同一句话：串行保证绑定在"key 到队列的映射永不改变"。

### 取舍：Striped 执行器与按需队列的分工

固定 N 条队列（Striped）实现简单、内存有界，代价是不同 key 可能共享队列（伪串行，无害但限吞吐）；按需 per-key 队列并发精确，代价是队列生命周期管理与内存增长（空队列回收有竞态，通常保留或用缓存淘汰）。订单、账户类场景优先 Striped，热 key 少而重的场景才上按需队列。

## 案例

### 对照操作：串行保证的破坏与恢复

教学验证：同 key 高频更新任务分别跑三种实现——全局锁（正确但串行全量）、按 key 哈希分片（正确且并行）、round-robin 分发（错误：同 key 并行）。预期：round-robin 版本出现同账户余额错乱，分片版本结果与全局锁完全一致且吞吐随 key 分布扩展。实验可复跑。

### 追问：同 key 的任务顺序如何证明

串行执行保证"完成顺序等于提交顺序"仅在同一条队列内成立；跨执行器提交（先 A 队后 B 队）没有顺序承诺。验证方法：任务携带序号，执行时断言序号单调递增。把"顺序保证的范围"写进接口文档，是这类执行器最重要的契约。

## 总结点

1. 同 key 同队，异 key 异队
2. 映射一变，串行即失效
3. 热点二次拆，队列要有界
