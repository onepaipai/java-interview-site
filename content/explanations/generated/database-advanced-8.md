## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB 教学场景：流水表按时间翻页，OFFSET 深页越来越慢，且同秒多条记录导致漏读。设计 (created_at, id) 复合游标：稳定性、唯一性与索引匹配三要素。

1. 游标三元组：WHERE (created_at, id) < (:lastTime, :lastId) ORDER BY created_at DESC, id DESC LIMIT n——行定位由"时间 + 主键"唯一确定，同秒并列由 id 补齐，不漏不重。
2. 索引前提：复合索引 (created_at, id) 与游标条件完全同构（MySQL 8.0+ 支持真降序索引 INDEX(col DESC)，之前 DESC 语法被忽略、仍正向存储；无降序索引时 InnoDB 也能反向扫描满足 ORDER BY DESC，降序索引免去反向扫描开销），扫描从游标位置起连续向后——每页成本恒定，与页深无关。
3. 边界协议：游标参数由服务端下发（客户端只透传），防止伪造跳页；过滤条件变更即游标作废（游标绑定查询，见 database-basics 相关题）；时间列用 UTC 存储、展示层转换，避免夏令时回拨造成游标倒退。

## 参考分析

### 第二步扩展① 机制：游标是"上次的精确位置"，不是"第几页"

- OFFSET 翻页按"数数"定位（数过 10 万条），游标按"坐标"定位（从 created_at=T、id=X 的下一条开始）。
- 数数成本随页深线性涨，坐标定位永远走索引一次区间扫描。
- 类比从书签读书 vs 每次从第一页数第几段——书签（游标）把成本变成常数。

### 第二步扩展② 反例：只按时间翻页的漏读

- 同一秒内 3 条流水，LIMIT 翻页以 created_at = 上页最后时间 作 WHERE 条件续读：下一页从"大于该时间"开始，同秒的第 2、3 条被跳过。
- 修复即补上 id 维度：元组比较使同秒内按 id 精确续接。
- 这是"游标必须唯一化补列"的标准事故。

### 第二步扩展③ 取舍：游标与 OFFSET 的产品边界

- 游标只支持"下一页/上一页"连续浏览，不支持跳页与总页数显示（需要数总量，成本回来了）。
- OFFSET 支持跳页但深页退化。
- 多数流水场景（账单、日志、动态）用户只关心下一页——游标的体验损失接近零，性能收益无上限。
- 产品允许时优先游标。

## 案例

### 第三步发散·验证与推演 对照操作：同秒并列与深页的对照

- 教学验证：插入同秒 100 条流水，分别用"仅时间游标"与"时间+id 元组游标"翻页核对总数。
- 再对 100 万行执行 OFFSET 999990 与元组游标各翻一页。
- 预期：前者漏读同秒记录，后者完整。
- 深页 OFFSET 耗时秒级、元组游标毫秒级。
- 实验可复跑。

### 第三步发散·追问① 追问：为什么还要带上 id 而不只是 created_at 索引

- created_at 二级索引的叶子本身就是 (created_at, 主键) 复合结构——id 天然是排序的第二维。
- 显式写出元组条件才能让优化器把这个隐含有序性用足。
- 省略 id 条件时，同秒并列的边界交给引擎按主键隐式处理，语义上没有"不漏"的保证。

## 总结点

1. 游标是坐标，不是页码
2. 时间加 id，同秒不漏
3. 索引同构，每页恒定成本
