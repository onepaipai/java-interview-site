## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 7 教学场景：实例 A 的任务超时后锁易主给 B，A 完成后直接 DEL——删掉了 B 的锁，C 又获锁，B、C 并发执行。用持有者校验消除"释放他人锁"的竞态，给出 Lua 原子比较删除的正确写法。

1. DEL lockKey 不校验持有者：锁的值是唯一 token（实例+请求标识），任何能连接的客户端都能删——任务超时后锁易主，旧持有者的 DEL 会误删新持有者的锁。
2. 原子校验删除：Lua 脚本内 `if redis.call(GET, k) == token then DEL`——比较与删除单命令执行，不可分割；分两步（GET 判断再 DEL）重新引入竞态窗口（GET 后锁可能易主）。
3. token 的粒度必须是"本次请求"（实例 ID + UUID 或线程级），不是实例级——同一实例的多个并发请求会互相误删（见并发进阶第 45 题的三要素深化）。

## 参考分析

### 机制：DEL 是"对锁的无差别拆除"

分布式锁没有任何"你是持有人"的内置校验——DEL 就是物理拆除，不管锁属于谁。类比寄存的保险柜：取钥匙前必须核对编号（token），否则任何人报编号就能开柜。Lua 比较删除 = 柜台核对编号后才交钥匙，两步原子不可分割。

### 反例：误删引发的并发链式事故

A 持锁 30 秒执行，锁 10 秒过期 → B 获锁 → A 完成 DEL → C 立即获锁 → B、C 并发写同一资源。事故链的三环：长任务、短租约、无校验释放。修复校验只断最后一环（A 的 DEL 失败）；根治还需任务时长与租约匹配（看门狗）或资源端栅栏（并发进阶第 46 题）。

### 取舍：Lua 校验删除与 GETDEL 的版本差异

Redis 6.2+ 的 GETDEL 可以原子取出锁值——取出后判断"是自己的"再决定是否需要重新设置（非典型场景）；标准场景仍用 Lua 比较删除（锁留在原地，只是确认后才删）。两者都原子；Lua 版本语义更直观（"是我的才删"），兼容老版本。

## 案例

### 对照操作：误删的链式复现与校验修复

教学验证：A 持锁后人为过期 → B 获锁 → A DEL。预期：无校验版 B 的锁被删、C 获锁形成 B/C 并发（用计数器验证并发）；Lua 校验版 A 的 DEL 返回 0、B 的锁完好。实验可复跑，事故链三环在日志中逐环呈现。

### 追问：为什么"先 GET 比较再 DEL"不安全

GET 与 DEL 之间锁可能易主：GET 时值还是自己的、DEL 时已是别人的——检查通过不等于删除合法。竞态的通病：检查与动作分离就有窗口。这也是"凡校验必原子"的一般化原则（同并发进阶第 34 题限流扣减、第 11 题的加锁原子）。

## 总结点

1. DEL 无差别，先验 token
2. 比较与删除一个 Lua
3. token 粒度到请求级
