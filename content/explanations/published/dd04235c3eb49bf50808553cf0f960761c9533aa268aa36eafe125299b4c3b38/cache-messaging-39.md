> 场景与约束：Java 17 / Kafka 教学场景：为每条消息打 trace 后监控标签爆炸（消息 ID 作标签），监控系统内存告警。区分"消息级追踪"与"指标监控"两个维度：追踪进日志/链路系统、指标进聚合监控，基数纪律各不相同。

1. 高基数的来源：把无界值（消息 ID、订单号、用户 ID）当作监控指标的标签——每个新值创建一个新时间序列，序列数随业务量无限增长，监控系统内存与查询崩溃。
2. 正确分层：追踪维度（单条消息的完整链路）用 trace ID 贯穿日志与链路追踪系统（按 trace ID 检索）；监控维度用有界标签（topic、分区、错误类型、消费组）+ 聚合数值（速率、延迟分位、失败率）。无界值永远不进指标标签。
3. 联动的桥：日志与链路系统带 trace ID 与业务键索引，故障时从"指标异常"跳到"trace ID 列表"再跳到"单条消息全链路"——三层从聚合到个案逐级下钻，各系统各管各的基数纪律。

## 参考分析

### 第二步扩展① 机制：指标是"聚合的形状"，追踪是"个案的路径"

- 指标回答"这类消息整体表现如何"（速率/延迟/失败率），必须聚合（维度有界）。
- 追踪回答"这条消息经历了什么"（逐跳明细），天然无界。
- 类比人口统计与个人档案：人口统计按年龄段聚合（有界维度），个人档案按身份证索引（无界）——把身份证号当统计维度，统计系统就崩了。

### 第二步扩展② 反例：消息 ID 进标签的三重伤害

- 一，序列数爆炸：每条消息一个 series，千万条消息千万序列，TSDB 内存耗尽。
- 二，查询退化：按标签查询变成全序列扫描。
- 三，噪音淹没：有用的有界维度（topic、错误类型）被无界标签稀释。
- 三重伤害都是"把个案维度塞进聚合系统"的代价。

### 第二步扩展③ 取舍：采样追踪与全量追踪的选择

- 全量追踪：每条消息都打 trace——定位最全、存储与开销最大。
- 采样追踪：错误请求 100% 采样、正常请求按比例（如 1%）——错误必可查、正常路径靠聚合指标。
- 按"排障靠正常 trace 还是错误 trace"决定：多数排障由错误触发，错误全采 + 正常低采是性价比最优。

## 案例

### 第三步发散·验证与推演 对照操作：三层下钻的完整演练

- 教学验证：注入一条消费失败的消息，从监控面板（失败率上升的 topic/错误类型标签）→ 点击跳转日志（trace ID 检索）→ 链路视图（生产、存储、消费逐跳耗时与状态）。
- 三层下钻的每次跳转都由 trace ID 桥接，演练可复跑。

### 第三步发散·追问① 追问：为什么"消费失败的错误率"标签用错误类型不用错误堆栈

- 错误类型（超时/反序列化失败/业务拒绝）是有界枚举（十几个值），堆栈是近乎无界的文本（每处代码一个变体）。
- 有界枚举让"按错误类型分组的失败率"成为可用的告警维度。
- 堆栈进日志与追踪系统（个案层）。
- 标签的基数纪律：每个标签的取值集合必须有界且已知。

## 总结点

1. 指标聚合有界，追踪个案无界
2. 无界值永不进标签
3. trace ID 桥接三层下钻
