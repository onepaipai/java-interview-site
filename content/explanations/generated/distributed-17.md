## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银订单沙盘:雪花 ID 生成器所在机器 NTP 校时回拨 50ms,同一毫秒的序列号被复用,生成重复订单 ID 触发唯一约束冲突,下单失败率瞬时抬升。用回拨注入实验说明检测-应对策略族。

1. 雪花 ID 的唯一性建立在"时间单调"假设上:回拨打破假设,同毫秒+同序列=重复 ID;检测回拨是第一道防线。
2. 应对策略按回拨幅度分级:小幅等待(≤几百 ms)、按序号自旋/借位、大幅拒绝服务并告警——策略要写进发号器而不是靠 NTP 配置碰运气。
3. 替代思路:号段模式(DB 发号段)与纯随机+查重不依赖时钟;时钟依赖越少,发号器越稳,但趋势性越差。

## 参考分析

### 机制:回拨如何制造重复与检测

雪花结构:时间戳(41 位)+机器号+序列(12 位/4096)。同一毫秒内序列自增保证唯一;回拨后"同一个墙钟毫秒"被重新经历,序列从 0 重新自增 → 与回拨前生成的 ID 全同。检测:发号器记录 lastTs,新墙钟 < lastTs 即回拨(本机实验实测:t=100 发号后 t=99 返回 -1 拒绝)。检测只能发现,不能消除——消除靠应对策略。

### 反例:无检测发号器的重复 ID 事故

沙盘:回拨 50ms 未检测,新 ID 撞唯一约束,下单批量失败;更糟的形态是存储层没唯一约束——重复 ID 静默入库,对账时两笔订单共用一个 ID。修复分层:发号器层检测+拒绝(快速失败优于发重复);应用层对 -1 返回做重试或换实例;存储层唯一约束兜底(永远要有)。运维层:NTP 配置用渐变校时(slew)而不是跳变(step),回拨幅度可控。

### 取舍:三种发号方案的时钟依赖

雪花类:趋势递增、索引友好,强依赖时钟(需回拨防护)。号段模式:DB 批量发号段,本地内存分配,无时钟依赖,但趋势性弱、DB 是依赖点。UUIDv7(时间有序)仍依赖时钟,UUIDv4 无序无依赖但索引差。选择:强趋势需求(主键聚簇)用雪花+完整回拨防护;可接受无序用号段;发号器是全局单点风险,多机房部署要加机房位或按机房独立号段。

## 案例

### 实证:回拨注入的拒绝行为

本机实验(Java 17.0.17,D17):
```
t=100: 409600
t=100: 409601 (同毫秒递增序列)
t=99(回拨1ms): -1 (-1=拒绝发号,防止重复 ID)
t=101: 413696 (时钟恢复后继续)
```
验证:同程序重跑一致;把检测去掉重跑,t=99 会发出与 t=100 同结构的 ID(序列从 0 重新分配)——重复的机制直接可见。

### 追问链:发号器三刀

一刀:"同毫秒序列耗尽怎么办?"——自旋到下一毫秒(常用)或扩展序列位(减少时间位);实测 -2 分支即序列耗尽信号,发号器要把它当背压信号而不是异常。二刀:"机器位怎么分配?"——静态配置(运维分配)或一致性哈希/中心分配;机器位冲突=两个实例发同一 ID,比回拨更隐蔽,分配记录要持久化。三刀:"对账层怎么兜底?"——业务唯一约束(订单号唯一索引)必须与发号器独立存在;发号器是优化,唯一性责任在存储,这与第 15 题"锁只是优化"同一哲学。

## 总结点

1. 时间单调是假设,回拨必检测
2. 小幅等待大幅拒,策略写进发号器
3. 唯一性靠约束,不靠发号器
