## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 教学设计：订单外部编码存于 VARCHAR 索引列，应用却把编码以数值参数绑定。比较字符串与数值比较的语义、结果集合和访问计划。

1. 比较时的类型转换可能改变索引列的有序定位条件，也可能改变相等语义。例如字符串索引列与数字比较，不能直接沿用普通字符串等值查找结论。
2. 应让列类型、驱动参数类型、字符集和排序规则契约匹配；不是所有隐式转换都必然全表扫描，要确认转换发生在哪一侧及实际访问路径。
3. 先保证结果语义正确，再看执行计划和扫描量；给索引列随意加 CAST 虽能消除报错，也可能进一步破坏可定位性。

## 参考分析

### 比较语义：看起来相同的参数可能代表不同关系

VARCHAR 保存的业务编码可能包含前导零或非纯数字，数值比较会使用不同于字符等值的规则，多个不同字符串可能转换为相同数字。MySQL 官方说明字符串索引列与数字比较不能按该索引快速查找。因此问题不只是性能，也可能把本应不同的订单编码当成匹配值，甚至产生警告。类比身高尺用厘米刻度却报了英尺数字：单位（类型）不匹配，比较结果全错——索引要的是同一种尺子。

### 定位条件：参数转换和列转换要分开

如果数据库把常量转换成适合索引的类型，仍可能利用有序索引；若需要对大量列值逐个转换，则难以按原索引直接定位。函数索引等另有适用条件，不能用一条“隐式转换必失效”覆盖所有表达式。字符集与排序规则不一致时，同样要查看实际比较和转换，而不是只看 Java 变量类型。

### 修复边界：从接口契约到驱动绑定

将外部编码定义为字符串，贯通 DTO、校验、持久层和驱动参数绑定，避免先转成数值后再补成字符串导致前导零丢失。对历史混合数据先确认清洗与唯一性影响，再修改列或索引。修复后要比较结果集合、警告及计划，而不是仅确认 SQL 执行成功。

## 案例

### 输入矩阵：带前导零、普通数字和字母编码

隔离库准备多个编码值，分别以明确字符串参数和数值参数执行同一查询，记录命中集合、警告、所选索引和扫描量。预期能观察类型契约不同可能改变匹配及定位，具体转换细节按目标版本报告。不要把日志打印出来都像 123 当成驱动绑定类型相同的证明，应检查实际参数类型。

### 追问：直接 CAST 列为什么仍然慢

将候选修复分为正确绑定参数、转换常量和转换索引列三类，比较语义及计划；只有业务确实需要表达式检索时再评估对应索引设计。验证外部编码仍保持精确值、旧客户端兼容且不同租户不混查。此案例未执行目标引擎实验，不能把文档规则扩大为所有转换组合的已测结论。

## 总结点

1. 单位不匹配，比较全错
2. 类型契约先保证匹配语义
3. 转换哪一侧决定定位条件
4. 计划与结果集合都要比较
