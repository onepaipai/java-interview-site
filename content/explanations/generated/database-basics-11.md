## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 运维教学场景：排查慢语句时看到 EXPLAIN ANALYZE，准备把它直接加在生产 SQL 前。需要先区分普通估算计划与实际执行，以及语句支持范围。

1. EXPLAIN ANALYZE 会实际执行受支持的语句并收集迭代器耗时、行数等，不能把它当成只显示计划的安全前缀。即使 SELECT 也会消耗真实资源并可能涉及锁或函数副作用。
2. MySQL 8.4 文档列出的支持包括 SELECT、TABLE 和多表 UPDATE、DELETE；不能据此推断任意写语句都支持，或用语法不支持作为安全保护。
3. 先确认目标版本、语句、权限和可控数据，优先隔离环境；事务回滚也不是所有 DDL、外部副作用和资源影响的通用保险。

## 参考分析

### 估算与执行：诊断本身就是负载

普通 EXPLAIN 主要帮助理解优化器选择，ANALYZE 则真正执行并给出观测值。长扫描、大排序和锁定查询会占用 CPU、IO、内存或锁，结果不返回所有业务行也不表示内部没有做工作。诊断应有时间、并发与观察预算，不能在故障期间无界重复运行昂贵语句。类比彩排就是正式演出：ANALYZE 真的把语句跑一遍——对写语句彩排，观众（数据）已经被改变了。

### 版本与语句：支持矩阵要具体核对

MySQL 8.4 的 EXPLAIN ANALYZE 使用 TREE 输出，每个迭代器行显示 actual rows（实际行数）与 actual loops（执行轮次），对照估算 rows 即可发现统计失真——偏差大就该更新统计或加直方图；支持语句类型有明确限制。运行前先判断它是否受支持、会修改哪些对象、是否调用具有副作用的函数，以及是否有足够隔离的测试数据，不能只把关键字拼到任意语句上。

### 回滚边界：数据恢复不等于消除所有影响

即便某种写操作可在事务内回滚，执行期间的锁竞争、日志、资源占用和外部调用也不会被事后回滚抹除；部分 DDL 会隐式提交。更合适的流程是先脱敏复现数据和负载，必要的线上诊断另有明确范围及停止条件。不要给出“加 BEGIN 后就能安全分析一切”的建议。

## 案例

### 验收设计：只在可丢弃环境观察执行

在隔离 MySQL 准备小表，先对只读查询对照普通 EXPLAIN 与 ANALYZE 输出，确认前者估算、后者实际行数和 loops 的区别；若研究受支持写语句，独立记录执行前后数据。预期实验明确证明语句被执行，而不是把耗时较短或结果是计划文本当成未执行的证据。

### 故障追问：诊断查询自己成了慢请求

限制实验数据和执行时间，制造受控慢读并验证停止路径，同时观察连接与锁是否释放；不要依赖客户端断开就认定服务端停止。记录测试版本、语句类型和状态。本机没有对应引擎执行证据时保留此项待验证，不将 H2 的 EXPLAIN 输出冒充 MySQL ANALYZE 行为。

## 总结点

1. 对写语句彩排，数据已被改变
2. ANALYZE 会实际执行
3. 版本和语句支持范围必须确认
4. 回滚不能抹除资源与外部影响
