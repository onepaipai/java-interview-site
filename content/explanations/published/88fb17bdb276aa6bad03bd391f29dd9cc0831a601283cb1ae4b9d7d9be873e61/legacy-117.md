## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银助手沙盘:用户问"帮我查余额",模型不直接回答而是输出一个结构化调用(get_balance(account_id))——Function Calling 让模型从"语言生成"升级为"工具调用编排"。

1. 流程四步:一,注册工具(名称/描述/参数 JSON Schema 传给模型);二,模型决策(基于用户输入判断是否调用工具+生成参数 JSON);三,客户端执行(解析参数→调用真实 API→返回结果);四,结果回喂(工具结果作为新消息传入→模型基于结果生成回答)。
2. 模型的角色=决策与参数生成,不直接执行工具——执行由客户端代码完成(模型只输出"调用意图");这保证了安全边界(模型不能直接触达数据库/外部 API,第 29 题四道闸)。
3. 参数校验三层(第 37 题):结构层(JSON Schema 校验——类型/必填/格式)、业务层(余额/状态机——工具实现的校验)、权限层(调用主体是否有权——服务端强制);结构层失败可回喂模型重试(有限次),业务/权限层失败不回喂。

## 参考分析

### 第二步扩展① 机制:模型怎么"知道"该调什么工具

- 工具注册时传入的描述+参数 Schema 是模型的选择依据——模型从描述中匹配"用户意图与工具功能的相似度"。
- 工具描述的质量直接影响调用准确率(模糊描述=误调用)。
- 参数 Schema 的清晰度决定参数生成质量(缺必填标注=漏参数)。
- 类比 API 文档:文档写得好,调用才对。

### 第二步扩展② 反例:Function Calling 的三种事故

- 事故一:工具描述模糊——两个工具描述相似("查余额"vs"查交易明细"),模型选错。
- 修复=描述差异显式化+示例。
- 事故二:参数幻觉——模型编造了 schema 中不存在的字段。
- 修复=结构层 JSON Schema 校验(第 37 题)。
- 事故三:工具调用无权限校验——注入(第 25 题)诱导模型调用了用户无权的工具。
- 修复=权限层服务端强制(第 29 题)。

### 第二步扩展③ 取舍:原生 Function Calling vs 提示词模拟

- 原生 API(OpenAI/Anthropic 的 tools 参数):模型训练时学过工具调用,格式稳定准确率高。
- 提示词模拟(在提示词中描述工具+要求模型输出 JSON):通用(不依赖 API)但格式不稳定(需解析+重试)。
- 生产用原生。
- 提示词模拟用于原型/不支持原生的模型。

## 案例

### 第三步发散·验证与推演 验证:Function Calling 的推演核对

- 推演核对(教学示例):注册 3 工具(查余额/转账/查流水)×三类用户输入(明确查余额/模糊"我的钱"/转账请求)——预期:明确输入正确调用对应工具+参数正确。
- 模糊输入可能选错工具(标注)。
- 转账请求走权限层校验。
- 验证:调用断言(工具选择/参数正确性/权限拦截)可程序化。
- mock 工具可复跑。

### 第三步发散·追问扩展 追问链:FC 三刀

- **Q1：并行调用(一次调多个工具)?**
  - 答：模型可在一条回复中输出多个工具调用(并行执行提高效率);各调用独立校验+执行,结果统一回喂——并行失败处理(第 39 题编排)。
- **Q2：工具调用的结果回喂格式?**
  - 答：以 role=tool 的消息传回(与用户/助手消息区分),模型基于结果生成回答——结果也是不可信输入(第 25 题),过长结果截断(第 26 题)。
- **Q3：Function Calling 与 RAG 的组合?**
  - 答：模型可先调用检索工具获取知识再回答——RAG 是工具的一种,不冲突;组合编排(先检索再调用业务工具)由 Agent 框架管理(第 34 题状态机)。

## 总结点

1. 模型决策+客户端执行=安全边界
2. 工具描述=调用的选择依据
3. 三层校验,结构层可回喂重试
