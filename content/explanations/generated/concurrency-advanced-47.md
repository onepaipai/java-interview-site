> 场景与约束：Java 17 教学场景：秒杀活动中某明星商品把分片锁、缓存分片、数据库行三条链路全部拖慢，其他商品也被殃及。建立热点键的识别方法与三级治理手段（二次拆分、本地合并、请求合并）。

1. 识别的证据链：分片维度监控（每片的锁等待/请求量）——热点键表现为单片指标异常突出；慢查询与锁事件的 key 聚类；应用层按 key 统计 QPS 排名。三条证据指向同一个 key 才定罪。
2. 危害的机制：任何按 key 分片的隔离设计，在单 key 内部都退化为全局串行——热点 key 把"分片并行度"清零，且它的等待可能溢出到共享资源（连接池、队列）殃及邻居。
3. 治理三级：一是分散（二次哈希把一个逻辑 key 拆成 N 个物理槽，读写合并还原，代价是读侧聚合）；二是本地消解（本地缓存/请求合并把到达流量折叠，见第 41 题）；三是下沉（把该 key 的原子性下沉数据库原子更新，绕开应用层分片瓶颈）。按改造成本递增选。

## 参考分析

### 机制：分片隔离在单 key 上必然失效

分片的前提是"负载在 key 之间均匀"——热点键违反前提。类比景区 10 条检票通道：普通游客均匀分布各自排队，但某明星的粉丝全部挤 3 号通道——通道数再多也救不了 3 号。热点治理不是加通道（分片已到头），而是把 3 号通道的人群分流（二次拆分）或让很多人共用一次检票（合并）。

### 反例：二级缓存不监控分片导致的误诊

DBA 看到"某行锁等待高"先给数据库加索引加机器，无效；应用侧看全局平均 QPS 平稳，也认为正常——两边的平均值都把热点抹平了。定位转折点是分片级与 key 级的分布数据。教训：热点键的识别必须用分布（P100/最大桶），平均值在热点场景下全部失效。

### 取舍：二级拆分的读代价

逻辑 key 拆 N 个物理槽后，写分散到 N 把锁（吞吐恢复）；读需要聚合 N 槽（N 次访问），且"总量恰好为库存"的不变式从单行原子变成跨槽聚合——超卖的判定要从"每槽余量之和"来（聚合窗口内的轻微超卖需业务容忍或收紧槽余量）。拆分是拿读复杂度换写吞吐，按读写比例决策。

## 案例

### 对照操作：热点键的定位与治理对照

教学验证：8 片分段锁 + 1 个热点 key 占 60% 流量。预期：分片监控显示热点片锁等待占满，其余 7 片空闲；治理一（二次哈希×8）后热点片等待消失、读侧聚合成本上升；治理三（数据库原子更新）绕开应用分片。三组吞吐曲线并排，实验可复跑。

### 追问：为什么本地缓存对热点键特别有效

热点 key 的读请求高度重复（同一商品详情被反复查询），本地缓存命中率天然极高——把到达分片层的流量折叠几个量级。风险是缓存一致性与多节点视图差（第 38 题协议管本地一致）；对"允许秒级陈旧"的读场景，本地缓存是热点治理里性价比最高的一级。

## 总结点

1. 平均值会抹平热点，看分布
2. 拆分散写、缓存消读、下沉保原子
3. 治理成本递增，逐级选
