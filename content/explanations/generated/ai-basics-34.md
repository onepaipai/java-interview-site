> 场景与约束：网银平台沙盘:大促活动接入 AI 功能,并发 5000 打向模型 API——上游限流(429),全部失败;并发限制=入口并发池+多级配额+排队与超时,保护上游配额与自己(排队雪崩)——并发设计是模型集成的稳定性地基(reliability Q20 的限流+背压在模型场景)。

1. 三级限制:入口并发(自家网关的信号量/连接池——同时处理中的模型请求数上限,超出排队或拒绝)、用户/应用配额(按租户的并发与 RPM 配额(Q7)——防单方挤占)、上游配额对齐(模型 API 的 RPM/TPM 限制——总并发×平均 token≤上游配额,超配=批量 429);三级联动:上游配额是硬顶,自家并发≤硬顶×安全系数。
2. 排队与反馈:超出并发的请求排队(有界队列+排队超时——network Q9 排队年龄)或快速拒绝(429+Retry-After——Q47 客户端配合);背压传导:上游 429→网关感知→降速(令牌补充变慢)→调用方排队——闭环反馈防止重试风暴(Q33);优先级(核心业务优先放行——大促时客服 AI 与内部工具的优先级分层)。
3. 监控与自适应:并发水位/排队年龄/上游 429 率三指标(Q23);自适应并发(根据上游 429/延迟动态调节并发上限——AIMD 加法增乘法减)——静态配额在流量波动下失准,自适应是进阶。

## 参考分析

### 第二步扩展① 机制:配额的换算与对齐

- 换算:上游限 RPM(请求/分)与 TPM(token/分)——自家并发上限=上游 RPM×平均时长的倒数(每请求占用配额窗口的份额)。
- TPM 对齐:平均输入+输出 token×QPS≤TPM×安全系数——token 维度的配额常被忽略(长回答快速烧 TPM)。
- 多模型路由(sd Q42)时各上游独立核算。

### 第二步扩展② 反例:并发设计的三种事故

- 事故一:无入口并发——上游 429 全量失败,重试风暴(Q33)雪上加霜。
- 入口池先行。
- 事故二:排队无界——5000 请求排队,队列内存爆炸+排队年龄 10 分钟(等到了也没意义)。
- 有界+超时。
- 事故三:忽略 TPM——RPM 达标但长回答烧穿 TPM,批量 429。
- 双维度核算。

### 第二步扩展③ 取舍:排队 vs 拒绝的平衡

- 排队:平滑波动(短时突发),延迟增加。
- 拒绝:快速反馈(客户端可退避重试),体验差。
- 混合:短队列(秒级等待)+超限拒绝——按上游配额的"波动容忍"设计:上游配额紧→多拒绝,配额松→多排队。

## 案例

### 第三步发散·验证与推演 验证:三级限制的推演核对

- 推演核对:入口并发与 network Q30(背压)、reliability Q20(限流背压)同构。
- 配额对齐与 Q41(成本核算的 token 维度)衔接。
- 自适应与 sd Q46(水位反馈)同构。
- 429 配合与 network Q47(Retry-After 闭环)直接衔接。
- 验证:三级设计+排队语义可执行(明示:按限流实践推演)。

### 第三步发散·发散要点 追问链:并发三刀

- **追问①**：与 Q33 的衔接——并发限制是"僵尸请求"的兜底闸(重试也过池)
- **追问②**：与 Q42 的衔接——AI 网关的并发限制按应用/租户分层,成本与配额统一管理
- **追问③**：与 sd Q46 的衔接——恢复期的限速放行(水位反馈)在模型调用场景同样适用

## 总结点

1. 上游配额是硬顶
2. 排队有界拒绝快速
3. token 维度别漏算
