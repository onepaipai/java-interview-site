## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 教学设计：两个请求都读到库存 5、版本 0，分别尝试扣减。使用同一条条件 UPDATE 比较期望版本，并在成功时增加版本，检查影响行数。

1. 版本必须进入同一条原子 UPDATE 的 WHERE 条件，成功时再更新版本，才能把“读到的仍是当前状态”变成数据库执行的条件。只在内存比较会留下竞争窗口。
2. 按受控主键更新时，影响 1 行表示该次条件成立，0 行可能是版本冲突、库存条件失败、行不存在或无权访问，要按协议区分，不能直接覆盖重试。
3. 重试需重新读取并重做业务判断；乐观版本不等于数据库无锁，也不自动保护多行不变式或已发生的远程动作。

## 参考分析

### 第二步扩展① 原子比较：把检查与修改放在一条语句

- 先 SELECT version，再不带 version 的 UPDATE，会让两个请求都通过检查后覆盖彼此。
- 条件更新将比较、业务条件与修改交给数据库在执行时判断，成功路径同时增加版本，过期写就无法沿用同一期望值。
- 字段溢出、版本初始化与其他写入口同样要规范，否则绕过版本更新的路径仍会破坏协议。
- 类比文件编辑的基于版本三保存：提交时声明所见版本，服务器发现已是版本五就拒绝——检查与写入必须同一条语句。
- ABA 视角：纯值比较（WHERE balance=5）识别不了 A→B→A 的中间变化。
- 版本号单调递增天然免疫——乐观锁用版本号而非业务值比较，与 CAS 的 ABA 问题同源。

### 第二步扩展② 结果解释：0 行不是一种万能冲突码

- 下面样例中第二次使用旧版本更新为 0 行，但真实接口还可能因租户不匹配、记录已删除或库存不足而不匹配。
- 对外错误不能泄露无权知道的资源状态。
- 必要时在授权范围内重新读并分类。
- UPDATE 每次成功都改变版本，避免把未改变值的行数语义混入这个 CAS 样例。

### 第二步扩展③ 业务边界：单行比较不替代整笔事务

- 一个版本字段只保护对应更新条件，跨多行余额约束仍需合理事务与冲突处理。
- 失败后如果直接去掉版本重试，就等于取消保护。
- 正确流程是获取最新状态并重新评估请求是否仍允许。
- 高冲突时还要限制重试次数和退避，比较与悲观协调的成本，而不是假设乐观必然更快。

## 案例

### 第三步发散·验证与推演 完整 SQL：同一期望版本只成功一次

- 临时表初始库存 5、版本 0，连续两条语句模拟持有同一旧版本的两个写者。
- 预期两次 UPDATE 影响行数依次为 1、0，最终 SELECT 为库存 4、版本 1。
- 原样 SQL 在 H2 的结果只验证这个串行语义样本，并不证明目标引擎的并发锁行为。
~~~sql
CREATE TEMPORARY TABLE version_example (
  id INT PRIMARY KEY, stock INT NOT NULL, version INT NOT NULL
);
INSERT INTO version_example VALUES(1, 5, 0);
UPDATE version_example SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 0 AND stock >= 1;
UPDATE version_example SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 0 AND stock >= 1;
SELECT stock, version FROM version_example WHERE id = 1;
~~~

### 第三步发散·追问① 并发追问：两个连接同时提交和失败重算

- 在目标数据库用两个独立事务都先读取版本 0，再并发执行条件更新，检查影响行数、等待和最终版本。
- 失败方重新读取后按业务重新决定。
- 补测库存不足、删除、租户条件和重复业务请求。
- 预期冲突不会静默覆盖，但是否允许重新扣减要由请求幂等与业务规则确定，不能由简单重试循环自动决定。

## 总结点

1. 基于版本三保存，检查写入一条语句
2. 版本进入原子更新条件
3. 影响行数结合业务条件解释
4. 冲突后重读重算，不移除保护
