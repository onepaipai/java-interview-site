## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银报表协作沙盘:两人同时编辑同一单元格,后保存者覆盖前者——丢更新;协作文档的并发编辑=操作转换(OT)或 CRDT:本地立即生效、操作序广播、收敛算法保证多端一致——"各自改各自的,最终一致且不丢"。

1. 两种算法:OT:客户端发操作,服务端定序并按并发操作转换位置参数后广播——中心化,算法精细;CRDT:操作设计为可交换(带唯一 ID),任意顺序应用最终收敛——去中心化,元数据膨胀。Google Docs=OT 系,现代协作文档多走 CRDT(Yjs 类)。
2. 工程骨架:WebSocket 长连接(编辑操作流,network Q31 心跳)、服务端定序器(OT)或无需定序(CRDT)、离线编辑缓冲(断网编辑,恢复后同步)、光标与选区的存在性广播(不进文档状态);一致性校验(定期文档哈希比对,分叉告警)。
3. 与粗粒度锁的对比:悲观锁(编辑时锁文档/行):简单但协作性差(排队);段落锁:折中;OT/CRDT:字符级并发,体验最好,复杂度最高——按协作粒度需求选,内部报表用段落锁可能已够。

## 参考分析

### 第二步扩展① 机制:收敛与定序

- OT 三角:本地立即应用→发送操作→服务端定序→转换(与并发操作合成)→广播→各端应用转换后操作——正确性依赖转换函数的完备性(TP1 性质)。
- CRDT:操作天然可交换(唯一 ID 消除冲突),传输丢失/乱序不影响收敛。
- 两者的共同前提:操作可序列化+网络重传不产生重复(操作 ID 幂等,Q11 同构)。

### 第二步扩展② 反例:协作编辑的四种事故

- 事故一:后写覆盖(无 OT/CRDT)——丢编辑,用户数据丢失级事故。
- 并发算法是底线。
- 事故二:操作 ID 不幂等——网络重传使同一插入出现两次。
- 操作唯一 ID。
- 事故三:权限并发——A 撤销 B 的编辑权限,B 的在途操作仍被应用。
- 权限快照+操作校验(与 Q14 撤销衔接)。
- 事故四:大文档性能——百万字文档的 OT 转换成本 O(操作×文档)。
- 分段(按章节)加载与合并。

### 第二步扩展③ 取舍:OT vs CRDT vs 锁

- OT:中心定序可控,算法实现难(转换矩阵)。
- CRDT:离线友好(去中心收敛),元数据膨胀(每个字符 ID)。
- 锁:实现最简,协作粒度粗。
- 内部工具(低并发协作)锁够用,产品级协作文档 CRDT 为主流——按"并发编辑强度"付复杂度。

## 案例

### 第三步发散·验证与推演 验证:操作幂等的推演核对

- 推演核对:操作唯一 ID 的重传幂等与 Q11 幂等键/SD1 实测(重放被账本吸收)同构。
- 定序与 Q23 事件总线的顺序键同构(文档 ID 内操作序)。
- 离线缓冲的收敛与 distributed D16(按版本仲裁反熵)同源。
- 验证:并发编辑的"不丢+收敛"机制在既有实测模式上成立(明示:OT/CRDT 行为未实测,按算法文献推演)。

### 第三步发散·发散要点 追问链:协作三刀

- **追问①**：与 Q26 上传的衔接——文档快照(版本存档)走对象存储,增量操作日志与快照的配合(快照+其后操作=任意时刻状态)
- **追问②·版本历史与回滚——回滚到历史版本**：按快照重建,协作中的回滚要通知在线编辑者(避免覆盖他们未保存的工作)
- **追问③**：与 Q45 题库协作的衔接——本仓库题库的编辑协作是"文件+git"粗粒度模型,协作强度低够用——工具按协作强度选的实例

## 总结点

1. 本地生效服务端定序
2. 操作幂等重传无害
3. 按协作强度选算法
