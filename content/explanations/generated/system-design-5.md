## 参考回答

1. 支付成功但订单未更新时进入待同步，不能当作支付失败让用户再付。
2. 回调验签后可靠保存 Inbox，再异步核对和重试；订单迁移、处理标记与履约 Outbox 同事务提交。
3. 事件和支付业务身份双层去重，履约也要幂等；已取消订单收到迟到成功时走退款流程，不直接恢复发货。

## 参考分析

1. 支付平台和订单库之间不存在普通本地事务；响应丢失、库宕机与回调重复都是要正常处理的中间态。
2. 先返回成功再保存回调，进程崩溃会丢通知；可靠 Inbox 将“已经收到”与“业务已经完成”分开，便于恢复。
3. 先改订单后发消息存在提交后崩溃窗口；同事务 Outbox 记录履约意图，再由投递器至少一次发送。
4. 只有事件级查重不能挡住同一支付的不同事件；只有消息查重也不能防止消费者在执行后、记录前崩溃导致重复履约。
5. 退款是另一条可重试状态机，也需独立幂等键与查询确认；不能用删除本地支付记录来“回滚”已经完成的支付。

## 案例

1. 场景（教学示例）：支付号 P 已成功，订单 O 的数据库暂时不可用；平台回调可能重复并乱序。

2. 处理：分开可靠接收和业务处理；若 Inbox 也无法落库，本次按渠道协议返回失败，让其重试，同时由主动查单补齐。

```text
接收：验签并校验渠道身份 → Inbox 唯一事件 ID 持久化 → 确认接收
处理事务：锁订单，校验商户、支付身份、金额与币种
  WAIT_PAY → PAID；写支付关联、履约 Outbox、Inbox 已处理
  已 PAID 且同一支付 → 幂等结束并标记 Inbox 已处理
  已 CANCELLED → REFUND_PENDING，写退款任务，不写履约任务
  不同成功支付冲突 → 异常处理，不静默忽略
投递：Outbox 重试；履约端按订单和履约动作幂等执行
```

3. 结果：订单库恢复后同一支付只触发一次有效状态迁移；投递可重复，履约不重复；已取消订单走退款，不被迟到通知重新激活。

4. 验证：在 Inbox 落库后、订单事务提交后、消息发送后分别杀进程；重放同事件与不同事件的同一支付，再核订单、支付和履约三方结果。

## 总结点

1. 支付已成功，订单可恢复同步。
2. Inbox 收通知，Outbox 发意图。
3. 事件去重之外还要业务幂等。
