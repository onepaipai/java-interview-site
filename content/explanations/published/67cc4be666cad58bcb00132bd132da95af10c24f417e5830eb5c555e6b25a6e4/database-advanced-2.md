## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB 教学场景：status 列明明有索引，EXPLAIN 却显示全表扫描。逐项排查优化器放弃索引的常见原因：选择性、回表成本、隐式转换与统计信息。

1. 选择性不足是头号原因：如果 status 的 99% 行都是同一个值，优化器估算走索引要回表几十万次，不如全扫——索引在该值上"存在但无用"。
2. 回表成本被计入：即使命中行少，若查询要取大量列（回表随机 IO），优化器可能判断覆盖扫描的全表顺序读更便宜。
3. 隐式转换与函数包裹使索引失效：WHERE phone = 13800000000（列是 varchar）触发类型转换，WHERE DATE(created_at)=... 对列套函数——列被"加工"后无法走 B+ 树有序定位。

## 参考分析

### 机制：优化器在算成本账，不是在"认索引"

优化器比较各计划的预估成本：二级索引的成本 = 定位行数 + 回表随机 IO 估算；全扫成本 = 顺序读全表。类比打车与步行：距离远（命中多）时步行（全扫顺序读）反而快——优化器放弃索引不是故障，是成本比较的结果。要让索引被选中，要么提高选择性，要么减少回表（覆盖）。

### 反例：三类"有索引不走"的现场

一，隐式转换：varchar 列接了数字字面量，EXPLAIN type=ALL；二，前导通配 LIKE "%xx"；三，OR 连接的非索引列把整个查询拖向全扫。三类都有明确的写法修复：统一类型、改后缀匹配或全文索引、OR 拆分 UNION。

### 取舍：force index 是最后的诚实手段

当确认优化器误判（统计失真或成本模型局限）且短期无法改写时，FORCE INDEX 可保稳定——但它把计划钉死，数据分布变化后可能成为新瓶颈。正确次序：修写法 → 修统计（ANALYZE / 直方图）→ 最后才 force，并把 force 的原因写进注释。

## 案例

### 对照操作：EXPLAIN ANALYZE 的成本验证

教学验证：对同一查询分别构造"低选择性值"与"高选择性值"两版 EXPLAIN ANALYZE。预期：前者 actual rows 数十万且走全扫（或索引后回表巨量），后者走索引仅几十行。再修隐式转换，对比 type 从 ALL 变 ref。实验可复跑，把"优化器的账"变成可见数字。

### 追问：怎么快速确认是隐式转换

对比 `WHERE col = “值”` 与 `WHERE col = 值` 两个版本的 EXPLAIN type：ref 变 ALL 即坐实。根治在接口层统一类型（参数化绑定与列类型一致），数据库层的 CAST 补救只是止血——优化器无法对"加工后的列"使用有序定位。

## 总结点

1. 选择性决定值不值
2. 回表成本计入总账
3. 列被加工，索引失效
