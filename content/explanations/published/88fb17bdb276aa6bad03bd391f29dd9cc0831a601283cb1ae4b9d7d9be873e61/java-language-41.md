## 参考回答

> 场景与约束：网银表单沙盘:用户输入走正则校验(a{0,100}{0,100}{0,100} 的嵌套量词)——灾难性回溯(ReDoS:指数级回溯,CPU 100%)——ReDoS 的模式识别+输入长度限制+安全正则库(RE2)。

1. ReDoS 的机制:回溯正则的歧义匹配((a+)+$ 对 "aaaaaaaaaaaaaaaaaaaaaaaa!"——每字符回溯指数级)——恶意输入构造触发指数回溯(CPU 100% 单线程)——单请求拖死一个线程池线程(第 37 题 distributed)。
2. 模式识别:嵌套量词((a+)+/(a|a)*的歧义)+交替重叠((a|a)+)+字符类重叠——静态扫描(正则的安全分析工具)——危险模式的清单化。
3. 防御三层:输入长度限制(正则校验的输入上限——长度限制把指数截断)、安全正则库(RE2[线性时间,无回溯——Google 的正则引擎]——功能子集[无回溯引用])、超时(正则执行的线程超时——Java 无原生超时,需独立线程+中断[中断对正则无效!——只能放弃线程])。

## 参考分析

### 第二步扩展① 机制:回溯与指数爆炸

- 回溯:NFA 引擎的回溯(Java 正则=NFA——匹配失败时回溯尝试其他路径)——(a+)+$ 对 "aaaa...b":每个 a 的分组有两种解释(单个 a 或并入前组)——2^n 的路径(指数)。
- 线性引擎:RE2(自动机——无回溯,线性时间)——功能限制(不支持回溯引用/环视)——ReDoS 免疫的代价是功能子集。
- Java 的替代:RE2/J(Java 移植版)——安全场景的替换(第 17 题选型)。

### 第二步扩展② 反例:ReDoS 的两种事故

- 事故一,校验接口 ReDoS:用户输入走嵌套量词正则——恶意输入(长串+触发字符)——CPU 100%(该线程)——并发攻击=线程池耗尽(第 37 题 distributed 聚合同构)。
- 事故二,日志解析 ReDoS:日志解析的正则(非用户输入但日志内容含用户数据——间接注入)——日志内容的 ReDoS。
- 两条的正解:用户输入的正则长度限制+RE2 替换+静态扫描危险模式。

### 第二步扩展③ 取舍:ReDoS 防御的层次

- 层一,静态扫描:CI 的正则扫描(危险模式清单:嵌套量词/重叠交替)——开发期拦截。
- 层二,长度限制:正则校验的输入长度上限(长度截断回溯指数)——入口层。
- 层三,RE2 替换:安全敏感的正则用 RE2/J(线性)——正则层。
- 层四,超时+隔离:正则执行在独立线程+超时(放弃线程[不可中断——线程泄漏的代价评估])——最后防线。
- 四层按部署成本递增。

## 案例

### 第三步发散·验证与推演 验证:ReDoS 防御的断言组

- 验证:ReDoS 复现断言((a+)+$ 对长串的耗时——指数回溯实测[短输入即可演示])。
- 长度限制断言(输入截断后耗时线性)。
- RE2 对照断言(同一模式在 RE2 的线性时间)——三组固化 ReDoS 防御。
- 危险模式清单(CI 扫描的规则库)进安全文档。

### 第三步发散·追问扩展 追问链:ReDoS 三刀

- **Q1：Java 正则的超时?**
  - 答：Matcher 无原生超时——独立线程+放弃(线程泄漏[中断对回溯无效]——Thread.stop deprecated)——超时的代价评估(线程泄漏 vs ReDoS 的 CPU 占用——泄漏线程有限[池上限]优于 ReDoS 无限[CPU])。
- **Q2：RE2 的功能限制?**
  - 答：RE2 不支持回溯引用(反斜杠1)/环视(?=)——功能子集的正则迁移(受影响模式的清单)——RE2 的引入评估(第 17 题)。
- **Q3：正则的缓存?**
  - 答：Pattern.compile 的缓存(编译贵——Pattern 预编译常量)——每次 compile 的开销(热路径禁 inline compile,第 21 题distributed)——Pattern 的预编译纪律。

## 总结点

1. 嵌套量词是 ReDoS 的标志
2. 长度限制截断指数,RE2 治本
3. Java 无正则超时,独立线程兜底
