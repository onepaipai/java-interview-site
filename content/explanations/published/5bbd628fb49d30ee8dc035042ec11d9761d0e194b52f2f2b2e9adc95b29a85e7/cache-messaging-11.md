## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Redis 7 教学场景：SETNX lockKey 成功后、EXPIRE 执行前进程崩溃，锁永不释放。用"两条命令之间的崩溃窗口"解释原子性必要性，给出 SET NX EX 单命令与 Lua 的正确写法。

1. SETNX 与 EXPIRE 分两步执行，两步之间存在崩溃/网络/调度窗口：SETNX 成功后进程死亡，锁存在但无过期时间——其他实例永久等待，系统死锁。
2. 原子写法：`SET lockKey token NX EX ttl` 单命令同时完成"占位 + 设过期"——Redis 单线程保证两语义不可分割；旧版需 Lua 包裹 SETNX+PEXPIRE。
3. 原子性只是加锁的第一半：锁值必须是唯一 token（释放校验用），TTL 必须大于最大业务时长或配看门狗续期——加锁、锁值、过期三者是一个协议不是三个独立配置（见第 12、13 题）。

## 参考分析

### 机制：两步操作之间，进程不欠任何人"走完"

SETNX 成功后进程可能在任意指令边界死亡：OOM、kill、断电、网络断开——没有任何机制保证"接下来一定执行 EXPIRE"。类比先插钥匙后设闹钟：插完钥匙人就晕倒，闹钟没设，钥匙永远插着。原子命令把两步压缩成一个不可分割的动作。

### 反例：崩溃窗口的注入复现

教学验证：用 Lua 或客户端在 SETNX 与 EXPIRE 之间注入 `process.exit`。预期：锁存在但 TTL 为 -1，其他实例 SETNX 全部失败，系统对该资源永久不可用；只能人工 DEL。复现后改 SET NX EX 验证窗口消失。实验可复跑，事故从"听说过"变成"造出来过"。

### 取舍：单命令 SET 与 Lua 的边界

SET NX EX 覆盖"占位+过期"的两要素加锁，够用且最简单；Lua 用于加锁时还要携带额外状态（如重入计数、锁信息 Hash 字段）的场景。原则：单命令能表达就不写脚本——脚本多了要维护复杂度红线（第 10 题），锁协议尤其如此。

## 案例

### 对照操作：崩溃窗口的前后对照

教学验证：分步 SETNX+崩溃注入版（锁泄漏）与 SET NX EX 版（锁 10 秒自动过期），观察其他实例的获取延迟。预期：前者永久失败需人工干预，后者 10 秒后自然恢复。实验可复跑。

### 追问：TTL 设多长才是"安全"的

TTL > 业务最大执行时间才能避免"执行中过期"（引出第 46 题栅栏问题）；但 TTL 越长，崩溃后的不可用窗口越长。这个两难由看门狗续期解决（第 13 题）——TTL 设短 + 续期保持活性，崩溃后快速释放。TTL 的选择是协议设计的一部分，不是拍脑袋参数。

## 总结点

1. SETNX 后崩溃，锁成永久钉
2. SET NX EX 一条命令锁三事
3. TTL 两难由看门狗解
