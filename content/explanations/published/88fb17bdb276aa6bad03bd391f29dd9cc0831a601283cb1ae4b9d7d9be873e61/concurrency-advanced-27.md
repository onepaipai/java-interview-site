## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 21+ 服务把每个请求放到虚拟线程，但数据库连接池只有有限连接，查询还可能持有锁。讨论线程数量、连接容量、事务时长和排队之间的关系。

1. 虚拟线程降低线程创建和阻塞等待成本，但数据库连接、锁、CPU、磁盘和下游服务仍是有限资源。
2. 大量虚拟线程会在连接池或锁上排队；如果没有截止时间和舱壁，内存与超时会一起增长，吞吐不会因此线性提升。
3. 应在资源边界限制并发、缩短事务、设置连接获取超时并观察队列年龄、锁等待、连接占用和业务尾延迟。

## 参考分析

### 第二步扩展① 线程容量与数据库容量是两条曲线

- 虚拟线程可以让更多请求进入等待状态，但数据库连接池决定同时执行 SQL 的上限。
- 连接池满时，额外线程只是在等待连接。
- 如果事务持锁时间变长，还会把等待传播到其他请求。
- 数据库并发还受 CPU、磁盘、锁冲突、日志 fsync 和慢查询影响，不能用“线程数更多”推导更高吞吐。
- 类比高速免费后车流暴增：上路更容易了（线程廉价），收费站（数据库连接）照样堵——舱壁要设在收费站。

### 第二步扩展② 在真正瓶颈处做舱壁

- 按租户、查询类型或下游依赖隔离连接和并发许可，限制批量任务不要占满在线请求资源。
- Semaphore 可以保护特定外部操作，但要避免与连接池设置互相嵌套形成额外死锁。
- 获取连接、排队、执行 SQL 和提交事务都应共享 request deadline。
- 过期请求不应继续占用连接或启动新的副作用。

### 第二步扩展③ 虚拟线程使用前提

- 驱动、框架和监控需要验证对虚拟线程的支持。
- ThreadLocal 缓存昂贵对象也可能随任务数扩大内存。
- 连接池仍应按数据库能力配置，而不是按虚拟线程数量配置。
- 容量测试必须包含突发、慢查询、锁等待、数据库故障和恢复，比较用户 p99、拒绝率、连接等待和数据库资源，而不只看应用线程数。

## 案例

### 第三步发散·验证与推演 连接池饱和演练

- 让虚拟线程数量远大于数据库连接数，逐步提高并发并记录连接获取等待、SQL 执行、锁等待、内存和 p99。
- 预期超过数据库容量后排队年龄和超时上升。
- 增加虚拟线程不能消除瓶颈。

### 第三步发散·追问① 舱壁与恢复验证

- 为在线请求和批处理配置独立连接/并发预算，注入数据库慢查询后观察健康请求是否仍可用。
- 恢复时按速率释放积压，验证过期请求不会迟到执行，连接和锁最终回收。
- 同时检查连接获取超时、锁等待和数据库 CPU 是否回落，确认批处理没有通过重试重新占满在线资源。
- 恢复判断要以用户尾延迟和业务成功率为准。

## 总结点

1. 上路容易了，收费站照样堵
2. 虚拟线程不增加数据库容量
3. 在资源边界设置舱壁
4. 连接等待也要计入 deadline
