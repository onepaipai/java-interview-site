## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银行情与客服沙盘:行情推送只需服务器到客户端单向流,用 SSE(纯 HTTP,浏览器自动重连)比 WS(双向协议+自建心跳重连)省一半复杂度;而坐席双向聊天必须 WS——单向推送选 SSE,双向交互选 WS。

1. SSE 的本质:长连接上的 HTTP 响应流(Content-Type: text/event-stream),数据帧按 event 格式分隔;基于 HTTP 意味着——代理/网关/鉴权/压缩全部复用 HTTP 生态,无需协议升级。
2. SSE 的内建能力:自动重连(浏览器 EventSource 断线自动重发,带 Last-Event-ID 供服务端补发)、事件类型分发(event: 字段)、跨域复用 CORS——这些在 WS 里都要自己实现(见 Q31 心跳/重连/补投)。
3. 边界:SSE 仅单向(服务器→客户端)且文本格式(二进制要 base64,开销 33%);HTTP/1.1 下浏览器同域 6 连接限制(占满后其他请求排队,HTTP/2 无此限制);客户端到服务器的数据走独立 HTTP 请求(配合幂等键,见 Q11)。

## 参考分析

### 第二步扩展① 机制:SSE 帧与重连协议

- 帧格式:id(游标)/event(类型)/data(载荷)/retry(重连间隔)。
- 断线后浏览器携 Last-Event-ID 重连,服务端按游标补发缺口——推送不丢的协议级保障。
- WS 没有内建游标,补投要自建(消息 ID+确认)。

### 第二步扩展② 反例:SSE 误用的三种事故

- 事故一:高频行情用 SSE+HTTP/1.1——6 连接上限被行情占满,页面其他请求饿死。
- 升级 HTTP/2 或换 WS 多路复用。
- 事故二:大对象二进制推送——base64 膨胀 33%,带宽与解析成本双涨。
- 二进制通道选 WS。
- 事故三:把 SSE 当轮询替代但忽略代理缓冲——某些代理缓冲响应流,客户端长时间收不到分片。
- 网关需显式禁用对该路径的缓冲(X-Accel-Buffering: no)。

### 第二步扩展③ 取舍:SSE vs WS 决策表

- 单向+文本+复用 HTTP 基础设施+SSE。
- 双向+二进制+低延迟交互+WS。
- 两者都要(下单+行情):WS 一条连接承载双通道 vs SSE+普通请求组合——按"双向流量占比"定,双向少则 SSE 组合更简单。
- SSE 的运维成本显著低(无协议升级、无独立网关配置),默认首选,WS 按需上。

## 案例

### 第三步发散·验证与推演 验证:补投机制的推演核对

- 推演核对:SSE 的 Last-Event-ID 补投与 Q11 幂等键重放同构(游标=键,补发=重放缺口)。
- 断线自动重连与 Q31 的重连风暴控制(退避+抖动)是同一问题——SSE 的 retry 字段是内建退避入口。
- 验证:单向推送场景 SSE 覆盖"推送+不丢+自动恢复"三需求的结论,与 WS 自建三件套的成本对照成立。

### 第三步发散·发散要点 追问链:SSE 三刀

- **追问①**：连接数与 HTTP/2 的关系——H2 多路复用让 SSE 不再挤占 6 连接配额,HTTP/2 部署后 SSE 适用面扩大(见 Q17)
- **追问②**：SSE 与 CDN/代理的兼容——长响应流会被中间缓冲或超时切断,网关要放行该路径(读超时调大+禁缓冲)
- **追问③**：认证——SSE 是普通 HTTP 请求,Cookie/Token 鉴权复用现有体系(EventSource 不能自定义头时用 Cookie 或 query token 一次性换凭据)

## 总结点

1. 单向文本推送选 SSE
2. 重连补投协议内建
3. 双向二进制才上 WS
