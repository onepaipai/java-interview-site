## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 / Spring 6.2 教学实验：服务先插入一行再抛出异常，测试用 mock 仓储只检查调用发生。对照容器代理、真实事务管理器及 H2 数据状态，区分业务测试与事务证据。

1. mock 仓储验证调用和业务分支，不会真实提交、回滚、持锁或执行约束，因此无法证明事务生效。直接 new 服务还可能绕过 Spring 代理。
2. 事务测试要让调用经过受管代理、使用真实事务管理器和隔离数据库，并在服务调用结束后的独立观察边界检查最终数据。
3. 还应控制异常类型、捕获方式、传播规则和测试自身事务，避免测试自动回滚掩盖生产路径已提交的问题；H2 结果不能替代 MySQL 锁与隔离验证。

## 参考分析

### 替身的能力：能回答调用了什么，不能回答数据库留下什么

verify(repository).save 能确认业务向仓储发出操作，也能帮助覆盖库存不足等分支，但 mock 内部没有数据库连接和实际事务。即使服务的 @Transactional 被删除，这类测试也可能继续通过。把方法调用次数当作回滚证据，会漏掉自调用、错误管理器和异常被吞等实际问题。类比驾考模拟器：模拟器能记录你打了几次方向（调用），证明不了真实路面的摩擦与盲区（数据库提交结果）。

### 观察边界：避免测试事务替业务擦掉提交

测试方法自身开启事务并在结束时自动回滚时，服务可能加入这个测试事务；即使生产入口没有同样的事务，测试仍看似正确。应按要验证的风险决定是否关闭测试级事务，并在服务代理返回或抛错后从独立事务或连接观察持久状态。显式刷出 ORM 写入也很重要，否则 SQL 和约束错误可能还没有发生。

### 失败矩阵：默认回滚与目标数据库能力分别验证

默认情况下运行时异常和 Error 导致回滚，受检异常通常不回滚，除非显式规则或全局配置改变。对照异常抛出、被捕获后返回、跨 Bean 传播及自调用，才能解释最终行数。H2 适合窄范围验证代理和回滚规则，行锁、死锁、隔离和方言等必须在目标 MySQL 环境中做独立实验。

## 案例

### 真实状态对照：运行时异常与受检异常

建立隔离 H2 表，通过受管服务代理执行“插入后抛运行时异常”，在调用结束后查询行数，预期零行；再执行默认配置下“插入后抛受检异常”，预期该行已提交；显式 rollbackFor 的受检异常路径则应回滚。项目 SpringCoreExamplesTest 执行此窄范围对照，测试方法不包在自动回滚事务中，避免用测试边界替代服务边界。

### 追问：为什么目标数据库集成测试仍有必要

即便上述 H2 测试通过，也只证明当前服务代理与事务规则的特定路径。要讨论生产中的唯一约束竞争或锁等待，应在独立 MySQL 数据库组织两个连接的提交顺序并记录异常与最终状态。隔离环境不可用时保持该项未验证，而不是把跳过或内存库结果写成 MySQL 行为已通过。

## 总结点

1. 模拟器记动作，证不了真实路面
2. mock 调用不等于数据库状态
3. 服务调用后独立观察提交结果
4. 测试事务可能掩盖真实边界
