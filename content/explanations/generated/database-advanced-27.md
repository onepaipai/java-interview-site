## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB，两账户转账在同一事务内更新余额并写流水；请求可能同时出现 A→B 与 B→A。目标是避免可预防的死锁，同时保持余额与流水的原子性。

1. 两笔转账按入参顺序锁账户会形成 A 等 B、B 等 A 的环；按稳定的账户 ID 顺序获取两行锁可打破这个循环。
2. 锁顺序只是降低死锁的一种结构性措施，索引范围、其他表、触发器和不同代码路径仍可能引入死锁；事务必须短且统一访问顺序。
3. 即使有规范化顺序，应用仍要处理数据库选出的死锁受害事务：仅在事务副作用可安全重放时有限重试，并记录死锁证据。

## 参考分析

### 死锁来自等待图中的环

事务 T1 先锁账户 A，再请求 B；T2 先锁 B，再请求 A。两个请求都已持有第一把锁，第二次请求只能等待对方释放，等待图形成环，任何一方都不能自行继续。InnoDB 会选择一个事务回滚，让另一个前进。
按 account_id 从小到大加锁后，所有转账都遵循相同偏序，T1/T2 不再因为这两行产生反向环。若是同账户转账，要先定义是否拒绝，避免重复加锁和业务语义不清。类比十字路口红绿灯：四个方向各自合法直行，若无统一通行顺序照样互堵——统一加锁顺序就是给所有事务装上同一套灯。

### 顺序要覆盖整个事务访问图

只规范账户表还不够：流水表、额度表、冻结表和库存表也可能被不同路径以不同顺序访问。SELECT ... FOR UPDATE、UPDATE 条件扫描的索引范围和外键检查都可能扩大锁集合，因此要结合执行计划和死锁日志确认实际顺序。
统一在事务最早阶段锁定必要的行，随后做余额校验、更新两账户和写流水；不要持锁调用远程服务。事务越长，锁等待和死锁窗口越大。

### 重试不能掩盖错误边界

死锁回滚后可重试整个数据库事务，而不是只重放最后一条 UPDATE；否则可能重复写流水或使用已经失效的读结果。重试次数、退避和总截止时间必须有界。
如果事务已经触发不可逆外部副作用，就不能简单自动重试；应把副作用放到提交后的可靠事件流程，并以业务操作键去重。

## 案例

### 双向转账实验

在隔离 MySQL 8.4 环境并发执行 A→B 与 B→A，先用相反顺序的实现观察死锁错误，再改为按 ID 排序锁定。预期规范化顺序减少该类循环，但不把一次没有报错当作“所有死锁已消失”。
记录 SHOW ENGINE INNODB STATUS 或等价死锁日志、锁等待时间、回滚事务和最终余额，验证余额守恒且每笔成功转账只有一条流水。

### 故障推演：死锁受害者重试

让一笔事务被回滚，确认服务重试的是完整转账事务，成功后余额只发生一次净变化、流水唯一键不重复。若请求已经超时，调用方必须查询 operation_id，而不是创建新转账。
验收覆盖重复请求、余额不足、同账户、死锁重试耗尽和服务重启，分别返回确定失败或结果未知。

## 总结点

1. 全体事务按同一顺序取锁，环自消失
2. 所有路径按同一顺序取锁
3. 死锁重试必须重放完整事务
4. 外部副作用不能靠数据库重试撤销
