## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB 教学场景：值班医生排班系统中两个事务各自检查"还有一名医生在班"后各自下班，结果无人值班——写偏斜。解释写偏斜为什么绕过常规行锁，给出约束层的防御手段。

1. 写偏斜的形态：两个事务读取同一批行（各自读到"还有人在班"）、写入不相交的行（各自写自己的排班记录）——没有行锁冲突、没有唯一键冲突，常规并发控制全部放行，业务不变式被破坏。
2. InnoDB 无可串行化的乐观检测（没有 PostgreSQL 的 SSI），RR 的快照读也不防它：防御必须把"读取的前提"变成"被锁住或被约束的事实"。
3. 约束层手段按力降序：SELECT ... FOR UPDATE 锁住前提行（在班记录）使检查串行化；数据库 CHECK 约束或触发器在写入端复验不变式；外层用串行化隔离（代价大）；最实用的是把不变式表达为唯一/约束结构（如在班人数单独计数表，更新走原子增减）。

## 参考分析

### 机制：写偏斜是"前提"与"写入"的错位

两个事务写不相交的行，所以行锁不冲突；但它们共享一个"读取时的前提"（在班人数 ≥ 2），且都基于旧前提做决策。类比两人同时查看同一个"仅剩 1 间房"的列表、各自预订不同的房型——各自的操作都合法，合并起来房没了。防御的本质：让前提也成为被锁住的资源。

### 反例：换成 SELECT FOR UPDATE 后的新问题

锁住全部在班记录使检查串行化——正确，但把排班查询的并发压成串行（所有医生操作互斥）。改进：只锁"不变式相关的最小行集"（当前在班汇总行的 FOR UPDATE），或把不变式做成计数表原子增减——锁面缩小到不变式本身。防御的成本要花在不变式上，不是整张表。

### 取舍：约束、触发器与计数表的分工

唯一/CHECK 约束：数据库强制、零应用成本，但只能表达行级不变式；触发器：可表达跨行不变式，代价是隐藏逻辑与性能税；计数表（专用汇总行 + 原子更新）：把不变式变成单行原子操作，最常用。三者可叠加——约束兜底、计数表主防，触发器最后考虑。

## 案例

### 对照操作：写偏斜的复现与三级防御对照

教学验证：两事务并发"检查后下班"。预期：裸奔版本无人在班；FOR UPDATE 前提行版本正确但串行化；计数表版本正确且并发不受限。三版本的吞吐与正确性并排，实验可复跑。

### 追问：为什么 MySQL 没有像 PostgreSQL 那样的 SSI

可串行化快照隔离需要 SIREAD 谓词锁追踪读写依赖，实现复杂且冲突率高时性能塌陷；InnoDB 选择把 RR 做成"快照读 + 行锁"的轻量组合。工程含义：MySQL 的可串行化只是"RR + 共享锁化读"，不解决写偏斜——防御责任明确落在应用与约束层。

## 总结点

1. 写偏斜躲过行锁，前提要上锁
2. 计数表把不变式变成原子操作
3. MySQL 无 SSI，防御在约束层
