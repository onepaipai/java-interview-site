> 场景与约束：网银问答沙盘:Java 后端调用 LLM API(SSE 流式)+实时推送到前端——HTTP 客户端选择、SSE 分帧解析、断连/超时/取消的全链路处理。

1. Java 调用 LLM 三种形态:HTTP 客户端直调 REST API(stream=true);SSE 解析分帧(每帧 JSON 增量);Spring AI/LangChain4j 框架封装。直接调用可控性最高,框架开发效率高。
2. 流式处理:每帧解析出 delta.content→转发到前端(SSE/WebSocket);空帧/心跳帧(data: [DONE])是结束信号;分帧可能被 TCP 切断(一个 JSON 分两次到达)——需要缓冲区拼帧(不完全帧等待下一个 chunk)。
3. 断连与取消:客户端断开(SSE 写失败)→取消上游生成(第 16 题);服务端超时(模型 30s 无首 token)→超时取消+降级;流式过程中的异常(网络中断/模型错误)→已生成部分保留+错误提示。

## 参考分析

### 第二步扩展① 机制:SSE 分帧为什么要缓冲

- HTTP 响应以字节流到达,一个 SSE 事件(data: {"choices":[...]}\n\n)可能被 TCP 分段——如果逐行解析,半行 JSON 解析失败。
- 正确做法:累积到缓冲区,按 \n\n 分隔符切出完整事件,不完整的留在缓冲区等下一个 chunk。
- 类比收快递:包裹可能分两个箱子到,要等全到再拆。

### 第二步扩展② 反例:LLM 调用的两种事故

- 事故一:忽略 SSE 缓冲——逐 chunk 解析 JSON,半截 JSON 抛异常(偶发,网络快时不复现——最隐蔽)。
- 修复=缓冲区按分隔符切帧。
- 事故二:无取消令牌——客户端断开后服务端继续读完整个响应(token 浪费+并发占用,第 16 题)。
- 修复=HttpClient 的 cancel() 传导。

### 第二步扩展③ 取舍:直接调用 vs 框架封装

- 直接调用(HttpClient+手动 SSE 解析):可控性最高(分帧/超时/取消全自己管),代码量 200-300 行。
- 框架(Spring AI/LangChain4j):开发效率高(流式/工具/记忆封装好)但框架抽象层增加排查难度,框架版本升级可能改行为(第 9 题方言同构)。
- 建议:核心链路直接调用(可控),非核心(Agent 编排)用框架。

## 案例

### 第三步发散·验证与推演 验证:LLM 调用的推演核对

- 推演核对(教学示例):Java HttpClient 调用流式 API——SSE 分帧断言(拼接后完整 JSON 序列无丢失/无重复)。
- 断连取消断言(客户端断开后 token 停止增长)。
- 超时断言(首 token 超时触发降级,第 14 题)。
- 验证:分帧正确性断言(逐帧 JSON 可解析)可程序化。
- mock SSE 服务复跑。

### 第三步发散·追问扩展 追问链:调用三刀

- **Q1：重试怎么设计?**
  - 答：非流式可重试(幂等,第 38 题);流式重试=从头生成(内容随机性导致不同——前端要处理,第 17 题);重试预算+退避(第 14 题)。
- **Q2：多模型路由在哪层?**
  - 答：网关层(第 11 题)按任务类型路由(第 22 题策略 C),Java 侧只对接网关——直连多供应商的方言管理(第 9 题)在网关收口。
- **Q3：响应的日志?**
  - 答：流式的日志=指纹层(请求 ID+模型版本+token 数)+采样内容层(第 21 题三层),逐帧日志只记事件 ID 不记内容(存储省+隐私)。

## 总结点

1. SSE 分帧要缓冲,半截 JSON 等下一段
2. 断连取消传导全链路
3. 核心直调,编排用框架
