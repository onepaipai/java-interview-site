> 场景与约束：网银数据助手沙盘:自然语言转 SQL(text2SQL)直接执行——"删除所有表"或者 JOIN 出全库数据;安全执行=生成与执行分离+白名单校验(表/列/操作类型)+只读强制+行数与超时限制+审批通道(写操作)——模型生成建议,执行层的防线才是安全本体(Q24 的执行侧纪律的重度版)。

1. 防线五层:语法校验(parse 拦截)、白名单(表列在元数据白名单内+操作类型 AST 确认,只读场景禁写)、行数限制(LIMIT 强制+结果集上限)、执行沙箱(只读副本/受限账号/超时限额)、审批通道(写操作人工确认+影响预估,资金库默认拒绝)。
2. 生成质量层:schema 注入(把相关表结构(DDL+样例)供给模型——减少幻觉列名)、少示例(业务常用查询模式示例)、错误反馈重试(执行报错(语法/列不存在)反馈给模型修正——一轮修复率高,Q23 引导式重试);评测(text2SQL 的评测集:自然语言→期望 SQL 的精确匹配或执行结果匹配——Q36)。
3. 权限与审计:执行账号=只读+受限表(数据库侧权限,与应用权限分离);全量审计(SQL 文本+执行人+结果行数留痕,Q18);敏感列脱敏(结果中的 PII 列脱敏返回,Q30)——SQL 生成的安全=生成层(质量)+执行层(防线)+审计层(追溯)三层。

## 参考分析

### 第二步扩展① 机制:AST 级的白名单校验

- 字符串黑名单的危险("禁止 DELETE"用字符串匹配——绕过方式多(注释/编码/CTE))。
- AST 解析(SQL parse tree):准确识别语句类型(SELECT/DDL/DML)、访问的表与列、是否有子查询嵌套写操作——白名单判定基于结构而非文本。
- 解析器选型(sqlglot/calcite 类)与方言匹配。
- AST 校验+执行账号权限(数据库层的第二道)=纵深。

### 第二步扩展② 反例:SQL 生成的三种事故

- 事故一:字符串黑名单——"SELECT * FROM t。
- DROP TABLE x"用注释绕过(黑名单漏),库被删。
- AST+账号权限。
- 事故二:无行数限制——"查所有订单"返回 2 亿行,应用 OOM。
- LIMIT+游标。
- 事故三:写操作直通——"把欠费用户状态改为已缴"模型生成 UPDATE 直接执行(资损)。
- 写操作审批。

### 第二步扩展③ 取舍:能力开放 vs 安全边界

- 全开放(任意 SQL):能力强,风险极大。
- 白名单模板(预定义查询模板+参数填空):最安全,灵活性差。
- 折中=只读+AST 白名单+行数限制的受限开放(覆盖 80% 分析需求),写操作走模板化审批——开放度与防线强度同步演进。

- 脱敏与 Q30(假名化)衔接。
- 验证:五层防线可执行(明示:按 text2SQL 工程推演)。

### 第三步发散·发散要点 追问链:SQL 三刀

- **追问①**：与 Q27 的衔接——用户输入进入 SQL 生成提示的注入面(生成破坏性 SQL 的提示注入),AST 校验是兜底
- **追问②**：与 Q38 的衔接——text2SQL 的评测(执行结果匹配)是归因(生成错 vs schema 供给错)的案例
- **追问③**：与 Q30 的衔接——查询结果的 PII 脱敏在返回前执行

## 总结点

1. AST 校验强于字符串黑名单
2. 只读沙箱写走审批
3. schema 注入减少幻觉
