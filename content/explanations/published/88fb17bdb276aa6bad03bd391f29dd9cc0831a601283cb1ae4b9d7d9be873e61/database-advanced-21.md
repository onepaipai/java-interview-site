## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 / InnoDB 教学场景：SHOW ENGINE INNODB STATUS 报出 LATEST DETECTED DEADLOCK，堆栈里只有两条 SQL 与锁列表。把死锁日志还原成"业务调用链 + 数据访问图"的方法与映射表。

1. 日志三要素：两个事务各自正在执行的 SQL、各自已持有的锁（HELD 部分的索引与记录）、各自等待的锁（WAITING）——三者拼出"等待环"：A 持 X 等 Y，B 持 Y 等 X。
2. 还原路径：SQL 中的表与 WHERE 条件 → 定位到代码中的 DAO 方法 → 方法向上找事务边界（@Transactional 的入口）→ 标出事务内全部数据访问的顺序——死锁日志里的"锁顺序"对应代码里的"访问顺序"。
3. 固化证据：死锁日志只保留最近一次（SHOW ENGINE INNODB STATUS），生产应开启 innodb_print_all_deadlocks 把每次死锁打进错误日志，配合应用侧的事务日志（事务 ID/业务键）做精确映射。

## 参考分析

### 第二步扩展① 机制：死锁日志是"等待图"的快照

- 死锁检测的输出就是那张等待图：谁持有什么、在等什么——但它只写 SQL 不写业务语境。
- 类比事故现场的刹车痕：能复原碰撞几何，复原不了"司机为什么在这里"——业务映射表（SQL ↔ DAO ↔ 调用场景）就是把几何变成叙事的翻译层。

### 第二步扩展② 反例：只看两条 SQL 的误修

- 日志显示两条 UPDATE 冲突，团队给两条 SQL 各自加注释"注意顺序"——但真正的事务里这两条 UPDATE 之间还夹着一次 RPC 调用（拉长持锁时间）与一次额外的 SELECT（多拿一把锁）。
- 只改 SQL 顺序没改访问图，死锁复现。
- 修正必须覆盖事务内全部访问，不只是冲突的两条。

### 第二步扩展③ 取舍：防死锁的落点选择

- 还原后按代价选修复：统一加锁顺序（低成本高收益，见第 22 题反例的深化）、缩短事务（移出 RPC）、降级隔离级别减少锁（RC 消除部分间隙锁）、最后是死锁重试（捕获 1213 重放整个事务）。
- 重试永远排最后——它不消除死锁，只消费死锁。

## 案例

### 第三步发散·验证与推演 对照操作：日志到调用链的映射演练

- 教学验证：构造可预期的死锁（两事务交叉更新两行），取死锁日志逐字段还原：两条 SQL → 两个 DAO 方法 → 两个事务入口 → 访问顺序图。
- 把还原结果与代码实际对照验证无误。
- 演练产出"日志映射模板"，供真实事故套用。

### 第三步发散·追问① 追问：为什么要把事务 ID 与业务键打进应用日志

- 死锁日志与业务日志分属两个世界，唯一可靠的桥是应用打印的"事务开始/结束 + 业务键"。
- 没有这座桥，死锁日志只能还原到 SQL 层，无法定位是哪笔业务、哪个入口触发的。
- 桥的成本是一行日志，收益是定位时间从小时到分钟。

## 总结点

1. SQL 定位代码，访问图定原因
2. 事务内的每一笔访问都要进图
3. 重试排最后，修图才是本
