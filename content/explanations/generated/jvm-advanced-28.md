## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银状态消息沙盘:百万级消息串内容高度重复,团队在"开 -XX:+UseStringDeduplication"与"业务层 intern/缓存"之间纠结。用实测说明两者作用的层次、节省口径与适用边界。

1. G1 字符串去重省的是堆里 String 的 value 数组:后台线程把相同内容的不同 String 指向同一底层数组,实测 30 万串去重 98.4%、省 11.7MB。
2. 业务级缓存(intern、常量池、显式 Map)省的是对象本身:连 String 对象都不重复创建,还能省查找与 GC 账本,但治理责任在代码。
3. 两者不互斥:去重是自动的内存压缩(只对 G1,17 不含 ZGC),业务缓存是主动的共享设计;高频全等短串选业务缓存,长尾重复选去重。

## 参考分析

### 机制:去重在哪个环节生效

G1 的去重线程在并发标记后扫描 age 达标的 String,比较 hash 后用 char[]/byte[] 级的相等判定把多个 String 的 value 指向同底层数组;String 对象本身仍是多个。实测(Java 17.0.17,30 万个内容重复的 String,6 次 System.gc):
```
[0.712s][stringdedup] Deduplicated: 300033(98.4%) 11719.6K(8177.6%)
```
注意百分比是对"候选"而言;去重要求对象存活并熬过年龄阈值(DeduplicationAgeThreshold 默认 3),朝生暮死的串轮不到它。

### 边界:各自的适用与失效场景

去重失效场景:非 G1 回收器(17 的 ZGC 不支持该开关,支持矩阵按版本核对)、短命串(到不了年龄阈值)、内容本就互异。intern 的坑:常量池在元空间有账,大量动态 intern 会把压力转给元空间(见第 15 题),且 intern 表查找是全局锁竞争点。业务缓存的坑:上限与淘汰要做(否则见第 13 题),键设计要防内存对齐浪费。三者选型:热路径高频全等短串(状态码、渠道名)用业务常量;海量长尾重复(消息体、URL)用去重;两者都治不了的(内容互异)谁也不救。

### 取舍:开启去重的成本账

成本:去重线程的 CPU、字符串哈希的预计算、候选表的内存;收益:重复内容占比高且长寿命的场景(消息平台、规则串、报表模板)。判断先于开启:抽样统计重复率(对本机样例,8 个不同内容占 30 万实例,重复率近乎 100%,收益显著);若重复率不足 30%,收益大概率盖不住成本。业务缓存则零运行时开关成本,但吃代码评审——新增全局缓存要过上限与淘汰的设计评审。

## 案例

### 实证:去重的量化收益

命令与输出(Java 17.0.17):
```
java -XX:+UseStringDeduplication -Xms256m -Xmx256m \
     -Xlog:stringdedup*=debug DedupExp
[0.712s][debug][stringdedup] Deduplicated: 300033( 98.4%) 11719.6K(8177.6%)
```
负载:30 万个内容仅 8 种的 String 保活。验证:不加开关重跑,该日志行消失且堆占用更高;把内容改为全互异,去重比例趋零——收益与内容重复度直接挂钩。

### 追问链:字符串三刀

一刀:"String 不可变带来什么优化空间?"——内容可安全共享(hash 缓存、value 复用),这是去重与 intern 的前提;可变字符串类型没有这种全局压缩机会。二刀:"为什么去重只对长寿命串划算?"——候选要熬年龄阈值,短命串在成为候选前已死,扫描成本白花;它天然服务缓存型负载,与第 13 题的缓存治理是同一画像。三刀:"压缩指针和去重矛盾吗?"——不矛盾,压缩类指针针对 Class 元数据引用,去重针对 String value;两者都在"用小账本省大内存",但层次不同,排查时分开看。

## 总结点

1. 去重压 value,缓存省对象
2. 先量重复率,再开开关
3. intern 慎用,上限必配
