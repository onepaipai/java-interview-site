## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银接口沙盘:认证(你是谁)加授权(你能做什么)——认证通过不代表有权限。两层的防线分离,认证是授权的前提。

1. 认证(Authentication)验证身份凭证,产出 SecurityContext 中的 Authentication 对象——回答"你是谁";授权(Authorization)基于该 Authentication 做权限判定——回答"你能做什么"。两层独立:未认证 401,已认证无权限 403。
2. 工程分层:认证在 Filter 层统一处理;授权分布在 Filter 层 URL 规则、方法层 @PreAuthorize 与服务层资源归属校验——三层授权,粒度递增。
3. 锚点(spring-advanced 19 题):认证与授权共享 SecurityContext——认证是授权的前提,认证绿不代表授权绿。

## 参考分析

### 第二步扩展① 机制:认证与授权的语义边界

- 认证验证的是身份凭证——密码、令牌、生物特征,验证通过后把 Authentication 对象放进 SecurityContext。
- 授权基于该对象携带的权限做判定——角色、资源、方法级规则。
- 两层独立失败:未认证返回 401,已认证但无权限返回 403。
- 工程上认证收敛在 Filter 链(统一入口,spring-advanced 17 题),授权分散在 URL 层、方法层注解与服务层归属校验——三层各挡一段,粒度递增。

### 第二步扩展② 反例:认证通过但越权

- 已认证用户访问他人资源——认证通过但授权失败,这是横向越权的标准形态:URL 层只挡了"未登录",方法层或服务层没校验"资源归属"(spring-advanced 18 题),两层缺一即越权。
- 用例纪律:横向越权用例(改 ID 访问他人订单)必须进回归集——认证全绿不代表授权绿,两层要各自有断言。

### 第二步扩展③ 取舍:统一认证与分散授权

- 认证统一在 Filter 层处理(一次验证,处处可用)。
- 授权分散到 URL、方法、服务三层,按粒度拦截——统一认证+分散授权,灵活且安全。
- 评审点:每个写接口都要回答"谁有权调",答案落在方法注解或显式校验,而不是只靠 URL 配置——URL 配置漏一个 pattern 就是越权入口。

## 案例

### 第三步发散·验证与推演 验证:认证授权的断言组

- 验证:认证断言——未认证请求 401,认证通过 200。
- 授权断言——已认证但无权限 403。
- 分层断言——URL 层认证与方法层授权各自独立拦截。
- 三组固化两层防线。
- 断言失败即安全配置缺陷,修复后复跑至全绿。

### 第三步发散·发散要点 追问链:认证授权三刀

- **追问①**：JWT 场景两层怎么落——认证等于验签,授权等于读 Claims 中的权限
- **追问②**：@PreAuthorize 的复杂判定——简单角色用 SpEL 内置(hasRole),复杂归属判断调用服务返回 boolean,不在表达式里堆业务
- **追问③**：匿名用户也有 Authentication——空对象进 SecurityContext,上下文永不为 null,判定时判匿名标记而非判 null

## 总结点

1. 认证回答你是谁,授权回答能做什么
2. 401 未认证,403 无权限
3. 三层授权:URL、方法、服务
