## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 用 ForkJoinPool 执行数组分治计算，同时存在网络调用和长时间锁等待。比较可拆分 CPU 任务、阻塞任务和 ManagedBlocker 的适用边界。

1. ForkJoinPool 适合可拆分、短小、主要计算型的任务，工作线程在本地无任务时窃取其他队列以改善负载均衡。
2. 未管理的 I/O、长时间锁等待和外部调用会占住工作线程，池不能保证自动补偿；阻塞任务应隔离或使用合适的 ManagedBlocker。
3. 递归任务需要合理阈值和明确 join 结构；不能因为有工作窃取就把它当成通用阻塞任务线程池。

## 参考分析

### 第二步扩展① 窃取解决的是负载不均

- 递归分治把大任务拆为许多子任务，工作线程优先处理自己的队列，空闲线程从其他队列窃取。
- 任务足够细时，快线程可以继续取得工作，降低单个大任务拖慢整体完成的概率。
- 它解决的是任务分布，不是 CPU 增加，也不改变任务的共享状态、取消和异常语义。
- 类比同桌互看作业进度：先做完的帮忙分担后进者的剩余题（窃取），但这套互助帮不了每道题都要等老师的阻塞题。

### 第二步扩展② 阻塞会消耗并行度

- 线程在网络、文件、锁或 Future.join 中长时间阻塞时，其他任务可能没有足够工作线程执行。
- 官方明确不保证对未管理的阻塞 I/O 自动维持目标并行度。
- ManagedBlocker 只能让池知道可能阻塞，并不让慢依赖变快。
- 更稳妥的方案是把外部调用放进有界、按依赖隔离的执行器，或确认阻塞操作满足 ManagedBlocker 的设计条件。

### 第二步扩展③ asyncMode 和公共池边界

- 默认本地调度适合 fork 后 join 的递归计算。
- asyncMode 更适合 fork 后通常不 join 的事件式任务。
- 公共池是共享资源，库代码和应用代码可能互相影响，关键隔离任务应使用自有池并明确生命周期。
- 任务异常、取消和阻塞资源仍需显式处理，不能只观察池的 parallelism 数字。

## 案例

### 第三步发散·验证与推演 计算与阻塞对照

- 分别运行数组分治、每个任务 sleep/网络等待和锁竞争任务，记录池活跃线程、窃取数、完成时间和队列年龄。
- 预期计算任务能受益于窃取，阻塞任务会降低有效并行度。
- 这是 Java 17 教学对照，不代表固定吞吐。

### 第三步发散·追问① 阻塞管理验证

- 对照隔离执行器、ManagedBlocker 和直接阻塞三种方案，检查并行计算是否被拖慢、外部连接是否超限和取消能否释放资源。
- 验收还要覆盖公共池中其他任务，避免一个阻塞组件拖垮无关工作。
- 同时记录池的并行度、活跃线程、队列年龄和阻塞等待时间，确认补偿线程没有突破数据库或远程服务的并发上限。
- 结果需要在目标 JDK 和同一负载下复现。

## 总结点

1. 窃取治负载不均，治不了等老师
2. 窃取改善任务分布
3. 未管理阻塞会占住工作线程
4. 计算池与外部依赖要隔离
