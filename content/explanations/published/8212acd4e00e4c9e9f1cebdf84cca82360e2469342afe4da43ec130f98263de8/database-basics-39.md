## 参考回答

<!-- explanation:deep -->

> 场景与约束：MySQL 8.4 教学设计：租户允许删除后重新使用业务名称，并保留多次历史记录。查询只应看到有效记录，需要判断普通唯一键和 deleted 标记组合是否满足要求。

1. 软删除保留真实行，原唯一键仍可能占用名称；列表、关联、统计和权限查询若漏掉有效条件，也会把历史行当成当前资源。
2. 简单 UNIQUE(tenant, name, deleted) 可能限制同名历史记录数量；还要小心可空列与排序规则，唯一约束必须与“有效记录唯一”的业务规则一致。
3. 可评估生成列将有效名称映射为非空值、删除行映射为 NULL 再建唯一约束，或采用其他清晰模型；恢复时冲突、引用和数据保留需一起设计。

## 参考分析

### 第二步扩展① 唯一语义：标志位并不天然允许无限历史

- 若 deleted 只有 0、1，同租户同名最多对应一个有效组合和一个删除组合。
- 第二次删除重建可能又冲突。
- 若把删除时间直接放进可空唯一键，也可能因 NULL 的特殊唯一规则而允许多个有效行。
- 必须列出允许的记录组合，再按 MySQL 实际比较和 NULL 规则设计，而不是仅给索引多加一个字段。
- 类比工位牌：离职员工牌子上交（软删除），但编号不能立即复用给新员工，否则历史考勤（关联记录）张冠李戴。

### 第二步扩展② 模型选择：有效键与历史记录分开表达

- MySQL 唯一索引允许多个 NULL，可用确定性的生成列在有效时产生名称、删除时产生 NULL，与非空租户组合约束有效名称。
- 字符集、排序规则、长度和生成列支持需明确核对。
- 历史表或名称预留表也是候选，取舍取决于引用和归档需求。
- 不能无条件推广某个 SQL 到所有数据库。

### 第二步扩展③ 读取与恢复：查询规则必须贯穿各入口

- 主列表过滤 deleted 还不够，详情、JOIN、统计、缓存、导出和资源授权都要遵守一致有效规则。
- 外键通常仍引用存在的历史行，不会自动理解软删除的业务含义。
- 恢复旧记录时若名称已被新记录使用，应返回明确冲突或按产品规则改名，不能覆盖新资源来“恢复成功”。

## 案例

### 第三步发散·验证与推演 组合测试：反复创建、删除和重建

- 隔离 MySQL 按候选约束依次创建同名有效记录、删除后重建、再次删除及第三次重建，补测两个并发有效创建与不同租户同名。
- 预期允许任意合法历史组合，但同租户只能有一个有效名称。
- 若使用生成列方案，应检查真实生成值与唯一错误，而非只靠应用先查询判断。

### 第三步发散·追问① 恢复追问：旧记录恢复与新名称冲突

- 在新有效记录已占名称时恢复旧记录，验证事务拒绝冲突且不损坏两边数据。
- 再检查列表、关联统计、缓存和导出不会混入删除行。
- 记录保留与彻底清理规则也应受引用和审计要求约束。
- 以上是目标库验收矩阵，本轮未用 H2 的唯一语义冒充 MySQL 生成列及排序规则验证。

## 总结点

1. 离职工牌上交，编号不立即复用
2. 软删除保留行和约束占用
3. 有效唯一与历史重复分别建模
4. 恢复冲突和所有读路径一起验收
