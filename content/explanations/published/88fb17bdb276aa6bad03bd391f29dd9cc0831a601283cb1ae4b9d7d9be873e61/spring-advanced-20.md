> 场景与约束：网银风控沙盘:封禁用户后,其旧会话在其他节点仍有效 30 分钟(Session 未共享),期间继续下单。说明会话共享架构下的撤销传播与即时生效设计。

1. 多节点会话的三种形态:粘性会话(单节点,撤销只影响本节点)、共享存储(Spring Session,Redis/JDBC,撤销写共享即全局生效)、JWT(无状态,撤销是难题)。
2. 共享会话的撤销=删除共享会话+权限缓存失效(第 21 题):写 Redis 的会话记录与授权缓存,下一请求立即失效——生效时延=传播时延(毫秒级)。
3. JWT 的撤销:黑名单(签发状态表+网关校验)或短过期+刷新对(撤销刷新资格);纯无状态的"吊销"是伪命题,必须引入状态。

## 参考分析

### 第二步扩展① 机制:三种形态的撤销路径

- 粘性会话:封禁只写了数据库,节点上的 Session 对象仍活着——需广播失效(每节点清本地)或切共享存储。
- Spring Session:Session 存 Redis,封禁时按 userId 索引删除其全部 Session(findByPrincipalName),下一请求找不到会话→重新登录。
- 生效即时。
- JWT:令牌在客户端持有,服务端"无状态验证"无法单方面作废——黑名单表(按 jti)在网关校验,或把 access token 过期压到 5 分钟内+refresh token 撤销。
- 撤销的时效承诺必须与架构形态匹配,写进风控 SLO。

### 第二步扩展② 推演:撤销时延的量化(附真实上下文证据)

- 量化:共享会话撤销=删除 Redis 键+发布权限缓存失效事件,端到端毫秒级。
- JWT 黑名单=每次请求多一次黑名单查询(Redis O(1)),撤销即时生效。
- 本机锚点(Q19 真值示例):认证信息从上下文读取,清空即 anonymous——"撤销"在共享形态下就是清空那个上下文来源:
```
alice:anonymous
```
- 验证:共享会话撤销的 Redis 操作形态为规范推演(本机未搭 Redis Session),上下文清空行为为实测。

### 第二步扩展③ 取舍:撤销与可用性的平衡

- 强即时撤销:每次请求查撤销表(网关层 Redis)——多一次读,换取风控时效。
- 批量封禁(活动作弊):按用户批量删会话+黑名单写入,注意 Redis 管道批量化。
- 误封恢复:撤销要有"恢复通道"(解封后重新登录,黑名单条目带 TTL)。
- 审计:封禁与撤销动作写审计流水(谁、何时、依据),风控动作可追溯。

## 案例

### 第三步发散·验证与推演 验证:封禁测试账号后用其存量会话/令牌打接口,断言 401 的时延

- 验证:封禁测试账号后用其存量会话/令牌打接口,断言 401 的时延(撤销生效时延)并做成指标。
- JWT 形态另测黑名单命中——撤销演练自动化,每次发布跑一遍。
- 补充:撤销动作写审计流水(操作者/依据/时间),误封恢复通道单独验证。
- 会话形态切换时撤销预案同步更新。

### 第三步发散·追问扩展 追问链:会话撤销三刀

- **Q1：Spring Session 的 findByPrincipalName 为什么能找到全部会话?**
  - 答：它维护 principalName 索引(Redis set),按用户找会话集合;索引没建的旧会话漏网——升级共享会话时要做一次全量索引补建。
- **Q2：网关与业务服务的会话视图一致吗?**
  - 答：都读同一共享存储则一致;业务侧有独立缓存(权限缓存)时要连缓存一起失效(第 21 题)。
- **Q3：撤销演练?**
  - 答：封禁测试账号→用其存量 token 打接口→断言 401 的时延;把"撤销生效时延"做成监控指标。

## 总结点

1. 撤销即时生效,先选对会话形态
2. JWT 撤销必引状态
3. 封禁写审计,恢复留通道
