## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银长会话沙盘:网关与后端之间连接"看起来活着"——TCP keepalive 在探活线路,HTTP keep-alive 在复用连接承载多请求;两个"活"字完全是两件事,混用会得出"心跳开着连接就是好的"的错误判断。

1. TCP keepalive:空闲时内核周期发探针(默认 2 小时起步),作用是检测对端死活与中间设备状态,不传输业务数据;HTTP keep-alive:应用层复用同一条连接发多个请求,省握手,由 Connection 头与空闲超时管理。
2. 本机对照:预热后 100 次请求,连接复用 29ms(0.29ms/req)对每请求 close 90ms(0.90ms/req)——复用省下的正是每请求的握手成本;而 TCP keepalive 对这个数字毫无贡献,它只在空闲期活动。
3. 工程分工:连接复用归 HTTP 层(客户端连接池+服务端空闲超时),死连接检测归 TCP keepalive 或应用心跳——检测周期按故障发现预算定(分钟级靠 keepalive 调参,秒级上应用心跳)。

## 参考分析

### 第二步扩展① 机制:两层"活"的作用域

- TCP keepalive:SO_KEEPALIVE+三个内核参数(空闲时长/探针间隔/探针数),探测的是"对端协议栈是否可达"。
- HTTP keep-alive:连接池持有连接,请求按需在空闲连接上发起,空闲超时(如 60 秒)后双向都可能先关——被先关的一方下次借出连接会报错(见 Q9)。

### 第二步扩展② 反例:两层混用的三种事故

- 事故一:以为开了 keepalive 就不用应用心跳——NAT/防火墙静默丢弃空闲连接表项,TCP 探针也到不了对端,应用以为连接活着。
- 事故二:HTTP 空闲超时两端不一致——服务端 30 秒先关,客户端池 60 秒持有,借出即 Connection reset。
- 事故三:keepalive 默认 2 小时——故障发现预算分钟级,默认参数等于没有。

### 第二步扩展③ 取舍:探活手段的选择

- TCP keepalive:内核级零应用代码,但周期粗、穿不过静默丢表项的中间设备。
- 应用心跳:周期可控语义明确(带业务版本),占用应用线程。
- 连接池校验(borrow 时 ping):只在借出瞬间暴露问题,延迟感最差。
- 按故障发现预算选:秒级用心跳,分钟级调 keepalive,配合池的驱逐策略。

## 案例

### 第三步发散·验证与推演 验证:复用收益的实测证据

- 本机实测(JDK 17.0.17,loopback,预热后):
~~~
java N4KeepAlive
第1轮 100 请求:复用=42ms(0.42ms/req),close=91ms(0.91ms/req)
第2轮 100 请求:复用=29ms(0.29ms/req),close=90ms(0.9ms/req)
~~~
- 验证:预热后复用比每请求握手快约 3 倍。
- 首测曾出现复用反慢(冷 JIT 噪声),预热与交替测量消除——复用收益成立且随真实 RTT 放大。
- TCP keepalive 不参与该收益,两层"活"的分工实证。

### 第三步发散·发散要点 追问链:两层活三刀

- **追问①**：服务端先关还是客户端先关——谁先关谁背 TIME_WAIT(Q6),连接池客户端常配"服务端空闲超时的一半+主动校验"避免借出死连接
- **追问②**：HTTP/2 的 ping 帧——HTTP/2 在应用层内置心跳语义,替代 TCP keepalive 做秒级探活(见 Q17)
- **追问③**：连接池的最大空闲数——空闲连接也占对端资源与 NAT 表项,池要按"并发需求"而非"峰值历史"持有

## 总结点

1. TCP 活探线路 HTTP 活复用
2. 复用省握手三倍差
3. 探活周期按发现预算
