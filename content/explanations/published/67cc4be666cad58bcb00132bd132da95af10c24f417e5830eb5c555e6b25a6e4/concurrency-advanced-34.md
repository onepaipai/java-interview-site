## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：限流器用 `if (counter.get() > 0) counter.decrementAndGet()` 放行请求，压测发现超发。用 check-then-act 竞态解释超发成因，给出单机 CAS 与分布式原子扣减的正确写法。

1. 先读后减是两步操作：两个线程同时读到同一余量、各自判断可放行、各自减一——余量 1 被放行 2 个请求。读与减之间没有任何互斥，这是教科书级 check-then-act 竞态。
2. 单机正确写法：把"判断并扣减"合并为一次原子操作——AtomicInteger 的 compareAndSet 循环（读到 v，CAS(v, v-1)，失败重读重试），或 decrementAndGet 后与 0 比较的语义化封装。
3. 分布式限流扣减必须原子地在存储端完成：Redis 用 Lua 脚本把读、判、减合并为单命令执行，或用 DECR 加回滚语义——绝不能在应用侧先 GET 再 SET。

## 参考分析

### 机制：读与写之间的时间窗就是超发窗口

get 与 decrement 之间有纳秒到微秒的窗口，窗口越长、并发越高，双重放行概率越大。类比考试收卷：老师说"还有 1 份卷子"（读），两个考生同时伸手（减）——份额只有一份。原子扣减把"宣布余量"与"拿走"变成同一个不可分割的动作。

### 边界：扣减到零的语义设计

CAS 循环必须处理"余量为 0 时 CAS 永远失败"的终止条件：读到 0 直接拒绝，不进入重试循环空转。另有"扣减后请求失败要归还"的场景：归还也是原子操作，且要防归还把负数/超量补回去——配额的增减都必须走同一原子通道。

### 取舍：单机 CAS 与分布式脚本的分工

单机 Atomic/CAS 纳秒级、无网络成本，进程内限流首选；多实例部署时限流目标通常是"全集群配额"，扣减必须集中在共享存储（Redis Lua、数据库原子更新），代价是每请求一次网络往返。分层方案：本地预扣小额配额（批量取票），用尽再向中心补票——把网络成本摊薄而不破坏原子性。

## 案例

### 对照操作：超发的量化复现

教学验证：配额 1000，200 线程并发请求。预期：先读后减版本实际放行超过 1000（记录超发数），CAS 版本恰好 1000；分布式场景用 Redis Lua 对照 GET+SET 版本复现同样超发。三组数字并排，竞态的量级一目了然，实验可复跑。

### 追问：为什么 Lua 脚本能保证原子

Redis 单线程执行命令，Lua 脚本作为一个命令整体执行，期间不插入其他命令——读、判、减天然合并。要点是脚本内不要执行任何可能阻塞的操作，且把判定逻辑完整放进脚本；只把"读回来在 Java 里判断"是常见的伪原子。

## 总结点

1. 读与减之间，就是超发窗
2. 单机 CAS，分布式 Lua
3. 归还也走同一原子通道
