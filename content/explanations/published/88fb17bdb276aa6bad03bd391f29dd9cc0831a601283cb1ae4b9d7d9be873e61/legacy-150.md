## 参考回答

> 场景与约束：网银开放 API 沙盘:对外接口演进时不 breaking(版本兼容)、错误可程序化处理(错误码)、重复请求不重复扣款(幂等)、失败自动恢复(重试)——四件套是接口契约的完整闭环。

1. 版本兼容:URL 路径(/v1/orders→/v2)/请求头(Accept 版本)——兼容性原则:新增字段可选(旧客户端忽略)/删除或改语义字段=breaking(升版本)/字段类型不变(字符串数字别互转);deprecation 流程=新旧并存+响应头标记废弃(Sunset/Deprecation)+迁移窗口+下线公告(第 119 题幂等同篇)。
2. 错误码双层:HTTP 状态码(传输层语义:4xx 客户端/5xx 服务端)+业务错误码 body(精确原因:ACCOUNT_FROZEN/INSUFFICIENT_BALANCE)——错误响应统一结构(code/message/traceId/details);message 给人看(可变文案),code 给程序看(稳定不变——文案随版本变,码永远不变)。
3. 幂等:重复请求只产生一次效果——天然幂等(查询/删除)/条件幂等(带唯一键:Idempotency-Key 头或业务单号,服务端去重表+状态机)/非幂等改造(支付接口带 out_trade_no);重试:只重试幂等接口或确保幂等前提——超时/5xx/限流 429 可重试(指数退避+抖动,第 137 题),4xx 参数错不重试(重试必错)。

## 参考分析

### 第二步扩展① 机制:幂等与重试为什么绑定

- 重试的前提=第一次可能已成功(超时后结果未知)——不幂等接口重试=重复扣款。
- 幂等键让“重试”安全:服务端记录键→结果,重复请求返回首次结果(不重新执行)——重试策略(退避/次数/熔断)只解决“怎么重”,幂等解决“能不能重”——两者是同一问题(失败恢复)的两半(第 137 题可靠性同源)。

### 第二步扩展② 反例:接口设计的两种事故

- 事故一:v2 改字段语义不升版本——amount 从分改元,旧客户端少算百倍(资损)。
- 修复=breaking 必升版本。
- 事故二:错误码=文案——前端按 message 包含“余额不足”判断(文案一改判断失效)。
- 修复=稳定 code+文档化错误码表(OpenAPI 枚举,第 158 题契约同源)。
- 事故三(加分):重试无幂等——网络抖动重试导致重复下单。
- 修复=业务单号幂等+重试白名单。

### 第二步扩展③ 取舍:版本策略的选择

- 路径版本(/v1)最直观(路由/网关/监控都可见——推荐)。
- 头版本更 REST 纯但调试难。
- 同版本内向后兼容演进(加字段)是常态——API 设计=先定兼容原则(永远不 breaking 现有字段语义),再定版本机制。
- 内部接口用消费端兼容(容忍未知字段),对外接口用显式版本+废弃流程。

## 案例

### 第三步发散·验证与推演 验证:接口契约的实测走查

- 验证:兼容断言(旧客户端请求新版本——未知字段被忽略/缺失字段走默认)。
- 错误码断言(同错误同 code,文案变化不影响程序判断)。
- 幂等断言(同 Idempotency-Key 重放→返回首次结果,服务端只执行一次——第 119 题实验同源)。
- 重试断言(模拟超时→指数退避重试成功且只扣款一次)——四组固化契约,本机可复跑。

### 第三步发散·发散要点 追问链:接口三刀

- **追问①·OpenAPI 契约先行**：spec 驱动生成文档/SDK/校验(第 158 题场景评分同源)
- **追问②·traceId 贯穿**：错误响应携带 traceId+日志关联(排错入口,第 129 题可观测同源)
- **追问③·限流与错误码配合**：429+Retry-After 头(客户端可编程退避,第 51 题限流信号同源)

## 总结点

1. breaking 必升版本,加字段可选
2. code 稳定给程序,message 给人
3. 幂等键让重试安全
