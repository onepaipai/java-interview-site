## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：团队已统一"先更新订单再更新库存"，死锁依旧。揭示三种"顺序一致仍死锁"的机制：批量更新行序不一致、范围条件的间隙获取顺序、唯一键冲突的插入意向锁交错。

1. 批量 UPDATE 的行序由扫描路径决定：UPDATE ... WHERE id IN (5,1,9) 的加锁顺序是索引扫描顺序（通常按 id 升序），代码里写的 IN 列表顺序不改变它——两个事务各自按"自己的查询路径"扫描，行序可能不同（不同索引、不同条件）。
2. 范围条件的间隙锁按扫描顺序逐段获取：两个事务各扫一个重叠范围，加锁的间隙片段顺序可以不同（从两端向中间扫描），即使业务顺序一致也形成环。
3. 唯一键并发插入：两个事务插入相同唯一键，先到者持记录锁，后到者申请插入意向锁被阻塞并等待前者提交；此时若后者还持有前者需要的其他锁，环成——插入顺序"一致"也拦不住。

## 参考分析

### 第二步扩展① 机制：业务顺序与锁顺序之间隔着"执行计划"

- 业务写的顺序是"逻辑顺序"，加锁顺序是"物理顺序"（按哪个索引、什么方向扫描行）。
- 两者之间隔着优化器选择的执行计划——计划一变（换了索引、走了不同范围），物理顺序就变。
- 类比交通规则统一了行驶方向，但两条车流在不同匝道汇入，桥上仍可能交叉互堵。

### 第二步扩展② 反例：IN 列表顺序的"假一致"

- 事务 1 UPDATE ... WHERE id IN (1, 5)，事务 2 WHERE id IN (5, 1)——代码作者认为顺序一致。
- 引擎都按 id 升序加锁（1 后 5），实际安全。
- 真正的危险是两事务用不同索引：一个走主键（1→5），一个走二级索引（5→1）——业务顺序相同、物理顺序相反。
- 修复：让冲突事务对同一批行走"同一条索引路径"，例如显式 ORDER BY 主键分批更新。

### 第二步扩展③ 取舍：防御手段的分层

- 第一层：统一扫描路径（显式 ORDER BY 或固定索引 hint）——治"顺序不一致"。
- 第二层：缩小事务与降低隔离级别（RC 减少间隙锁，见第 23 题）——治"锁的面"。
- 第三层：死锁重试兜底。
- 三层都用上后仍偶发死锁属于可接受残留——死锁被检测并自动回滚一方，只要重放幂等，业务无损。

## 案例

### 第三步发散·验证与推演 对照操作：双索引路径的死锁复现

- 教学验证：两事务分别按主键序与二级索引序更新同一组行。
- 预期：高并发下稳定复现死锁（SHOW ENGINE INNODB STATUS 的持锁序列方向相反）。
- 统一 ORDER BY 后消失。
- 实验可复跑，把"物理顺序"从抽象概念变成可见日志。

### 第三步发散·追问① 追问：为什么"统一 ORDER BY"不是万能药

- ORDER BY 强制排序的前提是引擎按此序加锁（多数情况成立），但代价是强制使用可满足排序的索引——可能放弃更高效的过滤路径。
- 且混合语句（SELECT FOR UPDATE 与 UPDATE 混用）的加锁细节仍有差异。
- 它是高性价比的默认手段，不是终点。
- 残留死锁交给重试兜底。

## 总结点

1. 业务顺序不等于加锁顺序
2. 扫描路径一变，物理序就变
3. 统一路径、缩小事务、重试兜底
