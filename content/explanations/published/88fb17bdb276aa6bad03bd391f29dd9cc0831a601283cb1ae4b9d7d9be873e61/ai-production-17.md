## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银问答沙盘:流式输出中途网络抖动,前端重连后从头再显示一遍(重复)或半截答案卡死——流式的断线恢复与内容连续性是前端与服务端的协作协议。

1. 重复内容的三种来源:前端重连后重新发起请求(服务端重新生成,内容随机性导致两次不同——用户看到拼接混乱)、重试幂等缺失(同键生成两次)、前端渲染层重复追加(重连事件处理 bug)。
2. 恢复协议:请求带客户端生成 ID(幂等键,第 38 题)——断线重连同 ID,服务端返回"续传"(已生成部分从 offset 继续,SSE Last-Event-ID 语义)或完整缓存结果(生成已完成的,第 20 题缓存);不重新生成。
3. 前端纪律:重连时按事件 ID 去重(收过的分片不重复追加)、断线提示明确("连接中断,正在恢复")、恢复失败(服务端缓丢失效)的降级=展示已收部分+手动重新提问按钮。

## 参考分析

### 第二步扩展① 机制:流式的"连续性"是两端的责任

- 服务端负责:幂等键识别重连、生成缓存的续传能力、事件 ID 标记。
- 前端负责:重连去重、断线状态显式、恢复失败降级。
- 任何一端缺失都会出现"重复/卡死/半截"。
- 类比视频通话:断线重连要双方协议(续传+去重),单端努力无效。

### 第二步扩展② 反例:流式恢复的三种事故

- 事故一:重连=重新生成——同 ID 两次生成内容不同(采样随机),前端两次都渲染(重复混乱)。
- 修复=幂等键+服务端续传/缓存。
- 事故二:重连风暴——断线后前端指数重试无退避无上限,服务端被重连打爆。
- 修复=退避+上限+提示用户手动。
- 事故三:事件 ID 缺失——前端无法去重,重复追加。
- 修复=SSE 事件带递增 ID。

### 第二步扩展③ 取舍:续传、缓存与重新生成的选择

- 生成中断线:续传(offset 之后的分片)最优,但要求服务端保住生成状态(KV 在,第 33 题)——生成完成后状态释放,续传窗口有限。
- 生成完成后断线:缓存结果直返(幂等键命中)。
- 续传不可用(状态已释放):回退重新生成+前端清空重渲染(明确告知,不是静默拼接)。

## 案例

### 第三步发散·验证与推演 验证:流式恢复的推演核对

- 推演核对(教学示例):注入三类断线(生成中断线/生成完成后断线/渲染层重复事件)——断言:同 ID 重连命中续传或缓存(不重新生成)、事件去重生效(前端内容无重复)、恢复失败降级(已收部分保留+重问按钮)。
- 验证:连续性断言(内容无重复无丢失)可程序化(拼接结果与完整生成比对)。
- 对照无协议形态的重复渲染复现。

### 第三步发散·追问扩展 追问链:流式三刀

- **Q1：续传窗口多长?**
  - 答：生成状态( KV/生成中标记)在完成即释放(第 33 题容量),窗口=生成时长+短暂保留(秒级);窗口外的重连走缓存或重新生成。
- **Q2：事件 ID 与引用编号的关系?**
  - 答：流式事件 ID 是传输层概念,引用编号(第 27 题)是内容层概念,两套编号不混。
- **Q3：多轮会话的流式?**
  - 答：每轮独立幂等键+事件流,轮间的历史压缩(第 23 题)不干扰流式协议。

## 总结点

1. 幂等键识别重连,续传或缓存不重生成
2. 事件 ID 去重,断线状态显式
3. 恢复失败降级:保留已收,明示重问
