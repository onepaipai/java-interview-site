## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：订单服务的方法持全局锁后调用内部方法再触发重入，同时该方法内含远程调用。推演重入的语义边界、锁内长操作的放大效应，给出按数据分片与锁外执行 IO 的粒度设计。

1. 可重入指"同一线程可重复获取自己已持有的锁"（按持有者计数），它防止自调用死锁，但不改变互斥范围：重入路径上的所有代码都在同一临界区里。
2. 粒度设计的第一原则是临界区只包"必须互斥的状态变更"，IO、计算、回调一律移出；锁内远程调用把毫秒级临界区放大成秒级，是吞吐事故的头号来源。
3. 缩小范围的手段按序：按 key 分片锁（同 key 互斥、跨 key 并行）、先读后写分离（读无锁快照、写才加锁）、或把不变式下沉数据库。

## 参考分析

### 机制：重入是通行证，不是范围开关

可重入锁记录持有线程与次数：内部方法再次 synchronized 同一对象只是计数加一，出临界区逐层减一，减到零才真正释放。类比持有一张园区通票：一天内可以反复进出（重入），但你走到哪（执行什么代码）与票无关——锁内代码的全部耗时都计入"别人排队等待"的时间。

### 反例：锁内调用远程接口的三重放大

持全局锁调支付网关：一重，所有支付请求串行排队；二重，网关抖动时队列以秒级膨胀，线程池与连接池跟着堆积；三重，超时后的重试在锁内再跑一遍。修复三步：锁内只做"校验并预扣"的内存操作，远程调用移到锁外，结果回写时再短暂加锁并校验版本（乐观确认）。重入语义不变，临界区回到毫秒级。

### 取舍：分片锁的设计与代价

按 key 哈希到 N 个锁对象（或用 Guava Striped）：同 key 串行、不同 key 并行，代价是"全局操作"（如统计所有 key）需要依次取所有锁且顺序固定防死锁；key 的哈希倾斜会造成热点分片。分片数按"目标并发度"取 2 的幂（如 16、64）。粒度的终点是把互斥需求降级为数据原子性：能用条件更新（数据库）就不用进程内锁。

## 案例

### 对照操作：锁内 IO 与锁外 IO 的吞吐对比

教学验证：模拟 50 并发调用，任务含 50 毫秒"远程调用"与 1 毫秒内存变更。全局锁包全程预期吞吐约 20 每秒（50 毫秒串行）；锁外调用预期吞吐提升一个数量级。再演示重入：外层方法与内层方法都 synchronized 同一对象，确认不死锁且时间都计入等待方观测。实验可复跑。

### 追问：如何评审一个方法的锁粒度

三问：临界区内有没有 IO 或回调；锁保护的状态是否真的需要全量互斥（能否按 key 分）；锁的获取顺序是否固定。加上一条观测：生产上采集锁等待时间分布（JFR 的锁事件），P99 等待超过临界区预期值就是粒度问题的直接证据。

## 总结点

1. 重入是次数，不是范围
2. 锁里无 IO，远程出门再打
3. 按 key 分片，全局操作守顺序
