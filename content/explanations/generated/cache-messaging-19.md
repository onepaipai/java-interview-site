## 参考回答

> 场景与约束：Java 17 / Jackson 教学场景：缓存序列化从 Java 原生序列化切 JSON，切换后读到旧格式数据反序列化失败。设计"新写旧读"的兼容协议：格式标识、双读策略与过期自然清洗。

1. 根因：缓存里同时存在旧格式（切换前写入的，TTL 未到期）与新格式数据——反序列化器只认新格式。兼容的本质是"读写格式允许短暂不一致"。
2. 协议设计：value 加格式标识（前缀 magic byte 或 JSON 内嵌 version 字段）；反序列化按标识分发——新格式按新解析器、旧格式按旧解析器读出再转新格式回写。旧格式只读不写，随 TTL 自然清洗。
3. 加速清洗的三选一：切换时全量 FLUSH（可接受回源风暴时最干净）；SCAN 渐进重写（改写成本低时）；缩短 TTL 观察期（切换前把 TTL 压短，让旧值快速自然过期）。

## 参考分析

### 第二步扩展① 机制：缓存的"格式迁移"没有数据库那样的 ALTER

- 数据库改列类型有在线 DDL 与默认值机制。
- 缓存里的序列化格式存在于"每个 value 的字节流"里——没有 schema 层，格式信息只能由应用自己编码与解释。
- 类比文档库里新旧两版模板并存：读的时候看封面版本号选模板解释，写的时候一律用新版。

### 第二步扩展② 反例：直接换解析器的三种失败

- 一，旧值反序列化抛异常：读路径崩溃（要 try-catch 按未命中处理）。
- 二，旧值被"成功"解析出错误结构（字段错位）——比抛异常更危险，静默错误数据。
- 三，双写期间新格式与旧格式互相覆盖（写路径未统一）——先统一写路径再动读路径。
- 三者的共同预防：格式标识先行。

### 第二步扩展③ 取舍：Java 原生序列化为什么该退出

- 原生序列化有反序列化漏洞风险（任意类构造）、跨语言不可用、体积大。
- JSON/Protobuf 更安全紧凑且跨语言。
- 切换的最佳时机是"缓存可全量清洗"时（低峰 FLUSH + 预热），没有清洗窗口时用标识+双读过渡。
- 安全理由优先于迁移便利。

## 案例

### 第三步发散·验证与推演 对照操作：新旧共存的读写验证

- 教学验证：缓存中预置旧格式值，切换后读写各 1 万次。
- 预期：读旧值走旧解析器成功并回写新格式。
- 新写入全部新格式。
- TTL 过后旧格式清零、全量新格式。
- 用格式统计（SCAN 抽样）验证收敛，实验可复跑。

### 第三步发散·追问① 追问：为什么说"错误结构比异常好处理"

- 异常 fail-fast 会触发缓存未命中路径（回源），业务无感。
- 错误结构则把错位字段当业务数据用——污染决策链。
- 兼容设计的优先级：宁可抛异常走回源，不要静默错误解析。
- 格式标识 + 解析器严格校验（字段必填断言）是双保险。

## 总结点

1. value 加标识，读写允许短暂不一致
2. 旧格式只读不写，随 TTL 清洗
3. 错误结构比异常更危险
