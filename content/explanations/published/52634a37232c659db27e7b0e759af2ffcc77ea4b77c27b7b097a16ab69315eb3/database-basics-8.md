## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银客户检索沙盘:WHERE name LIKE '%银行%'——前导 % 让 B+ 树无法定位起始页(树的有序性按「从头比较」组织);'%x%' 与 '%x' 一样只能全扫;后缀 'x%' 可以。

1. B+ 树按「字典序从头比较」组织——LIKE 'abc%' 能定位(前缀确定,等价于范围 [abc,abd));'%abc' 的前缀未知——任何页都可能藏匹配项,树导航失效;剩余手段=全表扫/全索引扫+逐行过滤;ICP 只能让过滤在索引层发生(减少回表),不减少扫描范围。
2. 替代方案按场景:①倒排索引(全文索引 FULLTEXT ngram 或 ES)——分词后倒排,'%银行%' 变为分词命中+合并,海量文本的标准解;②反转存储——'银行%' 查后缀场景把串反转存索引列(后缀变前缀,如域名/文件后缀查询);③应用层内存检索(小数据量直接 LIKE 也无妨——量级优先于教条)。
3. 语义陷阱:大小写/排序规则(collation)影响 LIKE 命中与索引可用;通配符转义(% _ 在值内的字面匹配要 ESCAPE);中文 ngram 分词的最小词长配置决定召回——「LIKE 慢」的解法清单里,先确认语义正确再谈性能。

## 参考分析

### 第二步扩展① 机制:前缀确定性与树导航的关系

- B+ 树导航每层问「往左还是往右」——依据=查询键与节点键的字典序比较。
- 前缀未知时,比较的第一字符就不确定,任何分支都可能包含答案——无法排除任何一半,树的二分性质作废。
- 这正是第 45 题「索引失效」的根因族(有序性破坏):函数包装/隐式转换/前导通配都是「把可导航问题变成不可导航问题」。
- 后缀查询的修复=把数据旋转成前缀可查(反转列),本质是「为查询模式定制有序性」。

### 第二步扩展② 反例:LIKE 的三种事故

- 事故一:CONCAT('%',#{kw},'%') 以为走索引——仍全扫(ICP 减回表而已)。
- 事故二:用 LIKE 做搜索引擎——万级行以上响应崩,应上全文/ES(第 152 题架构选型)。
- 事故三:转义缺失——用户输入含 %/_ 使条件意外放宽(查询注入的一种),ESCAPE 转义+长度限制。

### 第二步扩展③ 取舍:倒排 vs 反转列 vs 应用层

- 文本大+模糊查询高频:全文索引/ES(成本=同步管道与运维)。
- 固定模式(域名后缀/单号后缀):反转列(零依赖)。
- 小表(万级以内)低频:LIKE 直查(优化过度反而添复杂度)。
- 判断基准=扫描行数×频率(第 12 题),不是「用了 LIKE 就是错」。

## 案例

### 第三步发散·验证与推演 验证:前缀断言组(本机可复跑)

- 验证:EXPLAIN 对照('abc%' type=range。
- '%abc%' type=ALL 或 index——定位差异立现)。
- ICP 断言('%abc%' 加索引列过滤后 Extra=Using index condition——回表减少但 rows 不变)。
- 反转列断言(后缀查询建反转索引 type=range)。
- 全文对照(FULLTEXT ngram 对 '%银行%' 的命中与耗时)。
- 转义断言(含 % 输入的 ESCAPE 行为)。
- 预期:导航能力与扫描范围一一对应。

### 第三步发散·发散要点 追问链:LIKE 三刀

- **追问①**：全文索引的机制——倒排表(词→文档列表)与 BM25 相关性,与 B+ 树是两种有序性(第 93 题哈希/B+ 对比的延伸:结构跟着查询模式);
- **追问②**：ES 的同步链路——binlog→ Canal→ ES 的延迟与一致性问题(第 43 题主从延迟同构);
- **追问③**：安全边界——LIKE 注入(#{} 已防)与通配符滥用(全 % 输入=全表扫 DoS)——输入侧限长限频(第 51 题限流同源)

## 总结点

1. 前缀 % 废导航,ICP 只省回表
2. 'x%' 是范围,'%x%' 是扫描
3. 倒排/反转列/应用层三替代
