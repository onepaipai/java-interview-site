## 参考回答

<!-- explanation:deep -->

> 场景与约束：Java 17 教学场景：业务把 Redis 分布式锁的释放写成 `DEL lockKey`，偶发删掉了其他实例的锁。对照本地锁与分布式锁的释放语义，说明持有者校验、原子释放与租约到期的三条差异。

1. 本地锁的释放由 JVM 保证"只有持锁线程能解锁"（ReentrantLock 校验持有者）；DEL lockKey 不校验持有者——租约过期换主后，旧持有者会删掉新持有者的锁。
2. 分布式释放必须原子校验并删除：Lua 脚本里"GET 值 == 自己的 token 才 DEL"（或 Redis 6.2 的 `GETDEL` 配比对），比较与删除不可分两步——分两步就重新引入竞态窗口。
3. 释放的时机语义也不同：本地锁显式 unlock 即释放；分布式锁有租约自动过期与显式释放两条路径，显式释放失败（网络抖动）不致命——租约到期兜底；但持有者必须意识到"释放成功前锁可能已易主"（见第 46 题）。

## 参考分析

### 第二步扩展① 机制：持有者身份的载体不同

- 本地锁的持有者身份在 JVM 内（线程 ID 由锁对象记录），校验零成本。
- 分布式锁的持有者身份是锁值里的 token（实例 ID + 唯一串），校验要跨网络到存储端完成。
- 类比本地锁是门内插销（谁来谁拔），分布式锁是寄存的保险柜钥匙（取钥匙前必须核对编号）——身份校验从"内置"变成了"协议"。

### 第二步扩展② 反例：无校验释放的换主事故

- 实例 A 持锁执行 30 秒长任务，租约 10 秒到期，实例 B 获锁开始工作。
- A 完成后 DEL lockKey——删掉的是 B 的锁，实例 C 随即获锁，B、C 并发执行。
- 事故链的三要素：长任务 + 短租约 + 无校验释放。
- 修复是 Lua 校验删除，并把租约时长与任务耗时重新匹配（或加续租看门狗）。

### 第二步扩展③ 取舍：token 设计与释放脚本的要点

- token 必须实例唯一且不可猜（实例 ID + UUID），否则可能误删同 ID 的旧请求锁。
- Lua 脚本要同时处理"锁不存在"与"值不匹配"两种情况（都视为释放失败而非报错）。
- 可重入场景把 token 换成计数 map——复杂度上升前先问是否真的需要可重入的分布式锁。

## 案例

### 第三步发散·验证与推演 对照操作：无校验释放的事故复现

- 教学验证：两个模拟实例，A 持锁后人为过期，B 获锁写入，A 随后 DEL——预期 B 的锁被删，C 立即获锁造成 A/B（或 B/C）并发。
- 换 Lua 校验释放后，A 的 DEL 影响行数为零，B 的锁完好。
- 实验可复跑，事故链三要素逐个验证。

### 第三步发散·追问① 追问：为什么要用 token 而不是线程 ID

- 分布式场景里"线程 ID"跨进程无意义，且同一实例可能有多个并发持锁请求——token（实例 + 请求唯一串）才能区分"同实例的第二个请求"。
- 身份标识的粒度必须与互斥的粒度一致：锁保护的是"这次请求的操作"，token 就要标识到请求级。

## 总结点

1. DEL 之前先验 token
2. 比较与删除，一个 Lua 原子完成
3. 显式失败不致命，租约兜底
