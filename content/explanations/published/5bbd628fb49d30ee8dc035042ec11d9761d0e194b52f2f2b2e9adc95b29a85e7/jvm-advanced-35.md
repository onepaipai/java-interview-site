## 参考回答

> 场景与约束：网银解析服务沙盘:用 NumberFormatException 判断"是否数字"驱动业务分支,压测吞吐低于显式判断版本。用本机基准实测异常路径的成本量级与方差,给出"异常当控制流"的评估清单。

1. 构造异常要填栈:fillInStackTrace 抓全线程栈,单次成本微秒级,比常规分支高 1-3 个数量级;本机 100 万次全抛路径实测 0-51ms 波动,方差本身就是警示。
2. JIT 会被异常路径扭曲:异常抛出点切断内联与块优化,catch 块限制代码重排;异常处理表让编译器保守。
3. 判断标准是频率与可预期性:可预期的、高频的"否"答案不该用异常表达;真异常(边界破坏)保持异常语义,可读性与性能兼得。

## 参考分析

### 机制:异常的成本构成

throw 时 JVM 走异常分派:fillInStackTrace 收集整条栈(深度决定成本)、查异常处理表、栈展开。本机基准(Java 17.0.17,百万次):正常路径 0-4ms,全抛路径 0-51ms——高方差来自 JIT 重新编译与栈深变化,单机循环基准不含生产栈深(生产栈更深,fill 更贵)。另一层成本:热点方法里 throw 点让 C2 放弃跨它的优化(内联链在异常边界断开),即使异常不抛,编译产物也变保守。

### 反例:把异常当枚举解析用

字段解析用 try { Integer.parseInt(s) } catch (NumberFormatException e) { /* 视为非法 */ },数据里 30% 是非法值:每秒百万次解析时异常构造成为分配与 CPU 双热点(JFR 分配采样栈顶是 NumberFormatException.<init>)。修正:预校验正则或手写 isDigit 扫描把"否"路径变普通分支;异常保留给真正的数据损坏。语义面:异常语义是"非预期状态",当控制流用会让监控告警(异常计数)失真。

### 取舍:什么场景异常可接受

可接受:低频真实异常(网络断、配置错)、框架边界防御(反序列化失败)、预热期的一次性探测。不可接受:高频可预期的否路径(格式校验、缓存 miss 探测)、循环体内的尝试型逻辑。灰度动作:把异常计数纳入监控,按接口建立异常率基线,异常率突增即是"异常被当控制流"的信号。

## 案例

### 实证:百万次异常路径的量级与方差

命令与输出(Java 17.0.17,ExcExp2:正常 div(i,3) 对照全抛 div(i,0) catch):
```
normal=0ms  allThrow(ok=1000000)=0ms
normal=2ms  allThrow(ok=1000000)=51ms
normal=0ms  allThrow(ok=1000000)=0ms
```
解读:51ms/百万次≈51ns/次,量级远超普通分支(纳秒级);0ms 轮说明 JIT 去优化/重编译使测量方差极大——基准数字只能定数量级,不能当精确成本;生产栈更深,成本只会更高。验证:同机重跑方差仍在,这本身就是结论的一部分(异常路径的性能不可预测性)。

### 追问链:异常三刀

一刀:"JIT 会消除异常成本吗?"——隐式异常(空指针、除零)走 fast-path 抛出点替换信号机制,不填栈不展开,成本接近分支;显式 throw(用户代码)不享受该机制,两者别混谈。二刀:"为什么监控异常率?"——异常率是"控制流被异常化"的温度计:业务低谷异常率上升说明有人在拿异常当分支;修复方向是把否路径显式化。三刀:"第三方库在热路径抛异常怎么办?"——包一层预校验跳过库的异常路径,或换库;别试图改库,把边界校验放在自己一侧成本最低。

## 总结点

1. 填栈是硬成本,栈深定价
2. 可预期的否,不配用异常
3. 监控异常率,先修控制流
