## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银升级沙盘:供应商推送新模型版本,直接替换 base URL——行为漂移(格式变化/拒答率变化/质量分布变化)全量暴露,坏 case 集中爆发;灰度替换=双版本并行+分维评测对比(Q35)+按流量灰度+停止条件(Q15)——模型升级=一次发布,走发布纪律。

1. 行为漂移的形态:格式漂移(输出结构变了——下游解析挂,Q23)、拒答漂移(对齐收紧,误拒上升——Q18)、质量分布变化(平均持平但某类下降,Q35)、成本变化(输出变长,token 成本+30%,Q41)——漂移是必然的(模型是黑盒升级),灰度是唯一的发现手段。
2. 灰度流程:双版本并行(新旧 API 共存,路由层切换)→分维评测(评测集双跑,分维对比——Q35 的矩阵)→灰度放量(1%→10%→100%,每步观察生产指标:错误率/拒答率/延迟/成本,Q15 的自动停止)→全量→旧版本保留(回滚窗口)——评测(离线)+灰度(在线)双闸。
3. 提示与参数的联动升级:新模型的最优提示不同(温度/格式/指令措辞)——升级=模型+提示+参数的组合变更(评测按组合评测,不是只换模型);回滚的完整性=模型+提示+参数一起回(Q39 的兼容窗口思想)。

## 参考分析

### 第二步扩展① 机制:双版本并行的路由

- 路由层按请求特征分配版本(灰度比例/用户分组/场景)——路由的开关=配置中心(Q16,可秒级回滚)。
- 双版本的日志分开统计(分维对比的在线版)。
- 成本双计(新旧各自的 token 消耗——成本漂移可见,Q41)。
- 供应商版本切换的主动权:固定版本号(不追 latest)——升级由你触发,不由供应商触发(变更自主权,Q17)。

### 第二步扩展② 反例:直接替换的三种事故

- 事故一:追 latest 自动升级——供应商静默更新,行为漂移无人知晓,故障晚发现。
- 固定版本+显式升级。
- 事故二:只测不灰——离线评测全绿直接全量,线上分布差异(真实流量形态)暴露问题。
- 灰度双闸。
- 事故三:提示不联动——新模型用旧提示(次优参数),质量下降被误判为"新模型不行"。
- 组合评测。

### 第二步扩展③ 取舍:灰度周期与回滚窗口

- 长灰度(2 周):漂移充分暴露,新能力上线慢。
- 短灰度(2 天):快,长尾场景未覆盖。
- 按影响面分级——核心链路长灰度,长尾快速。
- 回滚窗口(旧版本保留期)与"发现问题的滞后"匹配(至少覆盖一个完整业务周期)。

## 案例

### 第三步发散·验证与推演 验证:灰度流程的推演核对

- 推演核对:双版本路由与 Q16(配置中心开关)、Q15(灰度自动停止)直接复用。
- 分维评测与 Q35(矩阵)一致。
- 成本双计与 Q41(总成本)衔接。
- 固定版本号与 Q17(变更自主权)同源。
- 回滚窗口与 Q39(兼容窗口)同构。
- 验证:灰度流程可执行(明示:按发布实践推演)。

### 第三步发散·发散要点 追问链:升级三刀

- **追问①·与 Q43 的衔接——升级评测**：评测平台的回归(五元组含模型版本)
- **追问②**：与 Q44 的衔接——embedding 模型升级=索引重建+模型升级的双重灰度(更长流程)
- **追问③**：与 reliability Q44 的衔接——治理不拖慢发布的平衡:模型升级的灰度也是"发布"的一种,纪律一致

## 总结点

1. 模型升级等于发布
2. 评测与灰度双闸
3. 固定版本不追 latest
