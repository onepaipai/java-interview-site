## 参考回答

<!-- explanation:deep -->

> 场景与约束：网银交易列表沙盘:列表筛选条件(状态/日期)存在组件内存里——刷新丢失、复制链接给同事打开是默认列表、返回键丢筛选。用"筛选条件入 URL"的同步模式说明路由一致性(query 参数即状态)。

1. 筛选状态的三种存放:组件内存(刷新丢/不可分享/返回丢)、全局 store(同上)+刷新丢失、URL query(刷新保持/可分享/返回导航自然恢复)——URL 是筛选状态的唯一事实源。
2. 同步机制:筛选变更→router.replace 更新 query(replace 不污染历史);URL 变更(浏览器前进后退)→组件监听 query 恢复筛选——双向同步单向驱动(状态→URL→组件恢复)。
3. 工程细节:query 序列化(多值/日期范围的编码)、默认值处理(默认值不写入 URL——保持 URL 简洁)、深链接的校验(URL 里的非法值回退默认,不崩)。

## 参考分析

### 机制:URL 为事实源的同步

单向流:组件内筛选操作→更新 URL(query)→路由变化触发组件从 URL 重建筛选状态——组件不持有筛选的"私有副本"(状态只有 URL 一份,组件是视图)。刷新/分享/返回:三者天然正确(URL 即状态)。序列化:日期范围(a=2026-01-01_b=2026-01-31)、多状态(status=1,3)、分页(page=2)——编码工具统一(encode/decode 集中,不散落)。

### 反例:内存状态的四种事故

事故一,刷新丢失:用户调好筛选刷新页面——回到默认(重筛一遍)。事故二,不可协作:"看下第 3 页的失败交易"——口头描述筛选(复制 URL 一秒完成的事)。事故三,返回丢状态:从详情返回列表——筛选重置(用户从第 5 页重新找)。事故四,状态双源:URL 有 page 但组件内存里也有——两者不一致(后退键改了 URL,组件没监听)。四事故同解:状态入 URL+组件从 URL 恢复。

### 取舍:什么状态进 URL

进 URL:可分享/可恢复/构成"视图状态"的(筛选/排序/分页/标签页)。不进 URL:临时交互态(弹窗开合/表单未提交草稿——会话态)、敏感信息(token)——URL 是可书签的视图快照,不是数据存储。深链接的权限:URL 可分享=权限跟随分享者会话(第 18 题授权)——链接打开时重新鉴权,不信任 URL 里的身份。

## 案例

### 验证:路由一致的断言组

验证:刷新保持用例(设置筛选后刷新,断言筛选恢复);分享用例(复制 URL 新开页,断言同视图);导航恢复用例(详情返回列表,断言筛选与页码);非法值用例(URL 手改 status=99,断言回退默认不崩)——四组进 E2E(第 22 题:列表是高风险展示?按后果定级)。

### 追问链:路由一致三刀

一刀:"replace 与 push 的选择?"——筛选变更用 replace(每次筛选一条历史=历史爆炸);显式导航用 push(用户期望后退回到上一筛选)——策略:同视图的状态变更 replace,跨视图 push。二刀:"URL 与服务端排序分页?"——分页的 page 与筛选同入 URL;服务端按 query 查询(URL 即查询请求的完整描述,第 48 题可追踪)——URL 与 API 参数同构。三刀:"多标签页互斥?"——同 App 多标签的筛选互不干扰(URL 各自独立)——全局 store 存筛选才有跨标签污染问题(URL 方案天然隔离)。

## 总结点

1. URL 是筛选状态的唯一事实源
2. replace 管状态变更,push 管跨视图
3. 深链接鉴权,非法值回退默认
